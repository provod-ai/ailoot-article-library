# Gemini: Choosing Between the App and the API

> A practical guide to choosing between the Gemini app and API, evaluating models and estimating usage costs.



Gemini can be used through Google's consumer app or integrated into software through an API. The right starting point depends on whether you want to complete a task yourself or build a repeatable workflow for other people.

## Start with the job

For a one-off task, such as drafting a message or exploring an idea, an interactive app gives you a place to ask a question and refine the answer. Check the result before relying on it: a fluent answer may still contain an error, omit context or cite a source incorrectly.

An API is useful when an application needs to send inputs and process outputs as part of a workflow. For example, a support application might summarise a ticket for a human reviewer. The developer must handle instructions, data access, failures and the way results are displayed or stored.

The app and API are different products. Do not assume a feature, limit, subscription or data setting in one is automatically available in the other. Check the documentation and the settings for the product and account you actually use.

## Choose a model for the task

Start with a few representative examples rather than choosing a model by name alone. For a summarisation task, include a short message, a long message and a case with missing information. Decide what a good answer must preserve, what it must not invent and how long it should be.

If a task involves images, audio or other input, check that the specific model and endpoint support the format you need. Supported modalities, context limits and availability can differ by model and can change. Google's [Gemini API documentation](https://ai.google.dev/gemini-api/docs) is the place to check current options and request formats.

## Estimate cost with a realistic sample

For an API workflow, record the amount of input and output used by a small representative set of requests. Multiply the measured usage by the relevant published prices, accounting for every applicable input and output type. Then estimate how often the workflow will run and leave room for retries and variation in response length.

Treat the result as an estimate, not a guaranteed bill. Check the current [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing), quotas and billing settings for your account. An app subscription and API usage may have different terms.

## Evaluate before scaling

Compare results with examples reviewed by people. For each response, check the facts against the input, the requested format and any task-specific rules. Include difficult cases and cases the model should decline or send to a person. A valid-looking response is not necessarily a correct one.

Track failures and revise one part of the workflow at a time: the instructions, input preparation, model or output validation. Repeat the same test set after a change. If the model or the kind of incoming data changes, reassess the result rather than assuming the previous evaluation still applies.

## Handle data and failures deliberately

Send only the data needed for the task and review the relevant product's data-handling settings before using sensitive information. Validate outputs before an application acts on them. Plan for rate limits, timeouts and incomplete results; show an actionable error or route the case for review instead of silently treating a failure as a completed task.

For requests that can trigger external actions, keep a record of the operation and check its status before retrying. A response lost in transit does not prove that an action failed.
