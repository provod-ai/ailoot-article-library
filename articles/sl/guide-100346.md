# Arhitektura API-ja TTS: od besedila do produkcijskega zvoka

> Naučite se zasnovati produkcijski API TTS z vrstami, delavci, predpomnjenjem, ponovnimi poskusi, usmerjanjem med ponudniki, shranjevanjem, omejitvami hitrosti in opazljivostjo.



Klicanje API-ja za pretvorbo besedila v govor je preprosto. Zanesljivo delovanje v produkciji pa ni.

Osnovni prototip lahko vsebuje samo tri korake:

**Besedilo → ponudnik TTS → MP3**

To lahko dobro deluje pri lokalnem testiranju nekaj zahtev. Ko se pojavijo resnični uporabniki, mora sistem obravnavati sočasna opravila, omejitve hitrosti ponudnika, napake omrežja, dolgotrajno ustvarjanje zvoka, podvojene zahteve, shranjevanje, ponovne poskuse, kvote, več ponudnikov glasov in uporabnike, ki osvežijo stran, medtem ko se zvok še obdeluje.

Arhitektura hitro postane precej bolj zapletena od samega klica API-ja TTS. Bolj realističen produkcijski potek je videti tako:

**Odjemalec → API → opravilo → vrsta → delavec → ponudnik TTS → shramba/CDN → rezultat**

Ta članek pojasnjuje, kako zasnovati takšno arhitekturo, zakaj obstaja vsaka komponenta in katere težave se običajno pojavijo, ko aplikacija TTS preraste preprost prikaz.



## **Kaj mora rešiti produkcijski API TTS?**

Namen produkcijskega zaledja TTS ni zgolj ustvarjanje zvoka. Zvok mora ustvarjati **zanesljivo, učinkovito in predvidljivo**.

Dobra arhitektura bi morala odgovoriti na vprašanja, kot so:

1. Kaj se zgodi, ko 100 uporabnikov hkrati ustvarja govor?
2. Kaj se zgodi, ko ponudnik TTS vrne HTTP 429?
3. Kaj se zgodi, ko ponudnik TTS postane nedosegljiv?
4. Kaj se zgodi, ko ustvarjanje zvoka traja več minut?
5. Kaj se zgodi, ko uporabnik isto zahtevo odda dvakrat?
6. Kako preprečite, da bi en uporabnik porabil vso razpoložljivo kvoto ponudnika?
7. Kje naj se shrani ustvarjeni zvok?
8. Kako odjemalec izve, kdaj je dolgotrajno opravilo končano?
9. Kako ponoviti neuspešno delo, ne da bi znova ustvarjali že uspešen zvok?
10. Kako izmerite, kateri ponudnik je počasen ali nezanesljiv?

To so problemi zasnove sistema, ne sinteze govora.

## **Osnovna zahteva API-ja TTS**

Na najosnovnejši ravni lahko zahteva TTS vsebuje:

1. Besedilo
2. Jezik
3. Glas
4. Model
5. Hitrost govora
6. Zvočni format
7. Izbirna navodila za glas

Na primer, konceptualno:

**POST /tts**

Strežnik prejme zahtevo, pokliče ponudnika TTS in vrne zvočno datoteko. Ta sinhroni model je preprost za razumevanje:

**Zahteva HTTP → ponudnik → zvok → odgovor HTTP**

Pri zelo kratkem ustvarjanju govora je to lahko sprejemljivo. Težave se začnejo, ko se ustvarjanje upočasni, promet naraste ali ena zahteva vsebuje veliko besedila.

## **Zakaj dolgotrajna opravila TTS ne bi smela biti odvisna od ene zahteve HTTP**

Predstavljajte si, da uporabnik odda dovolj besedila za ustvarjanje 30-minutnega govornega posnetka. Če vaš API pusti prvotno zahtevo HTTP odprto, dokler ni vse končano, lahko gre več stvari narobe:

1. Brskalniku lahko poteče časovna omejitev.
2. Povratni posredniški strežnik lahko zapre zahtevo.
3. Aplikacijski strežnik se lahko znova zažene.
4. Ponudnik lahko začasno odpove.
5. Uporabnik lahko zapre stran.
6. Mobilna povezava lahko izgine.

Delo TTS je morda še vedno veljavno, vendar povezave, ki ga je sprožila, ni več. Dolgotrajne obremenitve TTS je običajno bolje modelirati kot **opravila**.

Potek postane:

**Odjemalec → Ustvari opravilo → Vrni ID opravila → Obdelaj v ozadju**

Odjemalec lahko pozneje preveri napredek.

## **1. korak: Sprejmite in preverite zahtevo**

Plast API-ja bi morala pred pošiljanjem dela v sistem za obdelavo opraviti osnovno preverjanje. Običajna preverjanja vključujejo:

1. Ali je besedilo prazno?
2. Ali je besedilo daljše od dovoljene velikosti zahteve?
3. Ali zahtevani glas obstaja?
4. Ali izbrani model podpira zahtevani jezik?
5. Ali je zahtevani zvočni format podprt?
6. Ali je uporabnik overjen?
7. Ali ima uporabnik dovolj kvote ali kreditov?
8. Ali je zahteva dovoljena v skladu s pravili omejevanja hitrosti?

Neveljavne zahteve bi morale biti zavrnjene, preden dosežejo delavce ali zunanje ponudnike. To prihrani infrastrukturne vire in kvoto ponudnika.

Pri sočasnih opravilih pred sprejemom atomsko rezervirajte ustrezno kvoto ali kredite ter rezervacijo natanko enkrat obračunajte ali sprostite glede na dejanski izid in pravila obračunavanja.

## **2. korak: Normalizirajte zahtevo**

Pred obdelavo normalizirajte zahtevo v predvidljivo notranjo obliko. Na primer:

1. Normalizirajte jezikovne kode.
2. Določite dejanski ID glasu.
3. Določite ponudnika, ki stoji za izbranim glasom.
4. Uporabite privzeto hitrost govora.
5. Normalizirajte presledke.
6. Izberite izhodni format.
7. Določite konfiguracijo modela.

Tako dobijo nadaljnji delavci dosleden vhodni dogovor. To pomaga tudi pri predpomnjenju: logično enake zahteve bi morale idealno ustvariti isti ključ predpomnilnika.



## **3. korak: Preverite, ali zvok že obstaja**

Večkratno ustvarjanje istega zvoka je preprost način za zapravljanje denarja v sistemu TTS. Recimo, da uporabnik večkrat pošlje:

*»Dobrodošli v naši aplikaciji.«*

z istim glasom, modelom, hitrostjo in nastavitvami. Če je rezultat za vaš primer uporabe dovolj determinističen, morda ni razloga, da bi vsakič poklicali ponudnika.

Ključ predpomnilnika je mogoče izpeljati iz vrednosti, kot so:

1. Normalizirano besedilo
2. ID glasu
3. Ponudnik
4. Model
5. Jezik
6. Hitrost
7. Zvočni format
8. Slog ali navodila za glas

Konceptualni ključ bi lahko bil:

**HASH(besedilo + glas + model + hitrost + format + nastavitve)**

Vsa polja generiranja serializirajte nedvoumno in v identiteto predpomnilnika vključite ustrezni obseg najemnika ali dostopa. Ponovno uporabo in dostop do rezultata avtorizirajte; med najemniki delite le ob izrecnem dovoljenju.

Potek zahteve postane:

**Zahteva → Preverjanje predpomnilnika → Obstoječi zvok?**

Če da:

**Vrni obstoječi rezultat**

Če ne:

**Ustvari opravilo za generiranje**

### **Ne predpomnite samo na podlagi besedila**

Uporaba samo besedila kot ključa predpomnilnika je običajno napačna. Isti stavek, ustvarjen z dvema različnima glasovoma, ne bi smel vrniti istega zvoka. Enako velja za model, hitrost, jezik, format in nastavitve sloga.

Identiteta predpomnilnika bi morala predstavljati vse, kar lahko bistveno spremeni rezultat.

## **4. korak: Ustvarite trajno opravilo**

Pred uvrstitvijo dela v vrsto shranite zapis opravila. Opravilo TTS lahko vsebuje:

1. ID opravila
2. ID uporabnika
3. Stanje
4. Zahtevani glas
5. Ponudnik
6. Model
7. Število znakov
8. Čas ustvarjanja
9. Čas začetka
10. Čas dokončanja
11. Število ponovnih poskusov
12. Napredek
13. Informacije o napaki
14. Izhodni URL

Preprost življenjski cikel stanja je lahko:

**Čaka → V obdelavi → Dokončano**

z neuspešnimi stanji, kot je:

**Čaka → V obdelavi → Neuspešno**

Morda boste potrebovali tudi stanja za ponovni poskus, preklicana, delno dokončana ali potekla opravila.

Trajno shranjevanje stanja opravila je pomembno, ker sistem za obdelavo ne bi smel biti odvisen od pomnilnika aplikacije. Če se vsebnik API-ja znova zažene, bi morali uporabniki še vedno imeti možnost pridobiti svoja opravila.

## **5. korak: Pošljite opravilo v čakalno vrsto sporočil**

Čakalna vrsta sporočil loči sprejemanje zahtev od obdelave zvoka. Namesto:

**API → ponudnik TTS**

uporabite:

**API → vrsta → delavec → ponudnik TTS**

API lahko skoraj takoj odgovori z identifikatorjem opravila, medtem ko delavci v ozadju obdelujejo zahteve.

Uporabite transakcijski outbox ali trajni mehanizem obnove za zapisana opravila, ki niso bila uvrščena v vrsto, ter zagotovite idempotentno obdelavo vrste, da sesutje ali ponovna dostava ne izgubita ali podvojita dela.

### Zakaj so čakalne vrste tako uporabne za TTS

Čakalne vrste prinašajo več pomembnih prednosti:

1. Sprejmejo prometne sunke.
2. Nadzorujejo, koliko dela poteka hkrati.
3. Ščitijo kvote zunanjih ponudnikov.
4. Olajšajo ponovne poskuse.
5. Omogočijo nadaljevanje opravil po koncu prvotne zahteve HTTP.
6. Omogočijo dodajanje delavcev z rastjo prometa.

To je še posebej pomembno, ko ponudniki TTS določijo omejitve zahtev na minuto, znakov, žetonov ali sočasnosti.



## **Vrsta je tudi mehanizem za uravnavanje povratnega pritiska**

Recimo, da lahko vaš ponudnik varno obdela 20 zahtev hkrati, vaš API pa prejme 200 zahtev naenkrat. Brez vrste lahko vseh 200 zahtev pošljete neposredno ponudniku. Verjeten rezultat je:

1. Napake zaradi omejitve hitrosti
2. Časovne omejitve
3. Velika obremenitev procesorja
4. Velika poraba pomnilnika
5. Omejevanje hitrosti s strani ponudnika
6. Kaskada ponovnih poskusov

Z vrsto lahko API sprejema opravila, medtem ko jih delavci obdelujejo z nadzorovano hitrostjo. Sistem ne potrebuje vsega obdelati takoj samo zato, ker so zahteve prispele takoj.

## **6. korak: Obdelujte opravila z delavci TTS**

Delavci obravnavajo potek ustvarjanja. Delavec lahko:

1. Prebere opravilo iz vrste.
2. Naloži konfiguracijo opravila.
3. Po potrebi razdeli veliko besedilo.
4. Izbere ustreznega ponudnika.
5. Pokliče API TTS.
6. Obravnava začasne napake.
7. Prenese ustvarjeni zvok ali ga prejme.
8. Preveri izhod.
9. Naloži rezultat v shrambo.
10. Posodobi stanje opravila.

Delavci bi morali biti dovolj brezstanjni, da lahko opravilo obdela drug delavec, če primerek izgine.

## **Kolikšno sočasnost naj uporablja delavec?**

Večja sočasnost ne pomeni samodejno večje prepustnosti. Preveč agresivno povečevanje sočasnosti delavcev lahko povzroči:

1. Doseganje omejitev ponudnika
2. Zasičenost procesorja
3. Obremenitev pomnilnika
4. Omejitve omrežja
5. Omejitve diskovnih V/I-operacij
6. Ozka grla FFmpeg

Obremenitve TTS lahko vključujejo več vrst virov. Klic oddaljenega API-ja za govor je lahko večinoma omejen z omrežjem, medtem ko lahko pretvorba ali združevanje zvoka postane omejeno s procesorjem. Produkcijskemu sistemu lahko zato koristijo ločeni nadzori sočasnosti za različne faze.

Na primer:

**Sočasnost prenosa: visoka**

**Sočasnost ponudnika TTS: odvisna od ponudnika**

**Sočasnost obdelave zvoka: odvisna od procesorja**

To je običajno varneje kot povsod uporabljati eno samo visoko vrednost sočasnosti.

## **7. korak: Razdelite veliko besedilo na manjše bloke**

Številni ponudniki TTS določajo omejitve velikosti zahtev. Tudi če ponudnik sprejema zelo velike vnose besedila, je lahko razdeljevanje dolgih dokumentov še vedno koristno.

Dolgotrajno opravilo TTS lahko postane:

**Dokument → Blok 1 + Blok 2 + Blok 3 + ... → TTS → Združitev**

Obdelava po blokih prinaša več prednosti:

1. Ponovite samo neuspešne bloke po preverjanju, da je to varno.
2. Neodvisne bloke obdelujte sočasno.
3. Spremljajte napredek.
4. Obnovite se po delnih napakah.
5. Predpomnite bloke posamično.
6. Izognite se omejitvam velikosti zahtev ponudnika.

### **Besedila ne razdeljujte na slepo**

Razdelitev na vsakih fiksnih nekaj znakov lahko poslabša kakovost govora, ker se blok konča sredi stavka. Boljša logika razdeljevanja lahko upošteva:

1. Meje odstavkov
2. Meje stavkov
3. Ločila
4. Omejitve ponudnika glede števila znakov
5. Pravila pisanja, specifična za jezik

Cilj je ohraniti bloke dovolj majhne za zanesljivo obdelavo, hkrati pa ohraniti naravni govorni kontekst.

## **8. korak: Usmerite zahteve k ustreznemu ponudniku TTS**

Produkcijska aplikacija lahko sčasoma podpira več ponudnikov TTS. Različni ponudniki lahko ponujajo različne:

1. Jezike
2. Kataloge glasov
3. Cene
4. Ravni kakovosti
5. Omejitve hitrosti
6. Zakasnitve
7. Čustvene kontrole
8. Zmogljivosti pretakanja

Namesto vdelave logike ponudnikov po vsej aplikaciji uporabite plast za usmerjanje ali abstrakcijo. Arhitektura postane:

**Delavec → usmerjevalnik glasov/modelov → prilagoditveni vmesnik ponudnika → ponudnik TTS**

Vsak prilagoditveni vmesnik ponudnika lahko izpostavi skupni notranji vmesnik in hkrati prevaja zahteve v obliko, ki jo pričakuje ta ponudnik.

### **Izogibajte se logiki, specifični za ponudnika, povsod**

Brez abstrakcije se lahko koda napolni s pogoji, kot je:

**Če je ponudnik A, naredi to. Če je ponudnik B, naredi nekaj drugega.**

Ko dodajate ponudnike, je takšno kodo težko vzdrževati. Skupni vmesnik ponudnika omogoči preostalemu delu sistema, da uporablja koncepte, kot so:

1. Ustvari govor
2. Pridobi podprte glasove
3. Preveri zahtevo
4. Vrni zvok

Vsak prilagoditveni vmesnik ponudnika obravnava podrobnosti izvedbe.

## **Nadomestni ponudnik: uporabno, vendar ni vedno preprosto**

Morda vas zamika, da vsako neuspešno zahtevo samodejno pošljete drugemu ponudniku. Včasih to deluje dobro, včasih pa ne. Dva ponudnika morda nimata enakovrednih glasov, nadomestni glas pa lahko zveni povsem drugače od izvirnega. To je morda nesprejemljivo pri dolgi zvočni knjigi ali videu z več prizori.

Pri odločitvah o nadomestnem ponudniku upoštevajte:

1. Ali obstaja enakovreden glas
2. Ali je doslednost pomembna
3. Ali je napaka začasna
4. Razliko v stroških
5. Ciljni jezik
6. Uporabniške nastavitve

Nadomestni ponudnik je arhitekturno orodje, ne zagotovilo, da je treba vsako neuspešno zahtevo takoj preusmeriti.

## **9. korak: Pravilno obravnavajte omejitve hitrosti**

HTTP 429 je ena najpogostejših težav v sistemih, ki veliko uporabljajo API-je. HTTP 429 lahko označuje omejitev ponudnika, vključno s hitrostjo ali številom sočasnih zahtev. Pred odločitvijo o načinu in času ponovnega poskusa preverite podrobnosti napake in navodila ponudnika, vključno z Retry-After, kadar je naveden.

Napačen odziv je:

**Ponovi takoj in čim hitreje.**

To običajno ustvari še več zahtev in poslabša težavo. Boljši pristop uporablja:

1. Omejitve sočasnosti
2. Eksponentno čakanje med ponovnimi poskusi
3. Naključni zamik
4. Politike omejevanja hitrosti, specifične za ponudnika
5. Zakasnitve v vrsti

Konceptualno:

**429 → Počakaj → Poskusi znova pozneje**

ne pa:

**429 → Takoj ponovi → 429 → Takoj ponovi → 429**

## **10. korak: Ponovite samo napake, ki se lahko odpravijo**

Ponovni poskusi so potrebni, vendar se ne bi smela ponoviti vsaka napaka. Uporabna razvrstitev je:

| Vrsta napake                | Običajno dejanje                    |
|-----------------------------|-------------------------------------|
| 429 Too Many Requests       | Počakajte in poskusite znova z zamikom |
| 500 Internal Server Error   | Preverite prvotni izid; ponovite le, če je varno|
| 502 / 503 Temporary Failure | Pred ponovitvijo ali prehodom na nadomestnega ponudnika preverite prvotni izid|
| Network Timeout             | Pred ponovnim poskusom preverite prvotni izid|
| 400 Invalid Request         | Ne ponavljajte na slepo              |
| Unsupported Voice           | Popravite zahtevo ali usmerjanje     |
| Insufficient User Credits   | Zavrnete pred obdelavo pri ponudniku |

Časovna omejitev, napaka 5xx ali odpoved delavca lahko pustijo izid pri ponudniku neznan. Pred ponovnim poskusom ali menjavo ponudnika, kjer je podprto, preverite prvotni ID operacije, stanje in porabo, uporabite že nastali rezultat in idempotentnost, ki jo podpira ponudnik. Neznani izid ohranite, namesto da bi slepo ponavljali morda že dokončano zahtevo.

Politika ponovnih poskusov bi morala določiti tudi največje število poskusov. V nasprotnem primeru lahko eno pokvarjeno opravilo ostane v sistemu za vedno.

## **Uporabite idempotentnost za preprečevanje podvojenega dela**

Podvojene zahteve so v resničnih aplikacijah pogoste. Uporabnik lahko dvakrat klikne gumb, vmesnik lahko po časovni omejitvi omrežja znova pošlje zahtevo, sporočilo vrste je lahko dostavljeno znova ali pa delavec uspešno konča delo, vendar se zruši, preden potrdi prejem sporočila.

Če vaš sistem predpostavlja, da je vsako sporočilo enolično, lahko isti zvok ustvari in zaračuna večkrat. Idempotentnost pomeni, da večkratna obdelava iste logične zahteve ne bi smela ustvariti več nenamernih rezultatov.

Možne tehnike vključujejo:

1. Idempotentne ključe
2. Enolične identifikatorje opravil
3. Zgoščene vrednosti predpomnilnika
4. Omejitve enoličnosti v zbirki podatkov
5. Preverjanje stanja bloka pred obdelavo

To je še posebej pomembno pri plačilih, kreditih ali stroških ponudnika.

## **Idempotentnost na ravni opravila in na ravni bloka**

Pri kratkih zahtevah TTS lahko zadostuje idempotentnost na ravni opravila. Pri velikih opravilih z več bloki je idempotentnost na ravni bloka pogosto uporabnejša.

Predstavljajte si opravilo zvočne knjige s 500 bloki, pri katerem odpove blok 487. Ne želite znova ustvarjati blokov od 1 do 486.

**Dokončani bloki → Ohranite**

**Neuspešni blok → Preverite stanje pri ponudniku → Poskusite znova le, če je varno**

To znatno zmanjša stroške in čas obnovitve.

## **11. korak: Preverite ustvarjeni zvok**

Uspešen odgovor ponudnika ne zagotavlja vedno uporabnega izhoda. Preden opravilo označite kot dokončano, lahko preverite:

1. Ali je bila vrnjena zvočna datoteka?
2. Ali je velikost datoteke večja od nič?
3. Ali je mogoče zvok dekodirati?
4. Ali je trajanje videti razumno?
5. Ali je zahtevani format pravilen?

Pri naprednih potekih lahko preverjanje trajanja zazna tudi sumljive izhode, na primer nepričakovano kratek ali dolg govor.

## **12. korak: Shranite zvok zunaj aplikacijskega strežnika**

Ustvarjeni zvok praviloma ne bi smel biti odvisen od lokalnega diska enega primerka API-ja ali delavca. Če se vsebnik ponovno ustvari, lahko datoteka izgine.

Boljša arhitektura je:

**Delavec → shramba objektov → CDN → uporabnik**

Shramba objektov loči ustvarjena sredstva od računalniške infrastrukture. CDN lahko nato učinkovito dostavlja zvok uporabnikom na različnih lokacijah.

Avtorizirajte dostop do vsakega opravila, njegovega stanja in zvočnega rezultata. Shranjeni zvok naj ostane zaseben, po potrebi pa uporabite časovno omejene povezave z določenim obsegom, namesto da URL obravnavate kot dokaz pravice dostopa.

### Kaj shraniti v zbirki podatkov?

Zbirka podatkov običajno ne potrebuje neobdelanih zvočnih bajtov. Namesto tega shranite metapodatke, kot so:

1. Ključ shrambe
2. URL zvoka
3. Trajanje
4. Velikost datoteke
5. Format
6. Ponudnik
7. Glas
8. Čas ustvarjanja

Dejanski zvok lahko ostane v shrambi objektov.

## **Razmislite o poteku veljavnosti datotek**

Ni treba, da vsaka ustvarjena datoteka TTS obstaja za vedno. Shramba lahko neopazno postane draga, ko se naberejo milijoni začasnih zvočnih datotek.

Razmislite o pravilih hrambe za:

1. Datoteke, ustvarjene za goste
2. Začasne datoteke obdelave
3. Vmesne bloke
4. Dokončane uporabniške projekte
5. Znova uporabljiv zvok v predpomnilniku

Vmesne datoteke imajo lahko pogosto precej krajši čas hrambe kot končni uporabniški izhodi.

## **13. korak: Vrnite rezultate s preverjanjem ali povratnimi klici**

Ko zahteva TTS postane asinhrona, odjemalec potrebuje način, da izve, kdaj je obdelava končana. Obstajata dva pogosta vzorca.

### **Preverjanje stanja**

Odjemalec občasno vpraša:

**GET /jobs/{jobId}**

Strežnik odgovori na primer:

**status = processing**

in pozneje:

**status = completed, audioUrl = ...**

Preverjanje stanja je preprosto za izvedbo in dobro deluje v številnih spletnih aplikacijah.

### **Spletni kavelj ali povratni klic**

Uporabnik API-ja lahko navede URL za povratni klic. Ko je obdelava končana, vaš strežnik samodejno pošlje obvestilo.

Potek postane:

**Ustvari opravilo → Vrni ID opravila → Obdelaj → Povratni klic odjemalca**

To je uporabno, ko zunanji sistemi obdelujejo velika opravila in ne želijo nenehno preverjati stanja.

### Podpora za oba načina je lahko koristna

Produkcijski API lahko ponuja preverjanje stanja opravil kot univerzalen mehanizem, spletne kaveljčke pa kot izbirno priročno možnost.

## **Spremljajte napredek pri velikih opravilih**

Pri 5-sekundni zahtevi TTS napredek morda ni pomemben. Pri enournem zvočnem projektu pa je zelo pomemben. Če opravilo vsebuje 1000 blokov, je mogoče napredek približno izračunati iz dokončanega dela:

**Napredek = dokončani bloki / skupno število blokov**

Tako lahko sprednji del prikaže:

1. V čakalni vrsti
2. V obdelavi 27%
3. V obdelavi 83%
4. Zaključevanje zvoka
5. Dokončano

Vidni kazalnik napredka tudi zmanjša verjetnost, da bi uporabniki menili, da je aplikacija zamrznila, in znova oddali isto opravilo.

## **14. korak: Zaščitite sistem z omejevanjem hitrosti**

Vaš ponudnik ima omejitve hitrosti. Imeti bi jih moral tudi vaš API. Omejevanje hitrosti je mogoče uporabiti glede na:

1. Uporabnika
2. Ključ API-ja
3. Naslov IP
4. Naročniški paket
5. Končno točko
6. Ponudnika

Omejitve hitrosti ščitijo infrastrukturo in kvote ponudnikov. Prav tako lahko preprečijo, da bi en zahteven uporabnik porabil vsa razpoložljiva mesta delavcev.

## **Prioritete so lahko uporabnejše od ene globalne vrste**

Ko izdelek raste, vsa opravila morda ne zaslužijo enake prioritete. Na primer:

1. Interaktivne kratke zahteve TTS morda potrebujejo hitre odgovore.
2. Velika opravila z dokumenti lahko nekoliko dlje čakajo.
3. Plačljivi uporabniki lahko dobijo višjo prioriteto obdelave.
4. Opravila paketnega API-ja v ozadju lahko uporabljajo ločeno zmogljivost delavcev.

Možna arhitektura je:

**Vrsta z visoko prioriteto → hitri delavci**

**Običajna vrsta → splošni delavci**

**Paketna vrsta → paketni delavci**

Natančna zasnova je odvisna od vzorcev prometa, vendar lahko ločevanje obremenitev prepreči, da bi nekaj velikih opravil zakasnilo vsako kratko zahtevo.

## **15. korak: Spremljajte uporabo in stroške**

Različni ponudniki TTS lahko zaračunavajo različno. Nekateri zaračunavajo po znakih, nekateri po žetonih, nekateri glede na trajanje ustvarjenega zvoka, nekateri pa uporabljajo bolj zapletene cenovne modele.

Produkcijski sistem bi moral približno vedeti, koliko porabi vsako opravilo. Koristne metrike vključujejo:

1. Vhodne znake
2. Vhodne žetone
3. Trajanje ustvarjenega zvoka
4. Ponudnika
5. Model
6. Vrsto glasu
7. Število ponovnih poskusov
8. Ocenjene stroške ponudnika
9. Porabljene uporabniške kredite

Brez sledenja uporabi je težko vedeti, ali je funkcija dobičkonosna ali pa je eden od ponudnikov nepričakovano drag.

## **Zaračunajte samo enkrat**

Zaračunavanje in ponovni poskusi zahtevajo skrbno usklajevanje. Če ponudnik trikrat odpove, preden uspe, uporabniku običajno ne bi smeli trikrat posebej zaračunati iste logične zahteve za ustvarjanje.

Če celotno opravilo dokončno odpove, mora vaš sistem imeti jasno politiko glede sprostitve ali vračila rezerviranih kreditov. Idempotentnost je tukaj izjemno pomembna. Zaračunavanje bi moralo slediti življenjskemu ciklu logičnega opravila, ne številu notranjih ponovnih poskusov.

## **16. korak: Dodajte opazljivost, preden jo potrebujete**

Ko uporabniki poročajo, da je TTS počasen, to samo po sebi ne pove, kje je težava. Opravilo je lahko porabilo:

1. 20 sekund čakanja v vrsti
2. 2 sekundi v delavcu
3. 30 sekund čakanja na ponudnika
4. 10 sekund za obdelavo zvoka
5. 5 sekund za nalaganje izhoda

Brez meritev so vse te faze videti kot ena sama počasna zahteva.

### **Koristne metrike TTS**

Spremljajte metrike, kot so:

1. Zakasnitev zahteve API-ja
2. Globina vrste
3. Čas čakanja v vrsti
4. Število aktivnih delavcev
5. Čas odgovora ponudnika
6. Delež uspešno ustvarjenega zvoka
7. Delež napak po ponudniku
8. Delež odgovorov 429
9. Delež ponovnih poskusov
10. Trajanje obdelave zvoka
11. Trajanje nalaganja
12. Skupno trajanje opravila
13. Strošek na opravilo

### **Ponudnike merite ločeno**

Če podpirate več ponudnikov, lahko združene metrike skrijejo pomembne informacije. Na primer, skupni delež uspeha je lahko 98%, medtem ko je en ponudnik padel na 85%.

Metrike bi zato morale omogočati filtriranje po dimenzijah, kot so:

1. Ponudnik
2. Model
3. Glas
4. Jezik
5. Delavec
6. Regija

## **Dnevniki naj vsebujejo ID opravila**

Porazdeljene sisteme je lažje odpravljati, kadar vsaka vrstica dnevnika, povezana z zahtevo, vsebuje isti identifikator opravila. Isti ID se lahko pojavi v:

1. Dnevnikih API-ja
2. Sporočilih vrste
3. Dnevnikih delavcev
4. Klicih ponudnika
5. Operacijah shrambe

Ko gre kaj narobe, lahko poiščete en ID opravila in rekonstruirate celotno pot izvajanja.

## **Praktična produkcijska arhitektura TTS**

Ko povežemo komponente, dobimo popolnejši sistem:

## **Kaj se zgodi, ko ponudnik TTS odpove?**

Zunanji ponudniki bodo sčasoma odpovedali, zato robustna arhitektura predvideva, da se to lahko zgodi. Ko se delež napak poveča, lahko vaš sistem:

1. Upočasni ponovne poskuse.
2. Začasno zmanjša sočasnost ponudnika.
3. Začasno ustavi prizadete vrste.
4. Upravičene zahteve preusmeri k drugemu ponudniku.
5. Obvesti uporabnike, da obdelava zamuja.

Najslabša strategija je običajno pošiljanje vedno več ponovnih poskusov ponudniku, ki že odpoveduje.

## **Razmislite o odklopniku**

Odklopnik lahko po ponavljajočih se napakah začasno ustavi zahteve ponudniku. Konceptualno:

**Ponudnik deluje → Zahteve dovoljene**

**Ponavljajoče se napake → Odklopnik se odpre → Zahteve so začasno blokirane**

**Preizkus obnovitve uspe → Ponudnik znova omogočen**

Tako lahko preprečite, da bi ena odpovedujoča se odvisnost porabila veliko zmogljivosti delavcev.

## **Kaj pa pretakanje TTS?**

Vsaka obremenitev TTS ne bi smela biti asinhrona. Glasovni pomočniki in pogovorni sistemi v realnem času bodo morda morali začeti predvajati govor, preden je ustvarjen celoten zvok.

Takšni sistemi lahko uporabljajo:

**Tok besedila → tok TTS → zvočni bloki → predvajanje pri odjemalcu**

Prednostne naloge so drugačne:

1. Čas do prvega zvoka
2. Zakasnitev pretakanja
3. Prekinitve
4. Stabilnost povezave

Produkcijska platforma lahko zato podpira dve ločeni poti:

**TTS v realnem času → pot pretakanja**

**TTS dolge oblike → vrsta in pot opravila v ozadju**

Če obe obremenitvi prisilite skozi popolnoma enako arhitekturo, lahko sistem po nepotrebnem otežite optimizirati.

## **Arhitektura API-ja TTS v primerjavi z arhitekturo SRT-to-Speech**

Običajni API TTS se začne z besedilom. Sistem SRT-to-Speech se začne z bloki podnapisov, ki so že umeščeni na časovnico.

Osnovni potek TTS je lahko:

**Besedilo → vrsta → TTS → zvok**

Potek SRT je lahko:

**SRT → razčlenitev blokov → TTS → merjenje trajanja → prilagoditev časovnih oznak → združitev zvoka**

Različica SRT doda več težav:

1. Ohranjanje časovnih oznak
2. Ciljno trajanje
3. Preslikava govorcev
4. Dolžina prevoda
5. Sinhronizacija zvoka
6. Ponovni poskusi na ravni bloka

## **Pogoste napake pri arhitekturi TTS**

### **1. Klicanje ponudnika neposredno iz vsake zahteve HTTP**

Na začetku je to preprosto, vendar postane krhko pri dolgotrajnih obremenitvah.

### **2. Uporaba neomejene sočasnosti**

Več delavcev ne pomaga, če ozko grlo postanejo ponudnik, procesor ali omrežje.

### **3. Ponovno poskušanje pri vsaki napaki**

Trajne napake pri preverjanju ne bi smele vstopiti v neskončne zanke ponovnih poskusov.

### **4. Ponovno ustvarjanje uspešnih blokov**

Velika opravila bi morala ohraniti dokončano delo in znova poskusiti samo tisto, kar je odpovedalo.

### **5. Shranjevanje pomembnega zvoka samo na lokalnem disku**

Vsebniki delavcev in začasni strežniki ne bi smeli postati trajna shramba sredstev.

### **6. Zanemarjanje omejitev, specifičnih za ponudnika**

Vsak ponudnik lahko zahteva drugačno strategijo sočasnosti in omejevanja hitrosti.

### **7. Dodajanje spremljanja šele po pojavu težav**

Brez metrik odpravljanje težav z zmogljivostjo postane ugibanje.

### **8. Mešanje vseh obremenitev v eni vrsti**

En velik dokument lahko zakasni več deset majhnih interaktivnih zahtev, če obremenitve niso ustrezno razvrščene po prioriteti.

## **Dobra arhitektura se lahko začne preprosto**

Ni vam treba že prvi dan zgraditi vseh komponent. Zgodnja aplikacija TTS se lahko začne z:

**API → ponudnik → shramba**

Nato z rastjo uporabe:

**API → vrsta → delavec → ponudnik → shramba**

In pozneje:

**API → predpomnilnik → vrste po prioriteti → skupine delavcev → usmerjevalnik ponudnikov → več ponudnikov → shramba/CDN → spletni kaveljčki + spremljanje**

Arhitektura bi morala rasti kot odziv na resnična ozka grla in ne na teoretično zapletenost. Pomembno je izbrati meje, ki omogočajo prihodnje izboljšave.

## **Kdaj dodati čakalno vrsto?**

Čakalna vrsta postane vse uporabnejša, ko:

1. Ustvarjanje lahko traja več kot nekaj sekund.
2. Uporabniki oddajajo veliko besedila.
3. Opravila vsebujejo več blokov.
4. Pogosto dosežete omejitve ponudnika.
5. Promet prihaja v sunkih.
6. Potrebujete zanesljive ponovne poskuse.
7. Delavce želite prilagajati neodvisno od API-ja.

Če je vsaka zahteva zelo majhna in se konča skoraj takoj, vrsta sprva morda ni potrebna.

## **Kdaj dodati več ponudnikov?**

Podpora za več ponudnikov je smiselna, kadar zanjo obstaja konkreten razlog, na primer:

1. Potrebni so različni glasovi.
2. En ponudnik ne podpira določenega jezika.
3. Potrebujete večjo skupno zmogljivost.
4. Potrebujete različne cenovne razrede.
5. Za kritične obremenitve potrebujete nadomestnega ponudnika.

Dodajanje ponudnikov zgolj zaradi arhitekturne elegance lahko poveča vzdrževalno breme, ne da bi prineslo veliko vrednosti.

## **Kdaj predpomniti izhod TTS?**

Predpomnjenje je še posebej koristno, kadar:

1. Se enaka vsebina pogosto ustvarja.
2. So klici ponudnika TTS dragi.
3. So nekateri izhodi dovolj deterministični za ponovno uporabo.
4. Uporabniki pogosto znova poskusijo ali odprejo obstoječe projekte.
5. Se pri velikih projektih naenkrat ureja le nekaj blokov.

Tudi če celotnega zvoka ni mogoče vedno ponovno uporabiti, lahko predpomnjenje na ravni blokov še vedno prinese znatne prihranke.

## **Produkcijski TTS je problem orkestracije**

Sam model TTS je samo ena komponenta. Produkcijski sistem mora usklajevati:

**Uporabnike + opravila + vrste + delavce + ponudnike + zvok + shrambo + zaračunavanje + spremljanje**

Zato je predstavitev lokalnega TTS mogoče hitro zgraditi, zanesljiva javna platforma TTS pa zahteva veliko več inženirskega dela. Zapletenost izvira iz vsega, kar obdaja model.

## **Sklepne misli**

Produkcijski API za pretvorbo besedila v govor bi moral biti že od začetka zasnovan za napake, sočasnost in dolgotrajno obdelavo.

Osnovna arhitektura je preprosta:

**Sprejmite zahtevo → Preverite jo → Po možnosti znova uporabite obstoječi izhod → Ustvarite opravilo → Uvrstite delo v vrsto → Ustvarite govor → Ponovite odpravljive napake → Shranite zvok → Vrnite rezultat.**

Z rastjo prometa postajajo vse pomembnejše dodatne plasti, kot so usmerjanje ponudnikov, vrste po prioriteti, obdelava po blokih, nadzor omejitev hitrosti, sledenje stroškom, povratni klici in opazljivost.

Najpomembnejša ugotovitev je, da je ustvarjanje govora običajno preprost del. Resnični produkcijski izziv je zgraditi sistem, ki lahko zanesljivo ustvarja govor za veliko uporabnikov in pri številnih ponudnikih, hkrati pa ohranja stroške in napake pod nadzorom.
