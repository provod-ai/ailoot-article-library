# Modellrouting absichern: Wenn der günstigste Weg die Schutzmaßnahme auswählt

> Wie sich Modellrouting auf Kosten, Sicherheit und Schutzmaßnahmen auswirkt und warum Schutzmaßnahmen für jede Route gelten sollten.






## Was Modellrouting tatsächlich ist

Ein Modellrouter wählt für eine Anfrage ein Modell oder einen Anbieter aus. Je nach Aufbau kann er dafür feste Regeln, Verfügbarkeit, Anfrageattribute oder einen Klassifikator nutzen. Zu den möglichen Optionen gehören Modelle: schwach oder stark, Generalist oder Spezialist, Anbieter A oder Anbieter B, Cloud oder lokal. Die Vorteile und Risiken des Routings ergeben sich aus diesem Aufbau.

Einige Varianten helfen dabei, ein System einzuordnen:

- **Kosten-/Qualitätsrouting** — leitet Anfragen zwischen stärkeren und schwächeren Modellen weiter.
- **Semantisches oder fähigkeitsbasiertes Routing** — sendet eine Matheaufgabe an ein auf Mathematik spezialisiertes Modell und ordnet jede Anfrage einem Modell zu, das auf ihre Kategorie abgestimmt ist.
- **Gateway-Routing** — ein LLM-Gateway oder ein selbst gehosteter Proxy schaltet viele Anbieter hinter einer einzigen API vor, mit Failover und Kostenverfolgung.
- **Routing innerhalb eines Modells** — Mixture-of-Experts, bei dem ein Router *im* Modell auswählt, welche Experten jedes Token verarbeiten. Ob ein Angriff auf diese Ebene übertragbar ist, hängt vom Modell und Bedrohungsszenario ab.

Wenn das Routing den Promptinhalt nutzt, kann ein Benutzer die Eingabe für die Routing-Entscheidung beeinflussen. Festes oder metadatenbasiertes Routing hat eine andere Angriffsfläche.

## Die Vorteile

Routing kann in vier Bereichen helfen. Bei großem Umfang können die Vorteile Routing zu einer erwägenswerten Option machen.

**Kosten.** Routing kann die Kosten senken, indem nur ein Teil der Anfragen an stärkere, teurere Modelle gesendet wird. Die wirtschaftliche Begründung lautet, dass der Produktionsverkehr oft einfache Anfragen enthält und es verschwenderisch sein kann, für alle den Preis von Spitzenmodellen zu zahlen. Die Ergebnisse hängen von der Arbeitslast und der Auswertung ab; ein Benchmarkwert ist keine allgemeingültige Einsparungsgarantie.

**Latenz.** Ein gut entwickelter Router kann leichtgewichtig sein. Semantisches Caching kann außerdem für eine Anfrage, die einer bereits gesehenen ähnelt, eine gespeicherte Antwort zurückgeben und so die Latenz sowie die Last auf dem Backend verringern.

**Qualität.** Beim Routing geht es um mehr als den Wechsel zu einem schwächeren Modell, um Geld zu sparen. Es kann jede Anfrage einem dafür geeigneten Modell zuordnen, etwa eine Matheaufgabe einem auf Mathematik abgestimmten Modell. Im Vergleich zu einem einzigen Allzweckmodell kann die Qualität durch Routing steigen.

**Ausfallsicherheit.** Ein Gateway vor mehreren Anbietern kann Failover unterstützen, wenn ein Anbieter die Anfragerate begrenzt oder ausfällt, und eine zentrale Steuerungsebene für Authentifizierung, Ratenbegrenzung, Beobachtbarkeit und Kostenverfolgung bereitstellen. Transparenter Failover funktioniert gut, bevor ein Stream beginnt; ein Fehler mitten im Stream muss weiterhin im Anwendungscode behandelt werden.

Diese Vorteile machen es nicht überflüssig, die Risiken des Routings zu berücksichtigen.

## Die routing-spezifische Bedrohungsklasse

Routenmanipulation unterscheidet sich von Prompt Injection gegen ein Modell. Allgemeine Injection zielt auf die Ausgabe des Modells; Routenmanipulation zielt auf die Modellauswahl. Ein Angreifer kann versuchen, zu beeinflussen, welches Modell und welche Schutzmaßnahmen die Anfrage bearbeiten.

Ein adversarialer Trigger, der einer Anfrage vorangestellt wird, kann mehrere Ziele verfolgen:

**Kostensteigerung.** Den Router dazu zwingen, bei jeder Anfrage ein teures Modell auszuwählen, wodurch das Risiko einer kostenbedingten Dienstverweigerung entsteht. Dies betrifft Budget und Verfügbarkeit.

**Qualitätsübernahme.** Den Router dazu zwingen, ein schwächeres Modell auszuwählen, um die Ausgabe eines Gegners unbemerkt zu verschlechtern. Das kann schwer zu erkennen und überall dort schädlich sein, wo die Ausgabequalität das Produkt ist.

**Umgehung von Schutzmaßnahmen.** Eine schädliche Anfrage zu einem Modell oder einem Experten in einem Mixture-of-Experts-System mit schwächerer Ausrichtung lenken und so stärkere Schutzmaßnahmen umgehen. 

Ein Angreifer ist für den Fehler nicht erforderlich. Die Robustheit des Routings hängt von der Implementierung ab und muss getestet werden. Präferenzbasierte Router können kategoriebedingte, suboptimale Entscheidungen treffen und Jailbreak-Versuche unbeabsichtigt an schwächere Modelle weiterleiten. Die Schwachstelle kann bereits bestehen, bevor jemand versucht, sie auszunutzen.

## Warum dadurch die Annahme zu Schutzmaßnahmen nicht mehr gilt

Das grundlegende Problem ist strukturell: Bei manchen Architekturen wird Sicherheit zu einer *Funktion der Routing-Ausgabe* statt zu einer *Invariante über alle Routen hinweg*.

Der Kostenoptimierer und der Angreifer können denselben Hebel betätigen. Der Betreiber verschiebt die Trennlinie zwischen schwachen und starken Modellen, um Geld zu sparen. Ein Angreifer kann versuchen, eine Anfrage über diese Trennlinie zu bewegen, indem er sie weniger schwierig erscheinen lässt.

Kostenoptimierung kann schwaches Routing konstruktionsbedingt verstärken. Je stärker ein System auf Einsparungen optimiert ist, desto mehr Datenverkehr kann in den Bereich geleitet werden, den ein Angreifer beeinflussen möchte.

Es fehlt die Absicherung durch die Annahme, dass die Schutzmaßnahmen des starken Modells das System schützen. Sie schützen keine Anfragen, die an das schwache Modell gesendet werden: Die Schutzmaßnahmen des starken Modells werden konstruktionsbedingt umgangen, weil es nicht mehr Teil des Ablaufs ist.

Den Router einfach so zu verschärfen, dass er schwaches Routing ablehnt, kann den Kostenvorteil zunichtemachen und zugleich Spielraum dafür lassen, dass ein Angreifer den Schwierigkeitsgrad vortäuscht. Beide Seiten wirken auf denselben Hebel ein.

Die Sicherheitsabdeckung kann stattdessen unabhängig von der Weiterleitungsentscheidung gestaltet werden: Führe Schutzmaßnahmen und Inhaltsklassifizierung bei jeder Anfrage aus, unabhängig davon, welches Modell sie bearbeitet. Einbettungsbasierte Erkennung und adaptive Schwellenwerte sind Ansätze, die in Schutzsystemen verwendet werden. Der architektonische Schritt besteht darin, Prüfungen vor die gesamte Modellgruppe zu setzen, nicht hinter die Route. Prüfungen über alle Routen hinweg verringern das Risiko, dass allein die Routenwahl sie auslässt; die Prüfungen selbst können weiterhin versagen oder auf anderen Wegen umgangen werden. Zwei weitere Maßnahmen können helfen: Behandle eine unplausibel niedrige Einschätzung des Schwierigkeitsgrads als verdächtig und führe die Sicherheitsergebnisse an den Routing-Schwellenwert zurück, damit das System lernen kann, wohin es gelenkt wird.

## Ein weiteres Risiko: der Router als Engpass

Ein separates Risiko geht von der Routing-Ebene selbst aus. Je nach Architektur und Konfiguration kann ein Gateway oder Proxy Zugriff auf laufende Prompts, Antworten, Zugangsdaten oder Tool-Aufrufe haben. Dieser Zugriff kann das Lesen, Speichern oder Ändern von Informationen ermöglichen; prüfe daher die tatsächlichen Berechtigungen und Datenflüsse.



- Jeder hinzugefügte Anbieter kann eine weitere Gerichtsbarkeit, Aufbewahrungsrichtlinie oder einen Unterauftragsverarbeiter mit sich bringen. Ein Gateway kann anhand der Datenaufbewahrungspraktiken der einzelnen Anbieter routen. Prüfe diese Praktiken daher, bevor du sensible Informationen sendest.
- Verwaltete Gateways bieten möglicherweise Kontrollen wie Routing ohne Datenspeicherung und eine Beschränkung auf EU-Regionen. Teams mit Anforderungen an den Datenstandort sollten bestätigen, welche Kontrollen für die Anbieter gelten, an die sie routen.

Stimme die Gegenmaßnahmen auf das Risiko ab: Entferne personenbezogene Daten vor der Übermittlung nach außen, leite sensible Arbeitslasten an selbst gehostete oder lokale Modelle weiter, fixiere und prüfe das Gateway und behandle es als kritische Infrastruktur.

## Routen, aber verschiebe die Schutzmaßnahme mit dem Datenverkehr

Modellrouting ist eine Entscheidung, die sowohl ein Kostenhebel als auch eine Angriffsfläche sein kann. Einsparungen und Risiko teilen sich einen Kontrollpunkt.

Wähle eine häufig genutzte geroutete Arbeitslast und frage: Wird die Sicherheitsprüfung für den gesamten Datenverkehr ausgeführt oder nur für den Datenverkehr, den der Router an ein stärkeres Modell sendet? Falls Letzteres zutrifft, besteht eine Lücke.

Die Schwachstelle besteht nicht darin, dass es kostengünstiges Routing gibt. Sie besteht darin, dass Sicherheit zu einer Funktion der Route werden kann. Mache sie zu einer Invariante über alle Routen hinweg, damit durch Kosteneinsparungen kein Teil des Datenverkehrs ungeschützt bleibt.
