# How to Measure Errors in an LLM Judge

> A practical guide to measuring false passes, false fails and stability in an LLM judge against human-reviewed examples.



A model judge can help review AI responses at scale, but a score is useful only when you know what it measures and how often the judge gets it wrong. This guide shows how to examine those errors against human-reviewed examples.

## Define the decision first

Choose one clear question, such as whether an answer includes a required eligibility condition. Give the judge the relevant source material, the answer being assessed and a criterion it can apply. Decide what a pass, a fail and an uncertain result mean before collecting scores.

A model's explanation can help a reviewer investigate a decision, but the explanation is not proof that the decision is correct. Check it against the supplied evidence.

## Build a reference set

Collect examples that represent the actual task, including common answers, borderline cases and known failures. Have people apply the same written criterion to each item. Use overlapping reviews for a portion of the set, resolve disagreements and record the agreed labels and criterion version.

Keep some examples separate for later evaluation when you revise the prompt or select a judge. If you repeatedly tune to the same examples, the measured improvement on that set may not carry over to new cases. Include sensitive or costly mistakes deliberately, while keeping track of how the sample was assembled.

## Count both kinds of error

Compare the judge's decisions with the agreed human labels. A false pass means the judge passes an answer that reviewers marked as failing. A false fail means it rejects an answer that reviewers marked as passing. Both matter: one can hide defects, while the other can create unnecessary review work.

For a simple illustration, suppose reviewers marked 20 answers as failing and the judge passed 4 of those. The false-pass rate among reviewer-labelled failures is 4 out of 20, or 20%. Suppose reviewers marked another 80 answers as passing and the judge rejected 8 of them: the false-fail rate among reviewer-labelled passes is 8 out of 80, or 10%. These are illustrative numbers, not a performance claim.

Always report the denominator and the sample period with a rate. A small or unrepresentative sample can make an estimate unstable. Inspect the actual mismatches; a single aggregate number will not show whether errors cluster around missing sources, long answers or a particular kind of question.

## Check stability, not just agreement

For pairwise comparisons, repeat a sample with the answer order reversed and inspect decisions that flip. If outputs vary between runs, measure that variation on unchanged inputs before treating a small score movement as a real change. A plausible or longer answer should not receive credit for style when the criterion concerns factual support.

Route uncertain cases and the cases where a mistake matters most to a qualified reviewer. Use deterministic checks for properties a program can verify directly, such as whether required JSON fields are present.

## Recheck after a change

Record the judge model, instructions, criterion, reference set and evaluation date alongside results. Re-evaluate when any of those inputs or the underlying task changes. For a release decision, examine the judge's error patterns and the consequences of mistakes rather than relying on a single threshold alone.

Evaluation tools still need criteria and a validation set suited to your own task. See [OpenAI's evaluation best practices](https://platform.openai.com/docs/guides/evaluation-best-practices) for further guidance.
