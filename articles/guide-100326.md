# What is an LLM router?

> Understand model routing, router components, build-versus-adopt tradeoffs, and when a router may be unnecessary.



## What is an LLM router — and do you actually need one?

An LLM router sits between an application and its model endpoints. For each inference request it can choose the model, the provider serving that model, or both. Its policy defines when to try a different endpoint after a failure.

The term is having a moment, which means it's being stretched to cover things it shouldn't. Before you evaluate any router, or build one, it's worth being precise about what's actually in the box.

## Two different things wear the same name

**Model routing** selects the model for an inference request. A smaller model may be enough for routine classification, while a harder synthesis task may need a more capable model. **Provider routing** can keep the selected model and switch to another compatible endpoint if one provider is temporarily overloaded.

**Tool-call routing** selects the service that executes a tool call after the agent has chosen the tool. For a web search, it can start with a local index and try another search API if it needs broader coverage. The providers in the chain perform the same tool action.

In both cases, the routing policy orders targets that can meet the request's requirements. Model quality can be hard to judge in advance. Some tool outputs are easier to check, such as whether extraction returned an article body. A search result can contain hits and still miss what the user asked for.

This post covers both, because the anatomy is shared.

## What's actually inside an LLM router

Strip the marketing and a router has four components. If a product can't show you all four, it's a proxy with opinions.

**Policy.** First filter for the capabilities the request requires. Then order eligible targets by criteria such as expected quality, price or latency. A fixed priority list can be enough. A classifier that picks the model tier adds work of its own, so measure what it improves.

**Health signals.** Track error rates, timeouts and latency percentiles per endpoint. Set a timeout for each attempt so a single call can move on when an endpoint never answers. Use trends across requests to decide whether to temporarily skip a degraded endpoint.

**Fallback rules.** Define which failures allow another attempt, such as a temporary overload or a timeout when repeating the request is safe. Decide separately what to do when a search returns HTTP 200 with zero results. Limit the number of attempts and the total time. A client timeout leaves the outcome and any charge uncertain.

**Accounting.** Record the model and service that answered, the latency, and any usage and charges that are available. Record every attempt under the same logical request, including failed ones. Track estimated cost separately from confirmed charges so you can compare the cost of the whole chain.

## Build or adopt?

A simple router can start with a list of eligible targets, a timeout per attempt, a total deadline, fallback rules and an attempt log. Keep the policy in your application as long as that covers your workload.

Adopt when you want the parts that are tedious to build and maintain: provider integrations that track API churn, health tracking with sane defaults, cost tables that stay current, transport plumbing. An MCP server can expose a tool through one interface and choose the provider behind it.

Check whether you can control provider credentials, export usage records and change endpoints without rewriting calls. Compare the costs of running your own router and using a hosted one, including any fees the router charges.

## When a router is overkill

Honest section, because the answer to the title question is sometimes no.

A router is often unnecessary when one model from one provider serves a low-volume, non-critical path. As an example, with a $40 monthly bill, compare the plausible savings with the cost of engineering and maintenance.

A small integration may need one backup provider. Handle a specific temporary error and try that compatible provider within the deadline if repeating the request is safe.

Consider centralizing the rules if several providers serve the same workload, outages have affected users, measured costs justify the work, or routing logic is scattered across the application. A shared policy gives you one place to maintain and test those decisions.

Start by listing which targets are eligible, in what order to try them and which outcomes allow another attempt. A fixed list can be enough at first. Add a backup when the workload needs one.
