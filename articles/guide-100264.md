# What is AI Inference? A Complete Guide

> AI inference is the runtime phase in which a trained model produces outputs from new inputs. It is the layer that shapes the cost, latency, and reliability of AI-powered products in production.



AI inference is the process by which a trained machine learning model produces an output in response to new input. When a chatbot answers a question, a search system returns a ranked result, or an image model generates a picture, inference is the step that turns a saved set of model weights into the response the user sees. Training builds the model; inference runs it whenever someone uses it.

Every chatbot reply, AI code completion, and AI-generated search summary requires inference. A model's training run happens once, while inference runs for each user request. As a result, the cost, latency, and reliability of the serving layer matter to the economics of AI-powered products.

## What inference actually means

Inference is the runtime execution of a trained model with fixed weights. During training, the model's weights change as it learns from examples. After training, those weights are saved. Inference takes those fixed weights, combines them with a new input, and computes an output. The model itself does not change during inference; it performs a read-only forward computation.

For large language models, a single inference request has four stages, each with its own cost and latency profile:

![LLM inference pipeline: a prompt is tokenized, processed in a parallel prefill pass, then generated token-by-token during the autoregressive decode stage before being detokenized back into text]()

1. **Tokenization.** The input text is split into tokens—units roughly the size of a syllable or short word—that the model's vocabulary represents numerically. A 500-word document may become between 600 and 800 tokens, depending on the tokenizer. Tokenization affects the number of tokens processed per request.
2. **Prefill.** The tokens pass through the model's layers in a single forward pass, producing a representation of the input and the first output token. This stage is compute-bound and highly parallelizable.
3. **Autoregressive decode.** The model generates each subsequent output token one at a time, with each new token conditioned on the previous tokens. This stage is memory-bandwidth-bound rather than compute-bound, which helps explain its role in latency for long responses.
4. **Detokenization.** The output tokens are converted back into the visible text the user receives.

Prefill is fast and parallel; decode is slower and sequential. This difference is one reason LLM inference has developed infrastructure specializations distinct from traditional machine-learning model serving. It also helps explain inference performance: time to first token is affected by prefill, while tokens per second is affected by decode. The two respond to different optimizations.

## Inference vs training: the short version

Training and inference differ in many operational dimensions. Training consumes a large dataset and produces a set of weights; inference repeatedly consumes an input and produces an output.

| Dimension | Training | Inference |
|----|----|----|
| Frequency | Once per model version | Once per user request |
| Duration | Days to months | Milliseconds to seconds |
| Hardware | Tightly coupled GPU clusters with high inter-node bandwidth | Individual GPUs or small groups |
| Cost shape | Capital-like, paid upfront | Operating-like, proportional to usage |
| Who absorbs the cost | Model creator | Application team |
| Optimization priority | Model quality | Cost, latency, reliability |

For teams building on foundation models, training economics are often handled by the model provider, while application teams manage inference economics. Decisions about provider, deployment location, batching, caching, and fallback all affect inference.

## Types of inference workloads

The definition covers any case where a trained model produces an output, but workload profiles vary enough that it is useful to name the main categories separately.

![Map of the five LLM inference workload types positioned by response latency and per-request cost: embeddings cheapest and fastest, chat in the middle, vision and reasoning progressively slower and more expensive, and batch as the latency-tolerant discounted tier]()

**Text generation (chat).** A common inference workload. A prompt enters, tokens are generated one at a time, and the response may be streamed to the user. 

**Reasoning and chain-of-thought.** A variant of text generation in which a model produces a block of internal reasoning before its visible response.  Examples include OpenAI's o-series, Anthropic's extended thinking modes, and DeepSeek-R1.

**Embeddings.** A text input produces a fixed-length vector rather than generated text. Embeddings are used for search, retrieval-augmented generation (RAG), clustering, and deduplication.  Embedding inference supports many modern search and memory systems.

**Vision and multimodal.** An image, video frame, or audio clip combined with text produces a text or structured output. Latency can scale with input resolution, and cost depends on how many tokens the input decodes to. The same serving infrastructure can handle these workloads, but tokenization can be more expensive than for plain text.

**Batch inference.**  For pipelines that do not require real-time responses—such as overnight enrichment, offline evaluation, or scheduled data preparation—batch inference can reduce costs.

## Where inference actually runs

Running inference at production quality depends on three infrastructure layers that are not visible from the API surface but affect costs.

**The GPU tier.** Modern LLMs require GPUs with high memory capacity and bandwidth. NVIDIA H100 and H200 cards are used for large models. Smaller models can run on A100 or L40S cards, and very small models on consumer cards. The card choice affects throughput and the minimum model size that can be served without sharding across multiple cards. GPU memory sizing is a key part of planning LLM inference.

**The serving engine.** Raw GPU access is not sufficient. Efficient model serving requires an engine—also called an inference engine or inference server—to manage the KV cache, batch concurrent requests, and optimize memory layout. Commonly used engines include vLLM (open source, general purpose), TensorRT-LLM (NVIDIA-specific, high performance), and SGLang (open source, optimized for structured generation). The serving engine can significantly affect throughput on the same hardware.

**Regional deployment.** Compute time is a major contributor to inference latency, and network round trips add further delay. For user-facing workloads, serving from a region close to the user can affect perceived responsiveness.

Operating this stack can suit teams with significant scale and dedicated infrastructure engineering. Others may purchase infrastructure, making the choice of purchasing model important.

## How teams access inference in practice

Three patterns cover many production inference setups.

![Architecture comparison of the three inference access patterns: a self-hosted stack with serving engine and rented GPUs, a direct single-provider API, and a unified platform routing one API across multiple providers]()

**Self-hosting on rented GPUs.** The team rents GPU capacity, deploys an open-weight model on a serving engine, and operates the full stack. This gives the team control and can be economical at very high volume, but requires infrastructure expertise in areas such as KV cache tuning, autoscaling, failover, and observability.

**Direct provider APIs.** The team calls a single provider's API. The provider handles the infrastructure. This is a fast path to a working product and a common way to start. The tradeoff is concentration risk and dependence on one pricing structure. Each request's cost, latency, and reliability depend on that provider's service.

**Unified inference platforms.** The team calls a single API that routes requests to multiple underlying providers and may include fallback, observability, and cost controls. This can retain the speed-to-ship advantage of direct provider APIs while reducing single-provider concentration risk and enabling workload-aware routing, such as using a lower-cost model for simple queries and a more capable model for complex ones.

| Access pattern | Speed to ship | Operational burden | Economical at | Concentration risk |
|----|----|----|----|----|
| Self-hosted on rented GPUs | Slow | High (full infrastructure stack) | Very high volume | None |
| Direct provider API | Fast | Low | Low to medium volume | High (single provider) |
| Unified inference platform | Fast | Low | Any volume, mixed workloads | Lower (multiple providers) |

The choice among these patterns depends on scale, engineering capacity, and how much variation in provider cost and reliability the team is willing to manage directly.

## Why inference is the ongoing cost center

Inference affects the economics of AI-powered products because its cost scales with usage. A model's training cost is fixed and paid once by the provider or the team that trains it. Each inference request consumes additional compute. Ten users generate ten inferences; one million users generate one million. In practice, the unit economics of an AI product depend on the unit economics of inference.

![Chart of cumulative cost over a model's lifetime: training cost rises once then stays flat, while inference cost starts at zero and grows with every request served, eventually passing the entire training cost]()

This structure has two consequences. First, the cost of an AI feature grows with its usage: a feature with low adoption has a small inference bill, while one with high adoption has a larger one. Second, architectural choices that change inference cost compound as usage grows. These choices include model selection, prompt design, caching strategy, provider choice, and retry policy. A 20% reduction in per-request cost reduces marginal cost by the same proportion as usage grows.

The headline cost-per-million-token figure describes a particular request scenario; production workloads may differ from that scenario.

## What most inference guides leave out

The mechanics above are well documented. Some operational considerations become clear when inference is run across providers in production:

- **The cheapest model is rarely the cheapest system.** A model with a lower per-token price that fails more often, needs longer prompts to reach the same quality, or causes more retries can cost more per completed task than a nominally pricier model. Effective cost depends on the whole request path, so cost optimization involves architecture as well as price lists.
- **Output length is a strong lever.** Because decode affects both inference latency and output cost, prompt changes that shorten responses can improve both.
- **Fallback policy affects price.** Providers can have outages and rate limits. Whether a system fails, queues, or reroutes during those periods is an economic decision. Fallback chains affect availability and cost.
- **The ground can shift silently.** Providers may change prices, quantize deployments, or swap model versions behind stable names. An inference setup tuned once and never rechecked can degrade over time.
- **Benchmark rank does not decide what serves a request.** Leaderboards can help identify capable models, but choosing among them for a specific request also requires considering cost, latency, and availability constraints.

These considerations are not part of the definition of inference, but they can strongly affect production costs.

## The question inference leads to

Understanding inference is a starting point. Production decisions include which model should handle each request, on which provider, at what price, and with what fallback. Choosing one fixed model makes those decisions once for all future traffic. Another approach is to treat model selection as a per-request decision, based on the request's needs.

For teams mapping workloads to models, model selection involves weighing the workload's requirements against model capabilities and costs.
