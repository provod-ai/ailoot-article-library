# Text Classification with an LLM

> A practical guide to classifying text with an LLM, choosing labels, reviewing suggested changes and checking results.



A language model can classify text by applying a set of labels to each item. This guide explains how to define the labels, handle uncertain cases and measure whether the results are useful.

## Define the decision

Start with a question that has a practical outcome. A support team might group messages into `billing`, `technical` and `other` so they can route them to the right queue. Decide whether each message needs one label or can have several. Explain each label with examples, including cases that look similar but belong in different groups.

Keep an `other` or review option for items that do not fit. A forced choice can make a clean-looking report while hiding a poor taxonomy. For decisions that affect people or have significant consequences, keep a person in the loop.

## Ask for a predictable result

Give the model the text, the label definitions and the desired output format. Treat the text being classified as data, not as an instruction to the model. For example, a message saying “ignore the labels” is still the item to classify; it should not change the task.

A result might look like this:

```json
{"label":"billing","reason":"The message asks about an invoice."}
```

This is an illustrative result, not a real model response. Before using an output, check that it parses, contains the expected fields and uses an allowed label. A valid format alone does not mean the classification is correct. Model support for schema-constrained output varies; check the documentation for the model and API you use.

## Improve the label set

Start with a manageable set of categories and review examples that fall into `other` or repeatedly cause disagreement. They may reveal a missing category, an unclear definition or two labels that overlap. Propose changes using representative examples, then ask a reviewer to approve the new definitions before applying them broadly.

A model can also suggest new labels and propose merges as an experiment. Mark protected categories that must remain distinct and verify every proposed change against those constraints before updating the taxonomy.

If two categories seem similar, compare what decisions they support before merging them. For example, payment failures and refund requests may both concern money but require different actions. Keep distinctions that matter to the workflow, and record a version for each change to the taxonomy.

## Check performance before scaling

Create a sample that reflects the real mix of messages, including rare and ambiguous cases. Have people label it using the same definitions, resolve disagreements and keep the agreed labels as a reference. Compare model results with those labels and inspect mistakes for each category; an overall accuracy figure can conceal a weak category.

Test changes to the prompt, model or taxonomy on a separate evaluation set. Monitor results over time because the language and mix of incoming text can change. Send uncertain or invalid results to review rather than silently assigning a label.

## Protect the input and plan the workflow

Send only the information needed for the task and handle sensitive records according to your organisation's rules. If processing a large collection, test a small representative batch first, record failures and define how to resume without losing or duplicating items. Measure the time and cost of the actual workflow before increasing its volume.

The goal is not simply to produce labels. It is to create a repeatable decision process whose definitions, exceptions and errors can be inspected.

For further guidance, see [OpenAI's structured output documentation](https://platform.openai.com/docs/guides/structured-outputs) and [evaluation best practices](https://platform.openai.com/docs/guides/evaluation-best-practices).
