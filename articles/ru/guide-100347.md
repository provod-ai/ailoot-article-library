> Как взаимодействуют шлюзы, маршрутизация, кэширование и обслуживание моделей и как контекст запроса может проходить через эти уровни.

Как взаимодействуют шлюзы, маршрутизация, кэширование и обслуживание моделей и как контекст запроса может проходить через эти уровни.

Контекст запроса может пройти через шлюз и маршрутизатор к обслуживанию моделей. Этот контекст связывает выбор модели, повторное использование кэша и выполнение с идентичностью вызывающей стороны и стоимостью каждой попытки. Маршрутизатор, который игнорирует состояние кэша, может потратить всю экономию, достигнутую соседним уровнем.

Общий контекст требует интеграционной работы, а маршрутизатор, учитывающий состояние кэша, сложнее заменить. Передача контекста вместе с запросом при раздельных продуктах позволяет команде использовать шлюз и маршрутизатор со средой выполнения другого провайдера. Тогда маршрутизатор принимает решения на основе информации, которую предоставляет этот провайдер.

## Более дешёвый маршрут может обойтись дороже

Рассмотрим условную службу извлечения данных из документов: в каждом запросе передаются длинные неизменные инструкции и короткий документ. Кэширование префикса и маршрутизация выглядят привлекательно, но каждое может свести на нет выгоду от другого. Кэшированный префикс — это состояние ключей и значений, вычисленное одной моделью, поэтому запрос, направленный к другой модели, считывает инструкции с нуля.

В опубликованных Anthropic ценах на кэширование на пять минут запись стоит 1,25 от базовой цены входных данных, а чтение — 0,1 от неё; для отдельных моделей действуют исключения ([анонс](https://www.anthropic.com/news/prompt-caching), [документация](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). При таком тёплом кэше альтернативная модель без кэширования должна стоить менее одной десятой цены входных данных у текущей модели, чтобы выиграть на общем префиксе. Одна запись и одно попадание в кэш обходятся в 1,35 прохода входных данных по кэшируемой части против двух проходов без кэширования. Запись, которую ни один последующий запрос не использует, обходится в 1,25.

Маршрутизатор, сравнивающий цены из прайс-листов, может заметить модель с ценой входных данных вдвое ниже и переключиться на неё, заплатив за префикс как минимум в пять раз больше. В объявленных правилах маршрутизации указывается, какие модели могут заменять друг друга; общий контекст показывает стоимость каждой такой замены.

## Для повторного использования ответов нужна идентичность вызывающей стороны

<figure>
<ol>
<li><strong>Точный ответ</strong> — Повторное использование ответа для совпадающего запроса</li>
<li><strong>Префикс</strong> — Повторное использование вычислений для входных данных с генерацией нового ответа</li>
<li><strong>Семантический кэш</strong> — Определение эквивалентности разных запросов</li>
</ol>
Повторное использование должно учитывать модель, промпт, схему и требования к актуальности.
<figcaption>Три разных вида повторного использования · Кэш ответов — не префиксный кэш.</figcaption>
</figure>

Кэш ответов возвращает сохранённый результат; семантический кэш также решает, когда для двух разных запросов подходит один и тот же результат. [GPTCache](https://github.com/zilliztech/GPTCache) определяет попадания по сходству эмбеддингов, а в его README содержится предупреждение о «ложных срабатываниях при попаданиях в кэш».

При извлечении данных ложное срабатывание может привести к неверному номеру счёта: два счёта от одного поставщика, созданные по одному шаблону, могут оказаться близкими в пространстве эмбеддингов, и кэш может выдать для второго счёта номер счёта из первого. Семантический кэш без идентичности приложения может вызвать ошибку корректности, а его панель показателей попаданий учтёт каждый неверный ответ как экономию.

Anthropic изолирует кэши промптов между организациями, а в собственном API — и между рабочими пространствами, хотя префиксный кэш не возвращает сохранённый ответ. Для кэша ответов как минимум нужна такая же граница. Приложение может объявить, допускает ли задача повторное использование результатов для похожих входных данных; при таком повторном использовании ключ может учитывать вызывающую сторону, данные, к которым ей разрешено обращаться, и версию задачи.

При извлечении данных можно использовать повторное применение только при точном совпадении или отказаться от него; при неизвестном ключе запускать вычисление заново. Это правило снижает долю попаданий и заставляет оплачивать работу, которую пропустил бы менее строгий кэш. Возможно, по умолчанию правило слишком строгое: для большого общедоступного FAQ повторное вычисление по неизвестным ключам может обходиться дороже, чем редкий неверный ответ, от которого оно защищает.

## Найдите причину сбоя, прежде чем выбирать способ исправления

Предположим, более дешёвая модель возвращает недопустимые поля, а более крупная модель их исправляет, увеличивая стоимость и задержку обработки документа. Стоимость можно считать за одно корректное извлечение данных при требуемой задержке; цена токенов первого вызова — лишь одна из входных величин.

Анализ составных систем искусственного интеллекта, выполненный в Беркли, предлагает оптимизировать взаимодействующие компоненты совместно. В трассировке необходимо отличать сбой модели от устаревшего результата повторного использования, медленного инструмента или неверного маршрута, поскольку каждый из этих случаев требует исправления на своём уровне. Контроль выполнения может помочь определить, откуда берутся затраты, а более быстрая среда выполнения может перенести потери на решения вокруг неё. Связывание трассировок с оценкой на производственном трафике позволяет проверить, улучшает ли изменение задачу, включая путь восстановления после сбоя.

Оператор может использовать эту трассировку, чтобы изменить уровень, на котором произошёл сбой. Если история запросов, тестовые случаи для оценки и выбор развёртывания остаются в приложении заказчика, улучшения могут опираться на накопленный опыт самого приложения.
