# LLM маршрутизаторы дегеніміз не?

> Модельдерді маршрутизациялау, маршрутизатор компоненттері, өзіңіз әзірлеу мен дайын шешімді таңдау арасындағы ымыралар және маршрутизатор қажет болмауы мүмкін жағдайлар туралы біліңіз.



## LLM маршрутизаторы дегеніміз не — және ол сізге шынымен керек пе?

LLM маршрутизаторы қолданба мен модельдердің API нүктелері арасында жұмыс істейді. Әр инференс сұрауына ол модельді, сол модельді ұсынатын провайдерді немесе екеуін де таңдай алады. Ережелер ақаудан кейін басқа API нүктесін қашан қолдануға болатынын анықтайды.

Бұл термин қазір жиі қолданылып жүр, демек оған жатпайтын нәрселерді де қамтитындай етіп кеңейтіліп жатыр. Кез келген маршрутизаторды бағаламас немесе өзіңіз жасамас бұрын, оның құрамында нақты не барын анықтап алған жөн.

## Бір атаумен аталатын екі бөлек нәрсе

**Модельдерді бағыттау** сұрауды өңдейтін модельді таңдайды. Кәдімгі жіктеуге шағын модель жеткілікті болуы мүмкін, ал күрделі синтезге мүмкіндігі кеңірек модель қажет болуы ықтимал. **Провайдерлер арасында бағыттау** бірінші провайдер уақытша шамадан тыс жүктелсе, таңдалған модельді сақтап, басқа үйлесімді API нүктесіне ауысуға мүмкіндік береді.

**Құрал шақыруларын бағыттау** агент құралды таңдағаннан кейін шақыруды орындайтын сервисті іріктейді. Веб-іздеуді жергілікті индекстен бастап, ауқымын кеңейту керек болса, басқа іздеу API-ін қолдануға болады. Тізбектегі сервистер бірдей операция орындайды.

Екі жағдайда да бағыттау ережелері сұрау талаптарына сай нұсқаларды реттейді. Модель жауабының сапасын алдын ала бағалау қиын болуы мүмкін. Кей құралдардың нәтижесін тексеру оңайырақ, мысалы, мақала мәтіні алынды ма. Іздеу нәтиже берсе де, ол пайдаланушының сұрағына жауап бермеуі мүмкін.

Бұл жазбада екеуі де қарастырылады, өйткені олардың құрылымы ортақ.

## LLM маршрутизаторының құрамында не бар

Маркетингті алып тастасаңыз, маршрутизатор төрт компоненттен тұрады. Өнім осы төртеуін де көрсете алмаса, ол — өз пікірі бар прокси ғана.

**Саясат.** Алдымен сұрауға қажет мүмкіндіктері бар нұсқаларды іріктеңіз. Оларды күтілетін сапа, баға немесе кідіріс бойынша реттеңіз. Тұрақты басымдық тізімі жеткілікті болуы мүмкін. Модель санатын жіктеуіш таңдаса, оның қандай пайда әкелетінін өлшеңіз.

**Күй көрсеткіштері.** Әр API нүктесінің қате жиілігін, күту шегіне жеткен әрекеттерін және кідіріс процентильдерін бақылаңыз. API жауап бермесе, шақыруды жалғастыру үшін әр әрекетке уақыт шегін қойыңыз. Бірнеше сұраудың дерегі бойынша нашар жұмыс істейтін нүктені қашан уақытша өткізіп жіберуді анықтаңыз.

**Резервке ауысу ережелері.** Қай ақаудан кейін қайта әрекет етуге болатынын белгілеңіз. Мысалы, сұрауды қауіпсіз қайталауға болса, уақытша артық жүктемеден немесе күту уақытының аяқталуынан кейін. Нәтиже жоқ HTTP 200 іздеу жауабын бөлек өңдеңіз. Әрекеттер санын және жалпы уақытты шектеңіз. Клиенттің күту уақыты біткенде, нәтиже мен ықтимал төлем әлі белгісіз.

**Шығын есебі.** Жауап берген модель мен сервисті, кідірісті, қолдағы пайдалану мен ақы деректерін жазыңыз. Сәтсіз әрекеттерді қоса алғанда, барлық әрекетті сол сұраумен байланыстырыңыз. Бүкіл тізбектің құнын салыстыру үшін болжамды және расталған шығындарды бөлек есептеңіз.

## Өзіңіз жасау ма, әлде дайын шешімді алу ма?

Қарапайым маршрутизаторға бастапқыда үйлесімді API нүктелерінің тізімі, әр әрекет пен бүкіл сұрауға арналған уақыт шектері, резервке ауысу ережелері және әрекеттер журналы жеткілікті болуы мүмкін. Бұл ережелер қолданбаның қажетіне сай келгенше сол қолданбада қала алады.

Құрып, күтіп ұстау машақатты бөліктер қажет болса, дайын шешімді таңдаңыз: API өзгерістеріне бейімделіп отыратын провайдер интеграциялары, орынды әдепкі баптаулары бар денсаулық мониторингі, жаңарып тұратын шығын кестелері, деректерді тасымалдау инфрақұрылымы. MCP сервері құралға бірыңғай интерфейс ұсынып, шақыруды орындайтын провайдерді өзі таңдай алады.

Провайдердің қол жеткізу деректерін басқара алатыныңызды, пайдалану жазбаларын экспорттау және шақыруларды өзгертпей API нүктелерін ауыстыру мүмкіндігін тексеріңіз. Өз маршрутизаторыңыз бен хостингтегі нұсқаның құнын салыстырып, маршрутизатор ақысын да ескеріңіз.

## Маршрутизатор артық болатын жағдайлар

Бұл — ашық айтылатын бөлім, өйткені тақырыптағы сұрақтың жауабы кейде «жоқ» болады.

Бір провайдердің бір моделі аз сұрау келетін, аса маңызды емес міндетті атқарса, маршрутизатор көбіне қажет емес. Мысалы, айлық шот 40 доллар болса, ықтимал үнемді әзірлеу және қолдау шығындарымен салыстырыңыз.

Шағын интеграцияға бір резервтік провайдер жеткілікті болуы мүмкін. Нақты уақытша қатені өңдеңіз және сұрауды қауіпсіз қайталауға болса, белгіленген уақыт ішінде үйлесімді резервтік API-ді қолданыңыз.

Бір міндетті бірнеше провайдер атқарса, ақаулар пайдаланушыларға әсер етсе, өлшенген шығындар жұмысты ақтаса немесе бағыттау логикасы қолданбаға шашырап кетсе, ережелерді бір жерге жинаңыз. Ортақ саясат шешімдерді бір жерде қолдап, тексеруге мүмкіндік береді.

Үйлесімді API нүктелерінің тізімінен, оларды сынау ретінен және келесі әрекетке өту шарттарынан бастаңыз. Басында тұрақты тізім жеткілікті болуы мүмкін. Міндет қажет етсе, резервтік нұсқа қосыңыз.
