# How to Test an LLM Judge for Bias

> A practical guide to testing LLM judges for order, style and self-preference biases and interpreting results.



An LLM judge can help assess open-ended AI outputs, but its verdict may change for reasons unrelated to the quality you want to measure. Controlled comparisons can reveal some of those weaknesses before you use the judge in an evaluation workflow.

## Decide what the judge should assess

Choose one criterion and define it in terms a reviewer can check. For example: does an answer state the cancellation deadline supported by the supplied policy? Give both the judge and human reviewers the same question, source material and criterion. Record what counts as a pass, a fail and an uncertain case.

Collect examples that reflect the actual task, including difficult and ambiguous cases. Have people label a representative sample and resolve disagreements. A human label is a reference for the test, not a guarantee that every case has a single obvious answer.

## Test whether order changes the result

For a pairwise judge, present the same two answers in both orders while keeping the question, source and rubric fixed. Map the verdict back to the answer itself, not its position on screen. Count how often the preferred answer changes when the order changes and inspect those cases.

Randomising order can reduce systematic exposure to one position across a set, but it does not prove that position bias has disappeared. If order changes the result, consider routing the pair for review or reporting the instability alongside the comparison.

## Separate style from substance

Build test pairs that differ in presentation while preserving the facts relevant to the criterion. For example, compare a concise supported answer with a longer version that adds no relevant evidence. Ask reviewers to check that the intended quality really is equivalent before using the pair.

If the judge prefers one style, inspect its explanation and the specific rubric. Add examples and clearer criteria where appropriate, then retest on examples that were not used to revise the prompt. A preference observed in one task or model should not be assumed to apply to every judge.

## Check model and prompt effects

When comparing outputs from different models, remove unnecessary identifiers from the material being judged. Test a sample with more than one judge or with human reviewers where the decision warrants it. A model evaluating its own output may show self-preference; a different model may have its own biases. Neither choice removes the need to validate the actual workflow.

Keep the judge model, prompt, examples and output format versioned. Change one component at a time when diagnosing a shift, and compare results on a held-out set. A short rationale can help identify why a verdict changed, but it is itself a model output and must be checked against the evidence.

## Decide how the result will be used

Measure errors and disagreements on human-reviewed examples, including cases where a false pass or false fail would be costly. Use deterministic checks for properties a program can verify directly, and send uncertain or high-impact cases to qualified reviewers. An LLM judge may assess support against material or tools it is given; do not assume that it has independently verified a claim beyond those inputs.

Recheck the judge when the task, model, prompt or input distribution changes. A stable score is not by itself proof of correctness. For guidance on building evaluations, see [OpenAI's evaluation best practices](https://platform.openai.com/docs/guides/evaluation-best-practices).
