# モデルルーティングのセキュリティ：最安の経路がガードレールを選ぶとき

> モデルルーティングがコスト、セキュリティ、安全性の制御にどう影響するのか、そしてガードレールをすべてのルートに適用すべき理由。






## モデルルーティングとは何か

モデルルーターは、リクエストに対するモデルまたはプロバイダーを選びます。設計に応じて、固定ルール、可用性、リクエストの属性、分類器を使う場合があります。選択肢には、弱いモデルまたは強いモデル、汎用モデルまたは専門モデル、プロバイダー A または B、クラウドまたはローカルへのデプロイが含まれます。ルーティングの利点とリスクは、この設計に由来します。

システムの位置づけを理解するには、いくつかの種類が参考になります。

- **コスト／品質ルーティング** — 強いモデルと弱いモデルの間で振り分けます。
- **セマンティックルーティングまたは能力ベースのルーティング** — 数学の問題を数学に特化したモデルに送り、各リクエストをそのカテゴリ向けに調整されたモデルに対応づけます。
- **ゲートウェイルーティング** — LLM ゲートウェイまたはセルフホスト型プロキシが、1つの API の背後で複数のプロバイダーを仲介し、フェイルオーバーとコスト追跡を行います。
- **モデル内部のルーティング** — Mixture-of-Experts では、モデル *内部の* ルーターが各トークンを処理するエキスパートを選びます。攻撃がこの層に転移するかは、モデルと脅威の状況によって異なります。

プロンプトの内容を使ってルーティングする場合、ユーザーはルーティング判断への入力に影響を与えられます。固定方式やメタデータに基づく方式では攻撃対象領域が異なります。

## 利点

ルーティングは4つの面で役立ちます。大規模に運用する場合、その効果からルーティングを検討する価値が生まれることがあります。

**コスト。** ルーティングでは、一部のクエリだけをより強力で高価なモデルに送ることで、コストを削減できます。経済的な根拠は、本番環境のトラフィックには簡単なクエリが含まれることが多く、そのすべてに最先端モデルの料金を払うのは無駄になりうる、という点です。結果はワークロードと評価方法によって異なります。ベンチマークの数値は、普遍的な節約を保証するものではありません。

**レイテンシ。** 適切に設計されたルーターは軽量にできます。セマンティックキャッシュを使えば、既出のクエリに似たクエリに保存済みの回答を返すこともでき、レイテンシとバックエンドの負荷を減らせます。

**品質。** ルーティングの役割は、コスト削減のために弱いモデルへ切り替えることだけではありません。数学の問題に数学向けに調整されたモデルを使うなど、各リクエストに適したモデルを選べます。汎用モデルを1つだけ使う場合と比べて、ルーティングによって品質が向上することがあります。

**耐障害性。** 複数のプロバイダーを仲介するゲートウェイは、プロバイダーがレート制限を設けたり停止したりした場合のフェイルオーバーを支援できます。また、認証、レート制限、可観測性、コスト追跡を一元管理する制御プレーンも提供できます。ストリーム開始前の透過的なフェイルオーバーは円滑ですが、ストリームの途中で障害が起きた場合は、アプリケーションコードでの処理が必要です。

こうした利点があっても、ルーティングのリスクを考慮する必要はなくなりません。

## ルーティング固有の脅威

ルート操作は、モデルに対するプロンプトインジェクションとは異なります。一般的なインジェクションはモデルの出力を狙いますが、ルート操作はモデルの選択を狙います。攻撃者は、どのモデルがリクエストに答えるか、そしてどのガードレールが適用されるかに影響を与えようとする可能性があります。

クエリの先頭に付けられた敵対的なトリガーは、いくつかの目的を追求することがあります。

**コストの急増。** すべてのリクエストで高価なモデルを選ぶようルーターに強制し、予算を枯渇させるリスクを生みます。これは予算と可用性に関わる問題です。

**品質の乗っ取り。** 弱いモデルを選ぶようルーターに強制し、相手の出力品質をひそかに低下させます。検出が難しいことがあり、出力品質が製品の価値そのものである場面では大きな損害につながります。

**安全性の回避。** 有害なリクエストを、アライメントが弱いモデルや Mixture-of-Experts 内のエキスパートに誘導し、より強いガードレールを迂回します。

攻撃者がいなくても障害は起こります。ルーターは、初期設定のままで堅牢とは限りません。選好ベースのルーターは、カテゴリに引きずられた最適でない判断をすることがあり、脱獄の試みを意図せず弱いモデルに送る場合があります。誰かが悪用を試みる前から、こうした弱点が存在することがあります。

## ガードレールの前提が崩れる理由

最も根本的な問題は構造にあります。一部のアーキテクチャでは、安全性を「すべてのルートで成り立つ不変条件」ではなく、「ルーティングの出力に依存する関数」にしてしまいます。

コスト最適化と敵対者は、同じレバーを動かせます。運用者はコストを削減するため、弱いモデルと強いモデルを分ける境界を調整します。攻撃者は、クエリの難易度を低く見せることで、その境界を越えさせようとする可能性があります。

コスト最適化は、設計上、弱いルーティングを強めることがあります。節約を重視してシステムを調整するほど、攻撃者が影響を与えたい領域に多くのトラフィックが送られる可能性があります。

欠けている歯止めは、強いモデルのガードレールがシステムを守るという前提です。そのガードレールは、弱いモデルに送られたクエリを守りません。強いモデルが経路から外れているため、設計上、そのガードレールは迂回されます。

弱いモデルへのルーティングを拒むようルーターを単に厳しくすると、コスト上の利点を損ないながら、攻撃者が難易度を偽装する余地を残すことがあります。どちらの側も同じレバーを動かそうとしています。

代わりに、安全性のカバレッジを振り分けの判断から独立させることができます。どのモデルがリクエストを処理するかにかかわらず、すべてのリクエストにガードレールとコンテンツ分類を適用します。埋め込みベースの検出と適応型のしきい値設定は、ガードレールシステムで使われている手法です。アーキテクチャ上の要点は、ルートの後ろではなく、モデル群全体の前にチェックを置くことです。すべての経路にチェックを適用すると、ルーティングだけでチェックが省略されるリスクを減らせます。ただし、チェック自体が失敗したり、別の経路から回避されたりする可能性は残ります。さらに2つの対策が役立つ可能性があります。難易度の推定値が不自然なほど低い場合は疑わしいものとして扱い、安全性の結果をルーティングのしきい値に反映して、システムが誘導されている箇所を学習できるようにします。

## もう1つのリスク：ボトルネックとしてのルーター

ルーティング層そのものにも、別のリスクがあります。ゲートウェイやプロキシは、アーキテクチャと設定に応じて、送受信中のプロンプト、応答、認証情報、ツール呼び出しにアクセスできる場合があります。そのアクセスによって情報の読み取り、保持、変更が可能になることがあるため、実際の権限とデータフローを確認してください。



- プロバイダーを追加するたびに、別の法域、データ保持ポリシー、またはサブプロセッサが加わる可能性があります。ゲートウェイは各プロバイダーのデータ保持方針に基づいてルーティングできるため、機密情報を送る前に各方針を確認してください。
- マネージドゲートウェイでは、データを保持しないルーティングや EU リージョンへの固定などの制御機能が提供される場合があります。データレジデンシー要件のあるチームは、ルーティング先のプロバイダーにどの制御が適用されるか確認してください。

リスクに合わせて対策を選びます。外部へ送信する前に個人を特定できる情報を除去し、機密性の高いワークロードはセルフホスト型またはローカルモデルにルーティングし、ゲートウェイを固定して監査し、重要なインフラとして扱います。

## ルーティングするなら、トラフィックとともにガードレールも移す

モデルルーティングは、コストを調整する手段であると同時に、攻撃対象領域にもなりうる判断です。節約とリスクは、同じ制御点を共有しています。

頻繁に使われるルーティング対象のワークロードを1つ選び、次の点を確認してください。安全性チェックはすべてのトラフィックに実行されていますか。それとも、ルーターが強いモデルに送るトラフィックだけに実行されていますか。後者なら、そこにギャップがあります。

問題は、低コストのルーティングが存在することではありません。安全性がルートに依存してしまうことです。すべてのルートで安全性を不変条件にすれば、コスト削減のために一部のトラフィックを無防備にする必要はありません。
