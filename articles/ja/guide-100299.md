# LLMを判定者として使う：完全ガイド

> LLM-as-a-judgeとは、ある言語モデルを使って別のモデルの出力をルーブリックに照らして評価する手法です。これにより、チャットボット、RAGシステム、エージェントを対象とするAI評価を実用的な規模で行えます。この記事では、3つの主要な判定モード、LLM判定者が有効な場面と失敗する場面、信頼できるルーブリックの書き方、そして本番利用前にラベル付きゴールドセットでのキャリブレーションが必須である理由を解説します。




LLM-as-a-judgeとは、ある言語モデルを使って別のモデルの出力をルーブリックに照らして評価する手法です。これにより、チャットボット、RAGシステム、エージェントを対象とするAI評価を実用的な規模で行えます。この記事では、3つの主要な判定モード、LLM判定者が有効な場面と失敗する場面、信頼できるルーブリックの書き方、そして本番利用前にラベル付きゴールドセットでのキャリブレーションが必須である理由を解説します。

> **要約 —** LLMを判定者として使うとは、人間の評価者に代わって（または併用して）、言語モデルに記述されたルーブリックに照らして別のモデルの出力を採点させる手法です。本番評価には明示的なルーブリックによる単一回答採点を使い、モデルのバージョンを順位付けするにはペアワイズ比較を使います。ラベル付きゴールドセットに対する測定をしていない判定者を、決して信頼してはいけません。

この記事は、すでに評価を構築していて、「ここでLLM判定者を使うべきか。使うなら、どう使うべきか」という問いに根拠ある答えを求めるエンジニア向けです。評価を書いたことがない場合は、ラベル付きの小さな例セットから始めてください。

## 「LLMを判定者として使う」とは実際には何を意味するのか

LLM判定者とは、何かを評価するよう求めるプロンプトとともに呼び出すモデルです。通常は別のモデルの応答を評価します。スコア、ラベル、または選好を返します。アーキテクチャの全体はこれだけです。重要な点はすべて、プロンプト、ルーブリック、そして判定者の評価が現実と一致するかをどう測るかにあります。

これが普及した理由は、思想的なものではなく運用上のものです。人間だけに頼る評価パイプラインは拡張が難しくなります。その代わり、判定者自身のバイアスが持ち込まれ、人間の評価者と異なり、そのバイアスは体系的です。

## LLM判定者が出力を採点する方法

採点モードは3つあり、どれを選ぶかで評価から分かることと分からないことが変わります。

- ‍**ペアワイズ比較**では、2つの応答のどちらが優れているかを判定者に選ばせます。2つのモデルバージョンまたは2つのプロンプトをA/Bテストするときに使います。絶対的な品質しきい値が必要な場合には使わないでください。ペアワイズスコアには最低水準がないため、応答Bがすべての比較に勝っても、実用に耐えない可能性があります。**‍**
- **ルーブリックによる単一回答採点**では、1つの応答を明示的な基準に照らして採点するよう判定者に求めます。本番で使うべきモードです。すべての応答が同じ軸で採点され、その結果を基にデプロイのゲートを設定できるためです（「カナリーセットで忠実性の基準に合格したらリリースする」など）。必要な違いを捉えられる範囲で、精度が最も低い尺度を選びます。問いたいのが「モデルはルーブリックに違反したか、はいかいいえか」であれば合否の二択、失敗の程度がトリアージに関係するなら3段階尺度（不合格／一部合格／合格）を使います。1〜5や1〜10にするのは、本当にその細かさが必要であり、判定者がその尺度を使いこなせると検証するためのゴールドセットデータがある場合に限ります。細かい尺度は、判定者が根拠を示せない区別を作り出すよう促し、その結果生じるノイズが測りたかったシグナルを覆い隠します。尺度の選択より、ルーブリックの品質のほうが重要です。曖昧なルーブリック（「有用性を1〜5で評価する」）では、情報量のない数値しか得られません。主張単位のルーブリック（「取得した文章が直接裏付けていない事実上の主張が1つでもあれば、0点とする」）なら、行動につながる数値が得られます。評価要件が変わったときには、ルーブリックを見直す必要があります。**‍**
- **参照回答ベースの採点**では、既知の正解を判定者に与え、候補がそれにどれだけ近いかを尋ねます。意味に基づいて評価する点で、BLEUやROUGEのような従来のNLP指標に最も近い方式です。出力が制約されたタスク（翻訳、正解要約との比較による要約、構造化データ抽出）では有効です。自由形式のタスクでは、許容できる回答が通常複数あるため、それらと異なる良い回答まで判定者が減点し、うまく機能しません。

実際には、本番環境の多くで基準ごと（忠実性、関連性、形式への準拠）の単一回答採点を使い、候補となるプロンプトを選ぶ開発中に限ってペアワイズ比較を使います。

## LLM判定者が適切な場面

LLM判定者は、明確に示されたルーブリックに照らした読解問題に相当するタスクで有効です。「この応答に、取得したコンテキストが裏付けていない事実上の主張が含まれているか」は読解問題です。「仕様で回答を拒否する必要があるケースで、この応答は回答を拒否しているか」も同様です。判定モデルは主張を抽出し、裏付けとなる文章を特定（または、その不在を指摘）して、判定を返す必要があります。最先端モデルはこれをうまく行います。

一方、プロンプトに記述できないことを判定者が知っている必要があるタスクでは、うまく機能しません。「この応答は面白いか」はどのモデルも答えられる問いですが、その答えに反映されるのは読者ではなく判定者の事前傾向です。「このコードは慣用的なRustか」を判断するには、判定者があなたのチームと同じ慣習を身につけている必要がありますが、おそらくそうではありません。こうしたタスクでは、判定者を正解そのものではなく、複数あるシグナルの1つとして扱ってください。

見逃した失敗のコストが高く、その失敗の発生パターンがまれなタスクでは、積極的に悪影響を及ぼします。判定者は失敗を見逃す可能性があり、見逃した問題の結果が重大な場合には重要な点です。そうしたケースでは、判定者はトリアージフィルター（人間のレビュー担当者が見るケース数を減らすもの）であり、最終判断ではありません。

## 実例：40行で作る忠実性判定者

最も単純で実用的な判定者は、RAG応答に対する単一回答の忠実性ルーブリックです。OpenAI Python SDKを使った例を示します。

```

from openai import OpenAI
from pydantic import BaseModel

client = OpenAI()

JUDGE_PROMPT = """You are evaluating whether an assistant's response is faithful
to a retrieved context passage. Faithful means every factual claim in the response
is directly and explicitly supported by the context. A claim is unfaithful if it
is added, modified, or drawn from outside the context.

Steps:
1. Enumerate every factual claim in the response (numbers, rules, entity names,
   negations, comparisons).
2. For each claim, locate the specific sentence in the context that supports it.
3. If any claim has no direct support, the response is unfaithful.
4. Truncated or cut-off context counts as zero support for whatever follows.

Return JSON: {{"verdict": "faithful" | "unfaithful", "reason": ""}}.

CONTEXT:
{context}

RESPONSE:
{response}
"""

class Verdict(BaseModel):
    verdict: str
    reason: str

def judge(context: str, response: str) -> Verdict:
    completion = client.beta.chat.completions.parse(
        model="gpt-4o-2024-11-20",
        messages=[{"role": "user",
                   "content": JUDGE_PROMPT.format(context=context, response=response)}],
        response_format=Verdict,
        temperature=0.0,
    )
    return completion.choices[0].message.parsed
  
```

このプロンプトでは、判定者に評価の前に主張を列挙させ、主張単位のチェックを行います。取得パイプラインではチャンク境界でテキストが切り詰められ、判定者がそうしない限り部分的な文を完全な裏付けとして扱うため、切り詰められたコンテキストを明示的に考慮しています。二択分類タスクでは、ゼロ以外の温度を設定すると解釈できないばらつきが生じるため、温度はゼロです。

この内容で実行はできますが、リリースには不十分です。次の2つのセクションでは、動く例をデプロイ可能な判定者にするための要点、つまりプロンプトを適切に作ることと、人間の評価者と実際に一致するかを測定することを説明します。

## 判定者のプロンプトとルーブリックを書く

LLM-as-a-judgeの設定で実際に成果の大半を左右するのは、判定者のプロンプトです。モデルはプロバイダーによって固定され、採点尺度はルーブリックの設計によって固定され、ゴールドセットはドメインによって固定されます。判定者をラベル付きの例と比較しながら反復できるのは、プロンプトという要素です。

機能する判定者プロンプトには4つの要素があります。まず、一般的なML用語ではなく、ドメインで使う言葉による評価基準の定義です（「取得したコンテキストに忠実」はドメインに即した定義ですが、「高品質」はそうではありません）。次に、採点前に個別の主張、条件、ツール呼び出しを列挙するよう指示する、明示的な推論の枠組みです（これにより、確認事項の順序が判定者に示されます）。そして、「判断に任せる」ではなく、「列挙した主張のうち、取得したコンテキストが直接裏付けていないものが1つでもあれば、0点とする」のように、推論結果を尺度に対応させる採点ルールです。最後に、本番で起きる端のケース、つまり切り詰められたコンテキスト、検索結果が空の場合、部分的な回答、回答拒否を扱う条項です。

プロンプトに入れるべきでないのは、「回答を有用かつ正直で無害にすること」のような長い指示の羅列です。一般的な指示は無視されます。主張単位の具体的なルールは守られます。もう1つ避けるべきなのは、判定形式を過度に細かく指定することです。スコアを出す前に長く構造化された根拠をモデルに作らせると、読む予定のないトークンに費用を払うことになります。

## 素朴な判定者の信頼性を損なうバイアス

LLM判定者にはさまざまなバイアスが影響することがあるため、評価を設計する際には考慮してください。

- ‍**位置バイアス**とは、ペアワイズ比較で最初（または時には最後）に提示された応答を好む傾向です。対処法は、比較を両方の順序で評価し、判定が一貫しているケースだけを数えることです。比較を両方の順序で採点する必要があります。**‍**
- **冗長性バイアス**とは、長い応答を好む傾向です。ルーブリックの基準に長さが含まれていなくても、長い応答が好まれることがあります。ルーブリックに「同程度に正確なら、簡潔な応答は冗長な応答と同等以上に評価する」と明記しない場合、判定者は暗黙のうちに長さを最適化します。対処法は、長さを中立に扱うことをルーブリックに明示することです。**‍**
- **自己選好バイアス**とは、判定者が自身の属するモデルファミリーの出力を好む傾向です。同じモデルファミリーの出力を含む比較を、そのモデルで判定しないでください。第3のモデルを判定者として使うか、その比較に限って人間の評価者を使ってください。

ほかにも、センチメントバイアスや迎合バイアスなどの問題があります。キャリブレーションに使用するラベル付きゴールドセットには、関連する失敗パターンを含めてください。

## ラベル付きゴールドセットに対して判定者をキャリブレーションする

判定者のプロンプトは、デプロイ前にラベル付きゴールドセットを使って検証する必要があります。事前に確認する方法がキャリブレーションです。ラベル付きゴールドセットに対して判定者を実行し、判定結果と人間のラベルとのずれを測定して、そのずれが小さくなるまでプロンプトを反復します。

キャリブレーションのループには3つの入力があります。評価対象の分布から抽出したラベル付きゴールドセット、関連する一致度とエラーの指標を記録するベースライン実行、そして判定者がラベルと食い違った例を使ってプロンプトを改訂する最適化のステップです。プロンプトや評価対象の分布が変わったら、キャリブレーションを繰り返してください。

全体の精度ではクラスごとの再現率が見えません。精度が高くてもカッパ係数が低い場合、一致度が偶然とほとんど変わらない可能性があります。カッパ係数が高いほど、偶然を超えた一致度が高いことを示します。判定者を評価する際は、精度以外の指標も報告してください。

## ゴールドセットを作る

キャリブレーションにはゴールドセットが必要ですが、ゴールドセットは最初から存在するものではありません。まずそれを構築する必要があり、この手順によって、後続のすべてが実際に意味のあるものを測定しているのか、それともノイズを測定しているのかが決まります。

ゴールドセットとは、判定者に出してほしい判定をドメイン専門家がラベル付けした、入出力ペアの集合です。ゴールドセットを評価の基盤にするには、3つの特性が必要です。実際の評価対象の分布から抽出すること、つまり、データセットを作成した人にとってもっともらしく見える合成例ではなく、実際のクエリ、実際に取得したコンテキスト、実際のエージェント応答を使う必要があります。失敗クラスが含まれていることも必要です。すべて忠実な例からなる100例のゴールドセットでは、判定者が非忠実性を検出できるかどうかは何も分かりません。その失敗だけが重要なのです。また、ゴールドセットを使う前に、評価者間の一致度を測定する必要があります。ドメイン専門家がラベルについて頻繁に意見を異にするなら、ノイズではなく失敗モードを基に最適化できるよう、キャリブレーション前にルーブリックを明確にしてください。

ゴールドセット用のクエリと、合成ながら現実的な回答を生成すること自体が、独立したエンジニアリング課題です。ソース文書からこれらを生成するフレームワークがいくつかすでにあり、フレームワーク間の違いは、生成されたゴールドセットがどのような失敗を明らかにするかに影響します。 

## 判定者と人間の一致度はタスクごとに異なる

LLM判定者と人間の評価者の一致度はタスクによって異なり、いくつかの違いが重要です。

評価者の意見が分かれる可能性がある自由形式のタスクより、検証可能な結果がある閉じたタスクのほうが、一致度を解釈しやすい傾向があります。対象タスクについて人間同士がどの程度一致するかを考慮せずに、判定者を評価することはできません。

2つ目の点は、一致度とアラインメントは同じではないことです。判定者は全体として正確に見えても、重要な失敗クラス（たとえば、裏付けのない応答を忠実として合格させるケース）を見逃すことがあります。全体の数値は判定者を実際より優秀に見せます。リリースしてよいかを示すのはクラス別の再現率です。これを解決するのが上のキャリブレーションのセクションです。両方を測定し、失敗例に合わせてプロンプトを修正し、繰り返します。

3つ目は、一致度指標の結果がどの指標を使うかによって変わることです。合格例が大半で失敗例が少ない不均衡なゴールドセットで生の精度を報告すると、判定者が実際より優秀に見えます。偶然による一致を調整するCohenのカッパ係数を報告するほうが、ごまかしにくい指標です。見かけ上の精度が高くてもカッパ係数が低い場合、一致度が偶然に近い可能性があります。連続スコアにはPearson相関が有用です。絶対値ではなく順位だけを信頼する場合は、Spearman相関のほうが適しています。

本番パイプラインでは、ラベル付きゴールドセットで測定し、適切な一致度指標またはエラー指標を複数報告してください。

LLM判定者だけを使うか、フラグが付いたサブセットを人間が確認するトリアージフィルターとして使うか、判定者を使わず人間だけに任せるかは、見逃した失敗のコスト、評価の件数、評価対象の分布が変化する速度という3つの変数によって決まります。

## 実例から本番導入へ：判定者を接続する

この記事の前半にある40行の例は、Python REPLで1つの応答を採点するには十分です。本番のすべての応答の前段に判定者を置く（または、CIですべてのプルリクエストに対して実行する）ことは、別のエンジニアリング課題です。

大規模運用で必要になる作業は、華やかではありません。判定者の推論がエンドツーエンドのレイテンシを支配しないよう、リクエストをバッチ処理すること。判定者が不正なJSONを返す場合、レート制限を超える場合、またはタイムアウトする場合に備えたリトライ処理。特定のケースにフラグが付いた理由を後から診断できるようにする、判定結果と推論トレースの構造化ログ。デプロイ間でカナリーゴールドセットに対するアラインメントが低下した際に作動する回帰検出。特定のプロンプト編集にアラインメントの変化を帰属できるよう、アプリケーションコードと同様に判定者プロンプトをバージョン管理すること。そして、時間に追われている担当者が手動チェックを忘れても、デプロイゲートの一部として判定者の実行が行われるように、CIシステムと統合することです。

これらのどれも、考え方としては難しくありません。どれも作業は必要であり、実装の順序によって、本番環境で最初に遭遇する失敗が変わります。プロンプトのバージョン管理がなければ、アラインメントが変化したときに回帰の原因を特定するのが難しくなります。

## LLM判定者を使うべきでない場合

判定者を使うべきでない状況は3つあります。チームがそれでも使ってしまいがちな状況です。

タスクに決定論的な正しさのチェックがある場合、判定者は使わないでください。SQLクエリの同等性、JSONスキーマ検証、正規表現によるマッチング、完全一致比較、ツール呼び出しの引数照合は、すべて解決済みの問題です。これらにLLM判定者を追加すると、レイテンシとコストが増え、明確な答えがある問題について誤る可能性もゼロではありません。まず決定論的なチェックを実行して、不一致があればすぐに失敗とし、本当に自然言語の推論を必要とする部分だけに判定者を呼び出してください。

ラベル付きゴールドセットを構築していない場合は、本番環境で判定者を使わないでください。判定者は数値を返します。正解がなければ、その数値に意味があるかどうかは分かりません。ゴールドセットは、実際の評価タスクを反映し、重要な失敗ケースを含める必要があります。

見逃した失敗のコストが人間のレビューより大きい場合、判定者を最終ゲートとして使わないでください。人間がレビューするケース数を減らすトリアージフィルターとして使います。規制対象の領域で、人間が介在しない判定者をデプロイすることは別の意思決定です。判定者がたまたま開発用セットで高いスコアを出したからと暗黙に決めるのではなく、法務およびコンプライアンス部門を交えて明示的に判断すべきです。

判定者はツールであり、判決ではありません。ほかの方法なら見逃して出荷していた失敗を検出することで、その役割を果たします。検出し続けているかどうかの測定をやめた時点で、その役割を失います。

Ailootは、蓄積した運営経験、幅広い顧客基盤、安定したサービス、継続的なKPI管理を基盤としています。

企業とそのプロジェクト群：数百万の顧客、毎月数十億規模の売上。

Ailootはこの運営経験を、お客様の製品、エージェント、アプリケーション、自動化でAI機能を利用するためのAPIアクセスに活かしています。

[LLMを判定者として使う：完全ガイド](<https://ailoot.ai/blog/ja/llm-as-a-judge-the-complete-guide/>)

[AilootのAIモデルAPI](<https://ailoot.ai/>)では、Ailootが発行するAPIキー1つで、15カテゴリにわたる計1,284種のモデルとバリエーションを利用できます。Ailootはモデル数で世界最大級のAIルーターです。同じキーでGPT、Claude、Gemini、Grok、Qwen、DeepSeekを利用できます。写真にはNano Banana、動画にはVeo、音声にはEleven v4、音楽にはSuno、3D素材にはTripo3D、検索にはBGEを使えます。

モデルの出力を比較したりLLM評価器を構築したりする際は、[Ailootが発行するAPIキー](<https://ailoot.ai/>)1つでGPT、Claude、Geminiを呼び出せます。同じキーで画像、動画、音声、3Dの各モデルも製品に接続できます。

対応するSDKや、すぐ使える開発・自動化連携を通じてAilootに接続できます。1つのアカウントでサブスクリプション、プロジェクトキー、利用状況を管理できます。

サブスクリプション1つでAilootのカタログにある全モデルを利用でき、新しいフラッグシップモデルも提供開始当日から同じキーで呼び出せます。サブスクリプションやプロモコードで、モデル提供元の公式API料金に比べて最大50%節約できます。[https://ailoot.ai/](<https://ailoot.ai/>)でキーを取得して、アカウントでプロモコードをご確認ください。
