# Hoe een inferentieplatform in elkaar zit

> Hoe gateways, routering, caching en modelserving samenwerken, en hoe de verzoekcontext door die lagen kan worden doorgegeven.




08 MRT 2026 | Engineering | 4 min lezen

Hoe gateways, routering, caching en modelserving samenwerken, en hoe de verzoekcontext door die lagen kan worden doorgegeven.

Een verzoekcontext kan via een gateway en router naar modelserving worden doorgegeven. Die context verbindt de modelkeuze, het hergebruik van de cache en de uitvoering met de identiteit van de aanroeper en de kosten van elke poging. Een router die geen rekening houdt met de cachestatus kan de besparingen tenietdoen die de aangrenzende laag heeft opgeleverd.

Het delen van context vereist integratiewerk, en een router die de cachestatus uitleest is moeilijker te vervangen. Door context met het verzoek mee te sturen terwijl de producten gescheiden blijven, kan een team een gateway en router gebruiken op de runtime van een andere provider. De router neemt dan beslissingen op basis van de informatie die die provider beschikbaar stelt.

## Een goedkopere route kan meer kosten

Neem als voorbeeld een illustratieve dienst voor het extraheren van gegevens uit documenten, met lange, vaste instructies en bij elk verzoek een kort document. Prefixcaching en routering lijken allebei aantrekkelijk, maar ze kunnen elkaars voordeel tenietdoen. Een gecachte prefix is key-value-status die door één model is berekend. Een verzoek dat naar een ander model wordt gerouteerd, leest de instructies daarom opnieuw vanaf het begin.

De gepubliceerde cacheprijzen van Anthropic voor vijf minuten bedragen 1.25 keer de basisprijs voor invoer bij een schrijfactie en 0.1 keer bij een leesactie, met uitzonderingen per model ([aankondiging](https://www.anthropic.com/news/prompt-caching), [documentatie](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). Tegenover die warme cache moet een alternatief zonder cache minder dan een tiende van de invoerprijs van het huidige model kosten om op de gedeelde prefix voordeliger te zijn. Eén schrijfactie en één cachehit kosten 1.35 invoerpassages voor het gecachte deel, tegenover twee zonder caching. Een schrijfactie die geen enkel later verzoek leest, kost 1.25.

Een router die catalogusprijzen vergelijkt, kan een model zien met de helft van de invoerprijs en overschakelen, maar betaalt dan minstens vijf keer zoveel voor de prefix. Gedocumenteerde routeringsregels geven aan welke modellen elkaar mogen vervangen; gedeelde context maakt duidelijk wat elke vervanging kost.

## Voor hergebruik van antwoorden is de identiteit van de aanroeper nodig

<figure>
<ol>
<li><strong>Exact antwoord</strong> — Een antwoord hergebruiken voor een overeenkomend verzoek</li>
<li><strong>Prefix</strong> — Invoerberekeningen hergebruiken en een nieuw antwoord genereren</li>
<li><strong>Semantisch</strong> — Bepalen wanneer verschillende verzoeken gelijkwaardig zijn</li>
</ol>
Bij hergebruik moet rekening worden gehouden met het model, de prompt, het schema en de vereiste actualiteit.
<figcaption>Drie verschillende soorten hergebruik · Een antwoordcache is geen prefixcache.</figcaption>
</figure>

Een antwoordcache geeft een opgeslagen uitvoer terug; een semantische cache bepaalt ook wanneer twee verschillende verzoeken hetzelfde antwoord verdienen. [GPTCache](https://github.com/zilliztech/GPTCache) bepaalt cachehits op basis van embeddingovereenkomst. De README waarschuwt voor “false positives during cache hits”.

Bij gegevensextractie kan een false positive een verkeerd rekeningnummer opleveren: twee facturen van één leverancier die hetzelfde sjabloon gebruiken, kunnen dicht bij elkaar liggen in de embeddingruimte, waarna de cache het rekeningnummer van de eerste factuur aan de tweede koppelt. Een semantische cache zonder applicatie-identiteit kan een correctheidsfout veroorzaken, terwijl het dashboard voor het hitpercentage elk verkeerd antwoord als een besparing telt.

Anthropic isoleert promptcaches tussen organisaties en, op de eigen API, per werkruimte, hoewel een prefixcache geen opgeslagen antwoord teruggeeft. Een antwoordcache heeft minstens diezelfde grens nodig. Een applicatie kan aangeven of een taak hergebruik voor vergelijkbare invoer toestaat; bij hergebruik kan de sleutel gebaseerd zijn op de aanroeper, de gegevens die die aanroeper mag lezen en de taakversie.

Bij gegevensextractie kan hergebruik alleen bij een exacte overeenkomst worden toegestaan, of helemaal worden uitgeschakeld; bij een onbekende sleutel wordt dan opnieuw gerekend. Die regel verlaagt het hitpercentage en laat betalen voor werk dat een minder strikte cache zou overslaan. De standaardinstelling is misschien te strikt: bij een grote openbare FAQ kunnen de kosten van opnieuw rekenen voor onbekende sleutels hoger zijn dan die van het zeldzame verkeerde antwoord dat dit voorkomt.

## Spoor de fout op voordat je een oplossing kiest

Stel dat een goedkoper model ongeldige velden teruggeeft en een groter model die herstelt, waardoor de rekening en vertraging voor dat document toenemen. Kosten kunnen worden berekend per correcte gegevensextractie binnen de vereiste vertraging; de tokenprijs van de eerste aanroep is één invoerfactor.

De analyse van Berkeley van samengestelde AI-systemen pleit ervoor om op elkaar inwerkende onderdelen gezamenlijk te optimaliseren. Een trace moet een modelstoring kunnen onderscheiden van hergebruik van verouderde gegevens, een trage tool of een verkeerde route, omdat elk geval om een oplossing in een andere laag vraagt. Controle over de uitvoering kan helpen vaststellen waar kosten ontstaan, terwijl een snellere runtime verspilling kan verplaatsen naar de beslissingen eromheen. Door traces te koppelen aan evaluaties op productieverkeer kun je testen of een wijziging de taak verbetert, inclusief het herstelpad.

Een operator kan die trace gebruiken om de laag te wijzigen waar de fout is opgetreden. Als de verzoekgeschiedenis, evaluatiegevallen en implementatiekeuze binnen de applicatie van de klant blijven, kunnen verbeteringen voortbouwen op de eigen ervaring van die applicatie.
