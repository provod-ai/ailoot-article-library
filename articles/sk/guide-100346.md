# Architektúra API TTS: od textu k produkčnému zvuku

> Zistite, ako navrhnúť produkčné API TTS s frontami, workermi, ukladaním do vyrovnávacej pamäte, opakovanými pokusmi, smerovaním k poskytovateľom, úložiskom, limitmi frekvencie a pozorovateľnosťou.



Volanie API na prevod textu na reč je jednoduché. Spoľahlivo ho prevádzkovať v produkčnom prostredí už nie.

Základný prototyp môže obsahovať iba tri kroky:

**Text → Poskytovateľ TTS → MP3**

Pri lokálnom testovaní niekoľkých požiadaviek to môže fungovať dobre. Keď pribudnú skutoční používatelia, systém musí zvládať súbežné úlohy, limity frekvencie poskytovateľa, výpadky siete, dlhotrvajúce úlohy generovania zvuku, duplicitné požiadavky, úložisko, opakované pokusy, kvóty, viacerých poskytovateľov hlasov aj používateľov, ktorí obnovia stránku, kým sa zvuk ešte spracúva.

Architektúra sa rýchlo stane zložitejšou než samotné volanie API TTS. Realistickejší produkčný pracovný postup vyzerá takto:

**Klient → API → Úloha → Fronta → Worker → Poskytovateľ TTS → Úložisko/CDN → Výsledok**

Tento článok vysvetľuje, ako takúto architektúru navrhnúť, prečo existuje každý komponent a aké problémy sa zvyčajne objavia, keď aplikácia TTS prerastie jednoduchú ukážku.



## **Čo musí produkčné API TTS riešiť?**

Účelom produkčného backendu TTS nie je iba generovať zvuk. Musí ho generovať **spoľahlivo, efektívne a predvídateľne**.

Dobrá architektúra by mala odpovedať na otázky, ako sú:

1. Čo sa stane, keď 100 používateľov generuje reč súčasne?
2. Čo sa stane, keď poskytovateľ TTS vráti HTTP 429?
3. Čo sa stane, keď poskytovateľ TTS nebude dostupný?
4. Čo sa stane, keď generovanie zvuku trvá niekoľko minút?
5. Čo sa stane, keď používateľ odošle tú istú požiadavku dvakrát?
6. Ako zabránite tomu, aby jeden používateľ spotreboval celú dostupnú kvótu poskytovateľa?
7. Kde sa má ukladať vygenerovaný zvuk?
8. Ako sa klient dozvie, že sa dlhotrvajúca úloha dokončila?
9. Ako zopakujete neúspešnú prácu bez opätovného generovania už úspešného zvuku?
10. Ako zistíte, ktorý poskytovateľ je pomalý alebo nespoľahlivý?

Ide o problémy návrhu systému, nie syntézy reči.

## **Základná požiadavka API TTS**

Požiadavka TTS môže v najjednoduchšom prípade obsahovať:

1. Text
2. Jazyk
3. Hlas
4. Model
5. Rýchlosť reči
6. Formát zvuku
7. Voliteľné pokyny pre hlas

Napríklad, koncepčne:

**POST /tts**

Server prijme požiadavku, zavolá poskytovateľa TTS a vráti zvukový súbor. Tento synchrónny model sa dá ľahko pochopiť:

**Požiadavka HTTP → Poskytovateľ → Zvuk → Odpoveď HTTP**

Pri generovaní veľmi krátkej reči to môže byť prijateľné. Problémy sa začnú, keď sa generovanie spomalí, narastie prevádzka alebo jedna požiadavka obsahuje veľké množstvo textu.

## **Prečo by dlhotrvajúce úlohy TTS nemali závisieť od jednej požiadavky HTTP**

Predstavte si, že používateľ odošle dostatok textu na vytvorenie 30-minútového komentára. Ak vaše API ponechá pôvodnú požiadavku HTTP otvorenú až do dokončenia všetkého, môže sa stať viacero vecí:

1. V prehliadači môže vypršať časový limit.
2. Reverzný proxy server môže požiadavku ukončiť.
3. Aplikačný server sa môže reštartovať.
4. Poskytovateľ môže dočasne zlyhať.
5. Používateľ môže stránku zavrieť.
6. Mobilné pripojenie sa môže stratiť.

Práca TTS môže byť stále platná, no spojenie, ktoré ju spustilo, už neexistuje. Dlhotrvajúce úlohy TTS je zvyčajne lepšie modelovať ako **úlohy**.

Pracovný postup sa zmení na:

**Klient → Vytvorenie úlohy → Vrátenie ID úlohy → Spracovanie na pozadí**

Klient môže neskôr skontrolovať priebeh.

## **Krok 1: Prijmite a overte požiadavku**

Vrstva API by mala pred odoslaním práce do systému spracovania vykonať základné overenie. Typické kontroly zahŕňajú:

1. Je text prázdny?
2. Je text dlhší než povolená veľkosť požiadavky?
3. Existuje požadovaný hlas?
4. Podporuje vybraný model požadovaný jazyk?
5. Je požadovaný formát zvuku podporovaný?
6. Je používateľ autentifikovaný?
7. Má používateľ dostatok kvóty alebo kreditov?
8. Je požiadavka povolená podľa pravidiel obmedzovania frekvencie?

Neplatné požiadavky by sa mali odmietnuť skôr, než sa dostanú k workerom alebo externým poskytovateľom. Šetrí sa tým infraštruktúra aj kvóta poskytovateľa.

Pri súbežných úlohách pred prijatím atomicky rezervujte príslušnú kvótu alebo kredity a rezerváciu podľa skutočného výsledku a pravidiel fakturácie práve raz vyúčtujte alebo uvoľnite.

## **Krok 2: Normalizujte požiadavku**

Pred spracovaním normalizujte požiadavku do predvídateľného interného formátu. Napríklad:

1. Normalizujte kódy jazykov.
2. Zistite skutočné ID hlasu.
3. Zistite poskytovateľa priradeného k vybranému hlasu.
4. Použite predvolenú rýchlosť reči.
5. Normalizujte medzery.
6. Vyberte výstupný formát.
7. Zistite konfiguráciu modelu.

Nadväzujúce workery tak dostanú konzistentnú vstupnú zmluvu. Pomáha to aj pri ukladaní do vyrovnávacej pamäte: logicky identické požiadavky by mali v ideálnom prípade vytvoriť rovnaký kľúč vyrovnávacej pamäte.



## **Krok 3: Skontrolujte, či zvuk už existuje**

Opakované generovanie toho istého zvuku je jednoduchý spôsob, ako v systéme TTS míňať peniaze. Predpokladajme, že používateľ viackrát odošle:

*„Vitajte v našej aplikácii.“*

s rovnakým hlasom, modelom, rýchlosťou a nastaveniami. Ak je výsledok pre váš prípad použitia dostatočne deterministický, možno nie je dôvod zakaždým volať poskytovateľa.

Kľúč vyrovnávacej pamäte možno odvodiť z hodnôt, ako sú:

1. Normalizovaný text
2. ID hlasu
3. Poskytovateľ
4. Model
5. Jazyk
6. Rýchlosť
7. Formát zvuku
8. Štýl alebo pokyny pre hlas

Koncepčný kľúč môže vyzerať takto:

**HASH(text + hlas + model + rýchlosť + formát + nastavenia)**

Všetky polia generovania serializujte jednoznačne a do identity vyrovnávacej pamäte zahrňte príslušný rozsah tenanta alebo prístupu. Opätovné použitie aj prístup k výsledku autorizujte; medzi tenantmi zdieľajte iba pri výslovnom povolení.

Priebeh požiadavky sa zmení na:

**Požiadavka → Kontrola vyrovnávacej pamäte → Existuje zvuk?**

Ak áno:

**Vrátenie existujúceho výsledku**

Ak nie:

**Vytvorenie úlohy generovania**

### **Neukladajte do vyrovnávacej pamäte iba podľa textu**

Používať ako kľúč vyrovnávacej pamäte iba text je zvyčajne nesprávne. Tá istá veta vytvorená dvoma rôznymi hlasmi by nemala vrátiť ten istý zvuk. To isté platí pre model, rýchlosť, jazyk, formát a nastavenia štýlu.

Identita vyrovnávacej pamäte by mala predstavovať všetko, čo môže podstatne zmeniť výstup.

## **Krok 4: Vytvorte trvalú úlohu**

Pred zaradením práce do fronty uložte záznam úlohy. Úloha TTS môže obsahovať:

1. ID úlohy
2. ID používateľa
3. Stav
4. Požadovaný hlas
5. Poskytovateľa
6. Model
7. Počet znakov
8. Čas vytvorenia
9. Čas začatia
10. Čas dokončenia
11. Počet opakovaní
12. Priebeh
13. Informácie o chybe
14. URL výstupu

Jednoduchý životný cyklus stavu môže byť:

**Čaká → Spracúva sa → Dokončená**

s chybovými stavmi, ako napríklad:

**Čaká → Spracúva sa → Zlyhala**

Možno budete potrebovať aj stavy pre opakované spracovanie, zrušené, čiastočne dokončené alebo expirované úlohy.

Trvalé ukladanie stavu úlohy je dôležité, pretože systém spracovania by nemal závisieť od pamäte aplikácie. Ak sa kontajner API reštartuje, používatelia by mali mať naďalej možnosť načítať svoje úlohy.

## **Krok 5: Pošlite úlohu do fronty správ**

Fronta správ oddeľuje prijatie požiadavky od spracovania zvuku. Namiesto:

**API → Poskytovateľ TTS**

použijete:

**API → Fronta → Worker → Poskytovateľ TTS**

API môže takmer okamžite odpovedať identifikátorom úlohy, zatiaľ čo workery spracúvajú požiadavky na pozadí.

Použite transakčný outbox alebo trvalý mechanizmus obnovy pre zaznamenané, no nezaradené úlohy, a spracovanie fronty urobte idempotentným, aby zlyhanie alebo opätovné doručenie prácu nestratilo ani nezdvojilo.

### Prečo sú fronty pre TTS také užitočné

Fronty prinášajú niekoľko dôležitých výhod:

1. Pohlcujú nárazové zvýšenie prevádzky.
2. Riadi, koľko práce prebieha súčasne.
3. Chránia kvóty externých poskytovateľov.
4. Uľahčujú opakovanie úloh.
5. Umožňujú pokračovať v úlohách aj po skončení pôvodnej požiadavky HTTP.
6. Umožňujú pridávať workery s rastúcou prevádzkou.

Je to obzvlášť dôležité, keď poskytovatelia TTS stanovujú limity požiadaviek za minútu, znakov, tokenov alebo súbežnosti.



## **Fronta slúži aj ako mechanizmus spätnej regulácie**

Predpokladajme, že váš poskytovateľ dokáže bezpečne spracovať 20 požiadaviek naraz, no vaše API prijme naraz 200 požiadaviek. Bez fronty môžete poslať všetkých 200 požiadaviek priamo poskytovateľovi. Pravdepodobným výsledkom bude:

1. Chyby limitu frekvencie
2. Časové limity
3. Vysoké využitie CPU
4. Vysoké využitie pamäte
5. Obmedzovanie zo strany poskytovateľa
6. Reťazová reakcia opakovaných pokusov

S frontou môže API prijímať úlohy, zatiaľ čo workery ich spracúvajú riadeným tempom. Systém nemusí spracovať všetko okamžite len preto, že požiadavky prišli naraz.

## **Krok 6: Spracúvajte úlohy pomocou workerov TTS**

Workery obsluhujú pracovný postup generovania. Worker môže:

1. Načítať úlohu z fronty.
2. Načítať konfiguráciu úlohy.
3. V prípade potreby rozdeliť rozsiahly text.
4. Vybrať správneho poskytovateľa.
5. Zavolať API TTS.
6. Ošetriť dočasné zlyhania.
7. Stiahnuť alebo prijať vygenerovaný zvuk.
8. Overiť výstup.
9. Nahrať výsledok do úložiska.
10. Aktualizovať stav úlohy.

Workery by mali byť dostatočne bezstavové, aby úlohu mohol spracovať iný worker, ak jedna inštancia zmizne.

## **Akú súbežnosť má worker používať?**

Vyššia súbežnosť automaticky neznamená vyššiu priepustnosť. Príliš agresívne zvýšenie súbežnosti workerov môže spôsobiť:

1. Dosiahnutie limitov poskytovateľa
2. Nasýtenie CPU
3. Tlak na pamäť
4. Sieťové obmedzenia
5. Obmedzenia vstupno-výstupných operácií disku
6. Úzke miesta vo FFmpeg

Pracovné zaťaženie TTS môže zahŕňať viacero typov zdrojov. Volanie vzdialeného API na syntézu reči môže byť prevažne závislé od siete, zatiaľ čo konverzia alebo spájanie zvuku môže byť závislé od CPU. Produkčnému systému preto môžu pomôcť samostatné limity súbežnosti pre jednotlivé fázy.

Napríklad:

**Súbežnosť sťahovania: vysoká**

**Súbežnosť poskytovateľa TTS: závisí od poskytovateľa**

**Súbežnosť spracovania zvuku: závisí od CPU**

Zvyčajne je to bezpečnejšie než používať všade jednu vysokú hodnotu súbežnosti.

## **Krok 7: Rozdeľte rozsiahly text na menšie bloky**

Mnohí poskytovatelia TTS stanovujú limity veľkosti požiadaviek. Aj keď poskytovateľ prijíma veľmi rozsiahly vstupný text, rozdelenie dlhých dokumentov môže byť stále užitočné.

Dlhotrvajúca úloha TTS sa môže zmeniť na:

**Dokument → Blok 1 + Blok 2 + Blok 3 + ... → TTS → Spojenie**

Spracovanie po blokoch prináša viacero výhod:

1. Opakujte iba neúspešné bloky po overení, že je to bezpečné.
2. Spracúvajte nezávislé bloky súčasne.
3. Sledujte priebeh.
4. Zotavte sa z čiastočných zlyhaní.
5. Ukladajte bloky do vyrovnávacej pamäte samostatne.
6. Vyhnite sa limitom veľkosti požiadaviek poskytovateľa.

### **Nerozdeľujte text naslepo**

Rozdeľovanie po pevnom počte znakov môže zhoršiť kvalitu reči, ak sa blok skončí uprostred vety. Lepšia logika delenia môže zohľadniť:

1. Hranice odsekov
2. Hranice viet
3. Interpunkciu
4. Limity znakov poskytovateľa
5. Pravidlá písania špecifické pre daný jazyk

Cieľom je zachovať bloky dostatočne malé na spoľahlivé spracovanie a zároveň udržať prirodzený kontext reči.

## **Krok 8: Nasmerujte požiadavky na správneho poskytovateľa TTS**

Produkčná aplikácia môže časom podporovať viacerých poskytovateľov TTS. Rôzni poskytovatelia môžu ponúkať odlišné:

1. Jazyky
2. Katalógy hlasov
3. Ceny
4. Úrovne kvality
5. Limity frekvencie
6. Latenciu
7. Ovládanie emócií
8. Možnosti streamovania

Namiesto toho, aby ste logiku poskytovateľov rozmiestnili po celej aplikácii, použite smerovaciu alebo abstrakčnú vrstvu. Architektúra bude vyzerať takto:

**Worker → Smerovač hlasu/modelu → Adaptér poskytovateľa → Poskytovateľ TTS**

Každý adaptér poskytovateľa môže poskytovať spoločné interné rozhranie a zároveň prekladať požiadavky do formátu, ktorý očakáva daný poskytovateľ.

### **Vyhnite sa logike špecifickej pre poskytovateľa na každom mieste**

Bez abstrakcie sa kód môže naplniť podmienkami, ako napríklad:

**Ak je poskytovateľ A, urob toto. Ak je poskytovateľ B, urob niečo iné.**

S pribúdajúcimi poskytovateľmi sa takýto kód ťažko udržiava. Spoločné rozhranie poskytovateľa umožňuje zvyšku systému pracovať s pojmami, ako sú:

1. Generovanie reči
2. Získanie podporovaných hlasov
3. Overenie požiadavky
4. Vrátenie zvuku

Každý adaptér poskytovateľa rieši detaily implementácie.

## **Záložný poskytovateľ: užitočný, ale nie vždy jednoduchý**

Môže byť lákavé automaticky posielať každú neúspešnú požiadavku inému poskytovateľovi. Niekedy to funguje dobre, inokedy nie. Dvaja poskytovatelia nemusia mať ekvivalentné hlasy a záložný hlas môže znieť úplne inak než pôvodný. Pri dlhej audioknihe alebo videu s viacerými scénami to môže byť neprijateľné.

Pri rozhodovaní o záložnom poskytovateľovi zvážte:

1. Či existuje ekvivalentný hlas
2. Či je dôležitá konzistentnosť
3. Či je zlyhanie dočasné
4. Rozdiel v nákladoch
5. Cieľový jazyk
6. Preferencie používateľa

Záložné smerovanie poskytovateľov je architektonický nástroj, nie záruka, že každá neúspešná požiadavka sa má okamžite presmerovať.

## **Krok 9: Správne riešte limity frekvencie**

HTTP 429 je jedným z najčastejších problémov v systémoch, ktoré intenzívne využívajú API. HTTP 429 môže signalizovať limit poskytovateľa vrátane frekvencie alebo počtu súbežných požiadaviek. Pred rozhodnutím, ako a kedy opakovať pokus, skontrolujte podrobnosti chyby a pokyny poskytovateľa vrátane Retry-After, ak je uvedený.

Nesprávna reakcia je:

**Opakovať okamžite a čo najrýchlejšie.**

Zvyčajne to vytvorí ešte viac požiadaviek a problém zhorší. Lepší prístup používa:

1. Limity súbežnosti
2. Exponenciálne čakanie pred ďalším pokusom
3. Náhodný rozptyl času (jitter)
4. Pravidlá limitov frekvencie špecifické pre poskytovateľa
5. Oneskorenie vo fronte

Koncepčne:

**429 → Počkať → Skúsiť znova neskôr**

nie:

**429 → Okamžite skúsiť znova → 429 → Okamžite skúsiť znova → 429**

## **Krok 10: Opakujte iba chyby, ktoré sa môžu napraviť**

Opakované pokusy sú potrebné, ale nie každé zlyhanie sa má opakovať. Užitočné rozdelenie je:

| Typ chyby                   | Typická akcia                       |
|-----------------------------|-------------------------------------|
| 429 Too Many Requests       | Počkať a zopakovať s odstupom       |
| 500 Internal Server Error   | Overiť pôvodný výsledok; opakovať iba ak je to bezpečné|
| 502 / 503 Temporary Failure | Pred opakovaním alebo záložným poskytovateľom overiť pôvodný výsledok|
| Network Timeout             | Pred opakovaním overiť pôvodný výsledok|
| 400 Invalid Request         | Neopakovať naslepo                  |
| Unsupported Voice           | Opraviť požiadavku alebo smerovanie  |
| Insufficient User Credits   | Zlyhať ešte pred spracovaním poskytovateľom |

Časový limit, chyba 5xx alebo zlyhanie workera môžu ponechať výsledok u poskytovateľa neznámy. Pred opakovaním alebo zmenou poskytovateľa podľa možností overte pôvodné ID operácie, stav a spotrebu, použite už vytvorený výstup a idempotenciu podporovanú poskytovateľom. Neznámy výsledok zachovajte namiesto slepého opakovania potenciálne dokončenej požiadavky.

Politika opakovania by mala stanoviť aj maximálny počet pokusov. Inak môže jedna chybná úloha zostať v systéme navždy.

## **Použite idempotenciu, aby ste zabránili duplicitnej práci**

Duplicitné požiadavky sú v reálnych aplikáciách bežné. Používateľ môže dvakrát kliknúť na tlačidlo, frontend môže po vypršaní časového limitu siete zopakovať požiadavku, správa vo fronte môže byť doručená znova alebo worker môže úspešne dokončiť prácu, no zlyhať skôr, než potvrdí prijatie správy.

Ak váš systém predpokladá, že každá správa je jedinečná, môže rovnaký zvuk vygenerovať a naúčtovať viackrát. Idempotencia znamená, že opakované spracovanie tej istej logickej požiadavky nevytvorí viacero nechcených výsledkov.

Možné techniky zahŕňajú:

1. Idempotentné kľúče
2. Jedinečné ID úloh
3. Hash hodnoty vyrovnávacej pamäte
4. Obmedzenia jedinečnosti v databáze
5. Kontrolu stavu bloku pred spracovaním

Je to obzvlášť dôležité, ak ide o platby, kredity alebo náklady poskytovateľa.

## **Idempotencia na úrovni úlohy a na úrovni bloku**

Pri krátkych požiadavkách TTS môže stačiť idempotencia na úrovni úlohy. Pri veľkých úlohách s mnohými blokmi je často užitočnejšia idempotencia na úrovni bloku.

Predstavte si úlohu audioknihy s 500 blokmi, v ktorej zlyhá blok 487. Nechcete znova generovať bloky 1 až 486.

**Dokončené bloky → Ponechať**

**Neúspešný blok → Overiť stav u poskytovateľa → Zopakovať iba ak je to bezpečné**

Výrazne sa tým znížia náklady aj čas potrebný na obnovu.

## **Krok 11: Overte vygenerovaný zvuk**

Úspešná odpoveď poskytovateľa nezaručuje, že výstup bude použiteľný. Pred označením úlohy za dokončenú môžete overiť:

1. Bol vrátený zvukový súbor?
2. Je veľkosť súboru väčšia než nula?
3. Dá sa zvuk dekódovať?
4. Vyzerá dĺžka primerane?
5. Je požadovaný formát správny?

Pri pokročilých pracovných postupoch môže overenie dĺžky odhaliť aj podozrivé výstupy, napríklad nečakane krátku alebo dlhú reč.

## **Krok 12: Ukladajte zvuk mimo aplikačného servera**

Vygenerovaný zvuk by vo všeobecnosti nemal závisieť od lokálneho disku jednej inštancie API alebo workera. Ak sa kontajner vytvorí znova, súbor môže zmiznúť.

Lepšia architektúra je:

**Worker → Objektové úložisko → CDN → Používateľ**

Objektové úložisko oddeľuje vytvorené zdroje od výpočtovej infraštruktúry. CDN potom môže efektívne poskytovať zvuk používateľom na rôznych miestach.

Autorizujte prístup ku každej úlohe, jej stavu a zvukovému výsledku. Uložený zvuk ponechajte súkromný a podľa potreby používajte časovo obmedzené odkazy s určeným rozsahom namiesto považovania URL za dôkaz oprávnenia.

### Čo ukladať do databázy?

Databáza zvyčajne nemusí obsahovať surové bajty zvuku. Namiesto nich ukladajte metadáta, ako sú:

1. Kľúč úložiska
2. URL zvuku
3. Dĺžka
4. Veľkosť súboru
5. Formát
6. Poskytovateľ
7. Hlas
8. Čas generovania

Samotný zvuk môže zostať v objektovom úložisku.

## **Zvážte expiráciu súborov**

Nie každý vygenerovaný súbor TTS musí existovať navždy. Úložisko sa môže nenápadne predražiť, keď sa nahromadia milióny dočasných zvukových súborov.

Zvážte pravidlá uchovávania pre:

1. Súbory vygenerované hosťami
2. Dočasné súbory spracovania
3. Medzibloky
4. Dokončené používateľské projekty
5. Opakovane použiteľný zvuk vo vyrovnávacej pamäti

Medzisúbory môžu mať často oveľa kratšiu dobu uchovávania než konečné výstupy používateľov.

## **Krok 13: Vráťte výsledky pomocou pollingu alebo callbackov**

Keď sa požiadavka TTS stane asynchrónnou, klient potrebuje spôsob, ako zistiť, kedy sa spracovanie dokončilo. Existujú dva bežné vzory.

### **Polling**

Klient sa pravidelne pýta:

**GET /jobs/{jobId}**

Server odpovie napríklad:

**status = processing**

a neskôr:

**status = completed, audioUrl = ...**

Polling sa implementuje jednoducho a v mnohých webových aplikáciách funguje dobre.

### **Webhook alebo callback**

Zákazník API môže poskytnúť URL callbacku. Po dokončení spracovania server automaticky odošle oznámenie.

Pracovný postup sa zmení na:

**Vytvorenie úlohy → Vrátenie ID úlohy → Spracovanie → Callback klientovi**

Je to užitočné, keď externé systémy spracúvajú rozsiahle úlohy a nechcú neustále používať polling.

### Podpora oboch možností môže byť užitočná

Produkčné API môže ponúkať polling úloh ako univerzálny mechanizmus a webhooky ako voliteľné pohodlie.

## **Sledujte priebeh rozsiahlych úloh**

Pri 5-sekundovej požiadavke TTS nemusí na priebehu záležať. Pri hodinovom zvukovom projekte záleží veľmi. Ak úloha obsahuje 1000 blokov, priebeh možno približne odhadnúť podľa dokončenej práce:

**Priebeh = Dokončené bloky / Celkový počet blokov**

Frontend tak môže zobrazovať:

1. Vo fronte
2. Spracúva sa 27%
3. Spracúva sa 83%
4. Dokončovanie zvuku
5. Dokončené

Viditeľný indikátor priebehu tiež znižuje pravdepodobnosť, že používatelia usúdia, že aplikácia zamrzla, a odošlú tú istú úlohu znova.

## **Krok 14: Chráňte systém obmedzovaním frekvencie**

Váš poskytovateľ má limity frekvencie. Malo by ich mať aj vaše API. Obmedzovanie frekvencie možno uplatniť podľa:

1. Používateľa
2. Kľúča API
3. IP adresy
4. Predplatného
5. Endpointu
6. Poskytovateľa

Limity frekvencie chránia infraštruktúru a kvóty poskytovateľov. Môžu tiež zabrániť jednému náročnému používateľovi spotrebovať všetky dostupné kapacity workerov.

## **Priority môžu byť užitočnejšie než jedna globálna fronta**

S rastom produktu si jednotlivé úlohy nemusia zaslúžiť rovnakú prioritu. Napríklad:

1. Krátke interaktívne požiadavky TTS môžu vyžadovať rýchlu odozvu.
2. Úlohy s rozsiahlymi dokumentmi môžu čakať o niečo dlhšie.
3. Platiaci používatelia môžu dostať vyššiu prioritu spracovania.
4. Hromadné úlohy API na pozadí môžu využívať samostatnú kapacitu workerov.

Možná architektúra je:

**Fronta s vysokou prioritou → Rýchle workery**

**Bežná fronta → Všeobecné workery**

**Hromadná fronta → Dávkové workery**

Konkrétny návrh závisí od vzorcov prevádzky, ale oddelenie pracovných zaťažení môže zabrániť tomu, aby niekoľko obrovských úloh zdržiavalo každú krátku požiadavku.

## **Krok 15: Sledujte používanie a náklady**

Rôzni poskytovatelia TTS môžu účtovať odlišne. Niektorí účtujú podľa znakov, iní podľa tokenov, ďalší podľa dĺžky vygenerovaného zvuku a niektorí používajú zložitejšie cenové modely.

Produkčný systém by mal približne vedieť, čo každá úloha spotrebuje. Medzi užitočné metriky patria:

1. Vstupné znaky
2. Vstupné tokeny
3. Dĺžka vygenerovaného zvuku
4. Poskytovateľ
5. Model
6. Typ hlasu
7. Počet opakovaní
8. Odhadované náklady poskytovateľa
9. Spotrebované kredity používateľa

Bez sledovania používania je ťažké zistiť, či je funkcia zisková alebo či niektorý poskytovateľ nie je neočakávane drahý.

## **Účtujte iba raz**

Účtovanie a opakovanie pokusov si vyžadujú dôkladnú koordináciu. Ak poskytovateľ trikrát zlyhá a až potom uspeje, používateľovi by sa zvyčajne nemalo trikrát účtovať za tú istú logickú požiadavku na generovanie.

Ak celá úloha natrvalo zlyhá, systém potrebuje jasné pravidlá, či sa rezervované kredity uvoľnia alebo vrátia. Idempotencia je tu mimoriadne dôležitá. Účtovanie by sa malo riadiť životným cyklom logickej úlohy, nie počtom interných opakovaných pokusov.

## **Krok 16: Pridajte pozorovateľnosť skôr, než ju budete potrebovať**

Keď používatelia nahlásia, že TTS je pomalé, samo osebe to neprezradí, kde je problém. Úloha mohla stráviť:

1. 20 sekúnd čakaním vo fronte
2. 2 sekundy vo workeri
3. 30 sekúnd čakaním na poskytovateľa
4. 10 sekúnd spracovaním zvuku
5. 5 sekúnd nahrávaním výstupu

Bez meraní vyzerajú všetky tieto fázy ako jedna pomalá požiadavka.

### **Užitočné metriky TTS**

Sledujte metriky, ako sú:

1. Latencia požiadavky API
2. Hĺbka fronty
3. Čas čakania vo fronte
4. Počet aktívnych workerov
5. Čas odozvy poskytovateľa

11. Trvanie nahrávania

### **Poskytovateľov merajte samostatne**

Ak podporujete viacerých poskytovateľov, súhrnné metriky môžu zakryť dôležité informácie. Napríklad celková miera úspešnosti môže byť 98%, hoci jeden poskytovateľ klesol na 85%.

Metriky by preto mali umožňovať filtrovanie podľa dimenzií, ako sú:

1. Poskytovateľ
2. Model
3. Hlas

6. Región

## **Záznamy by mali obsahovať ID úlohy**

Distribuované systémy sa ľahšie ladia, keď každý riadok záznamu súvisiaci s požiadavkou obsahuje rovnaký identifikátor úlohy. Rovnaké ID sa môže objaviť v:

## **Čo sa stane, keď poskytovateľ TTS vypadne?**

Externí poskytovatelia napokon zlyhajú, preto robustná architektúra počíta s tým, že sa to môže stať. Keď miera zlyhaní narastie, systém môže:

1. Spomaliť opakované pokusy.
2. Dočasne znížiť súbežnosť poskytovateľa.
3. Pozastaviť dotknuté fronty.
4. Presmerovať oprávnené požiadavky na iného poskytovateľa.
5. Informovať používateľov, že spracovanie mešká.

Najhoršou stratégiou je zvyčajne posielať čoraz viac opakovaných požiadaviek poskytovateľovi, ktorý už zlyháva.

## **Zvážte circuit breaker**

Circuit breaker môže po opakovaných zlyhaniach dočasne zastaviť požiadavky na poskytovateľa. Koncepčne:

**Poskytovateľ je v poriadku → Požiadavky povolené**

**Opakované zlyhania → Circuit breaker sa otvorí → Požiadavky sú dočasne zablokované**

**Test obnovy uspeje → Poskytovateľ sa znova povolí**

Tým možno zabrániť tomu, aby jedna zlyhávajúca závislosť spotrebovala veľkú časť kapacity workerov.

## **A čo streamovanie TTS?**

Nie každé pracovné zaťaženie TTS musí byť asynchrónne. Hlasoví asistenti a konverzačné systémy v reálnom čase môžu potrebovať začať prehrávať reč ešte pred vygenerovaním celého zvuku.

Takéto systémy môžu používať:

**Prúd textu → Prúd TTS → Zvukové bloky → Prehrávanie na klientovi**

Priority sú odlišné:

1. Čas do prvého zvuku
2. Latencia streamovania
3. Prerušenia
4. Stabilita spojenia

Produkčná platforma preto môže podporovať dve samostatné cesty:

**TTS v reálnom čase → Streamovacia cesta**

**TTS dlhého formátu → Fronta a cesta úlohy na pozadí**

Ak sa pokúsite prevádzkovať oba typy zaťaženia presne rovnakou architektúrou, optimalizácia systému môže byť zbytočne náročná.

## **Architektúra API TTS v porovnaní s architektúrou SRT-to-Speech**

Bežné API TTS začína textom. Systém SRT-to-Speech začína blokmi titulkov, ktoré už patria do časovej osi.

Základný pracovný postup TTS môže byť:

**Text → Fronta → TTS → Zvuk**

Pracovný postup SRT môže vyzerať takto:

**SRT → Rozparsovanie blokov → TTS → Zmeranie trvania → Úprava časovania → Spojenie zvuku**

Verzia SRT pridáva niekoľko problémov:

1. Zachovanie časových značiek
2. Cieľové trvanie
3. Mapovanie hovoriacich
4. Dĺžka prekladu
5. Synchronizácia zvuku
6. Opakovanie na úrovni blokov

## **Bežné chyby v architektúre TTS**

### **1. Priame volanie poskytovateľa z každej požiadavky HTTP**

Spočiatku je to jednoduché, no pri dlhotrvajúcich úlohách sa riešenie stáva krehkým.

### **2. Používanie neobmedzenej súbežnosti**

Viac workerov nepomôže, ak sa úzkym miestom stane poskytovateľ, CPU alebo sieť.

### **3. Opakovanie každej chyby**

Trvalé chyby validácie by sa nemali dostať do nekonečných slučiek opakovaných pokusov.

### **4. Opätovné generovanie úspešných blokov**

Pri veľkých úlohách treba zachovať dokončenú prácu a opakovať iba to, čo zlyhalo.

### **5. Ukladanie dôležitého zvuku iba na lokálny disk**

Kontajnery workerov a dočasné servery by sa nemali stať trvalým úložiskom súborov.

### **6. Ignorovanie limitov špecifických pre poskytovateľa**

Každý poskytovateľ môže vyžadovať inú stratégiu súbežnosti a obmedzovania frekvencie.

### **7. Pridanie monitorovania až po objavení problémov**

Bez metrík sa problémy s výkonom menia na hádanie.

### **8. Zmiešanie všetkých pracovných zaťažení v jednej fronte**

Jeden obrovský dokument môže zdržať desiatky malých interaktívnych požiadaviek, ak pracovné zaťaženia nemajú správne nastavené priority.

## **Dobrá architektúra sa môže začať jednoducho**

Nemusíte vytvoriť každý komponent hneď v prvý deň. Počiatočná aplikácia TTS môže začať takto:

**API → Poskytovateľ → Úložisko**

Potom, keď používanie narastie:

**API → Fronta → Worker → Poskytovateľ → Úložisko**

A neskôr:

**API → Vyrovnávacia pamäť → Fronty podľa priority → Skupiny workerov → Smerovač poskytovateľov → Viacerí poskytovatelia → Úložisko/CDN → Webhooky + Monitorovanie**

Architektúra by sa mala rozvíjať v reakcii na skutočné úzke miesta, nie na teoretickú zložitosť. Dôležité je zvoliť hranice, ktoré umožnia budúce vylepšenia.

## **Kedy pridať frontu?**

Fronta je čoraz užitočnejšia, keď:

1. Generovanie trvá viac než niekoľko sekúnd.
2. Používatelia odosielajú rozsiahly text.
3. Úlohy obsahujú viacero blokov.
4. Pravidelne narážate na limity poskytovateľa.
5. Prevádzka prichádza v nárazoch.
6. Potrebujete spoľahlivé opakované pokusy.
7. Chcete škálovať workery nezávisle od API.

Ak je každá požiadavka malá a dokončí sa takmer okamžite, fronta spočiatku nemusí byť potrebná.

## **Kedy pridať viacerých poskytovateľov?**

Podpora viacerých poskytovateľov dáva zmysel, keď na to existuje konkrétny dôvod, napríklad:

1. Sú potrebné rôzne hlasy.
2. Jeden poskytovateľ nepodporuje určitý jazyk.
3. Potrebujete vyššiu celkovú kapacitu.
4. Potrebujete rôzne cenové úrovne.
5. Pri kritických úlohách potrebujete záložného poskytovateľa.

Pridávať poskytovateľov iba kvôli architektonickej elegancii môže zvýšiť náročnosť údržby bez veľkého prínosu.

## **Kedy ukladať výstup TTS do vyrovnávacej pamäte?**

Ukladanie do vyrovnávacej pamäte je obzvlášť užitočné, keď:

1. Sa rovnaký obsah generuje často.
2. Sú volania poskytovateľa TTS nákladné.
3. Sú niektoré výstupy dostatočne deterministické na opätovné použitie.
4. Používatelia často opakujú požiadavky alebo znova otvárajú existujúce projekty.
5. Sa vo veľkých projektoch upravuje naraz iba niekoľko blokov.

Aj keď nie je vždy možné opätovne použiť celý zvuk, ukladanie po blokoch môže stále priniesť značné úspory.

## **Produkčné TTS je problém orchestrácie**

Samotný model TTS je iba jednou súčasťou. Produkčný systém musí koordinovať:

**Používateľov + Úlohy + Fronty + Workery + Poskytovateľov + Zvuk + Úložisko + Účtovanie + Monitorovanie**

To vysvetľuje, prečo sa lokálne demo TTS dá vytvoriť rýchlo, zatiaľ čo spoľahlivá verejná platforma TTS si vyžaduje oveľa viac inžinierskej práce. Zložitosť pochádza zo všetkého, čo obklopuje model.

## **Záverečné myšlienky**

Produkčné API na prevod textu na reč treba od začiatku navrhovať s ohľadom na zlyhania, súbežnosť a dlhotrvajúce spracovanie.

Základná architektúra je jednoduchá:

**Prijmite požiadavku → Overte ju → Ak je to možné, použite existujúci výstup → Vytvorte úlohu → Zaraďte prácu do fronty → Vygenerujte reč → Opakujte pokusy pri napraviteľných zlyhaniach → Uložte zvuk → Vráťte výsledok.**

S rastúcou prevádzkou sú čoraz dôležitejšie ďalšie vrstvy, ako sú smerovanie poskytovateľov, prioritné fronty, spracovanie po blokoch, riadenie limitov frekvencie, sledovanie nákladov, callbacky a pozorovateľnosť.

Najdôležitejšie ponaučenie je, že generovanie reči býva zvyčajne jednoduchou časťou. Skutočnou produkčnou výzvou je vytvoriť systém, ktorý dokáže spoľahlivo generovať reč pre mnohých používateľov a cez mnohých poskytovateľov, pričom udrží náklady a zlyhania pod kontrolou.
