# Using LLM Features in a Text Classification Pipeline

> A practical guide to using LLM-generated features in a classification pipeline and evaluating thresholds and calibration.



A language model can classify text directly, or produce signals that another model uses alongside other data. Neither approach is automatically better. The useful choice depends on the task, the available labels and the cost of mistakes.

## Start with a baseline

Define the outcome and collect examples that reflect the decisions you need to make. For a support workflow, the task might be to identify tickets that need urgent human review. Agree on what counts as urgent, include ambiguous cases and record how people labelled them.

Test a simple baseline before adding complexity. It could be a rule, a model prompted to return a label, or a supervised classifier trained on existing labelled data. Compare approaches on the same held-out examples. A direct LLM classifier can be useful; it should not be rejected merely because another approach exists.

## Turn model outputs into features

Instead of asking a language model for only a final decision, ask it to report a small set of task-specific signals. In the support example, those signals might indicate whether the message describes a service outage or a billing question. A downstream classifier can use those signals together with permitted structured fields, such as product category.

Define each signal precisely and validate the output format. A generated signal can be wrong or missing, and a downstream model can learn from those errors. Do not include information that would not be available when the real decision is made.

## Split the data before fitting

Separate training data from validation and test data before selecting features or tuning thresholds. Where messages from the same customer or a later time period are related, choose a split that reflects how the system will be used. Otherwise, information from the test set can leak into training and make results look better than they are.

Fit the downstream model on the training set. Use validation data to choose features and a decision threshold, then evaluate the selected workflow on a separate test set. Check the entire pipeline, including failures to obtain or parse an LLM output; do not evaluate only successful calls.

## Choose a threshold for the consequences

A classifier may produce a score or probability for each item. A threshold turns that value into an action, such as sending a ticket for review. Moving the threshold can change precision and recall, but the right trade-off depends on the cost of missed cases and unnecessary reviews.

If you intend to interpret scores as probabilities, evaluate their calibration on suitable held-out data. Fitting a logistic regression or asking a model for confidence does not guarantee calibrated probabilities. Compare calibration as well as classification metrics, and inspect performance for important groups and rare cases.

## Measure the full workflow

Compare the baseline and the feature-based system on the same evaluation set. Record false positives, false negatives, latency, cost and the proportion of calls that failed or needed human review. A more complex workflow should earn its extra operational cost with a measurable benefit on the task.

Track the version of the prompt, model, features and threshold. Re-evaluate when they change or when incoming data shifts. For further guidance on creating and maintaining evaluations, see [OpenAI's evaluation best practices](https://platform.openai.com/docs/guides/evaluation-best-practices).
