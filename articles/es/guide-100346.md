# Arquitectura de API TTS: del texto al audio en producción

> Aprende a diseñar una API TTS para producción con colas, workers, caché, reintentos, enrutamiento de proveedores, almacenamiento, límites de solicitudes y observabilidad.



Llamar a una API de texto a voz es fácil. Ejecutarla de forma fiable en producción no lo es.

Un prototipo básico puede tener solo tres pasos:

**Texto → Proveedor TTS → MP3**

Esto puede funcionar bien al probar unas pocas solicitudes en local. Cuando llegan usuarios reales, el sistema debe gestionar trabajos simultáneos, límites de solicitudes de los proveedores, fallos de red, tareas de generación de audio largas, solicitudes duplicadas, almacenamiento, reintentos, cuotas, varios proveedores de voz y usuarios que actualizan la página mientras el audio aún se está procesando.

La arquitectura pronto se vuelve más compleja que la propia llamada a la API TTS. Un flujo de trabajo de producción más realista sería así:

**Cliente → API → Trabajo → Cola → Worker → Proveedor TTS → Almacenamiento/CDN → Resultado**

Este artículo explica cómo diseñar esa arquitectura, por qué existe cada componente y qué problemas suelen aparecer cuando una aplicación TTS crece más allá de una demo sencilla.



## **¿Qué debe resolver una API TTS de producción?**

El objetivo de un backend TTS de producción no es simplemente generar audio. Debe generarlo **de forma fiable, eficiente y predecible**.

Una buena arquitectura debería responder a preguntas como estas:

1. ¿Qué ocurre cuando 100 usuarios generan voz al mismo tiempo?
2. ¿Qué ocurre cuando el proveedor TTS devuelve HTTP 429?
3. ¿Qué ocurre cuando el proveedor TTS deja de estar disponible?
4. ¿Qué ocurre cuando un trabajo de generación de audio tarda varios minutos?
5. ¿Qué ocurre cuando un usuario envía la misma solicitud dos veces?
6. ¿Cómo se evita que un usuario consuma toda la cuota disponible del proveedor?
7. ¿Dónde debería almacenarse el audio generado?
8. ¿Cómo sabe el cliente que ha terminado un trabajo de larga duración?
9. ¿Cómo se reintenta el trabajo fallido sin volver a generar el audio que sí se generó correctamente?
10. ¿Cómo se mide qué proveedor es lento o poco fiable?

Estos son problemas de diseño de sistemas, no de síntesis de voz.

## **La solicitud básica de una API TTS**

En el nivel más sencillo, una solicitud TTS puede contener:

1. Texto
2. Idioma
3. Voz
4. Modelo
5. Velocidad del habla
6. Formato de audio
7. Instrucciones de voz opcionales

Por ejemplo, de forma conceptual:

**POST /tts**

El servidor recibe la solicitud, llama a un proveedor TTS y devuelve un archivo de audio. Este modelo síncrono es fácil de entender:

**Solicitud HTTP → Proveedor → Audio → Respuesta HTTP**

Para generar intervenciones muy cortas, puede ser aceptable. Los problemas empiezan cuando la generación se ralentiza, aumenta el tráfico o una solicitud contiene mucho texto.

## **Por qué los trabajos TTS largos no deberían depender de una sola solicitud HTTP**

Imagina que un usuario envía suficiente texto para generar una voz en off de 30 minutos. Si la API mantiene abierta la solicitud HTTP original hasta que todo termina, pueden ocurrir varias cosas:

1. El navegador puede agotar el tiempo de espera.
2. Un proxy inverso puede cerrar la solicitud.
3. El servidor de aplicaciones puede reiniciarse.
4. El proveedor puede fallar temporalmente.
5. El usuario puede cerrar la página.
6. La conexión móvil puede interrumpirse.

El trabajo TTS puede seguir siendo válido, pero la conexión que lo inició ya no existe. Por lo general, es mejor modelar las cargas de trabajo TTS de larga duración como **trabajos**.

El flujo pasa a ser:

**Cliente → Crear trabajo → Devolver ID del trabajo → Procesar en segundo plano**

El cliente puede consultar el progreso más tarde.

## **Paso 1: aceptar y validar la solicitud**

La capa de API debería realizar una validación ligera antes de enviar el trabajo al sistema de procesamiento. Las comprobaciones habituales incluyen:

1. ¿El texto está vacío?
2. ¿El texto supera el tamaño máximo permitido para la solicitud?
3. ¿Existe la voz solicitada?
4. ¿El modelo seleccionado admite el idioma solicitado?
5. ¿Se admite el formato de audio solicitado?
6. ¿Está autenticado el usuario?
7. ¿Tiene el usuario cuota o créditos suficientes?
8. ¿Está permitida la solicitud según las reglas de limitación de solicitudes?

Las solicitudes no válidas deberían rechazarse antes de llegar a los workers o a los proveedores externos. Así se ahorran recursos de infraestructura y cuota del proveedor.

Para trabajos concurrentes, reserva de forma atómica la cuota o los créditos aplicables antes de admitirlos y liquida o libera esa reserva una sola vez según el resultado real y la política de facturación.

## **Paso 2: normalizar la solicitud**

Antes de procesarla, normaliza la solicitud a un formato interno predecible. Por ejemplo:

1. Normaliza los códigos de idioma.
2. Resuelve el ID real de la voz.
3. Resuelve el proveedor asociado a la voz seleccionada.
4. Aplica la velocidad de habla predeterminada.
5. Normaliza los espacios en blanco.
6. Selecciona el formato de salida.
7. Resuelve la configuración del modelo.

Esto proporciona a los workers posteriores un contrato de entrada coherente. También ayuda con el almacenamiento en caché: idealmente, las solicitudes lógicamente idénticas deberían producir la misma clave de caché.



## **Paso 3: comprobar si el audio ya existe**

Generar el mismo audio repetidamente es una forma fácil de desperdiciar dinero en un sistema TTS. Supongamos que un usuario envía varias veces:

*«Te damos la bienvenida a nuestra aplicación».*

con la misma voz, modelo, velocidad y configuración. Si el resultado es suficientemente determinista para tu caso de uso, quizá no haya motivo para llamar al proveedor cada vez.

Se puede derivar una clave de caché de valores como estos:

1. Texto normalizado
2. ID de la voz
3. Proveedor
4. Modelo
5. Idioma
6. Velocidad
7. Formato de audio
8. Estilo o instrucciones de voz

Una clave conceptual podría ser:

**HASH(texto + voz + modelo + velocidad + formato + configuración)**

Serializa de forma inequívoca todos los campos de generación e incluye el ámbito adecuado de tenant o acceso en la identidad de caché. Autoriza la reutilización y el acceso al resultado; comparte entre tenants solo cuando esté expresamente permitido.

El flujo de la solicitud pasa a ser:

**Solicitud → Comprobación de caché → ¿Existe el audio?**

Si sí:

**Devolver el resultado existente**

Si no:

**Crear un trabajo de generación**

### **No uses solo el texto para la clave de caché**

Usar únicamente el texto como clave de caché suele ser incorrecto. La misma oración generada con dos voces diferentes no debería devolver el mismo audio. Lo mismo se aplica al modelo, la velocidad, el idioma, el formato y la configuración de estilo.

La identidad de la caché debería representar todo lo que pueda cambiar materialmente el resultado.

## **Paso 4: crear un trabajo persistente**

Antes de colocar el trabajo en una cola, guarda un registro del trabajo. Un trabajo TTS podría contener:

1. ID del trabajo
2. ID del usuario
3. Estado
4. Voz solicitada
5. Proveedor
6. Modelo
7. Recuento de caracteres
8. Hora de creación
9. Hora de inicio
10. Hora de finalización
11. Recuento de reintentos
12. Progreso
13. Información del error
14. URL de salida

Un ciclo de vida de estado sencillo podría ser:

**Pendiente → En procesamiento → Completado**

con estados de error como:

**Pendiente → En procesamiento → Fallido**

También puede que necesites estados para trabajos en reintento, cancelados, parcialmente completados o caducados.

Es importante persistir el estado del trabajo porque el sistema de procesamiento no debería depender de la memoria de la aplicación. Si se reinicia el contenedor de la API, los usuarios deberían poder seguir recuperando sus trabajos.

## **Paso 5: enviar el trabajo a una cola de mensajes**

La cola de mensajes separa la aceptación de la solicitud del procesamiento de audio. En lugar de:

**API → Proveedor TTS**

se usa:

**API → Cola → Worker → Proveedor TTS**

La API puede responder casi de inmediato con un identificador de trabajo mientras los workers procesan las solicitudes en segundo plano.

Usa un outbox transaccional o recuperación duradera para trabajos registrados pero no encolados, y haz idempotente el procesamiento de la cola para que un fallo o una nueva entrega no pierda ni duplique trabajo.

### Por qué las colas son tan útiles para TTS

Las colas aportan varios beneficios importantes:

1. Absorben los picos de tráfico.
2. Controlan cuántos trabajos se ejecutan simultáneamente.
3. Protegen las cuotas de los proveedores externos.
4. Facilitan los reintentos.
5. Permiten que los trabajos continúen después de que termine la solicitud HTTP original.
6. Permiten añadir workers a medida que crece el tráfico.

Esto es especialmente importante cuando los proveedores TTS imponen límites de solicitudes por minuto, caracteres, tokens o concurrencia.



## **La cola también es un mecanismo de contrapresión**

Supongamos que tu proveedor puede procesar de forma segura 20 solicitudes a la vez, pero tu API recibe 200 solicitudes simultáneamente. Sin una cola, podrías enviar las 200 solicitudes directamente al proveedor. El resultado probable sería:

1. Errores de límite de solicitudes
2. Tiempos de espera agotados
3. Uso elevado de CPU
4. Uso elevado de memoria
5. Limitación por parte del proveedor
6. Una cascada de reintentos

Con una cola, la API puede aceptar trabajos mientras los workers los procesan a un ritmo controlado. El sistema no tiene que procesarlo todo de inmediato solo porque las solicitudes hayan llegado de inmediato.

## **Paso 6: procesar trabajos con workers TTS**

Los workers gestionan el flujo de generación. Un worker puede:

1. Leer un trabajo de la cola.
2. Cargar la configuración del trabajo.
3. Dividir el texto largo si es necesario.
4. Seleccionar el proveedor correcto.
5. Llamar a la API TTS.
6. Gestionar los fallos temporales.
7. Descargar o recibir el audio generado.
8. Validar el resultado.
9. Subir el resultado al almacenamiento.
10. Actualizar el estado del trabajo.

Los workers deberían ser lo bastante independientes del estado para que otro worker pueda procesar el trabajo si una instancia desaparece.

## **¿Cuánta concurrencia debería usar un worker?**

Más concurrencia no significa automáticamente más rendimiento. Aumentar la concurrencia de los workers con demasiada agresividad puede provocar:

1. Alcanzar los límites del proveedor
2. Saturación de la CPU
3. Presión sobre la memoria
4. Límites de red
5. Límites de E/S de disco
6. Cuellos de botella de FFmpeg

Las cargas de trabajo TTS pueden implicar varios tipos de recursos. Llamar a una API de voz remota puede estar limitado principalmente por la red, mientras que la conversión o la unión de audio pueden quedar limitadas por la CPU. Por tanto, un sistema de producción puede beneficiarse de controles de concurrencia separados para cada etapa.

Por ejemplo:

**Concurrencia de descarga: alta**

**Concurrencia del proveedor TTS: depende del proveedor**

**Concurrencia del procesamiento de audio: depende de la CPU**

Esto suele ser más seguro que usar un único valor alto de concurrencia en todas partes.

## **Paso 7: dividir el texto largo en bloques más pequeños**

Muchos proveedores TTS imponen límites al tamaño de las solicitudes. Incluso cuando un proveedor acepta entradas de texto muy grandes, dividir los documentos largos puede seguir siendo útil.

Un trabajo TTS largo podría convertirse en:

**Documento → Bloque 1 + Bloque 2 + Bloque 3 + ... → TTS → Unión**

El procesamiento por bloques ofrece varias ventajas:

1. Reintentar solo los bloques fallidos tras confirmar que es seguro.
2. Procesar bloques independientes simultáneamente.
3. Seguir el progreso.
4. Recuperarse de fallos parciales.
5. Almacenar bloques en caché de forma individual.
6. Evitar los límites de tamaño de las solicitudes del proveedor.

### **No dividas el texto a ciegas**

Dividir cada cantidad fija de caracteres puede perjudicar la calidad del habla al terminar un bloque a mitad de una oración. Una lógica de división mejor puede tener en cuenta:

1. Límites entre párrafos
2. Límites entre oraciones
3. Puntuación
4. Límites de caracteres del proveedor
5. Reglas de escritura específicas del idioma

El objetivo es mantener los bloques lo bastante pequeños para procesarlos de forma fiable y, al mismo tiempo, conservar un contexto de habla natural.

## **Paso 8: enrutar las solicitudes al proveedor TTS correcto**

Una aplicación de producción puede acabar admitiendo varios proveedores TTS. Cada uno puede ofrecer diferentes:

1. Idiomas
2. Catálogos de voces
3. Precios
4. Niveles de calidad
5. Límites de solicitudes
6. Latencia
7. Controles emocionales
8. Capacidades de streaming

En lugar de integrar la lógica de los proveedores en toda la aplicación, usa una capa de enrutamiento o abstracción. La arquitectura pasa a ser:

**Worker → Enrutador de voz/modelo → Adaptador del proveedor → Proveedor TTS**

Cada adaptador de proveedor puede exponer una interfaz interna común y, a la vez, traducir las solicitudes al formato que espera ese proveedor.

### **Evita la lógica específica de cada proveedor en todas partes**

Sin una abstracción, el código puede llenarse de condiciones como estas:

**Si el proveedor es A, haz esto. Si el proveedor es B, haz otra cosa.**

Esto se vuelve difícil de mantener a medida que se añaden proveedores. Una interfaz común de proveedor permite que el resto del sistema trabaje con conceptos como:

1. Generar voz
2. Obtener las voces admitidas
3. Validar la solicitud
4. Devolver el audio

Cada adaptador de proveedor gestiona los detalles de implementación.

## **Alternativa de proveedor: útil, pero no siempre sencilla**

Puede resultar tentador enviar automáticamente cada solicitud fallida a otro proveedor. A veces funciona bien; otras, no. Puede que dos proveedores no tengan voces equivalentes, y una voz alternativa puede sonar completamente diferente de la original. Eso puede ser inaceptable en un audiolibro largo o un vídeo con varias escenas.

Las decisiones de usar un proveedor alternativo deberían tener en cuenta:

1. Si existe una voz equivalente
2. Si la coherencia es importante
3. Si el fallo es temporal
4. La diferencia de coste
5. El idioma de destino
6. Las preferencias del usuario

La alternativa de proveedor es una herramienta arquitectónica, no una garantía de que cada solicitud fallida deba redirigirse de inmediato.

## **Paso 9: gestionar correctamente los límites de solicitudes**

HTTP 429 es uno de los problemas más comunes en los sistemas que dependen mucho de las API. HTTP 429 puede indicar un límite del proveedor, incluida la frecuencia de solicitudes o las solicitudes concurrentes. Consulta los detalles del error y las indicaciones de reintento del proveedor, incluido Retry-After cuando se proporcione, antes de decidir cómo y cuándo reintentar.

La respuesta incorrecta es:

**Reintentar de inmediato y lo más rápido posible.**

Esto suele generar aún más solicitudes y empeorar el problema. Un enfoque mejor usa:

1. Límites de concurrencia
2. Retroceso exponencial
3. Jitter
4. Políticas de límites de solicitudes específicas de cada proveedor
5. Retrasos en la cola

De forma conceptual:

**429 → Esperar → Reintentar más tarde**

no:

**429 → Reintentar de inmediato → 429 → Reintentar de inmediato → 429**

## **Paso 10: reintentar solo los errores recuperables**

Los reintentos son necesarios, pero no deberían repetirse todos los fallos. Una clasificación útil es:

| Tipo de error               | Acción habitual                     |
|-----------------------------|-------------------------------------|
| 429 Demasiadas solicitudes  | Esperar y reintentar con retroceso  |
| 500 Error interno del servidor | Conciliar el resultado original; reintentar solo si es seguro |
| 502 / 503 Fallo temporal    | Conciliar el resultado original antes de reintentar o cambiar de proveedor |
| Tiempo de espera de red agotado | Conciliar el resultado original antes de reintentar |
| 400 Solicitud no válida     | No reintentar a ciegas              |
| Voz no admitida             | Corregir la solicitud o el enrutamiento |
| Créditos de usuario insuficientes | Fallar antes del procesamiento del proveedor |

Un tiempo de espera agotado, un 5xx o un fallo del worker pueden dejar desconocido el resultado en el proveedor. Antes de reintentar o cambiar de proveedor, concilia el ID de la operación original, el estado y el uso cuando se admita, reutiliza una salida ya aplicada y usa la idempotencia admitida por el proveedor. Conserva un resultado desconocido en lugar de repetir a ciegas una solicitud que podría haberse completado.

Una política de reintentos también debería establecer un número máximo de intentos. De lo contrario, un trabajo defectuoso podría permanecer en el sistema para siempre.

## **Usar idempotencia para evitar trabajos duplicados**

Las solicitudes duplicadas son habituales en aplicaciones reales. Un usuario puede hacer doble clic en un botón, el frontend puede reintentar después de agotarse el tiempo de espera de la red, un mensaje de la cola puede entregarse de nuevo o un worker puede terminar correctamente y fallar antes de confirmar la recepción del mensaje.

Si tu sistema supone que cada mensaje es único, puede generar y cobrar varias veces por el mismo audio. La idempotencia significa que procesar varias veces la misma solicitud lógica no debería crear varios resultados no deseados.

Algunas técnicas posibles:

1. Claves de idempotencia
2. Identificadores de trabajo únicos
3. Hashes de caché
4. Restricciones de unicidad en la base de datos
5. Comprobar el estado de los bloques antes de procesarlos

Esto es especialmente importante cuando intervienen pagos, créditos o costes del proveedor.

## **Idempotencia a nivel de trabajo frente a idempotencia a nivel de bloque**

Para las solicitudes TTS cortas, puede bastar con la idempotencia a nivel de trabajo. Para trabajos grandes con muchos bloques, la idempotencia a nivel de bloque suele ser más útil.

Imagina un trabajo de audiolibro de 500 bloques en el que falla el bloque 487. No querrás volver a generar los bloques del 1 al 486.

**Bloques completados → Conservar**

**Bloque fallido → Comprobar estado del proveedor → Reintentar solo si es seguro**

Esto reduce significativamente el coste y el tiempo de recuperación.

## **Paso 11: validar el audio generado**

Una respuesta correcta del proveedor no siempre garantiza un resultado utilizable. Antes de marcar un trabajo como completado, quizá quieras validar lo siguiente:

1. ¿Se devolvió un archivo de audio?
2. ¿El tamaño del archivo es mayor que cero?
3. ¿Se puede decodificar el audio?
4. ¿La duración parece razonable?
5. ¿Es correcto el formato solicitado?

En flujos de trabajo avanzados, validar la duración también puede detectar resultados sospechosos, como voz inesperadamente corta o larga.

## **Paso 12: almacenar el audio fuera del servidor de aplicaciones**

Por lo general, el audio generado no debería depender del disco local de una sola instancia de API o worker. Si se recrea el contenedor, el archivo podría desaparecer.

Una arquitectura mejor sería:

**Worker → Almacenamiento de objetos → CDN → Usuario**

El almacenamiento de objetos separa los recursos generados de la infraestructura de cómputo. Después, una CDN puede servir el audio de forma eficiente a usuarios de distintas ubicaciones.

Autoriza el acceso a cada trabajo, su estado y el audio resultante. Mantén privado el audio almacenado y, cuando sea necesario, usa enlaces con alcance limitado y caducidad en vez de tratar una URL como prueba de acceso.

### ¿Qué debería almacenarse en la base de datos?

Normalmente, la base de datos no necesita contener los bytes del audio en bruto. En su lugar, almacena metadatos como:

1. Clave de almacenamiento
2. URL del audio
3. Duración
4. Tamaño del archivo
5. Formato
6. Proveedor
7. Voz
8. Hora de generación

El audio en sí puede permanecer en el almacenamiento de objetos.

## **Piensa en la caducidad de los archivos**

No todos los archivos TTS generados necesitan existir para siempre. El almacenamiento puede encarecerse silenciosamente cuando se acumulan millones de archivos de audio temporales.

Considera políticas de retención para:

1. Archivos generados por invitados
2. Archivos temporales de procesamiento
3. Bloques intermedios
4. Proyectos de usuario completados
5. Audio reutilizable almacenado en caché

Los archivos intermedios suelen poder tener periodos de retención mucho más cortos que los resultados finales de los usuarios.

## **Paso 13: devolver resultados mediante consultas periódicas o callbacks**

Cuando una solicitud TTS pasa a ser asíncrona, el cliente necesita una forma de saber cuándo termina el procesamiento. Hay dos patrones habituales.

### **Consultas periódicas**

El cliente pregunta periódicamente:

**GET /jobs/{jobId}**

El servidor responde con algo parecido a:

**status = processing**

y más tarde:

**status = completed, audioUrl = ...**

Las consultas periódicas son fáciles de implementar y funcionan bien en muchas aplicaciones web.

### **Webhook o callback**

Para clientes de API, el cliente puede proporcionar una URL de callback. Cuando termina el procesamiento, el servidor envía una notificación automáticamente.

El flujo pasa a ser:

**Crear trabajo → Devolver ID del trabajo → Procesar → Notificar al cliente mediante callback**

Esto es útil cuando los sistemas externos procesan trabajos grandes y no quieren consultar el estado constantemente.

### **Puede ser útil admitir ambos métodos**

Una API de producción puede ofrecer la consulta de trabajos como mecanismo universal y los webhooks como opción práctica.

## **Seguir el progreso de trabajos grandes**

Para una solicitud TTS de 5 segundos, quizá no importe el progreso. Para un proyecto de audio de una hora, sí importa mucho. Si un trabajo contiene 1000 bloques, el progreso puede aproximarse a partir del trabajo completado:

**Progreso = Bloques completados / Total de bloques**

Esto permite que el frontend muestre:

1. En cola
2. En procesamiento 27%
3. En procesamiento 83%
4. Finalizando audio
5. Completado

Un indicador de progreso visible también reduce la probabilidad de que los usuarios crean que la aplicación se ha bloqueado y vuelvan a enviar el mismo trabajo.

## **Paso 14: proteger el sistema con límites de solicitudes**

Tu proveedor tiene límites de solicitudes. Tu propia API también debería tenerlos. Se pueden aplicar límites por:

1. Usuario
2. Clave de API
3. Dirección IP
4. Plan de suscripción
5. Endpoint
6. Proveedor

Los límites de solicitudes protegen la infraestructura y las cuotas de los proveedores. También pueden impedir que un usuario con mucho consumo agote todos los slots de worker disponibles.

## **Las prioridades pueden ser más útiles que una sola cola global**

A medida que crece el producto, quizá no todos los trabajos deban tener la misma prioridad. Por ejemplo:

1. Las solicitudes TTS interactivas y cortas pueden necesitar respuestas rápidas.
2. Los trabajos de documentos grandes pueden esperar un poco más.
3. Los usuarios de pago pueden recibir mayor prioridad de procesamiento.
4. Los trabajos de API masivos en segundo plano pueden usar una capacidad de workers independiente.

Una posible arquitectura es:

**Cola de alta prioridad → Workers rápidos**

**Cola normal → Workers generales**

**Cola masiva → Workers por lotes**

El diseño exacto depende de los patrones de tráfico, pero separar las cargas de trabajo puede evitar que unos pocos trabajos enormes retrasen todas las solicitudes cortas.

## **Paso 15: hacer un seguimiento del uso y el coste**

Los distintos proveedores TTS pueden cobrar de formas diferentes. Algunos cobran por carácter, otros por token, otros por duración del audio generado y otros usan modelos de precios más complejos.

Un sistema de producción debería saber aproximadamente cuánto consume cada trabajo. Entre las métricas útiles se incluyen:

1. Caracteres de entrada
2. Tokens de entrada
3. Duración generada
4. Proveedor
5. Modelo
6. Tipo de voz
7. Recuento de reintentos
8. Coste estimado del proveedor
9. Créditos consumidos por el usuario

Sin hacer un seguimiento del uso, resulta difícil saber si una función es rentable o si un proveedor cuesta inesperadamente más.

## **Cobra solo una vez**

La facturación y los reintentos requieren una coordinación cuidadosa. Si el proveedor falla tres veces antes de tener éxito, normalmente no debería cobrarse al usuario tres veces por la misma solicitud lógica de generación.

Si el trabajo completo falla de forma definitiva, tu sistema necesita una política clara para decidir si se liberan o reembolsan los créditos reservados. La idempotencia es muy importante aquí. La facturación debería seguir el ciclo de vida del trabajo lógico, no el número de intentos internos de reintento.

## **Paso 16: añadir observabilidad antes de necesitarla**

Cuando los usuarios informan de que TTS va lento, eso por sí solo no indica dónde está el problema. El trabajo puede haber pasado:

1. 20 segundos esperando en la cola
2. 2 segundos dentro del worker
3. 30 segundos esperando al proveedor
4. 10 segundos procesando el audio
5. 5 segundos subiendo el resultado

Sin mediciones, todas esas etapas parecen una sola solicitud lenta.

### **Métricas TTS útiles**

Haz un seguimiento de métricas como estas:

1. Latencia de las solicitudes de API
2. Profundidad de la cola
3. Tiempo de espera en la cola
4. Número de workers activos
5. Tiempo de respuesta del proveedor
6. Tasa de éxito de la generación
7. Tasa de errores por proveedor
8. Tasa de 429
9. Tasa de reintentos
10. Duración del procesamiento de audio
11. Duración de la subida
12. Duración total del trabajo
13. Coste por trabajo

### **Mide los proveedores por separado**

Si admites varios proveedores, las métricas agregadas pueden ocultar información importante. Por ejemplo, la tasa de éxito global podría ser del 98% mientras que la de un proveedor haya caído al 85%.

Por tanto, las métricas deberían poder filtrarse por dimensiones como:

1. Proveedor
2. Modelo
3. Voz
4. Idioma
5. Worker
6. Región

## **Los registros deberían incluir un ID de trabajo**

Los sistemas distribuidos son más fáciles de depurar cuando cada línea de registro relacionada con una solicitud contiene el mismo identificador de trabajo. El mismo ID puede aparecer en:

1. Registros de la API
2. Mensajes de la cola
3. Registros de los workers
4. Llamadas al proveedor
5. Operaciones de almacenamiento

Cuando algo falla, puedes buscar un ID de trabajo y reconstruir toda la ruta de ejecución.

5. Políticas de reintento

## **¿Qué ocurre cuando un proveedor TTS deja de funcionar?**

Los proveedores externos acabarán fallando, así que una arquitectura robusta da por hecho que esto puede ocurrir. Cuando aumentan las tasas de fallos, tu sistema puede:

1. Espaciar más los reintentos.
2. Reducir temporalmente la concurrencia del proveedor.
3. Pausar las colas afectadas.
4. Enrutar las solicitudes aptas a otro proveedor.
5. Informar a los usuarios de que el procesamiento se está retrasando.

La peor estrategia suele ser enviar cada vez más reintentos a un proveedor que ya está fallando.

## **Considera un circuit breaker**

Un circuit breaker puede detener temporalmente las solicitudes a un proveedor después de fallos repetidos. De forma conceptual:

**Proveedor disponible → Solicitudes permitidas**

**Fallos repetidos → El circuito se abre → Solicitudes bloqueadas temporalmente**

**La prueba de recuperación tiene éxito → El proveedor vuelve a habilitarse**

Esto puede impedir que una dependencia que falla consuma una gran cantidad de capacidad de los workers.

## **¿Qué pasa con el TTS en streaming?**

No todas las cargas de trabajo TTS deberían ser asíncronas. Es posible que los asistentes de voz y los sistemas conversacionales en tiempo real necesiten empezar a reproducir el habla antes de que se haya generado todo el audio.

Estos sistemas pueden usar:

**Flujo de texto → Flujo TTS → Fragmentos de audio → Reproducción en el cliente**

Las prioridades son diferentes:

1. Tiempo hasta el primer audio
2. Latencia del streaming
3. Interrupciones
4. Estabilidad de la conexión

Por tanto, una plataforma de producción puede admitir dos rutas independientes:

**TTS en tiempo real → Ruta de streaming**

**TTS de formato largo → Cola y ruta de trabajos en segundo plano**

Intentar forzar ambas cargas de trabajo a través exactamente de la misma arquitectura puede dificultar innecesariamente la optimización del sistema.

## **Arquitectura de API TTS frente a arquitectura de SRT a voz**

Una API TTS normal suele empezar con texto. Un sistema de SRT a voz empieza con bloques de subtítulos que ya pertenecen a una línea de tiempo.

La canalización TTS básica puede ser:

**Texto → Cola → TTS → Audio**

El flujo de SRT puede ser:

**SRT → Analizar bloques → TTS → Medir duración → Ajustar tiempos → Unir audio**

La versión SRT añade varios problemas:

1. Conservación de marcas de tiempo
2. Duración de destino
3. Asignación de hablantes
4. Longitud de la traducción
5. Sincronización de audio
6. Reintentos a nivel de bloque

## **Errores habituales en la arquitectura TTS**

### **1. Llamar directamente al proveedor desde cada solicitud HTTP**

Al principio es fácil, pero se vuelve frágil en cargas de trabajo largas.

### **2. Usar concurrencia ilimitada**

Más workers no ayudan si el proveedor, la CPU o la red se convierten en el cuello de botella.

### **3. Reintentar todos los errores**

Los errores de validación permanentes no deberían entrar en bucles de reintentos infinitos.

### **4. Volver a generar bloques completados correctamente**

Los trabajos grandes deberían conservar el trabajo ya completado y reintentar solo lo que falló.

### **5. Almacenar audio importante únicamente en el disco local**

Los contenedores de workers y los servidores temporales no deberían convertirse en almacenes permanentes de recursos.

### **6. Ignorar los límites específicos de cada proveedor**

Cada proveedor puede requerir una estrategia diferente de concurrencia y límites de solicitudes.

### **7. Añadir supervisión solo después de que aparezcan los problemas**

Sin métricas, el análisis de los problemas de rendimiento se convierte en una conjetura.

### **8. Mezclar todas las cargas de trabajo en una sola cola**

Un documento enorme puede retrasar decenas de solicitudes interactivas pequeñas si las cargas de trabajo no se priorizan correctamente.

## **Una buena arquitectura puede empezar de forma sencilla**

No es necesario crear todos los componentes el primer día. Una aplicación TTS inicial podría empezar con:

**API → Proveedor → Almacenamiento**

Después, a medida que crece el uso:

**API → Cola → Worker → Proveedor → Almacenamiento**

Y más adelante:

**API → Caché → Colas prioritarias → Grupos de workers → Enrutador de proveedores → Varios proveedores → Almacenamiento/CDN → Webhooks + Supervisión**

La arquitectura debería crecer en respuesta a cuellos de botella reales, no a una complejidad teórica. Lo importante es elegir límites que permitan mejoras futuras.

## **¿Cuándo deberías añadir una cola?**

Una cola resulta cada vez más útil cuando:

1. La generación puede tardar más de unos segundos.
2. Los usuarios envían mucho texto.
3. Los trabajos contienen varios bloques.
4. Alcanzas con frecuencia los límites del proveedor.
5. El tráfico llega en ráfagas.
6. Necesitas reintentos fiables.
7. Quieres escalar los workers de manera independiente de la API.

Si todas las solicitudes son pequeñas y terminan casi al instante, al principio puede que no haga falta una cola.

## **¿Cuándo deberías añadir varios proveedores?**

Tiene sentido admitir varios proveedores cuando existe un motivo concreto, como:

1. Se necesitan distintas voces.
2. A un proveedor le falta un idioma.
3. Necesitas más capacidad total.
4. Necesitas distintos niveles de precio.
5. Necesitas una alternativa para cargas de trabajo críticas.

Añadir proveedores solo por elegancia arquitectónica puede aumentar el mantenimiento sin aportar mucho valor.

## **¿Cuándo deberías almacenar en caché el resultado TTS?**

El almacenamiento en caché es especialmente valioso cuando:

1. Se genera con frecuencia contenido idéntico.
2. Las llamadas a los proveedores TTS son caras.
3. Algunos resultados son suficientemente deterministas como para reutilizarlos.
4. Los usuarios suelen reintentar o volver a abrir proyectos existentes.
5. Los proyectos grandes solo modifican unos pocos bloques cada vez.

Aunque no siempre se pueda reutilizar todo el audio, el almacenamiento en caché a nivel de bloque puede seguir generando ahorros considerables.

## **La producción TTS es un problema de orquestación**

El modelo TTS es solo un componente. Un sistema de producción debe coordinar:

**Usuarios + Trabajos + Colas + Workers + Proveedores + Audio + Almacenamiento + Facturación + Supervisión**

Esto explica por qué una demo TTS local puede crearse rápidamente, mientras que una plataforma TTS pública y fiable requiere mucho más trabajo de ingeniería. La complejidad reside en todo lo que rodea al modelo.

## **Reflexiones finales**

Una API de texto a voz para producción debería diseñarse desde el principio teniendo en cuenta los fallos, la concurrencia y el procesamiento de larga duración.

La arquitectura central es sencilla:

**Aceptar la solicitud → Validarla → Reutilizar resultados existentes cuando sea posible → Crear un trabajo → Poner el trabajo en cola → Generar voz → Reintentar los fallos recuperables → Almacenar el audio → Devolver el resultado.**

A medida que crece el tráfico, cobran cada vez más importancia las capas adicionales, como el enrutamiento de proveedores, las colas prioritarias, el procesamiento a nivel de bloque, el control de límites de solicitudes, el seguimiento de costes, los callbacks y la observabilidad.

La lección más importante es que generar voz suele ser la parte fácil. El verdadero reto de producción es crear un sistema capaz de generar voz de forma fiable para muchos usuarios, con distintos proveedores y manteniendo los costes y los fallos bajo control.
