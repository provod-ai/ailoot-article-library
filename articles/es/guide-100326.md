# ¿Qué es un router de LLM?

> Comprende el enrutamiento de modelos, los componentes de un router, las ventajas y desventajas de construirlo o adoptarlo y cuándo quizá no sea necesario.



## ¿Qué es un router de LLM y realmente necesitas uno?

Un enrutador de LLM se sitúa entre una aplicación y los endpoints de los modelos. Para cada solicitud de inferencia puede elegir el modelo, el proveedor que lo ofrece o ambos. Su política define cuándo probar otro endpoint tras un fallo.

El término está de moda, lo que significa que se está ampliando para abarcar cosas que no debería. Antes de evaluar cualquier router, o de construir uno, conviene precisar qué incluye realmente.

## Dos cosas diferentes reciben el mismo nombre

El **enrutamiento de modelos** elige el modelo que atenderá la solicitud. Para una clasificación rutinaria puede bastar un modelo pequeño, mientras que una síntesis compleja puede requerir uno más capaz. El **enrutamiento entre proveedores** permite mantener el modelo elegido y cambiar a otro endpoint compatible si el primer proveedor sufre una sobrecarga temporal.

El **enrutamiento de llamadas a herramientas** elige el servicio que ejecutará la llamada una vez que el agente ha elegido la herramienta. Una búsqueda web puede empezar en un índice local y pasar a otra API de búsqueda si necesita más cobertura. Los servicios de la cadena ejecutan la misma operación.

En ambos casos, la política ordena las opciones que cumplen los requisitos de la solicitud. La calidad de la respuesta del modelo puede ser difícil de estimar de antemano. Algunos resultados de herramientas se comprueban con más facilidad, por ejemplo si la extracción devolvió el texto del artículo. Una búsqueda con resultados todavía puede omitir lo que pidió el usuario.

Esta publicación trata ambos, porque comparten la misma anatomía.

## Qué hay realmente dentro de un router de LLM

Si quitamos el marketing, un router tiene cuatro componentes. Si un producto no puede mostrarte los cuatro, es un proxy con opiniones.

**Política.** Filtra primero las opciones por las capacidades que requiere la solicitud. Después ordénalas según la calidad esperada, el precio o la latencia. Una lista de prioridades fija puede bastar. Si usas un clasificador para elegir la categoría del modelo, mide qué mejora aporta.

**Señales de estado.** Registra la tasa de errores, los tiempos de espera agotados y los percentiles de latencia por endpoint. Define un tiempo máximo para cada intento, de modo que la llamada pueda continuar si el endpoint no responde. Usa las tendencias de varias solicitudes para decidir cuándo descartar temporalmente un endpoint degradado.

**Reglas de respaldo.** Define qué fallos permiten otro intento, como una sobrecarga temporal o un tiempo de espera agotado cuando sea seguro repetir la solicitud. Decide por separado qué hacer si la búsqueda devuelve HTTP 200 sin resultados. Limita los intentos y el tiempo total. Si vence el plazo del cliente, el resultado y cualquier cargo quedan por confirmar.

**Contabilidad.** Registra el modelo y el servicio que respondieron, la latencia y los datos de uso y cargos disponibles. Agrupa todos los intentos, incluidos los fallidos, bajo una misma solicitud. Separa el coste estimado de los cargos confirmados para comparar el coste de la cadena completa.

## ¿Construir o adoptar?

Un enrutador sencillo puede partir de una lista de endpoints compatibles, un plazo por intento, un plazo total, reglas de respaldo y un registro de intentos. Mantén la política en la aplicación mientras cubra la carga de trabajo.

Adóptalo cuando quieras las partes tediosas de construir y mantener: integraciones con proveedores que siguen los cambios de sus API, seguimiento del estado con valores predeterminados razonables, tablas de costes actualizadas y la infraestructura de transporte. Un servidor MCP puede ofrecer una interfaz única para la herramienta y decidir qué proveedor ejecuta la llamada.

Comprueba si puedes controlar las credenciales de los proveedores, exportar los registros de uso y cambiar de endpoint sin reescribir las llamadas. Al comparar un enrutador propio con uno alojado, incluye las tarifas del enrutador.

## Cuándo un router es excesivo

Una sección honesta, porque a veces la respuesta a la pregunta del título es no.

Un enrutador suele sobrar cuando un modelo de un solo proveedor atiende una función no crítica con poco tráfico. Con una factura de 40 dólares al mes, por ejemplo, compara el ahorro plausible con el coste de desarrollo y mantenimiento.

Para una integración pequeña puede bastar un proveedor de respaldo. Gestiona un error temporal concreto y prueba ese endpoint compatible dentro del plazo si es seguro repetir la solicitud.

Plantéate centralizar las reglas si varios proveedores atienden la misma carga, las caídas han afectado a usuarios, los costes medidos justifican el trabajo o la lógica de enrutamiento está repartida por la aplicación. Una política común facilita mantener y probar esas decisiones.

Empieza por enumerar los endpoints compatibles, el orden de uso y las condiciones para pasar al siguiente intento. Al principio puede bastar una lista fija. Añade un proveedor de respaldo cuando la carga de trabajo lo necesite.
