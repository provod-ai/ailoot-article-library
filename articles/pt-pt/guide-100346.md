# Arquitetura de API TTS: do texto ao áudio de produção

> Saiba como conceber uma API TTS de produção com filas, workers, cache, novas tentativas, encaminhamento entre fornecedores, armazenamento, limites de taxa e observabilidade.



Chamar uma API de conversão de texto em voz é fácil. Operá-la de forma fiável em produção já não é.

Um protótipo básico pode conter apenas três passos:

**Texto → Fornecedor TTS → MP3**

Isto pode funcionar bem ao testar alguns pedidos localmente. Quando chegam utilizadores reais, o sistema tem de lidar com tarefas simultâneas, limites de taxa do fornecedor, falhas de rede, tarefas longas de geração de áudio, pedidos duplicados, armazenamento, novas tentativas, quotas, vários fornecedores de vozes e utilizadores que atualizam a página enquanto o áudio ainda está a ser processado.

A arquitetura torna-se rapidamente mais complexa do que a própria chamada à API TTS. Um fluxo de produção mais realista é o seguinte:

**Cliente → API → Tarefa → Fila → Worker → Fornecedor TTS → Armazenamento/CDN → Resultado**

Este artigo explica como conceber essa arquitetura, porque existe cada componente e que problemas surgem habitualmente à medida que uma aplicação TTS ultrapassa a fase de simples demonstração.



## **O que tem de resolver uma API TTS de produção?**

O objetivo de um backend TTS de produção não é simplesmente gerar áudio. Tem de gerar áudio **de forma fiável, eficiente e previsível**.

Uma boa arquitetura deve responder a perguntas como:

1. O que acontece quando 100 utilizadores geram voz ao mesmo tempo?
2. O que acontece quando o fornecedor TTS devolve HTTP 429?
3. O que acontece quando o fornecedor TTS fica indisponível?
4. O que acontece quando uma tarefa de geração de áudio demora vários minutos?
5. O que acontece quando um utilizador envia o mesmo pedido duas vezes?
6. Como impedir que um utilizador consuma toda a quota disponível do fornecedor?
7. Onde deve ser armazenado o áudio gerado?
8. Como sabe o cliente quando terminou uma tarefa de longa duração?
9. Como repetir tarefas falhadas sem voltar a gerar áudio já criado com sucesso?
10. Como medir qual fornecedor é lento ou pouco fiável?

Estes são problemas de conceção de sistemas, não de síntese de voz.

## **O pedido básico à API TTS**

No nível mais simples, um pedido TTS pode conter:

1. Texto
2. Idioma
3. Voz
4. Modelo
5. Velocidade de fala
6. Formato de áudio
7. Instruções de voz opcionais

Por exemplo, conceptualmente:

**POST /tts**

O servidor recebe o pedido, chama um fornecedor TTS e devolve um ficheiro de áudio. Este modelo síncrono é fácil de compreender:

**Pedido HTTP → Fornecedor → Áudio → Resposta HTTP**

Para a geração de fala muito curta, isto pode ser aceitável. Os problemas começam quando a geração fica mais lenta, o tráfego aumenta ou um pedido contém muito texto.

## **Porque não devem as tarefas TTS longas depender de um único pedido HTTP**

Imagine que um utilizador envia texto suficiente para gerar uma locução de 30 minutos. Se a sua API mantiver o pedido HTTP original aberto até tudo terminar, podem correr mal várias coisas:

1. O navegador pode exceder o tempo limite.
2. Um proxy inverso pode fechar o pedido.
3. O servidor da aplicação pode reiniciar.
4. O fornecedor pode falhar temporariamente.
5. O utilizador pode fechar a página.
6. A ligação móvel pode cair.

O trabalho de TTS pode continuar a ser válido, mas a ligação que o iniciou já desapareceu. Normalmente, é melhor modelar as cargas de trabalho TTS de longa duração como **tarefas**.

O fluxo passa a ser:

**Cliente → Criar tarefa → Devolver ID da tarefa → Processar em segundo plano**

O cliente pode consultar o progresso mais tarde.

## **Passo 1: Aceitar e validar o pedido**

A camada da API deve fazer uma validação ligeira antes de enviar trabalho para o sistema de processamento. As verificações habituais incluem:

1. O texto está vazio?
2. O texto excede o tamanho permitido para o pedido?
3. A voz pedida existe?
4. O modelo selecionado suporta o idioma pedido?
5. O formato de áudio pedido é suportado?
6. O utilizador está autenticado?
7. O utilizador tem quota ou créditos suficientes?
8. O pedido é permitido pelas regras de limitação de taxa?

Os pedidos inválidos devem ser rejeitados antes de chegarem aos workers ou a fornecedores externos. Isto poupa recursos de infraestrutura e quota do fornecedor.

Para tarefas concorrentes, reserve atomicamente a quota ou os créditos aplicáveis antes da admissão e liquide ou liberte essa reserva uma única vez de acordo com o resultado real e a política de faturação.

## **Passo 2: Normalizar o pedido**

Antes do processamento, normalize o pedido para um formato interno previsível. Por exemplo:

1. Normalize os códigos de idioma.
2. Determine o ID real da voz.
3. Determine o fornecedor associado à voz selecionada.
4. Aplique a velocidade de fala predefinida.
5. Normalize os espaços em branco.
6. Selecione o formato de saída.
7. Determine a configuração do modelo.

Isto dá aos workers um contrato de entrada consistente. Também ajuda com o cache: idealmente, pedidos logicamente idênticos devem produzir a mesma chave de cache.



## **Passo 3: Verificar se o áudio já existe**

Gerar repetidamente o mesmo áudio é uma forma fácil de desperdiçar dinheiro num sistema TTS. Suponha que um utilizador envia várias vezes:

*«Bem-vindo à nossa aplicação.»*

com a mesma voz, modelo, velocidade e definições. Se o resultado for suficientemente determinístico para o seu caso de utilização, talvez não haja motivo para chamar o fornecedor sempre.

É possível derivar uma chave de cache de valores como:

1. Texto normalizado
2. ID da voz
3. Fornecedor
4. Modelo
5. Idioma
6. Velocidade
7. Formato de áudio
8. Estilo ou instruções de voz

Uma chave conceptual poderia ser:

**HASH(text + voice + model + speed + format + settings)**

Serialize todos os campos de geração de forma inequívoca e inclua na identidade da cache o âmbito adequado de tenant ou de acesso. Autorize a reutilização e o acesso ao resultado; partilhe entre tenants apenas quando expressamente permitido.

O fluxo do pedido passa a ser:

**Pedido → Verificação do cache → O áudio já existe?**

Se sim:

**Devolver o resultado existente**

Se não:

**Criar tarefa de geração**

### **Não use apenas o texto como chave de cache**

Normalmente, é incorreto usar apenas o texto como chave de cache. A mesma frase gerada com duas vozes diferentes não deve devolver o mesmo áudio. O mesmo se aplica ao modelo, à velocidade, ao idioma, ao formato e às definições de estilo.

A identidade do cache deve representar tudo o que possa alterar materialmente o resultado.

## **Passo 4: Criar uma tarefa persistente**

Antes de colocar o trabalho numa fila, guarde um registo da tarefa. Uma tarefa TTS pode conter:

1. ID da tarefa
2. ID do utilizador
3. Estado
4. Voz pedida
5. Fornecedor
6. Modelo
7. Contagem de caracteres
8. Hora de criação
9. Hora de início
10. Hora de conclusão
11. Número de tentativas
12. Progresso
13. Informações sobre erros
14. URL de saída

Um ciclo de vida simples dos estados poderia ser:

**Pendente → Em processamento → Concluída**

com estados de falha como:

**Pendente → Em processamento → Falhada**

Também poderá precisar de estados para tarefas em nova tentativa, canceladas, parcialmente concluídas ou expiradas.

A persistência do estado da tarefa é importante porque o sistema de processamento não deve depender da memória da aplicação. Se o contentor da API reiniciar, os utilizadores devem continuar a poder consultar as suas tarefas.

## **Passo 5: Enviar a tarefa para uma fila de mensagens**

A fila de mensagens separa a aceitação dos pedidos do processamento do áudio. Em vez de:

**API → Fornecedor TTS**

usa-se:

**API → Fila → Worker → Fornecedor TTS**

A API pode responder quase imediatamente com um identificador da tarefa, enquanto os workers processam os pedidos em segundo plano.

Use um outbox transacional ou recuperação durável para tarefas registadas mas não colocadas na fila e torne o processamento da fila idempotente, para que uma falha ou nova entrega não perca nem duplique trabalho.

### Porque são as filas tão úteis para TTS

As filas oferecem várias vantagens importantes:

1. Absorvem picos de tráfego.
2. Controlam a quantidade de trabalho executada em simultâneo.
3. Protegem as quotas dos fornecedores externos.
4. Facilitam as novas tentativas.
5. Permitem que as tarefas continuem depois de terminar o pedido HTTP original.
6. Permitem adicionar workers à medida que o tráfego cresce.

Isto é especialmente importante quando os fornecedores TTS impõem limites de pedidos por minuto, caracteres, tokens ou simultaneidade.



## **A fila também é um mecanismo de controlo de pressão**

Suponha que o seu fornecedor consegue processar em segurança 20 pedidos de cada vez, mas a sua API recebe 200 pedidos em simultâneo. Sem uma fila, poderá enviar os 200 pedidos diretamente ao fornecedor. O resultado provável é:

1. Erros de limite de taxa
2. Tempos limite excedidos
3. Utilização elevada de CPU
4. Utilização elevada de memória
5. Limitação de tráfego pelo fornecedor
6. Uma cascata de novas tentativas

Com uma fila, a API pode aceitar tarefas enquanto os workers as processam a um ritmo controlado. O sistema não tem de processar tudo imediatamente só porque os pedidos chegaram de imediato.

## **Passo 6: Processar tarefas com workers TTS**

Os workers tratam do fluxo de geração. Um worker pode:

1. Ler uma tarefa da fila.
2. Carregar a configuração da tarefa.
3. Dividir texto longo, se necessário.
4. Selecionar o fornecedor correto.
5. Chamar a API TTS.
6. Tratar falhas temporárias.
7. Transferir ou receber o áudio gerado.
8. Validar o resultado.
9. Carregar o resultado para o armazenamento.
10. Atualizar o estado da tarefa.

Os workers devem ter um grau de ausência de estado suficiente para que outro worker possa processar a tarefa se uma instância desaparecer.

## **Que nível de simultaneidade deve usar um worker?**

Mais simultaneidade não significa automaticamente maior capacidade de processamento. Aumentar a simultaneidade dos workers de forma demasiado agressiva pode causar:

1. Atingir os limites do fornecedor
2. Saturação da CPU
3. Pressão sobre a memória
4. Limites de rede
5. Limites de E/S do disco
6. Estrangulamentos no FFmpeg

As cargas de trabalho TTS podem envolver vários tipos de recursos. Uma chamada a uma API de voz remota pode depender sobretudo da rede, enquanto a conversão ou junção de áudio pode passar a depender da CPU. Por isso, um sistema de produção pode beneficiar de controlos de simultaneidade separados para diferentes fases.

Por exemplo:

**Simultaneidade de transferências: elevada**

**Simultaneidade do fornecedor TTS: depende do fornecedor**

**Simultaneidade do processamento de áudio: depende da CPU**

Isto costuma ser mais seguro do que usar um único valor elevado de simultaneidade em todo o lado.

## **Passo 7: Dividir texto longo em blocos menores**

Muitos fornecedores TTS impõem limites ao tamanho dos pedidos. Mesmo quando um fornecedor aceita uma entrada de texto muito extensa, dividir documentos longos pode continuar a ser útil.

Uma tarefa TTS longa pode transformar-se em:

**Documento → Bloco 1 + Bloco 2 + Bloco 3 + ... → TTS → Junção**

O processamento por blocos oferece várias vantagens:

1. Repetir apenas os blocos que falharam depois de confirmar que é seguro.
2. Processar blocos independentes em simultâneo.
3. Acompanhar o progresso.
4. Recuperar de falhas parciais.
5. Guardar blocos individualmente em cache.
6. Evitar limites de tamanho dos pedidos do fornecedor.

### **Não divida o texto às cegas**

Dividir a cada número fixo de caracteres pode prejudicar a qualidade da fala ao terminar um bloco a meio de uma frase. Uma lógica de divisão melhor pode considerar:

1. Limites dos parágrafos
2. Limites das frases
3. Pontuação
4. Limites de caracteres do fornecedor
5. Regras de escrita específicas do idioma

O objetivo é manter os blocos suficientemente pequenos para um processamento fiável, preservando o contexto natural da fala.

## **Passo 8: Encaminhar pedidos para o fornecedor TTS correto**

Uma aplicação de produção poderá vir a suportar vários fornecedores TTS. Fornecedores diferentes podem oferecer diferentes:

1. Idiomas
2. Catálogos de vozes
3. Preços
4. Níveis de qualidade
5. Limites de taxa
6. Latência
7. Controlos emocionais
8. Capacidades de streaming

Em vez de espalhar a lógica dos fornecedores pela aplicação, use uma camada de encaminhamento ou abstração. A arquitetura passa a ser:

**Worker → Router de voz/modelo → Adaptador do fornecedor → Fornecedor TTS**

Cada adaptador de fornecedor pode expor uma interface interna comum e, ao mesmo tempo, traduzir os pedidos para o formato esperado por esse fornecedor.

### **Evitar lógica específica de cada fornecedor em todo o lado**

Sem abstração, o código pode encher-se de condições como:

**Se o fornecedor for A, faça isto. Se o fornecedor for B, faça outra coisa.**

A manutenção torna-se difícil à medida que se adicionam fornecedores. Uma interface comum de fornecedores permite que o resto do sistema trabalhe com conceitos como:

1. Gerar fala
2. Obter vozes suportadas
3. Validar o pedido
4. Devolver áudio

Cada adaptador de fornecedor trata dos detalhes da implementação.

## **Alternativa de fornecedor: útil, mas nem sempre simples**

Pode ser tentador encaminhar automaticamente todos os pedidos falhados para outro fornecedor. Por vezes, isto funciona bem; outras vezes, não. Dois fornecedores podem não ter vozes equivalentes, e uma voz alternativa pode soar completamente diferente da original. Isso pode ser inaceitável num audiolivro longo ou num vídeo com várias cenas.

As decisões de alternativa devem considerar:

1. Se existe uma voz equivalente
2. Se a consistência é importante
3. Se a falha é temporária
4. A diferença de custo
5. O idioma de destino
6. As preferências do utilizador

A alternativa de fornecedor é uma ferramenta arquitetónica, não uma garantia de que todos os pedidos falhados devam ser imediatamente encaminhados para outro fornecedor.

## **Passo 9: Tratar corretamente os limites de taxa**

HTTP 429 é um dos problemas mais comuns em sistemas com utilização intensiva de APIs. HTTP 429 pode indicar um limite do fornecedor, incluindo a frequência ou o número de pedidos concorrentes. Consulte os detalhes do erro e as orientações de repetição do fornecedor, incluindo Retry-After quando fornecido, antes de decidir como e quando tentar novamente.

A resposta errada é:

**Repetir imediatamente o mais depressa possível.**

Isto costuma gerar ainda mais pedidos e agravar o problema. Uma abordagem melhor usa:

1. Limites de simultaneidade
2. Atraso exponencial
3. Aleatoriedade
4. Políticas de limites de taxa específicas do fornecedor
5. Atrasos na fila

Conceptualmente:

**429 → Esperar → Tentar novamente mais tarde**

em vez de:

**429 → Tentar novamente de imediato → 429 → Tentar novamente de imediato → 429**

## **Passo 10: Repetir apenas erros recuperáveis**

As novas tentativas são necessárias, mas nem todas as falhas devem ser repetidas. Uma classificação útil é:

| Tipo de erro                | Ação habitual                       |
|-----------------------------|-------------------------------------|
| 429 Too Many Requests       | Esperar e tentar novamente com atraso progressivo |
| 500 Internal Server Error   | Reconciliar o resultado original; repetir apenas se for seguro |
| 502 / 503 Temporary Failure | Reconciliar o resultado original antes de repetir ou mudar de fornecedor |
| Network Timeout             | Reconciliar o resultado original antes de repetir        |
| 400 Invalid Request         | Não repetir às cegas                |
| Unsupported Voice           | Corrigir o pedido ou o encaminhamento |
| Insufficient User Credits   | Falhar antes do processamento pelo fornecedor |

Um tempo limite, erro 5xx ou falha do worker pode deixar desconhecido o resultado no fornecedor. Antes de repetir ou mudar de fornecedor, reconcilie o ID da operação original, o estado e a utilização quando suportado, reutilize uma saída já aplicada e use a idempotência suportada pelo fornecedor. Preserve um resultado desconhecido em vez de repetir cegamente um pedido que pode ter sido concluído.

Uma política de novas tentativas também deve definir um número máximo de tentativas. Caso contrário, uma tarefa avariada pode permanecer no sistema para sempre.

## **Usar idempotência para evitar trabalho duplicado**

Os pedidos duplicados são comuns em aplicações reais. Um utilizador pode clicar duas vezes num botão, um frontend pode repetir o pedido depois de um tempo limite da rede, uma mensagem da fila pode ser entregue novamente ou um worker pode concluir a tarefa com sucesso, mas falhar antes de confirmar a mensagem.

Se o sistema assumir que todas as mensagens são únicas, poderá gerar e cobrar várias vezes pelo mesmo áudio. Idempotência significa que o processamento repetido do mesmo pedido lógico não deve criar vários resultados indesejados.

As técnicas possíveis incluem:

1. Chaves de idempotência
2. Identificadores únicos de tarefas
3. Hashes de cache
4. Restrições de unicidade na base de dados
5. Verificar o estado do bloco antes do processamento

Isto é especialmente importante quando estão envolvidos pagamentos, créditos ou custos do fornecedor.

## **Idempotência ao nível da tarefa vs. ao nível do bloco**

Para pedidos TTS curtos, a idempotência ao nível da tarefa pode ser suficiente. Para tarefas grandes com muitos blocos, a idempotência ao nível do bloco é muitas vezes mais útil.

Imagine uma tarefa de audiolivro com 500 blocos em que o bloco 487 falha. Não quer voltar a gerar os blocos 1 a 486.

**Blocos concluídos → Manter**

**Bloco falhado → Verificar o estado no fornecedor → Repetir apenas se for seguro**

Isto reduz significativamente os custos e o tempo de recuperação.

## **Passo 11: Validar o áudio gerado**

Uma resposta bem-sucedida do fornecedor nem sempre garante um resultado utilizável. Antes de marcar uma tarefa como concluída, poderá querer validar:

1. Foi devolvido um ficheiro de áudio?
2. O tamanho do ficheiro é superior a zero?
3. É possível descodificar o áudio?
4. A duração parece razoável?
5. O formato corresponde ao pedido?

Em fluxos de trabalho avançados, a validação da duração também pode detetar resultados suspeitos, como fala inesperadamente curta ou longa.

## **Passo 12: Armazenar o áudio fora do servidor da aplicação**

Em geral, o áudio gerado não deve depender do disco local de uma única instância de API ou worker. Se o contentor for recriado, o ficheiro pode desaparecer.

Uma arquitetura melhor é:

**Worker → Armazenamento de objetos → CDN → Utilizador**

O armazenamento de objetos separa os recursos gerados da infraestrutura de computação. Uma CDN pode depois servir áudio de forma eficiente a utilizadores em diferentes localizações.

Autorize o acesso a cada tarefa, estado e resultado de áudio. Mantenha o áudio armazenado privado e, quando necessário, use ligações com âmbito e validade limitados, em vez de tratar um URL como prova de acesso.

### O que deve ser armazenado na base de dados?

Normalmente, a base de dados não precisa de conter os bytes de áudio originais. Em vez disso, guarde metadados como:

1. Chave de armazenamento
2. URL do áudio
3. Duração
4. Tamanho do ficheiro
5. Formato
6. Fornecedor
7. Voz
8. Hora de geração

O áudio propriamente dito pode permanecer no armazenamento de objetos.

## **Considerar a expiração dos ficheiros**

Nem todos os ficheiros TTS gerados têm de existir para sempre. O armazenamento pode tornar-se dispendioso sem se notar quando se acumulam milhões de ficheiros de áudio temporários.

Considere políticas de retenção para:

1. Ficheiros gerados por convidados
2. Ficheiros temporários de processamento
3. Blocos intermédios
4. Projetos de utilizadores concluídos
5. Áudio reutilizável em cache

Os ficheiros intermédios podem muitas vezes ter períodos de retenção muito mais curtos do que os resultados finais dos utilizadores.

## **Passo 13: Devolver resultados com consulta periódica ou callbacks**

Quando um pedido TTS passa a ser assíncrono, o cliente precisa de uma forma de saber quando o processamento terminou. Existem dois padrões comuns.

### **Consulta periódica**

O cliente pergunta periodicamente:

**GET /jobs/{jobId}**

O servidor responde com algo semelhante a:

**status = processing**

E, mais tarde:

**status = completed, audioUrl = ...**

A consulta periódica é fácil de implementar e funciona bem em muitas aplicações Web.

### **Webhook ou callback**

Um cliente da API pode fornecer um URL de callback. Quando o processamento termina, o servidor envia automaticamente uma notificação.

O fluxo passa a ser:

**Criar tarefa → Devolver ID da tarefa → Processar → Notificar cliente**

Isto é útil quando sistemas externos processam tarefas grandes e não querem fazer consultas constantemente.

### Pode ser útil suportar ambos

Uma API de produção pode disponibilizar a consulta periódica do estado das tarefas como mecanismo universal e oferecer webhooks como conveniência opcional.

## **Acompanhar o progresso de tarefas grandes**

Numa tarefa TTS de 5 segundos, o progresso pode não ser importante. Num projeto de áudio de uma hora, é muito importante. Se uma tarefa contiver 1000 blocos, é possível estimar o progresso com base no trabalho concluído:

**Progresso = Blocos concluídos / Total de blocos**

Isto permite ao frontend apresentar:

1. Na fila
2. A processar 27%
3. A processar 83%
4. A finalizar o áudio
5. Concluído

Um indicador de progresso visível também reduz a possibilidade de os utilizadores pensarem que a aplicação bloqueou e enviarem a mesma tarefa novamente.

## **Passo 14: Proteger o sistema com limitação de taxa**

O seu fornecedor tem limites de taxa. A sua própria API também deve tê-los. A limitação de taxa pode ser aplicada por:

1. Utilizador
2. Chave de API
3. Endereço IP
4. Plano de subscrição
5. Endpoint
6. Fornecedor

Os limites de taxa protegem a infraestrutura e as quotas dos fornecedores. Também podem impedir que um utilizador intensivo ocupe todos os slots disponíveis dos workers.

## **As prioridades podem ser mais úteis do que uma única fila global**

À medida que o produto cresce, nem todas as tarefas têm de ter a mesma prioridade. Por exemplo:

1. Os pedidos TTS interativos e curtos podem precisar de respostas rápidas.
2. As tarefas de documentos grandes podem esperar um pouco mais.
3. Os utilizadores pagantes podem receber maior prioridade de processamento.
4. As tarefas de API em lote executadas em segundo plano podem usar capacidade de workers separada.

Uma arquitetura possível é:

**Fila de alta prioridade → Workers rápidos**

**Fila normal → Workers gerais**

**Fila em lote → Workers de processamento em lote**

A conceção exata depende dos padrões de tráfego, mas separar as cargas de trabalho pode impedir que algumas tarefas enormes atrasem todos os pedidos curtos.

## **Passo 15: Acompanhar a utilização e os custos**

Os diferentes fornecedores TTS podem cobrar de formas diferentes. Alguns cobram por carácter, outros por token ou pela duração do áudio gerado, e alguns usam modelos de preços mais complexos.

Um sistema de produção deve saber aproximadamente o que cada tarefa consome. As métricas úteis incluem:

1. Caracteres de entrada
2. Tokens de entrada
3. Duração gerada
4. Fornecedor
5. Modelo
6. Tipo de voz
7. Número de tentativas
8. Custo estimado do fornecedor
9. Créditos consumidos pelo utilizador

Sem acompanhar a utilização, torna-se difícil saber se uma funcionalidade é rentável ou se um fornecedor está a ser inesperadamente caro.

## **Cobrar apenas uma vez**

A faturação e as novas tentativas precisam de ser coordenadas com cuidado. Se o fornecedor falhar três vezes antes de ter sucesso, normalmente o utilizador não deve ser cobrado três vezes pelo mesmo pedido lógico de geração.

Se a tarefa inteira falhar definitivamente, o sistema precisa de uma política clara sobre se os créditos reservados são libertados ou reembolsados. A idempotência é muito importante neste caso. A faturação deve seguir o ciclo de vida da tarefa lógica, e não o número de tentativas internas.

## **Passo 16: Adicionar observabilidade antes de ser necessária**

Quando os utilizadores dizem que o TTS é lento, isso, por si só, não indica onde está o problema. A tarefa pode ter passado:

1. 20 segundos à espera na fila
2. 2 segundos dentro do worker
3. 30 segundos à espera do fornecedor
4. 10 segundos no processamento de áudio
5. 5 segundos a carregar o resultado

Sem medições, todas estas fases parecem um único pedido lento.

### **Métricas TTS úteis**

Acompanhe métricas como:

1. Latência dos pedidos à API
2. Profundidade da fila
3. Tempo de espera na fila
4. Número de workers ativos
5. Tempo de resposta do fornecedor
6. Taxa de sucesso da geração
7. Taxa de erros por fornecedor
8. Taxa de respostas 429
9. Taxa de novas tentativas
10. Duração do processamento de áudio
11. Duração do carregamento
12. Duração total da tarefa
13. Custo por tarefa

### **Medir os fornecedores separadamente**

Se suportar vários fornecedores, as métricas agregadas podem ocultar informações importantes. Por exemplo, a taxa global de sucesso pode ser 98%, enquanto a de um fornecedor desceu para 85%.

As métricas devem, por isso, permitir filtros por dimensões como:

1. Fornecedor
2. Modelo
3. Voz
4. Idioma
5. Worker
6. Região

## **Os registos devem incluir um ID da tarefa**

É mais fácil depurar sistemas distribuídos quando cada linha de registo relacionada com um pedido contém o mesmo identificador da tarefa. O mesmo ID pode surgir em:

1. Registos da API
2. Mensagens da fila
3. Registos dos workers
4. Chamadas ao fornecedor
5. Operações de armazenamento

Quando algo falha, pode pesquisar um ID da tarefa e reconstruir todo o percurso de execução.

## **Uma arquitetura TTS de produção prática**

Ao juntar os componentes, obtém-se um sistema mais completo:

**Cliente**

↓

**Gateway de API / API TTS**

↓

**Autenticação + Validação + Limite de taxa**

↓

**Verificação de cache / Idempotência**

↓

**Base de dados de tarefas**

↓

**Fila de mensagens**

↓

**Conjunto de workers TTS**

↓

**Router de voz / fornecedor**

↓

**Fornecedor TTS**

↓

**Validação / Processamento de áudio**

↓

**Armazenamento de objetos / CDN**

↓

**Tarefa concluída**

↓

**Resultado por consulta ou webhook**

Os componentes de suporte incluem:

1. Redis ou outro cache
2. Monitorização
3. Registo centralizado
4. Contabilização da utilização
5. Políticas de novas tentativas
6. Acompanhamento do estado dos fornecedores

## **O que acontece quando um fornecedor TTS fica indisponível?**

Os fornecedores externos acabarão por falhar, por isso uma arquitetura robusta parte do princípio de que isso pode acontecer. Quando as taxas de falha aumentam, o sistema pode:

1. Abrandar as novas tentativas.
2. Reduzir temporariamente a simultaneidade do fornecedor.
3. Pausar as filas afetadas.
4. Encaminhar pedidos elegíveis para outro fornecedor.
5. Informar os utilizadores de que o processamento está atrasado.

A pior estratégia costuma ser enviar cada vez mais tentativas a um fornecedor que já está a falhar.

## **Considere um disjuntor**

Um disjuntor pode interromper temporariamente os pedidos a um fornecedor depois de falhas repetidas. Conceptualmente:

**Fornecedor saudável → Pedidos permitidos**

**Falhas repetidas → Disjuntor aberto → Pedidos temporariamente bloqueados**

**Teste de recuperação bem-sucedido → Fornecedor novamente ativo**

Isto pode impedir que uma única dependência em falha consuma grande parte da capacidade dos workers.

## **E quanto ao TTS em streaming?**

Nem todas as cargas de trabalho TTS devem ser assíncronas. Os assistentes de voz e os sistemas de conversação em tempo real podem precisar de começar a reproduzir a fala antes de o áudio completo ter sido gerado.

Estes sistemas podem usar:

**Fluxo de texto → Fluxo TTS → Fragmentos de áudio → Reprodução no cliente**

As prioridades são diferentes:

1. Tempo até ao primeiro áudio
2. Latência de streaming
3. Interrupções
4. Estabilidade da ligação

Uma plataforma de produção pode, por isso, suportar dois percursos separados:

**TTS em tempo real → Percurso de streaming**

**TTS de longa duração → Fila e percurso de tarefas em segundo plano**

Tentar forçar ambas as cargas de trabalho a passar exatamente pela mesma arquitetura pode tornar o sistema desnecessariamente difícil de otimizar.

## **Arquitetura de API TTS vs. arquitetura de conversão de SRT em fala**

Uma API TTS normal começa geralmente com texto. Um sistema de conversão de SRT em fala começa com blocos de legendas que já pertencem a uma linha temporal.

O pipeline TTS básico pode ser:

**Texto → Fila → TTS → Áudio**

O fluxo SRT pode, por sua vez, ser:

**SRT → Analisar blocos → TTS → Medir duração → Ajustar temporização → Juntar áudio**

A versão SRT acrescenta vários problemas:

1. Preservação dos carimbos temporais
2. Duração de destino
3. Mapeamento de oradores
4. Comprimento da tradução
5. Sincronização do áudio
6. Novas tentativas ao nível do bloco

## **Erros comuns na arquitetura TTS**

### **1. Chamar diretamente o fornecedor em cada pedido HTTP**

É fácil no início, mas torna-se frágil para cargas de trabalho de longa duração.

### **2. Usar simultaneidade ilimitada**

Mais workers não ajudam se o fornecedor, a CPU ou a rede se tornar o estrangulamento.

### **3. Repetir todos os erros**

Os erros de validação permanentes não devem entrar em ciclos intermináveis de novas tentativas.

### **4. Voltar a gerar blocos concluídos com sucesso**

As tarefas grandes devem preservar o trabalho concluído e repetir apenas o que falhou.

### **5. Armazenar áudio importante apenas no disco local**

Os contentores de workers e os servidores temporários não devem tornar-se armazenamento permanente de recursos.

### **6. Ignorar os limites específicos dos fornecedores**

Cada fornecedor pode exigir uma estratégia diferente de simultaneidade e de limites de taxa.

### **7. Adicionar monitorização apenas depois de surgirem problemas**

Sem métricas, os problemas de desempenho tornam-se uma questão de adivinhação.

### **8. Misturar todas as cargas de trabalho numa única fila**

Um documento enorme pode atrasar dezenas de pequenos pedidos interativos se as cargas de trabalho não forem devidamente priorizadas.

## **Uma boa arquitetura pode começar de forma simples**

Não precisa de construir todos os componentes logo no primeiro dia. Uma aplicação TTS inicial pode começar com:

**API → Fornecedor → Armazenamento**

Depois, à medida que a utilização cresce:

**API → Fila → Worker → Fornecedor → Armazenamento**

E mais tarde:

**API → Cache → Filas prioritárias → Conjuntos de workers → Router de fornecedores → Vários fornecedores → Armazenamento/CDN → Webhooks + Monitorização**

A arquitetura deve crescer em resposta a estrangulamentos reais, não a uma complexidade teórica. O importante é escolher limites que permitam melhorias futuras.

## **Quando deve adicionar uma fila?**

Uma fila torna-se cada vez mais útil quando:

1. A geração pode demorar mais do que alguns segundos.
2. Os utilizadores enviam muito texto.
3. As tarefas incluem vários blocos.
4. Atinge regularmente os limites do fornecedor.
5. O tráfego chega em picos.
6. Precisa de novas tentativas fiáveis.
7. Quer escalar os workers independentemente da API.

Se todos os pedidos forem pequenos e terminarem quase instantaneamente, uma fila pode ser desnecessária no início.

## **Quando deve adicionar vários fornecedores?**

Faz sentido suportar vários fornecedores quando existe um motivo concreto, como:

1. Serem necessárias vozes diferentes.
2. Um fornecedor não disponibilizar um idioma.
3. Precisar de maior capacidade total.
4. Precisar de diferentes escalões de preços.
5. Precisar de uma alternativa para cargas de trabalho críticas.

Adicionar fornecedores apenas por elegância arquitetónica pode aumentar a manutenção sem criar muito valor.

## **Quando deve guardar resultados TTS em cache?**

O cache é especialmente valioso quando:

1. Se gera frequentemente conteúdo idêntico.
2. As chamadas ao fornecedor TTS são dispendiosas.
3. Alguns resultados são suficientemente determinísticos para serem reutilizados.
4. Os utilizadores repetem frequentemente pedidos ou reabrem projetos existentes.
5. Em projetos grandes, só se editam alguns blocos de cada vez.

Mesmo que nem sempre seja possível reutilizar o áudio completo, o cache ao nível do bloco pode gerar poupanças substanciais.

## **O TTS de produção é um problema de orquestração**

O modelo TTS é apenas um componente. Um sistema de produção tem de coordenar:

**Utilizadores + Tarefas + Filas + Workers + Fornecedores + Áudio + Armazenamento + Faturação + Monitorização**

Isto explica porque se pode criar rapidamente uma demonstração local de TTS, enquanto uma plataforma pública de TTS fiável exige muito mais trabalho de engenharia. A complexidade vem de tudo o que rodeia o modelo.

## **Considerações finais**

Uma API de conversão de texto em voz de produção deve ser concebida desde o início para lidar com falhas, simultaneidade e processamento de longa duração.

A arquitetura central é simples:

**Aceitar o pedido → Validá-lo → Reutilizar resultados existentes sempre que possível → Criar uma tarefa → Colocar o trabalho numa fila → Gerar a fala → Repetir falhas recuperáveis → Armazenar o áudio → Devolver o resultado.**

À medida que o tráfego cresce, tornam-se cada vez mais importantes camadas adicionais, como o encaminhamento entre fornecedores, filas prioritárias, processamento por blocos, controlo de limites de taxa, acompanhamento de custos, callbacks e observabilidade.

A lição mais importante é que gerar fala costuma ser a parte fácil. O verdadeiro desafio de produção é construir um sistema que gere fala de forma fiável para muitos utilizadores, através de muitos fornecedores, mantendo os custos e as falhas sob controlo.
