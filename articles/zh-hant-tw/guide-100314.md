# LLM 推論成本最佳化：降低 AI 基礎架構支出的策略

> LLM 推論成本與最佳化的實用指南，從批次處理與量化到比較 API 與自行託管的成本。



## 簡介

推論成本是 AI 產品持續發生的營運支出，並會隨使用量增加。成本取決於模型、工作負載、硬體及服務設定。最佳化技術包括量化、批次處理、快取和模型選擇。這些技術對成本和輸出品質的影響取決於特定工作負載，因此應進行測量。

## 推論成本的組成

推論成本受到運算、記憶體及資料傳輸影響。

### 運算

在標準自迴歸解碼中，每個步驟會為每個序列預測一個新 token。運算需求取決於模型大小、架構、精度及服務實作方式。

### 記憶體

模型權重會占用 GPU 記憶體，而鍵值（KV）快取會儲存作用中序列的中間注意力資料。快取需求會隨著上下文長度和並行請求數增加，因此可能成為服務處理能力的重要限制。

### 頻寬

自回歸生成會反覆透過記憶體傳輸模型權重和快取資料。記憶體頻寬可能限制吞吐量，而減少表示權重所需的位元組數，可以降低資料傳輸量。

## 批次與即時推論的取捨

批次處理會將請求分組，以提高硬體使用效率。即時處理則優先考量回應延遲。較大的批次可能提高吞吐量，但排隊可能增加延遲。適合的方式取決於請求到達模式和延遲需求。

對於聊天、語音和搜尋等應用，低延遲服務或小型動態批次可能較為合適。資料擴充、內容生成和大量分析等離線工作，通常可以容忍較大的批次。

## 模型量化：INT8、INT4 與 FP8

量化會減少表示模型權重所使用的位元數，因此可能降低記憶體用量和頻寬需求。量化對吞吐量、成本及模型品質的影響，會因硬體、模型和量化方法而異。部署前，請在預定工作負載上評估量化模型。

### FP8

FP8 使用 8 位元浮點表示法。其支援情況和品質影響取決於硬體和模型。對於評估低精度推論的團隊來說，這可以作為起點。

### INT8

INT8 使用 8 位元整數表示權重。SmoothQuant 和 LLM.int8() 等方法可用於量化模型。請針對選定的模型和部署方式測量品質與效能。

### INT4

INT4 使用 4 位元表示法，並可進一步降低記憶體需求。GPTQ 和 AWQ 等方法可用於權重量化。品質影響可能有所不同，因此請在相關任務上評估結果。

## 推測解碼

在一種常見的推測解碼方式中，較小的草稿模型提出 token，由目標模型驗證。效能取決於目標模型接受草稿 token 的頻率和實作方式。對於批次處理受限、對延遲敏感的工作負載，可以評估這種方法。

vLLM 和 TensorRT-LLM 等服務框架提供推測解碼實作。請在目標部署環境中測試吞吐量、延遲和輸出行為。

## KV 快取最佳化

KV 快取會儲存作用中序列的中間注意力值。其記憶體需求取決於模型架構、上下文長度和並行程度。快取管理可能會影響每個 GPU 能服務的請求數量。

### KV 快取量化

降低 KV 快取項目的精度可能減少記憶體用量。品質影響取決於模型和工作負載。服務框架的支援情況和設定選項各有不同。

### 前綴快取

如果多個請求共用相同前綴，服務系統可能會重複使用該前綴的快取運算結果。視實作方式和請求模式而定，這可以減少共用系統提示或上下文文件的重複運算。

### PagedAttention

PagedAttention 以區塊方式管理 KV 快取記憶體。vLLM 使用它來管理快取配置和共用。實際效果取決於服務工作負載和設定。

## 批次處理策略

批次處理策略會影響吞吐量和延遲。動態批次與連續批次是兩種常見的請求排程方式。將預填充和解碼分開是可與批次處理搭配的部署方式。

### 動態批次

動態批次會在一段時間內收集請求，或等到達到批次門檻，再將請求一併處理。這可能提高資源使用效率，但等待時間可能增加延遲。

### 連續批次（執行中批次）

連續批次可以在其他序列繼續執行時，移除已完成的序列並加入新序列。當輸出長度不一時，這可能減少閒置運算。vLLM、TensorRT-LLM 和 TGI 均提供連續批次實作。

### 解耦式服務

解耦式服務會將處理輸入上下文的預填充（prefill）與生成 token 的解碼（decode），分別配置在不同的 GPU 資源上。效能影響取決於工作負載和資源配置。

## 透過模型蒸餾降低成本

知識蒸餾會訓練較小的學生模型，讓它重現較大教師模型的特定行為。較小模型在執行預定任務時可能需要較少資源，但結果取決於訓練資料、目標和評估方式。

蒸餾會因任務而異：為摘要訓練的模型，在程式碼生成方面的表現可能不佳。團隊需要適用於特定任務的訓練資料和評估，才能判斷較小模型是否符合需求。請將訓練和部署成本，與目標用量下預期節省的服務成本進行比較。

## 如何比較推論成本

使用文字 API 時，依供應商的計費單位，將計費的輸入和輸出 token 用量分別乘上相應費率。適用時請採用快取或批次費率。自行託管時，將包含閒置時間的 GPU 容量成本與其他基礎設施和營運成本相加。將各自的總成本除以同一期間內可用的回應數，並在相同的品質與延遲目標下比較。

## 監控每次查詢成本

請一併追蹤每次查詢成本、延遲和品質。實用指標包括：

- **每次生成成本** — 計算成本除以生成次數，並按模型、使用情境和提示範本追蹤。
- **每個 token 成本** — 計算成本除以生成的輸出 token 數量。
- **GPU 使用率** — 生成期間 GPU 的活動情況，並根據工作負載脈絡解讀。
- **KV 快取命中率** — 可快取工作中，透過前綴快取處理而非重新計算的比例。

監控可能會揭露過大的提示、成本與任務不成比例的模型，以及導致 GPU 使用不足的批次設定。監測工具有助於找出最佳化機會。

## 最佳化策略組合：整合運用

可以結合多種技術，但其效果取決於工作負載，不應假設效果會相乘。請在目標工作負載上測量每項變更。

實用的評估順序如下：

1. 評估 FP8 等較低精度的權重。
2. 評估服務框架中的連續批次。
3. 測量重複前綴的前綴快取效益。
4. 評估 KV 快取精度選項。
5. 在批次處理受限時測試推測解碼。
6. 評估適用於高用量路徑的 INT4 權重。
7. 將特定任務的蒸餾模型與現有模型比較。

前幾個步驟可以使用服務框架功能和應用程式設定。蒸餾則需要投入訓練資源，並進行特定任務的評估。

## 結論

推論成本最佳化是一項持續進行的工作。量化、推測解碼、KV 快取管理、批次處理和蒸餾，都是可針對特定工作負載評估的選項。導入變更時，請測量成本、延遲和輸出品質。

硬體和服務框架持續演進。團隊若能測量推論效能和成本，就能在模型和使用模式改變時做出明智的選擇。
