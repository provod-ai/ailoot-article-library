# 什麼是 LLM 路由器？

> 了解模型路由、路由器的組成元件、建置與採用之間的取捨，以及哪些情況可能不需要路由器。



## 什麼是 LLM 路由器 — 你真的需要它嗎？

LLM 路由器位於應用程式與模型端點之間。對每個推論請求，它可以選擇模型、提供該模型的供應商，或同時選擇兩者。路由規則會決定何時在失敗後改試其他端點。

這個詞最近很受關注，因此也被延伸用來指稱一些不該涵蓋的事物。在評估或建置任何路由器之前，最好先明確了解它實際包含哪些內容。

## 兩種不同的東西，共用同一個名稱

**模型路由**會選擇處理請求的模型。一般分類可能只需要較小的模型，複雜的資訊統整則可能需要能力更強的模型。**供應商路由**可以保留選定的模型，在第一家供應商暫時過載時切換到其他相容端點。

**工具呼叫路由**是在代理程式選定工具後，決定由哪項服務執行呼叫。舉例來說，網頁搜尋可以先查本機索引，需要更廣的涵蓋範圍時再嘗試其他搜尋 API。這些服務執行的是同一種工具操作。

這兩種路由都會依規則排列符合請求需求的選項。模型回答的品質可能很難事先判斷。部分工具輸出比較容易檢查，例如擷取是否傳回文章正文。搜尋有結果也可能沒有找到使用者要的資訊。

本文會涵蓋兩者，因為它們的結構相同。

## LLM 路由器裡實際有哪些東西

去掉行銷話術後，路由器由四個元件組成。如果產品無法讓你看見這四個元件，它就只是一個自帶主張的代理伺服器。

**策略**。先篩出支援必要功能的端點，再依預期品質、價格或延遲排序。固定的優先順序也可能足夠。如果用分類器決定模型等級，應衡量它帶來的改善。

**運作狀態指標**。依端點追蹤錯誤率、逾時次數及延遲百分位數。為每次嘗試設定時間上限，讓端點未回應時也能繼續處理。觀察多次請求的趨勢，判斷何時要暫時略過狀態不佳的端點。

**備援規則**。定義哪些失敗可以再試，例如暫時過載，或在可安全重送請求時遇到逾時。對 HTTP 200 但沒有搜尋結果的回應，另訂處理規則。限制嘗試次數及總時間。用戶端逾時後，呼叫結果和是否收費仍未確定。

**費用紀錄**。記錄回應的模型與服務、延遲，以及可取得的用量和收費資料。將所有嘗試，包括失敗的嘗試，關聯到同一個原始請求。分開記錄估算成本與已確認的收費，才能比較整個呼叫鏈的成本。

## 自行建置還是採用現成方案？

簡單的路由器可以從相容端點清單、單次及整體時間上限、備援規則與嘗試紀錄開始。只要這些規則能滿足工作需求，就可以留在應用程式內。

當你需要那些建置和維護起來很繁瑣的部分時，就採用現成方案：能跟上 API 變動的供應商整合、預設值合理的健康狀態追蹤、持續更新的成本表，以及傳輸層的連線機制。 MCP 伺服器可以透過一個介面提供工具，並在內部選擇執行呼叫的供應商。

確認能否掌控各供應商的憑證、匯出用量紀錄，以及在不重寫呼叫的情況下更換端點。比較自行運作與託管方案的成本時，也要計入路由器本身的費用。

## 什麼情況下路由器只是大材小用

坦白說，因為標題問題的答案有時候是否定的。

如果低流量且非關鍵的流程只用一家供應商的一個模型，通常用不到路由器。舉例來說，月費帳單若是 40 美元，可以把可能省下的金額與開發和維護成本比較。

小型整合可能只需要一家備援供應商。處理特定的暫時性錯誤，並在可以安全重送請求時，於期限內嘗試相容的備援端點。

如果多家供應商處理同一項工作、服務中斷已影響使用者、實測成本足以支持開發，或路由邏輯分散在應用程式各處，可以將規則集中。共用策略讓維護與測試能在同一處進行。

先列出適用端點、嘗試次序與可以繼續下一次嘗試的條件。剛開始用固定清單可能就夠了。等工作確實需要時再加入備援。
