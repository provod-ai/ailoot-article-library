# 什麼是小型語言模型？10B 以下級別的優勢與限制

> 說明小型語言模型是什麼、為什麼參數規模介於 1 到 10 billion 的開放權重模型會用於正式環境，以及何時應選擇小型語言模型而非前沿模型。



本指南以約十億至一百億個參數作為小型語言模型（SLM）的參考範圍。部分模型開放權重。當效率與成本是主要考量時，這類模型可處理大量特定任務，或直接在裝置上執行推論。

訓練方法、推論經濟效益，以及日益成熟的開放權重生態系，讓小型模型的檢查點在許多任務上更具競爭力。本指南將探討模型大小如何影響正式環境中的 AI 工作負載。

## SLM 實際上是什麼

小型語言模型通常指參數介於 1 到 10 billion 之間的 Transformer 語言模型。低於 1 billion 的模型常稱為微型模型或裝置端語言模型。這些模型適用於手機、筆記型電腦的 CPU 和嵌入式硬體；量化方式與架構選擇會影響部署方式。超過 10 billion 之後，成本和延遲特性就會改變：以單一 GPU 在消費級設備上部署會更困難，微調成本也會增加，取捨隨之不同。

量化以較少的位元儲存權重。具有 700 億個參數的 Llama 經過 4 位元量化後，參數數量仍然相同。記憶體用量和輸出品質可能改變。

## 為何這個類別在此時出現

訓練方面的三項進展有助於縮小差距。首先，合成資料和精選的資料混合方式，讓小型模型能使用品質更高的訓練 token。

其次，指令微調和偏好最佳化將部分前沿模型能力移轉至較小型的模型。經過強力指令微調的小型基礎模型，在該微調所針對的任務上，使用體驗可以接近大得多的原始模型。第三，蒸餾會訓練小型模型模仿大型模型在各種提示上的表現，使其一開始便具備優勢；若只靠預訓練，原本需要更多 token 才能達到相同效果。

這些技術結合後，催生了開放權重小型模型，其每個參數所具備的能力，若依據 2022 年對縮放定律的預期，原本會令人難以置信。如今的 SLM 類別正是這些進展的成果。

## 模型概況

這些範例在 2026 年 5 月前已可取得。有些模型系列也包含較大的版本，請確認個別變體。

Microsoft 的 Phi 家族位於較小型的一端，其中 Phi-3 mini 和 Phi-3.5 mini 版本用於成本受限的推理工作負載。Google 的 [Gemma 2](https://blog.google/technology/developers/google-gemma-2/) 有 2B、9B 和 27B 版本。Meta 的 Llama 3.1 8B 與 Llama 3.2（1B 和 3B）涵蓋廣泛的開放權重 SLM 部署情境。

Mistral 7B 和 Ministral 3 (3B, 8B) 系列也是此領域的其他選項。Alibaba 的 [Qwen 2.5](https://qwenlm.github.io/blog/qwen2.5/) 有 0.5B、3B、7B 和 14B 版本。較小型的 [DeepSeek](https://www.deepseek.com/) 版本也在此市場之列。

主要前沿模型訓練者也會發布其架構的較小型版本。在不同規模間重用架構、資料管線和基礎設施，可讓小型模型以較低的運算成本，承襲大型同系列模型的優勢與弱點。這或許有助於解釋為何不同模型家族在推理、遵循指令、程式設計和部署廣度等方面各有差異。

## SLM 接近前沿水準時能做到什麼

SLM 和前沿模型之間的能力差距會因任務而異。在許多常見的正式環境任務中，差距可能小到足以讓成本成為重要考量。SLM 能處理分類（情緒、意圖、主題、內容審核、語言偵測）、結構化擷取（命名實體、鍵值配對，以及符合結構描述的 JSON 輸出）、中短篇文件摘要、熟悉主題的單輪問答，以及改寫、翻譯、擴寫、精簡和重新格式化等日常生成任務。

只要工具描述清楚，小型模型也能呼叫工具。請用實際請求驗證所選工具及輸出是否符合結構規格。工具數量或任務複雜度改變時，請重新測試。

程式碼生成是 SLM 也能派上用場的另一個領域。對於 Python、JavaScript、SQL 和 Java 等常見語言，以及 CRUD、銜接程式碼、指令碼、重構和簡單演算法等標準任務，經過程式設計微調的版本能產出可用結果。遇到新穎架構、多檔案變更和較不熟悉的邊緣案例時，與前沿程式設計模型的差距就會更明顯。

在這些任務中，當提示符合模型的訓練和指令微調分布時，表現通常較好。正式環境中的一個關鍵問題是：當提示偏離該分布時，模型仍能維持多強的穩健性。

## SLM 不擅長的事

能力上限確實存在，在某些任務上，與前沿模型的差距最大。若答案必須結合訓練期間未曾一同出現過的事實，新穎的多步驟推理可能會很困難。長期規劃同樣不易：需要在執行中間動作的同時，將計畫保留在工作記憶中的任務，可能會偏離方向或失去連貫性。從大型工具目錄中進行複雜的工具選擇時，若相似工具只有細微差異，就可能暴露出差距；結合了訓練期間鮮少共同出現主題的跨領域提示，也可能如此。

長上下文表現是另一個弱項。即使 SLM 宣稱支援 128K 或更長的上下文視窗，在整個視窗中的檢索準確度也可能比相同長度的前沿模型下降得更快，對完整上下文進行推理的能力也可能較弱。宣稱的上下文長度與有效上下文長度可能有所不同，而且模型規模越小，這項差距往往越大。對於長文件任務，前沿模型或使用較小視窗的檢索增強架構，可能以較低的總成本達到更好的表現。

當可依據的既有訓練分布有限時，能力差距特別明顯：開放式創作、公用訓練資料有限領域的專家問答，以及結合多項罕見事實的多步驟推理。在大量例行任務上，差距較不明顯，而這些任務占正式環境 AI 使用的大部分。

## 微調的優勢

若可取得權重，LoRA 和 QLoRA 能減少微調所需的記憶體。成本取決於模型、資料與硬體。請在自己的任務上驗證微調是否有用。

因此，SLM 級別不僅經濟，也具有策略價值。前沿模型訓練者可以發布其旗艦模型的較小型版本，讓正式環境團隊進一步專門化。SLM 成為可為開放權重生態系加入領域專屬價值的一層。成功的微調也能累積內部技術，而這些技術未必能順利移植到其他供應商的託管 API。

實務上的選擇很少是現成 SLM 能否匹敵前沿模型。更有用的問題是：經過微調的 SLM，能否針對團隊的資料和任務匹敵前沿模型？這種情況可能比現成模型之間的比較所暗示的更容易實現。

## 部署經濟效益

比較相同品質門檻下每筆合格結果的成本。使用代管 API 時，計入輸入、輸出和重試費用。自行託管時，計入硬體、電力與利用率。以相同輸入長度和並行請求數，測量產生第一個 token 的時間及整體延遲。

SLM 能在消費級 GPU、單主機伺服器、邊緣裝置和使用者的硬體上執行。這使裝置端推論、離線產品，以及無法實際託管前沿模型的嚴格延遲預算系統成為可能。GPU 推論容量規劃指南涵蓋硬體選擇及相關取捨。

## 何時使用 SLM

關鍵在於 SLM 經成本調整後的能力，是否符合特定工作負載。以下情況通常有利於使用 SLM：

- **大量且範圍明確的任務。** 在正式環境規模下執行分類、擷取、路由、簡單問答和摘要，可分攤微調成本，並將較低的推論成本轉化為營運節省。
- **對延遲敏感的迴圈內工作。** 語音代理、IDE 助理、即時分類，以及使用者必須等待模型回應的功能，都能受惠於較低延遲和較高吞吐量。
- **裝置端或離線部署。** 無法將資料傳送到其他地方，或網路存取不穩定的行動應用程式、桌面軟體和邊緣裝置，可能需要 SLM。
- **運用自有資料進行專門化。** 擁有已標記資料或領域專屬資料的團隊，可以微調 SLM 來反映這些專業特性。
- **成本受限的正式環境迴圈。** 多輪代理迴圈、大規模批次推論，以及其他每次呼叫成本會累積的模式，可能更適合使用 SLM。

以下情況通常不利於使用 SLM：

- **真正新穎的推理。** 困難的數學問題、複雜程式碼，以及在陌生領域中的多步驟規劃，都更適合採用訓練涵蓋範圍較廣的前沿模型。
- **重視上下文的長上下文任務。** SLM 的長上下文檢索可能不可靠。若答案取決於準確回想 50K 以上 token 的視窗內容，前沿模型或檢索架構可能表現更好。
- **要求品質的跨領域遷移。** 開放式寫作、跨領域專家問答和高階創作工作，都仰賴廣泛的訓練涵蓋範圍，而要在前沿規模以下達到同等水準可能更加困難。
- **提示未知的工作負載。** 若無法事先界定任務範圍，SLM 較小的穩健性餘裕可能構成風險。

## 實務上的意義

正式環境中的 AI 通常以前沿模型處理較難的問題，以 SLM 處理例行流量。有些工作負載只使用 SLM；另一些則透過路由層，將較簡單的請求送至 SLM，較困難的請求送至前沿模型。隨著小型模型持續進步，且正式環境團隊累積微調經驗，SLM 的使用比例可能會增加。

對工程團隊而言，能力已不再是模型選擇中唯一有意義的衡量面向。在能力可能比成本更重要的原型開發階段，前沿模型可以是實用的預設選項。經過微調的 SLM，或經過謹慎路由、混合使用 SLM 和前沿模型的配置，可能更適合正式環境，因為此時各工作負載經成本調整後的能力更為重要。若團隊不依工作負載衡量模型適配度，就可能為 SLM 足以處理的任務支付前沿模型的費用。

對於多模型部署，路由層可以依據能力需求分類傳入流量，將其送至符合需求的最小模型；若小型模型拒絕處理或未通過驗證，則改送較大型模型，並依類別追蹤成功率，以便調整門檻。為每個請求選擇適當規模的模型，正是模型路由的核心概念。團隊可以自行建置，也可以使用將模型路由作為服務提供的平台。

若團隊透過單一 API 評估多個 SLM 和前沿模型，可以比較各供應商的統一推論服務，並確認哪些模型支援一致的工具呼叫和結構化輸出行為。自行託管的決策也取決於達成目標吞吐量所需的 GPU 容量。
