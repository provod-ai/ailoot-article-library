# 什麼是 AI 推論？完整指南

> AI 推論是訓練完成的模型從新輸入產生輸出的執行階段。這一層會左右 AI 產品在正式環境中的成本、延遲與可靠性。



AI 推論是訓練完成的機器學習模型回應新輸入並產生輸出的過程。聊天機器人回答問題、搜尋系統傳回排序結果，或圖像模型生成圖片時，推論就是將儲存的模型權重轉換成使用者看到的回應的步驟。訓練建立模型；每當有人使用模型時，推論就會執行模型。

每一則聊天機器人的回覆、AI 程式碼補全，以及 AI 生成的搜尋摘要，都需要推論。模型只需訓練一次，但每次使用者提出請求時都會執行推論。因此，服務層的成本、延遲與可靠性都會影響 AI 產品的經濟效益。

## 推論的實際意義

推論是使用固定權重，在執行階段運行訓練完成的模型。訓練期間，模型會在學習範例時調整權重。訓練完成後，這些權重會儲存下來。推論會使用固定權重搭配新輸入，計算出輸出。推論期間模型本身不會改變；它執行的是唯讀的前向計算。

對大型語言模型而言，單次推論請求包含四個階段，每個階段都有各自的成本與延遲特性：

![LLM 推論流程：提示詞先經過 tokenization，再由平行的 prefill 階段處理，接著在自回歸解碼階段逐一生成 token，最後轉回文字]()

1. **Tokenization。** 輸入文字會切分成 token，也就是大約相當於一個音節或短詞的單位，再由模型詞彙表以數值表示。視 tokenizer 而定，一份 500 字的文件可能會轉成 600 到 800 個 token。Tokenization 會影響每次請求需要處理的 token 數量。
2. **Prefill。** Token 會在一次前向傳遞中通過模型各層，產生輸入的表示形式與第一個輸出 token。此階段受運算能力限制，且高度適合平行處理。
3. **自回歸解碼。** 模型會一次生成一個後續輸出 token，每個新 token 都以前面的 token 為條件。此階段主要受記憶體頻寬限制，而非運算能力；這有助於說明它為何會影響長篇回應的延遲。
4. **Detokenization。** 輸出 token 會轉回使用者看到的文字。

Prefill 快速且可平行處理；解碼則較慢且必須循序進行。這項差異是 LLM 推論基礎設施逐漸發展出不同於傳統機器學習模型服務的專門技術之一，也有助於理解推論效能：首個 token 的產生時間會受 prefill 影響，而每秒 token 數會受解碼影響。兩者需要不同的最佳化方式。

## 推論與訓練：簡要比較

訓練與推論在許多營運面向上有所不同。訓練會使用大型資料集並產生一組權重；推論則會反覆使用輸入並產生輸出。

| 面向 | 訓練 | 推論 |
|----|----|----|
| 頻率 | 每個模型版本一次 | 每次使用者請求一次 |
| 時長 | 數天至數個月 | 毫秒至數秒 |
| 硬體 | 緊密耦合、節點間頻寬高的 GPU 叢集 | 單一 GPU 或小型群組 |
| 成本型態 | 類似資本支出，預先支付 | 類似營運支出，與使用量成正比 |
| 成本承擔者 | 模型建立者 | 應用程式團隊 |
| 最佳化優先事項 | 模型品質 | 成本、延遲、可靠性 |

對使用基礎模型打造產品的團隊而言，訓練經濟效益通常由模型供應商負責，應用程式團隊則管理推論經濟效益。供應商、部署位置、批次處理、快取與備援等決策都會影響推論。

## 推論工作負載的類型

這個定義涵蓋訓練完成的模型產生輸出的所有情況，但各種工作負載的特性差異很大，因此將主要類別分開命名會更實用。

![五種 LLM 推論工作負載依回應延遲與每次請求成本排列的示意圖：embeddings 最便宜、最快，chat 居中，vision 和 reasoning 的速度逐漸變慢、成本逐漸提高，而 batch 則是可容忍延遲的折扣級別]()

**文字生成（chat）。** 常見的推論工作負載。輸入提示詞後，模型會逐一生成 token，並可將回應串流傳送給使用者。

**Reasoning 與 chain-of-thought。** 一種文字生成方式，模型會先產生一段內部推理，再給出使用者可見的回應。例子包括 OpenAI 的 o-series、Anthropic 的 extended thinking 模式，以及 DeepSeek-R1。

**Embeddings。** 文字輸入會產生固定長度的向量，而非生成文字。Embeddings 用於搜尋、檢索增強生成（RAG）、分群與去重。Embedding 推論支援許多現代搜尋與記憶體系統。

**Vision 與多模態。** 將圖像、影片畫格或音訊片段與文字結合後，產生文字或結構化輸出。延遲可能隨輸入解析度增加，成本則取決於輸入解碼後會轉成多少 token。相同的服務基礎設施可以處理這些工作負載，但其 tokenization 成本可能高於純文字。

**Batch 推論。** 對於不需要即時回應的流程，例如夜間資料擴充、離線評估或定期資料準備，batch 推論可以降低成本。

## 推論實際運行的位置

要以正式環境的品質執行推論，必須具備三個從 API 介面看不見、但會影響成本的基礎設施層。

**GPU 層。** 現代 LLM 需要記憶體容量與頻寬都很高的 GPU。大型模型會使用 NVIDIA H100 和 H200 顯示卡。較小的模型可在 A100 或 L40S 顯示卡上運行，非常小的模型則可使用消費級顯示卡。顯示卡選擇會影響吞吐量，以及不必分散到多張卡上即可服務的最小模型大小。GPU 記憶體容量規劃是 LLM 推論規劃的重要一環。

**Serving engine。** 僅能直接使用 GPU 並不足夠。有效率的模型服務需要一個 engine，也稱為 inference engine 或 inference server，用來管理 KV cache、批次處理並行請求，以及最佳化記憶體配置。常用 engine 包括 vLLM（開放原始碼、通用型）、TensorRT-LLM（NVIDIA 專用、高效能）和 SGLang（開放原始碼、針對結構化生成最佳化）。即使使用相同硬體，serving engine 也可能大幅影響吞吐量。

**區域部署。** 運算時間是推論延遲的主要來源，網路往返也會增加額外延遲。對面向使用者的工作負載而言，從靠近使用者的區域提供服務可能影響使用者感受到的回應速度。

對處理規模大且有專責基礎設施工程團隊的團隊而言，營運這套堆疊可能很合適。其他團隊可能會採購基礎設施，因此採購模式的選擇也很重要。

## 團隊在實務上如何使用推論

三種模式涵蓋許多正式環境中的推論設定。

![三種推論存取模式的架構比較：搭配 serving engine 與租用 GPU 的自託管堆疊、單一供應商的直接 API，以及透過單一 API 將請求路由至多家供應商的統一平台]()

**在租用 GPU 上自託管。** 團隊租用 GPU 容量，在 serving engine 上部署開放權重模型，並自行營運整套堆疊。這讓團隊能掌握控制權，在極高用量下也可能具有成本效益，但需要具備基礎設施專業知識，例如調校 KV cache、自動擴縮、容錯移轉與可觀測性。

**直接使用供應商 API。** 團隊呼叫單一供應商的 API，由供應商處理基礎設施。這是快速推出可用產品的方式，也是常見的起步方式。代價是集中風險，以及依賴單一價格結構。每次請求的成本、延遲與可靠性都取決於該供應商的服務。

**統一推論平台。** 團隊呼叫單一 API，由它將請求路由至多家底層供應商，並可能提供備援、可觀測性與成本控制。這種方式能保留直接使用供應商 API 的快速推出優勢，同時降低集中於單一供應商的風險，並支援依工作負載進行路由，例如簡單查詢使用成本較低的模型，複雜查詢則使用能力較強的模型。

| 存取模式 | 推出速度 | 營運負擔 | 在何種規模下具成本效益 | 集中風險 |
|----|----|----|----|----|
| 在租用 GPU 上自託管 | 慢 | 高（完整基礎設施堆疊） | 極高用量 | 無 |
| 直接使用供應商 API | 快 | 低 | 低至中等用量 | 高（單一供應商） |
| 統一推論平台 | 快 | 低 | 任何規模、混合工作負載 | 較低（多家供應商） |

如何選擇這些模式，取決於規模、工程能力，以及團隊願意直接管理多少供應商成本與可靠性差異。

## 推論為何是持續性的成本中心

推論成本會隨使用量增加，因此會影響 AI 產品的經濟效益。模型訓練成本固定，由供應商或負責訓練的團隊支付一次。每次推論請求都會消耗額外運算資源。十位使用者會產生十次推論；一百萬位使用者會產生一百萬次。實際上，AI 產品的單位經濟效益取決於推論的單位經濟效益。

![模型生命週期累計成本圖：訓練成本上升一次後便維持平穩；推論成本則從零開始，隨每次服務的請求逐漸增加，最終超過全部訓練成本]()

這種結構有兩項影響。第一，AI 功能的成本會隨使用量增加：採用率低的功能推論費用較低，採用率高的功能則會產生較高費用。第二，改變推論成本的架構選擇會隨使用量成長而累積影響。這些選擇包括模型選擇、提示詞設計、快取策略、供應商選擇與重試政策。每次請求成本降低 20%，使用量增加時邊際成本也會按相同比例降低。

每百萬 token 的常見成本指標描述的是特定請求情境；正式環境的工作負載可能與該情境不同。

## 多數推論指南未提及的內容

上述機制已有充分說明。在正式環境中跨供應商執行推論時，會出現一些營運上的考量：

- **最便宜的模型很少代表整個系統成本最低。** 每個 token 單價較低的模型若更常失敗、需要更長的提示詞才能達到相同品質，或導致更多次重試，則每個已完成任務的成本可能高於名義價格較高的模型。實際成本取決於整條請求路徑，因此成本最佳化也涉及架構，而不只是價格表。
- **輸出長度是重要的調整槓桿。** 解碼會同時影響推論延遲與輸出成本，因此縮短回應的提示詞變更可以同時改善兩者。
- **備援政策會影響價格。** 供應商可能發生服務中斷或速率限制。系統在這些期間選擇失敗、排入佇列或重新路由，都是經濟上的決策。備援鏈會影響可用性與成本。
- **環境可能在未察覺時改變。** 供應商可能調整價格、對部署進行量化，或在穩定名稱底下替換模型版本。推論設定若只調整一次、之後從未重新檢查，效能可能會隨時間下降。
- **基準測試排名不會決定實際處理請求的模型。** 排行榜有助於找出能力較強的模型，但要為特定請求選擇模型，也需要考量成本、延遲與可用性限制。

這些考量不屬於推論的定義，但可能大幅影響正式環境的成本。

## 推論引出的問題

理解推論只是起點。正式環境中的決策包括每個請求應由哪個模型處理、使用哪家供應商、價格為何，以及採用何種備援方式。選擇一個固定模型，等於為所有未來流量一次做出這些決策。另一種做法是根據請求需求，逐次決定使用哪個模型。

對於要將工作負載對應至模型的團隊而言，模型選擇涉及權衡工作負載需求、模型能力與成本。
