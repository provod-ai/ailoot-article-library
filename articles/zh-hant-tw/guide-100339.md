# Gemini：如何選擇應用程式或 API

> 選擇 Gemini 應用程式或 API、評估模型與估算使用成本的實用指南。



Gemini 可透過 Google 的消費者應用程式使用，也能透過 API 整合到軟體中。適合的起點取決於您想自行完成任務，還是為其他人建立可重複執行的工作流程。

## 從任務開始

對撰寫訊息或探索想法等一次性任務，互動式應用程式讓您提出問題並逐步完善回答。依賴結果之前請先檢查：即使回答流暢，也可能有錯誤、遺漏脈絡或錯誤引用來源。

當應用程式需要在工作流程中傳送輸入並處理輸出時，API 很有用。例如，客服應用程式可以摘要一則支援請求，交由人員審查。開發者必須處理指示、資料存取、失敗情況，以及結果的顯示或儲存方式。

應用程式和 API 是不同產品。不要假設其中一者的功能、限制、訂閱或資料設定會自動適用於另一者。請查看實際使用的產品和帳戶的文件與設定。

## 為任務選擇模型

先從幾個具代表性的範例開始，不要只憑名稱選模型。對摘要任務，納入短訊息、長訊息和資訊缺漏的案例。確定好的回答必須保留什麼、不得編造什麼，以及應有的長度。

如果任務涉及圖片、音訊或其他輸入，請確認特定模型及端點支援所需格式。支援的模態、上下文限制及可用性可能因模型而異，也可能改變。請在 Google 的 [Gemini API 文件](https://ai.google.dev/gemini-api/docs)中確認目前的選項與請求格式。

## 用實際的樣本估算成本

對 API 工作流程，記錄一小組具代表性請求使用的輸入和輸出量。將測得用量乘以適用的公開價格，計入每種適用的輸入及輸出類型。再估算工作流程的執行頻率，並為重試和回答長度變動預留空間。

將結果視為估算，而非保證的帳單。請查看目前的 [Gemini API 價格](https://ai.google.dev/gemini-api/docs/pricing)、帳戶配額與計費設定。應用程式訂閱與 API 使用可能適用不同條款。

## 擴大規模前先評估

將結果與人工審查的範例比較。逐一對照輸入檢查回答中的事實，並檢查要求的格式及任務專屬規則。納入困難案例，以及模型應拒絕或轉交人員的案例。看似有效的回答不一定正確。

追蹤失敗情況，每次只修改工作流程的一個部分：指示、輸入準備、模型或輸出驗證。變更後重複相同的測試集。若模型或輸入資料的類型改變，應重新評估結果，不要假設先前評估仍然適用。

## 有意識地處理資料與失敗

只傳送任務所需的資料，並在使用敏感資訊前檢查相關產品的資料處理設定。應用程式根據輸出執行動作之前，先驗證輸出。規劃如何處理頻率限制、逾時和不完整結果；顯示可採取後續行動的錯誤訊息，或將案例送交審查，不要默默把失敗視為任務完成。

對可能觸發外部動作的請求，保留操作紀錄並在重試前檢查狀態。傳輸途中遺失回答並不代表動作失敗。
