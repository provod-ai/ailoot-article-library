# LLM 作為評審：完整指南

> **重點摘要 —** LLM 作為評審，是指使用語言模型依照書面評分規準為另一個模型的輸出評分，以取代人類評分者（或與其搭配使用）。正式環境評估請採用搭配明確評分規準的單一答案評分；比較模型版本時請使用成對比較；絕不要信任未曾以帶有標註的黃金資料集進行測量的評審模型。

## 「LLM 作為評審」實際上是什麼意思

LLM 評審是透過提示詞呼叫的模型，提示詞要求它評估某項內容，通常是另一個模型的回應。它會回傳分數、標籤或偏好。整個架構就是如此。所有值得關注的部分都在提示詞、評分規準，以及你如何衡量評審的判斷是否符合實際情況。

它之所以普及，原因在於營運考量，而非哲學理念。只靠人工的評估流程難以擴大規模。取捨之處在於，評審模型也會帶有自己的偏誤，而且與人類評分者不同，這些偏誤具有系統性。

## LLM 評審如何為輸出評分

評分模式有三種，選擇哪一種會改變你的評估能告訴你什麼、不能告訴你什麼。

- ‍**成對比較**會要求評審選出兩個回應中較好的一個。當你要對兩個模型版本或兩個提示詞進行 A/B 測試時，請使用成對比較。若你需要絕對品質門檻，就不要使用，因為成對比較分數沒有最低品質基準：回應 B 可能在每次比較中都勝出，卻仍然無法使用。**‍**
- **搭配評分規準的單一答案評分**會要求評審依據明確標準評估一個回應。這是正式環境應採用的模式，因為每個回應都會依相同標準獲得分數，而你可以據此設定部署門檻（「若在金絲雀測試集上通過忠實度標準，就發布」）。選擇能呈現你在意差異的最低精細度量尺：如果問題是「模型有沒有違反評分規準」，就用二元的通過／不通過；如果失敗程度會影響分類處理，就用三點量尺（不通過／部分通過／通過）；只有在確實需要更高解析度，且有黃金資料集資料可驗證評審能正確使用該量尺時，才使用 1 到 5 或 1 到 10。過於細緻的量尺會誘使評審捏造無法辯護的差異，產生的雜訊會淹沒你想測量的訊號。評分規準的品質比量尺選擇更重要。含糊的評分規準（「請將有用程度評為 1 到 5 分」）只會產生沒有資訊量的數字。以主張為單位的評分規準（「只要有任何事實主張未獲取回的段落直接支持，就評 0 分」）則會產生可供採取行動的數字。評估需求改變時，應重新檢視評分規準。**‍**
- **以參考答案為基準的評分**會提供一個已知的良好答案給評審，並詢問候選答案與它有多接近。這是最接近 BLEU 和 ROUGE 等傳統 NLP 指標的方式，但採用語意而非 n-gram 重疊進行比較。它適用於輸出受限的任務（翻譯、與黃金摘要比較的摘要評估、結構化資料擷取）。但對開放式任務就不適用，因為通常有許多可接受的答案，而評審會懲罰內容良好但表達不同的回應。

實務上，多數正式環境設定會針對每個標準（忠實度、相關性和格式遵循）使用單一答案評分，並且只在開發期間使用成對比較來挑選候選提示詞。

## 何時適合使用 LLM 評審

LLM 評審適用於判斷本質上是依照明確評分規準進行的閱讀理解問題。例如：「這個回應是否包含任何未獲取回脈絡支持的事實主張？」這是閱讀理解問題。「在規格要求拒答的情況下，這個回應是否拒絕回答？」也是如此。評審模型必須擷取主張、找出支持該主張的段落（或指出沒有相關段落），並給出判斷。最前沿的模型很擅長處理這類任務。

如果任務需要評審知道提示詞無法涵蓋的資訊，效果就較差。「這個回應有趣嗎？」每個模型都會回答，但答案反映的是評審模型的既有傾向，而不是讀者的看法。「這段程式碼是否符合 Rust 慣例？」則要求評審模型具備與你團隊相同的慣例知識，而它很可能沒有。對於這些任務，應把評審視為眾多訊號之一，而非絕對標準。

若漏掉失敗的代價很高，而且失敗模式罕見，LLM 評審甚至會造成實際傷害。評審可能漏掉失敗；當漏掉問題的後果重大時，這點尤其重要。在這些情況下，評審只是初步篩選工具（減少人工審查人員要檢視的案例數量），不是最後定論。

## 實作範例：用 40 行程式碼建立忠實度評審

最簡單而實用的評審，是用單一答案忠實度評分規準評估 RAG 回應。以下是使用 OpenAI Python SDK 的範例：

```

from openai import OpenAI
from pydantic import BaseModel

client = OpenAI()

JUDGE_PROMPT = """You are evaluating whether an assistant's response is faithful
to a retrieved context passage. Faithful means every factual claim in the response
is directly and explicitly supported by the context. A claim is unfaithful if it
is added, modified, or drawn from outside the context.

Steps:
1. Enumerate every factual claim in the response (numbers, rules, entity names,
   negations, comparisons).
2. For each claim, locate the specific sentence in the context that supports it.
3. If any claim has no direct support, the response is unfaithful.
4. Truncated or cut-off context counts as zero support for whatever follows.

Return JSON: {{"verdict": "faithful" | "unfaithful", "reason": ""}}.

CONTEXT:
{context}

RESPONSE:
{response}
"""

class Verdict(BaseModel):
    verdict: str
    reason: str

def judge(context: str, response: str) -> Verdict:
    completion = client.beta.chat.completions.parse(
        model="gpt-4o-2024-11-20",
        messages=[{"role": "user",
                   "content": JUDGE_PROMPT.format(context=context, response=response)}],
        response_format=Verdict,
        temperature=0.0,
    )
    return completion.choices[0].message.parsed
  
```

這個提示詞要求評審在評估之前先列出主張，進行以主張為單位的檢查。檢索流程會在區塊邊界截斷內容，而若不加以處理，評審會把不完整的句子當成完整支持，因此範例明確處理遭截斷的脈絡。由於二元分類任務使用非零溫度會引入無法解讀的變異，因此溫度設為零。

這樣已足以執行，但還不足以發布。接下來兩節會說明如何把可運作的範例變成可部署的評審：先寫好提示詞，再衡量它是否真的與人類評估者的判斷一致。

## 撰寫評審提示詞與評分規準

在 LLM-as-a-judge 設定中，大部分的實際成效都來自評審提示詞。模型由你的供應商固定，評分量尺由你的評分規準設計固定，黃金資料集則由你的領域固定。在拿評審與已標註範例比較時，提示詞是你可以反覆調整的部分。

有效的評審提示詞有四個要素。第一，以領域使用的詞彙定義評估標準，而非使用通用 ML 術語（「忠於取得的脈絡」是符合領域的定義；「高品質」則不是）。第二，提供明確的推理架構，指示評審在評分前列出個別主張、條件或工具呼叫（這會讓評審依照明確的檢查順序處理）。第三，提供把推理結果對應到量尺的評分規則，例如「若列出的任何主張未獲取回的脈絡直接支持，就評 0 分」，而不是「自行判斷」。第四，加入處理正式環境常見邊界案例的條款：脈絡遭截斷、檢索結果為空、部分回答，以及拒答。

提示詞中不應放入的是一長串「確保你的答案有用、誠實且無害」之類的內容。通用指示會被忽略；具體的主張層級規則則會被遵循。另一個應避免的做法是過度指定判定格式；如果模型必須先產生冗長而有結構的理由才能給分，你就得為不會閱讀的 token 付費。

## 讓直覺式評審不可靠的偏誤

多種偏誤都可能影響 LLM 評審；設計評估時應將它們納入考量。

- ‍**位置偏誤**是指在成對比較中，傾向偏好最先（有時是最後）出現的回應。解決方法是以兩種順序評估每組比較，只計入判斷一致的案例。這需要以兩種順序評分比較結果。**‍**
- **冗長偏誤**是指傾向偏好較長的回應。即使長度不是評分規準的一項標準，較長的回應仍可能更受青睞。如果你的評分規準沒有明訂「在正確性相當的情況下，簡潔的回應得分應等於或高於冗長的回應」，評審就會暗中以長度為最佳化目標。緩解方式是在評分規準中明確規定長度中立。**‍**
- **自我偏好偏誤**是指評審傾向偏好與自身所屬模型家族相同的模型輸出。若比較中包含同一模型家族的輸出，就不要使用該家族的模型擔任評審。請使用第三個模型作為評審，或針對該項比較使用人類評分者。

其他可能的問題還包括情緒偏誤和諂媚偏誤。用於校準的已標註黃金資料集應包含相關失敗模式。

## 以帶有標註的黃金資料集校準評審

正式部署前，應使用帶有標註的黃金資料集檢查評審提示詞。部署前的檢查方式就是校準：使用帶有標註的黃金資料集執行評審，衡量其判斷與人類標籤之間的差距，並反覆調整提示詞，直到差距縮小。

校準循環有三項輸入：取自評估分布的帶標註黃金資料集；記錄相關一致性和錯誤指標的基準執行；以及根據評審與標籤不一致的範例修改提示詞的最佳化步驟。提示詞或評估分布改變時，請重新校準。

整體準確率會掩蓋各類別的召回率。即使準確率很高，Kappa 值偏低也可能表示一致程度接近隨機。Kappa 值越高，代表超越隨機的一致程度越高。評估評審時，請報告準確率以外的指標。

## 建立黃金資料集

校準有賴黃金資料集，而黃金資料集並非預設就存在。建立黃金資料集是必要的先決步驟，它決定了後續工作究竟是在衡量真實事物，還是在衡量雜訊。

黃金資料集是由領域專家標註的一組輸入輸出配對，其標籤是你希望評審產生的判斷。黃金資料集要能成為評估的重要依據，必須具備三項特性。它必須取自實際評估分布：使用真實查詢、真實取得的脈絡和真實代理程式回應，而不是使用對資料集編寫者來說看似合理的合成範例。它必須涵蓋各種失敗類別；若 100 個範例全都忠實，便無法得知評審能否抓出不忠實的內容，而這正是唯一重要的失敗類別。使用前還必須測量黃金資料集上的評分者間一致性；若領域專家經常對標籤意見不一，請在校準前釐清評分規準，以免根據雜訊而非失敗模式進行最佳化。

為黃金資料集產生查詢和合成但逼真的答案，本身就是一項工程問題。目前已有一些框架能從來源文件產生這些內容，而框架間的差異會影響最終黃金資料集能揭露哪些類型的失敗。 

## 評審與人類的一致性取決於任務

LLM 評審與人類評估者之間的一致性會因任務而異，且有幾項差異值得注意。

與評估者可能意見不一的開放式任務相比，有可驗證結果的封閉式任務更容易解讀一致性。評估評審時，不能脫離人類評估者在底層任務上的一致程度。

第二，一致性不等於對齊。評審整體上看似準確，卻可能漏掉重要的失敗類別（例如，將沒有支持的回應判定為忠實並予以通過）。整體數字會讓評審顯得過於出色；是否值得發布，應看各類別的召回率。前面的校準章節就是用來解決這個問題：同時測量兩者，針對失敗調整提示詞，然後重複流程。

第三，一致性指標的結果取決於使用哪種指標。在通過範例占多數、失敗案例很少的不平衡黃金資料集上回報原始準確率，會讓評審顯得過於出色。Cohen's Kappa 會調整隨機一致性的影響，因此比準確率更難粉飾。看似準確率很高但 Kappa 偏低，可能表示一致程度接近隨機。連續分數適合使用 Pearson 相關；若你只相信排序而非絕對值，Spearman 相關會更可靠。

在正式環境的流程中，請使用帶有標註的黃金資料集進行測量，並報告一種以上適用的一致性或錯誤指標。

何時只使用 LLM 評審、何時將它用作篩出待標記子集交由人類審查的初步篩選工具，以及何時略過評審而只使用人工判斷，取決於三個變數：漏掉失敗的代價、評估數量，以及評估分布變動的速率。

## 從範例到正式環境：接上評審

本文前面介紹的 40 行範例，足以在 Python REPL 中評估一個回應。為每個正式環境回應都加上評審（或在 CI 中對每個提取要求執行評審），則是另一項工程問題。

在大規模運作時，需要處理的工作並不炫目。將請求批次處理，避免評審推論占用大部分端到端延遲。為評審回傳格式錯誤的 JSON、超過速率限制或逾時的情況處理重試。以結構化方式記錄判斷和推理軌跡，方便日後診斷特定案例為何被標記。當部署之間在金絲雀黃金資料集上的對齊度下降時，觸發回歸偵測。像管理應用程式程式碼一樣對評審提示詞進行版本控管，才能將對齊度變化歸因於特定提示詞修改。並與 CI 系統整合，讓評審執行成為部署門檻的一部分，而不是在時間壓力下由人員容易忘記的手動檢查。

這些工作在概念上都不難，但每一項都需要投入時間，而實作順序會影響你最先遇到哪些正式環境故障。缺乏提示詞版本控管時，對齊度改變後就更難找出回歸的原因。

## 何時不該使用 LLM 評審

有三種情況不應使用評審，但團隊仍常常這麼做。

如果任務有確定性的正確性檢查，就不要使用評審。SQL 查詢等價性、JSON schema 驗證、正規表示式比對、完全相同字串比較，以及工具呼叫參數比對，都是已解決的問題。對這些任務加上 LLM 評審，只會增加延遲和成本，也會讓一個有確定答案的問題多出非零的判錯機率。請執行確定性檢查，不符合時立即判定失敗，只有真正需要自然語言推理的部分才呼叫評審。

如果你尚未建立帶有標註的黃金資料集，就不要在正式環境使用評審。評審會給你一個數字；沒有真實標準，你無法判斷這個數字是否有意義。黃金資料集應代表實際評估任務，並涵蓋重要的失敗案例。

如果漏掉失敗的代價高於人工審查的成本，就不要把評審當成最終門檻。應將它用作篩選工具，減少人類需要檢視的案例數量。在受監管領域中，部署沒有人工介入的評審是另一項決策，應讓法務與合規部門參與並明確作出決定，而不是因為評審剛好在開發集上得分很高，就默默採用。

評審是工具，不是判決。它能抓出原本可能被你發布的失敗，就值得保留；一旦你不再衡量它是否仍能做到這點，它就不再值得保留。
