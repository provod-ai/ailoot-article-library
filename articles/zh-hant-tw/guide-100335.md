# 使用 LLM 分類文字

> 實用指南：使用 LLM 分類文字、選擇標籤、審查建議的變更並檢查結果。



語言模型可以為每個項目套用一組標籤來分類文字。本指南說明如何定義標籤、處理不確定的情況，以及衡量結果是否有用。

## 定義要做的決策

從有實際用途的問題開始。例如，客服團隊可以將訊息分成 `billing`、`technical` 和 `other`，以便送到正確的佇列。決定每則訊息需要一個標籤，還是可以有多個標籤。用範例說明每個標籤，包括看似相近卻屬於不同類別的情況。

為不符合既有分類的項目保留 `other` 或送交審查的選項。強迫選擇可能讓報告看起來整齊，卻掩蓋分類架構不佳的問題。對會影響人或造成重大後果的決策，應保留人工參與。

## 要求可預測的結果

向模型提供文字、標籤定義及所需的輸出格式。將待分類文字視為資料，而不是給模型的指令。例如，寫著「忽略標籤」的訊息仍是待分類的項目，不應改變任務。

結果可能如下：

```json
{"label":"billing","reason":"這則訊息詢問發票相關問題。"}
```

這是說明用的結果，並非模型的實際回答。使用輸出前，請檢查它能否解析、是否包含預期欄位，以及是否使用允許的標籤。格式有效本身並不代表分類正確。各模型對受結構描述約束之輸出的支援程度不同；請查閱所用模型和 API 的文件。

## 改善標籤集合

先使用數量容易管理的類別，並檢查被歸入 `other` 或反覆引起分歧的範例。這些範例可能顯示缺少類別、定義不清，或兩個標籤互相重疊。使用具代表性的範例提出修改，並在廣泛套用前請審查人員核准新定義。

模型也可以在實驗中建議新標籤和類別合併。標記必須保持區分的受保護類別，並在更新分類架構前，逐一檢查所有提議是否符合這些限制。

如果兩個類別看似相近，合併前先比較它們支援哪些決策。例如，付款失敗和退款請求都與金錢有關，但可能需要不同處理方式。保留對工作流程有意義的區別，並為每次分類架構變更記錄版本。

## 擴大規模前先檢查效能

建立反映實際訊息組成的樣本，包含罕見與模糊的情況。請人員使用相同定義為樣本標記、解決分歧，並保存達成共識的標籤作為參考。將模型結果與這些標籤比較，檢查每個類別的錯誤；整體準確率可能掩蓋表現不佳的類別。

在獨立的評估資料集上測試提示、模型或分類架構的變更。持續監測結果，因為輸入文字的用語和組成可能隨時間改變。將不確定或無效的結果送交審查，不要默默指派標籤。

## 保護輸入並規劃工作流程

只傳送任務所需的資訊，並依照組織規定處理敏感紀錄。處理大量資料時，先測試一小批具代表性的項目、記錄失敗情況，並規劃如何在不遺失或重複項目的情況下繼續處理。增加處理量之前，先測量實際工作流程的時間和成本。

目標不只是產生標籤，更是建立可重複執行的決策流程，讓定義、例外和錯誤都能接受檢視。

更多資訊請參閱 [OpenAI 結構化輸出文件](https://platform.openai.com/docs/guides/structured-outputs)及[評估最佳實務](https://platform.openai.com/docs/guides/evaluation-best-practices)。
