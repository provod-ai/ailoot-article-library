# LLM 推論的三難困境：吞吐量、延遲、成本

> 一份實用指南，說明如何在 LLM 推論中平衡吞吐量、延遲與成本，並涵蓋影響部署取捨的硬體、模型與排程選擇。



擴充傳統網路服務通常會在無狀態微服務前方放置負載平衡器，並隨著流量成長增加 CPU 執行個體。大型語言模型改變了這種做法，因為推論具有狀態，可能受限於記憶體頻寬，且仰賴實體硬體互連。擴充 LLM 推論涉及多維度的最佳化問題。

## 經典的三難困境

提高吞吐量可能會增加延遲。降低延遲可能會增加 GPU 成本。最佳化成本可能需要在另外兩個面向之一做出妥協。

吞吐量、延遲與成本之間的這種張力，是專用 LLM 代管服務的核心工程挑戰。了解這點有助於團隊在考量經濟效益與基礎架構預算的同時擴充規模。

本指南將說明這些取捨、推論成本的不同面向、影響成本的選擇，以及硬體選擇與效能基準測試如何協助揭示成本曲面。也會探討何時應以吞吐量或延遲為最佳化目標，以及相關取捨。

## LLM 推論中的「成本」究竟是什麼？

在標準網路代管中，通常會隨著流量增加而增添更多伺服器，成本也隨之提高。在 LLM 代管中，成本是多維度的指標。推論成本通常以**每百萬個 token 的美元金額**表示，但在專用基礎架構上提供 LLM 服務的成本至少包含四個面向。

### 資本成本（CapEx）：支付整個節點的費用

這是硬體成本。由於 GPU 透過 NVLink 等高速互連連接，容量可能必須以節點為單位購買。例如，即使 70B 模型只需要四個 GPU，配備 8 個 H100 GPU 的節點仍可能必須整台購買。模型可能只使用叢集部分容量，但成本仍按完整容量計算。

### 營運成本（OpEx）：電力與雲端成本

擁有硬體會持續產生電力與冷卻成本，而租用硬體則會將這些成本轉為按小時計費。雲端租用是 OpEx 的替代方案；閒置容量的成本仍是 OpEx 效率的一項挑戰。

### 機會成本：使用率落差

在流量較低的時段，GPU 每閒置一分鐘，就代表有一分鐘付費容量未被使用。由於專用硬體可能難以在不同模型間共用而不影響效能，突發性流量可能造成付費容量與實際使用量之間的落差。

若沒有協調機制或部署於專用硬體上的無伺服器架構，專用節點有限的多租戶能力可能降低投資報酬率。

因此，自動擴縮不只是可靠性機制，也可作為成本最佳化工具。例如，服務北美開發者的程式設計助理，可能在太平洋時間凌晨 2 點到上午 6 點縮減至單一複本，以減少 GPU 閒置時數。

### 工程成本：專業人力

工程成本往往遭到低估。除了硬體，調校部署也需要專業人力。為 vLLM 或 TensorRT-LLM 找出合適的設定，可能需要投入大量系統工程時間。

軟體堆疊涉及使用 Nsight 進行效能分析，以及管理 CUDA 版本等工作。即使目標是降低每月 GPU 成本，效能基準測試也可能耗費大量工程時間。

## 決定成本的槓桿

模型架構、量化、平行處理與批次處理，造成部署之間大部分的成本差異。這些選擇將工程決策與經濟效益連結起來。

### 模型架構：Dense 與 MoE

對於 Llama 3 70B 等 Dense 模型，成本會隨記憶體與 VRAM 需求而變化。對於 DeepSeek-V3 等混合專家（MoE）模型，通訊可能是重要因素。Dense 70B 模型會在每個 token 上啟用全部 700 億個參數。DeepSeek-V3 總共有 671B 個參數，但每個 token 約啟用 37B 個參數，這改變了成本計算方式。

BF16 每個參數占兩個位元組，因此 70B 模型約需 140 GB 來儲存權重。兩張各有 80 GB 的 H100 合計 160 GB，一張 MI300X 有 192 GB。選擇配置前，先確認可供 KV 快取和執行期緩衝區使用的剩餘記憶體。Llama 4 Maverick 共有 400B 參數，每個 token 啟用 17B。若採 BF16，光是權重就約占 800 GB，超過八張 80 GB GPU 合計的 640 GB。請依每張卡的可用記憶體及實測執行期需求規劃部署規模。

對 Dense 模型而言，成本挑戰在於記憶體：每個參數都會在每個 token 上啟用，因此成本取決於 GPU 將權重從 HBM 搬移至運算核心的速度。記憶體頻寬較低可能增加延遲。

對 MoE 模型而言，挑戰則從原始運算能力轉向通訊。由於每個 token 只會啟用部分專家，總運算量可能不高。然而，專家分散在不同 GPU 上，需要「all-to-all」路由模式，可能對互連造成壓力。

### 量化：以精度換取效率

相較於 BF16，FP8 可將原始權重的儲存空間約減半。VRAM 總需求也取決於 KV 快取、執行期緩衝區，以及可能存在的量化中繼資料。

FP8（E4M3/E5M2）已用於正式環境。DeepSeek-V3 原生以 FP8 訓練，Qwen3 等模型也有官方 FP8 檢查點。參考資料中列有 Qwen3-235B-A22B-FP8 模型卡。

在支援的加速器（H100、H200、B300、MI300X）上，FP8 可提高解碼吞吐量，同時將品質維持在可接受範圍內，實際效果取決於模型與工作負載。

INT4（GPTQ、AWQ）可將權重壓縮至四分之一，但在多步推理任務中，四捨五入誤差會累積，可能降低品質。MXFP4/NVFP4 使用區塊縮放微縮放；原生支援需要 Blackwell 或 MI350X GPU。

### 平行處理策略：張量、專家與資料平行處理

模型如何分散到不同 GPU，會同時影響硬體成本與延遲。

- <strong>張量平行處理（TP）</strong>會在每一層內將權重矩陣切分到多個 GPU。所有 GPU 都會處理每個 token，可降低每個 token 的延遲，但需要 AllReduce 同步與高頻寬互連。超過 8 個 GPU 後，擴充效果不佳。
- <strong>專家平行處理（EP）</strong>會將不同 MoE 專家放在不同 GPU 上。由於只有啟用的專家需要通訊，頻寬使用可能比 TP 更有效率；但若部分專家接到較多工作，可能造成負載不平衡。
- <strong>資料平行處理（DP）</strong>以不同的模型複本處理不同請求。請求分配均衡且共用資源有餘裕時，吞吐量可隨之提升。請在有負載時量測延遲。

選擇符合成本效益的平行處理策略，意即讓模型架構符合部署目標。對於延遲至關重要的 Dense 70B 模型，可選擇在單一 8-GPU 節點上採用張量平行處理（TP=8）。對於吞吐量密集的 MoE 部署，EP 有助於容納模型權重，再搭配 DP 擴充請求處理能力。

### 批次處理與排程

在解碼受制於記憶體頻寬的階段，同批多個序列可以共用權重讀取。增加批次大小有機會提高吞吐量，直到其他資源成為瓶頸。

接近飽和點 B_sat 時，加入更多序列可能使吞吐量增幅縮小，並拉長延遲。持續批次處理和分塊 prefill 可改變這個取捨出現的位置。

在相同工作負載下測試不同批次大小。比較各設定的吞吐量和尾端延遲，找出吞吐量增幅變小或延遲超出目標的位置。

## 何時應優先最佳化吞吐量或延遲

沒有放諸四海皆準的答案：正確的選擇取決於工作負載、使用者與商業模式。

兩項原則有助於說明 LLM 效能：

1. **Little 定律：連結 QPS、延遲與並行數**

```
Average in-flight requests = QPS * mean end-to-end time in seconds
```

在穩態下，若每秒 10 筆請求的端到端時間平均為兩秒，系統內平均約有 20 筆請求，包含在佇列中等候者。請依處理中的序列及其上下文長度估算 KV 快取需求。

若測試顯示一個複本可在目標延遲內維持 16 QPS，要處理 100 QPS 至少需要七個複本，再另計備用容量。請以接近實際的流量測試整套部署。

2. **Roofline 模型**

Roofline 模型用來判斷效能受限於處理能力（運算受限），還是受限於資料搬移速度（記憶體受限）。這項區別有助於引導硬體決策。

此模型對應 LLM 推論的兩個階段如下：

| **階段** | **瓶頸** | **效率目標** |
|----|----|----|
| 預填充（輸入） | 運算 | 平行處理提示詞區塊 |
| 解碼（輸出） | 記憶體 | 在同一批次的多個序列間共用權重讀取 |

### 延遲敏感型工作負載

互動式聊天、程式碼補全、即時代理、搜尋增強及其他面向使用者的應用程式，都很重視延遲。

主要 SLO 指標包括 TTFT（首個 token 時間）與 ITL（token 間延遲）。使用者將 TTFT 感受為回應速度，將 ITL 感受為串流速度。

#### 如何調校

將批次大小維持在適中範圍，因為排隊可能延遲 TTFT。

- 限制批次大小，使其遠低於 B_Sat「膝點」。
- 在延遲敏感的應用程式中，應最佳化 **P99 尾端延遲**，而不是平均吞吐量。
- 每增加一個請求至批次中，都會提高預填充突增而延遲其他使用者 token 的可能性。

使用 TP 將每個 token 的延遲降至最低，並讓所有 GPU 都處理每個 token。

- 在單一 NVLink 連接的節點內擴展張量平行處理（TP）。
- 使用 Ethernet 或 InfiniBand 跨越節點後，GPU 通訊開銷可能會**增加** ITL。
- 對延遲敏感的任務，應將模型放在能提供所需記憶體頻寬的最少 GPU 數量上。

啟用分塊預填充，避免長提示詞阻擋解碼步驟。

- 若不分塊，大型提示詞（例如 20k-token 文件）可能會占用 GPU，直到預填充完成，讓其他使用者等待。
- 將提示詞拆成較小區塊（例如 512 個 token），可讓引擎在其他作用中請求的解碼步驟之間穿插預填充工作。
- 這有助於維持 token 間延遲（ITL）的一致性，並讓排程器填補原本閒置的 GPU 運算週期，在預填充的高運算密度與解碼受記憶體限制的特性之間取得平衡。

考慮使用推測式解碼來降低有效 ITL。

- 推測式解碼會使用草稿模型預測後續 token，以運算效率換取較低的 ITL。
- 這是以運算效率（OpEx 成本）換取較低 ITL（延遲）。

預留一些額外容量，以便在流量突增時不必排隊。

- 使用率降低可能會提高每個 token 的成本，但為了符合使用者體驗要求，這可能是必要的。

### 吞吐量敏感型工作負載

批次摘要、離線資料擷取、合成資料生成、評估管線，以及重視整個工作完成時間勝過個別請求延遲的工作負載，都可以優先考量吞吐量。

每秒 token 數（或每美元 token 數）是主要指標。只要整個批次能在必要時間範圍內完成，個別請求延遲就是次要考量。

#### 如何調校

依實測吞吐量及工作負載的延遲或完成時間預算選擇批次大小。

- 如果記憶體頻寬是瓶頸，批次處理可在不同序列間共用權重讀取。
- 增加批次大小，可讓每個載入的權重資料位元組執行更多算術運算。
- 使用具有代表性的請求組合，在實測飽和點 B_sat 附近測試不同設定。
- 選擇實測總吞吐量最高的一組設定，同時符合工作期限與每筆請求的延遲限制。

增加資料平行的複本，以提高整體吞吐量。

- 資料平行由各個獨立部署的複本處理不同請求。一個複本可跨多張 GPU。DP 可與 TP 搭配，有支援時也可加上 EP。
- 四個獨立複本若各處理每秒 1,000 個 token，理想合計為每秒 4,000 個 token。請在共用基礎設施及實際流量下量測有效吞吐量。
- 量測大規模吞吐量時，將 TP 或 EP 帶來的通訊以及共用資源的影響納入考量。

提高預填充期間並行處理 token 的上限，以更有效率地處理大型提示詞區塊，並充分利用 GPU。

- 預填充是整個流程中運算最密集的部分。若要最大化吞吐量，應讓 GPU 的 Tensor Core 維持忙碌。
- 同時處理大量 token 區塊能讓 GPU 持續忙碌，最大化每秒使用的 FLOPS。

若品質要求允許，使用積極的量化（INT4/GPTQ）。將更多內容放入記憶體所帶來的吞吐量提升，可能大於精度損失的代價。

- 吞吐量部分取決於 VRAM 能容納多少序列。
- 依推論引擎和硬體的支援情況，分別量化模型權重與設定 KV 快取精度。
- 請以實際上下文長度量測同時處理數、吞吐量和延遲，以判斷量化是否降低每個 token 的成本。
- 量化後評估模型，確認精度影響在可接受範圍內。

在可接受排隊的情況下，盡量減少過度配置，並讓 GPU 維持高使用率。

- 在批次工作負載中，排隊可能有幫助。
- 佇列可確保一個請求完成時，另一個請求已準備好接替。
- 沒有人在等待回應時，高使用率造成的延遲突增可能可以接受。
- 成功與否以**完成整個工作的總時間**衡量；當 GPU 沒有閒置時，這段時間會降至最低。

### 混合型的現實

多數正式環境系統都會結合延遲敏感與吞吐量敏感的工作負載。部署可能在上班時間提供互動式聊天，並在夜間執行批次評估工作。

符合成本效益的做法可以採用工作負載感知排程：

- **動態自動擴縮**：在互動流量尖峰時段增加 GPU 複本，並在離峰時段減少。自動擴縮器可依據佇列深度（反應式）與流量預測（預測式）調整。
- **優先權排隊**：以較低延遲服務互動式請求，並在有閒置容量時於背景處理批次請求。
- **工作負載專屬設定**：執行具有不同調校參數的獨立 vLLM 執行個體，一個服務低延遲互動流量，另一個負責高吞吐量批次處理。

## 決策架構

面對這些取捨，該如何做出決策？以下架構可供參考：

**步驟 1：描述工作負載特性**

考量 ISL/OSL 分布、QPS 需求（平均與尖峰），以及延遲 SLO（p50、p95 和 p99 的 TTFT 與 ITL）。

**步驟 2：選擇模型與量化方式**

從符合品質需求的最小模型開始。先測試 FP8，因為它可能在精度只略微妥協的情況下帶來效率優勢。若測試顯示 FP8 造成品質退化，則使用 BF16。

**步驟 3：在候選硬體上進行基準測試**

在至少兩種硬體選項上，針對不同 QPS 執行 ISL/OSL 掃描。以工作負載下實測的吞吐量作為決策依據。

**步驟 4：找出膝點**

對每種硬體選項，找出仍符合延遲 SLO 的最高 QPS。這就是每個執行個體可持續提供的容量。

**步驟 5：決定部署規模**

依尖峰流量與每個複本在目標延遲內實測的 QPS，估算所需複本數量。預留容量吸收流量尖峰，同時讓各複本留在延遲目標範圍內。

**步驟 6：計算總成本**

```
TCO_per_token = (capital allocated to period + operating costs + engineering costs) / tokens served in the same period
```

比較不同硬體選項的數值。最便宜的 GPU 不一定會帶來成本最低的部署。

**步驟 7：規劃自動擴縮**

對於流量變動的情況，設計自動擴縮政策，以離峰時段的節省成本換取冷啟動延遲。將閒置容量用於批次工作負載。

## 為你的工作負載打造，而非迎合基準測試

吞吐量、延遲與成本的三難困境是需要管理的張力。每項設定選擇都會改變三個面向間的平衡，沒有任何設定能在所有情況下都完美適用。

團隊可使用特定提示詞、模型與硬體來進行基準測試並描述工作負載特性，而非只依賴規格表，藉此做出更好的部署決策。

服務框架與硬體持續演進，但 LLM 推論的基本物理原理並未改變。針對業務重視的指標進行基準測試與調校，有助於團隊應對這些取捨。
