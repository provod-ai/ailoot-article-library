# สถาปัตยกรรม TTS API: จากข้อความสู่เสียงสำหรับระบบโปรดักชัน

> เรียนรู้วิธีออกแบบ TTS API สำหรับระบบโปรดักชันที่มีคิว เวิร์กเกอร์ แคช การลองใหม่ การกำหนดเส้นทางผู้ให้บริการ พื้นที่จัดเก็บ การจำกัดอัตรา และการสังเกตการณ์ระบบ



การเรียกใช้ Text-to-Speech API นั้นง่าย แต่การทำให้ทำงานได้อย่างน่าเชื่อถือในระบบโปรดักชันนั้นไม่ง่าย

ต้นแบบพื้นฐานอาจมีเพียงสามขั้นตอน:

**ข้อความ → ผู้ให้บริการ TTS → MP3**

วิธีนี้อาจใช้ได้ดีเมื่อทดสอบคำขอไม่กี่รายการบนเครื่องของคุณเอง แต่เมื่อมีผู้ใช้จริงเข้ามา ระบบต้องรองรับงานที่ทำพร้อมกัน ขีดจำกัดอัตราของผู้ให้บริการ ปัญหาเครือข่าย งานสร้างเสียงที่ใช้เวลานาน คำขอซ้ำ พื้นที่จัดเก็บ การลองใหม่ โควตา ผู้ให้บริการเสียงหลายราย และผู้ใช้ที่รีเฟรชหน้าเว็บขณะที่เสียงยังอยู่ระหว่างประมวลผล

สถาปัตยกรรมจึงซับซ้อนกว่าการเรียก TTS API เพียงอย่างเดียวอย่างรวดเร็ว เวิร์กโฟลว์โปรดักชันที่สมจริงขึ้นมีลักษณะดังนี้:

**ไคลเอนต์ → API → งาน → คิว → เวิร์กเกอร์ → ผู้ให้บริการ TTS → พื้นที่จัดเก็บ/CDN → ผลลัพธ์**

บทความนี้อธิบายวิธีออกแบบสถาปัตยกรรมดังกล่าว เหตุผลที่มีแต่ละองค์ประกอบ และปัญหาที่มักเกิดขึ้นเมื่อแอปพลิเคชัน TTS เติบโตเกินกว่าการสาธิตแบบง่าย



## **TTS API สำหรับระบบโปรดักชันต้องแก้ปัญหาอะไรบ้าง?**

จุดประสงค์ของแบ็กเอนด์ TTS สำหรับระบบโปรดักชันไม่ใช่แค่สร้างเสียง แต่ต้องสร้างเสียงได้ **อย่างน่าเชื่อถือ มีประสิทธิภาพ และคาดการณ์ได้**

สถาปัตยกรรมที่ดีควรตอบคำถามต่าง ๆ เช่น:

1. จะเกิดอะไรขึ้นเมื่อผู้ใช้ 100 คนสร้างเสียงพูดพร้อมกัน?
2. จะเกิดอะไรขึ้นเมื่อผู้ให้บริการ TTS ตอบกลับ HTTP 429?
3. จะเกิดอะไรขึ้นเมื่อผู้ให้บริการ TTS ไม่พร้อมให้บริการ?
4. จะเกิดอะไรขึ้นเมื่องานสร้างเสียงใช้เวลาหลายนาที?
5. จะเกิดอะไรขึ้นเมื่อผู้ใช้ส่งคำขอเดิมซ้ำสองครั้ง?
6. จะป้องกันไม่ให้ผู้ใช้รายเดียวใช้โควตาผู้ให้บริการที่มีอยู่ทั้งหมดได้อย่างไร?
7. ควรจัดเก็บเสียงที่สร้างขึ้นไว้ที่ใด?
8. ไคลเอนต์จะทราบได้อย่างไรว่างานที่ใช้เวลานานเสร็จแล้ว?
9. จะลองทำงานที่ล้มเหลวใหม่โดยไม่สร้างเสียงที่สำเร็จแล้วซ้ำได้อย่างไร?
10. จะวัดได้อย่างไรว่าผู้ให้บริการรายใดช้าหรือไม่น่าเชื่อถือ?

สิ่งเหล่านี้เป็นปัญหาด้านการออกแบบระบบ ไม่ใช่ปัญหาด้านการสังเคราะห์เสียงพูด

## **คำขอ TTS API พื้นฐาน**

ในระดับพื้นฐานที่สุด คำขอ TTS อาจประกอบด้วย:

1. ข้อความ
2. ภาษา
3. เสียง
4. โมเดล
5. ความเร็วในการพูด
6. รูปแบบเสียง
7. คำแนะนำเสียงเพิ่มเติมที่ไม่บังคับ

ตัวอย่างเชิงแนวคิด:

**POST /tts**

เซิร์ฟเวอร์รับคำขอ เรียกผู้ให้บริการ TTS และส่งคืนไฟล์เสียง รูปแบบซิงโครนัสนี้เข้าใจง่าย:

**คำขอ HTTP → ผู้ให้บริการ → เสียง → การตอบกลับ HTTP**

สำหรับการสร้างเสียงพูดที่สั้นมาก วิธีนี้อาจยอมรับได้ ปัญหาจะเริ่มขึ้นเมื่อการสร้างช้าลง ปริมาณการใช้งานเพิ่มขึ้น หรือคำขอหนึ่งมีข้อความจำนวนมาก

## **เหตุใดงาน TTS ที่ใช้เวลานานจึงไม่ควรพึ่งพาคำขอ HTTP เพียงรายการเดียว**

ลองนึกภาพผู้ใช้ส่งข้อความที่เพียงพอสำหรับสร้างเสียงบรรยายยาว 30 นาที หาก API ของคุณเปิดคำขอ HTTP เดิมค้างไว้จนกว่าทุกอย่างจะเสร็จ อาจเกิดปัญหาหลายอย่าง:

1. เบราว์เซอร์อาจหมดเวลารอ
2. reverse proxy อาจปิดคำขอ
3. เซิร์ฟเวอร์แอปพลิเคชันอาจรีสตาร์ต
4. ผู้ให้บริการอาจขัดข้องชั่วคราว
5. ผู้ใช้อาจปิดหน้าเว็บ
6. การเชื่อมต่อมือถืออาจขาดหาย

งาน TTS อาจยังดำเนินต่อได้ แต่การเชื่อมต่อที่เริ่มงานนั้นสิ้นสุดลงแล้ว โดยทั่วไป ภาระงาน TTS ที่ใช้เวลานานควรจำลองเป็น **งาน**

เวิร์กโฟลว์จะเปลี่ยนเป็น:

**ไคลเอนต์ → สร้างงาน → ส่งคืนรหัสงาน → ประมวลผลเบื้องหลัง**

ไคลเอนต์สามารถตรวจสอบความคืบหน้าได้ภายหลัง

## **ขั้นตอนที่ 1: รับและตรวจสอบคำขอ**

ชั้น API ควรตรวจสอบเบื้องต้นก่อนส่งงานเข้าสู่ระบบประมวลผล การตรวจสอบทั่วไปได้แก่:

1. ข้อความว่างเปล่าหรือไม่?
2. ข้อความยาวเกินขนาดคำขอที่อนุญาตหรือไม่?
3. เสียงที่ร้องขอมีอยู่หรือไม่?
4. โมเดลที่เลือกสนับสนุนภาษาที่ร้องขอหรือไม่?
5. รูปแบบเสียงที่ร้องขอรองรับหรือไม่?
6. ผู้ใช้ผ่านการยืนยันตัวตนหรือไม่?
7. ผู้ใช้มีโควตาหรือเครดิตเพียงพอหรือไม่?
8. คำขอได้รับอนุญาตตามกฎการจำกัดอัตราหรือไม่?

ควรปฏิเสธคำขอที่ไม่ถูกต้องก่อนถึงเวิร์กเกอร์หรือผู้ให้บริการภายนอก วิธีนี้ช่วยประหยัดทรัพยากรโครงสร้างพื้นฐานและโควตาผู้ให้บริการ

สำหรับงานที่ทำพร้อมกัน ให้สงวนโควตาหรือเครดิตที่เกี่ยวข้องแบบอะตอมก่อนรับงาน และชำระหรือปล่อยยอดสงวนนั้นเพียงครั้งเดียวตามผลจริงและนโยบายการเรียกเก็บเงิน

## **ขั้นตอนที่ 2: ปรับคำขอให้เป็นรูปแบบมาตรฐาน**

ก่อนประมวลผล ให้ปรับคำขอเป็นรูปแบบภายในที่คาดเดาได้ ตัวอย่างเช่น:

1. ปรับรหัสภาษาให้เป็นมาตรฐาน
2. ระบุ ID เสียงจริง
3. ระบุผู้ให้บริการที่อยู่เบื้องหลังเสียงที่เลือก
4. ใช้ความเร็วในการพูดเริ่มต้น
5. ปรับช่องว่างให้เป็นมาตรฐาน
6. เลือกรูปแบบเอาต์พุต
7. ระบุการกำหนดค่าโมเดล

วิธีนี้ทำให้เวิร์กเกอร์ปลายทางได้รับสัญญาข้อมูลขาเข้าที่สม่ำเสมอ และยังช่วยเรื่องแคชด้วย กล่าวคือ คำขอที่มีความหมายเหมือนกันควรสร้างคีย์แคชเดียวกัน



## **ขั้นตอนที่ 3: ตรวจสอบว่ามีเสียงนั้นอยู่แล้วหรือไม่**

การสร้างเสียงเดิมซ้ำ ๆ เป็นวิธีง่าย ๆ ที่ทำให้ระบบ TTS เสียค่าใช้จ่ายโดยเปล่าประโยชน์ สมมติว่าผู้ใช้ส่ง:

*"ยินดีต้อนรับสู่แอปพลิเคชันของเรา"*

หลายครั้งด้วยเสียง โมเดล ความเร็ว และการตั้งค่าเดิม หากผลลัพธ์มีความคงที่เพียงพอสำหรับกรณีใช้งานของคุณ ก็อาจไม่มีเหตุผลที่ต้องเรียกผู้ให้บริการทุกครั้ง

คีย์แคชอาจสร้างจากค่า เช่น:

1. ข้อความที่ปรับเป็นมาตรฐานแล้ว
2. ID เสียง
3. ผู้ให้บริการ
4. โมเดล
5. ภาษา
6. ความเร็ว
7. รูปแบบเสียง
8. รูปแบบหรือคำแนะนำเสียง

คีย์เชิงแนวคิดอาจเป็น:

**HASH(ข้อความ + เสียง + โมเดล + ความเร็ว + รูปแบบ + การตั้งค่า)**

ทำซีเรียลไลซ์ฟิลด์ทั้งหมดที่ใช้สร้างเสียงให้มีรูปแบบไม่กำกวม และใส่ขอบเขต tenant หรือสิทธิ์เข้าถึงที่เหมาะสมในตัวตนแคช ตรวจสอบสิทธิ์ก่อนใช้ซ้ำและเข้าถึงผลลัพธ์ โดยแชร์ข้าม tenant เฉพาะเมื่อได้รับอนุญาตอย่างชัดเจน

ลำดับคำขอจะเป็น:

**คำขอ → ตรวจสอบแคช → มีเสียงอยู่แล้วหรือไม่?**

ถ้ามี:

**ส่งคืนผลลัพธ์เดิม**

ถ้าไม่มี:

**สร้างงานสร้างเสียง**

### **อย่าใช้เฉพาะข้อความเป็นคีย์แคช**

โดยทั่วไป การใช้ข้อความเพียงอย่างเดียวเป็นคีย์แคชไม่ถูกต้อง ประโยคเดียวกันที่สร้างด้วยเสียงสองแบบควรได้เสียงที่ต่างกัน เช่นเดียวกันกับโมเดล ความเร็ว ภาษา รูปแบบ และการตั้งค่ารูปแบบเสียง

ตัวระบุแคชควรแทนทุกสิ่งที่อาจเปลี่ยนเอาต์พุตได้อย่างมีนัยสำคัญ

## **ขั้นตอนที่ 4: สร้างงานแบบถาวร**

ก่อนนำงานเข้าคิว ให้บันทึกระเบียนงาน งาน TTS อาจมีข้อมูลดังนี้:

1. ID งาน
2. ID ผู้ใช้
3. สถานะ
4. เสียงที่ร้องขอ
5. ผู้ให้บริการ
6. โมเดล
7. จำนวนอักขระ
8. เวลาที่สร้าง
9. เวลาเริ่มต้น
10. เวลาที่เสร็จสิ้น
11. จำนวนครั้งที่ลองใหม่
12. ความคืบหน้า
13. ข้อมูลข้อผิดพลาด
14. URL เอาต์พุต

วงจรสถานะอย่างง่ายอาจเป็น:

**รอดำเนินการ → กำลังประมวลผล → เสร็จสมบูรณ์**

พร้อมสถานะความล้มเหลว เช่น:

**รอดำเนินการ → กำลังประมวลผล → ล้มเหลว**

คุณอาจต้องมีสถานะสำหรับงานที่กำลังลองใหม่ ถูกยกเลิก เสร็จบางส่วน หรือหมดอายุด้วย

การบันทึกสถานะงานเป็นสิ่งสำคัญ เพราะระบบประมวลผลไม่ควรพึ่งพาหน่วยความจำของแอปพลิเคชัน หากคอนเทนเนอร์ API รีสตาร์ต ผู้ใช้ก็ควรยังเรียกดูงานของตนได้

## **ขั้นตอนที่ 5: ส่งงานไปยังคิวข้อความ**

คิวข้อความแยกการรับคำขอออกจากการประมวลผลเสียง แทนที่จะใช้:

**API → ผู้ให้บริการ TTS**

ให้ใช้:

**API → คิว → เวิร์กเกอร์ → ผู้ให้บริการ TTS**

API สามารถตอบกลับด้วยตัวระบุงานแทบจะทันที ขณะที่เวิร์กเกอร์ประมวลผลคำขออยู่เบื้องหลัง

ใช้ transactional outbox หรือกลไกกู้คืนที่ทนทานสำหรับงานที่บันทึกแล้วแต่ยังไม่เข้าคิว และทำให้การประมวลผลคิวเป็น idempotent เพื่อไม่ให้งานสูญหายหรือซ้ำเมื่อระบบแครชหรือส่งข้อความซ้ำ

### เหตุใดคิวจึงมีประโยชน์มากสำหรับ TTS

คิวมีข้อดีสำคัญหลายประการ:

1. รองรับปริมาณการใช้งานที่พุ่งขึ้น
2. ควบคุมปริมาณงานที่ทำพร้อมกัน
3. ปกป้องโควตาของผู้ให้บริการภายนอก
4. ทำให้การลองใหม่ง่ายขึ้น
5. ช่วยให้งานดำเนินต่อได้หลังคำขอ HTTP เดิมสิ้นสุดลง
6. ช่วยให้เพิ่มเวิร์กเกอร์ได้เมื่อปริมาณการใช้งานเติบโต

สิ่งนี้สำคัญเป็นพิเศษเมื่อผู้ให้บริการ TTS กำหนดขีดจำกัดจำนวนคำขอต่อนาที จำนวนอักขระ โทเค็น หรือการทำงานพร้อมกัน



## **คิวยังเป็นกลไกควบคุมแรงดันย้อนกลับด้วย**

สมมติว่าผู้ให้บริการของคุณประมวลผลได้อย่างปลอดภัยครั้งละ 20 คำขอ แต่ API ได้รับ 200 คำขอพร้อมกัน หากไม่มีคิว คุณอาจส่งคำขอทั้ง 200 รายการไปยังผู้ให้บริการโดยตรง ผลที่น่าจะเกิดขึ้นคือ:

1. ข้อผิดพลาดจากการจำกัดอัตรา
2. หมดเวลารอ
3. ใช้ CPU สูง
4. ใช้หน่วยความจำสูง
5. ผู้ให้บริการจำกัดการใช้งาน
6. เกิดการลองใหม่ต่อเนื่องเป็นทอด ๆ

เมื่อมีคิว API สามารถรับงานไว้ได้ ขณะที่เวิร์กเกอร์ประมวลผลในอัตราที่ควบคุมได้ ระบบไม่จำเป็นต้องประมวลผลทุกอย่างทันที เพียงเพราะคำขอมาถึงทันที

## **ขั้นตอนที่ 6: ประมวลผลงานด้วย TTS workers**

เวิร์กเกอร์จัดการเวิร์กโฟลว์การสร้างเสียง เวิร์กเกอร์อาจทำสิ่งต่อไปนี้:

1. อ่านงานจากคิว
2. โหลดการกำหนดค่างาน
3. แบ่งข้อความยาวหากจำเป็น
4. เลือกผู้ให้บริการที่ถูกต้อง
5. เรียก TTS API
6. จัดการความล้มเหลวชั่วคราว
7. ดาวน์โหลดหรือรับเสียงที่สร้างขึ้น
8. ตรวจสอบเอาต์พุต
9. อัปโหลดผลลัพธ์ไปยังพื้นที่จัดเก็บ
10. อัปเดตสถานะงาน

เวิร์กเกอร์ควรไม่มีสถานะมากพอที่จะให้เวิร์กเกอร์ตัวอื่นประมวลผลงานต่อได้ หากอินสแตนซ์หนึ่งหายไป

## **เวิร์กเกอร์ควรใช้การทำงานพร้อมกันมากเพียงใด?**

การทำงานพร้อมกันมากขึ้นไม่ได้หมายความว่าจะมีอัตราประมวลผลสูงขึ้นเสมอไป การเพิ่มการทำงานพร้อมกันของเวิร์กเกอร์มากเกินไปอาจทำให้:

1. ชนขีดจำกัดของผู้ให้บริการ
2. CPU อิ่มตัว
3. หน่วยความจำตึงตัว
4. ชนขีดจำกัดเครือข่าย
5. ชนขีดจำกัด I/O ของดิสก์
6. เกิดคอขวดที่ FFmpeg

ภาระงาน TTS อาจเกี่ยวข้องกับทรัพยากรหลายประเภท การเรียก API เสียงพูดระยะไกลอาจขึ้นกับเครือข่ายเป็นหลัก ส่วนการแปลงหรือรวมเสียงอาจขึ้นกับ CPU ดังนั้น ระบบโปรดักชันอาจได้ประโยชน์จากการควบคุมจำนวนงานพร้อมกันแยกกันในแต่ละขั้นตอน

ตัวอย่างเช่น:

**การดาวน์โหลดพร้อมกัน: สูง**

**การเรียกผู้ให้บริการ TTS พร้อมกัน: ขึ้นอยู่กับผู้ให้บริการ**

**การประมวลผลเสียงพร้อมกัน: ขึ้นอยู่กับ CPU**

โดยทั่วไปวิธีนี้ปลอดภัยกว่าการใช้ค่าการทำงานพร้อมกันขนาดใหญ่เพียงค่าเดียวในทุกส่วน

## **ขั้นตอนที่ 7: แบ่งข้อความยาวเป็นบล็อกเล็ก ๆ**

ผู้ให้บริการ TTS จำนวนมากกำหนดขีดจำกัดขนาดคำขอ แม้ผู้ให้บริการจะรับข้อความขนาดใหญ่มากได้ การแบ่งเอกสารยาวก็ยังมีประโยชน์

งาน TTS ที่ยาวอาจกลายเป็น:

**เอกสาร → บล็อก 1 + บล็อก 2 + บล็อก 3 + ... → TTS → รวมเสียง**

การประมวลผลเป็นบล็อกมีข้อดีหลายประการ:

1. ลองใหม่เฉพาะบล็อกที่ล้มเหลวหลังยืนยันว่าปลอดภัย
2. ประมวลผลบล็อกที่เป็นอิสระต่อกันพร้อมกัน
3. ติดตามความคืบหน้า
4. กู้คืนจากความล้มเหลวบางส่วน
5. แคชแต่ละบล็อกแยกกัน
6. หลีกเลี่ยงขีดจำกัดขนาดคำขอของผู้ให้บริการ

### **อย่าแบ่งข้อความโดยไม่พิจารณา**

การแบ่งทุก ๆ จำนวนอักขระคงที่อาจทำให้คุณภาพเสียงพูดเสียหาย เพราะบล็อกอาจจบกลางประโยค วิธีแบ่งที่ดีกว่าควรพิจารณา:

1. ขอบเขตย่อหน้า
2. ขอบเขตประโยค
3. เครื่องหมายวรรคตอน
4. ขีดจำกัดจำนวนอักขระของผู้ให้บริการ
5. กฎการเขียนเฉพาะภาษา

เป้าหมายคือทำให้บล็อกเล็กพอสำหรับการประมวลผลที่เชื่อถือได้ พร้อมรักษาบริบทของคำพูดให้เป็นธรรมชาติ

## **ขั้นตอนที่ 8: กำหนดเส้นทางคำขอไปยังผู้ให้บริการ TTS ที่ถูกต้อง**

แอปพลิเคชันโปรดักชันอาจรองรับผู้ให้บริการ TTS หลายรายในที่สุด ผู้ให้บริการแต่ละรายอาจมีสิ่งต่าง ๆ เช่น:

1. ภาษา
2. แคตตาล็อกเสียง
3. ราคา
4. ระดับคุณภาพ
5. ขีดจำกัดอัตรา
6. เวลาแฝง
7. การควบคุมอารมณ์
8. ความสามารถด้านสตรีมมิง

แทนที่จะฝังตรรกะเฉพาะผู้ให้บริการไว้ทั่วแอปพลิเคชัน ให้ใช้ชั้นกำหนดเส้นทางหรือชั้นนามธรรม สถาปัตยกรรมจะเป็นดังนี้:

**เวิร์กเกอร์ → ตัวกำหนดเส้นทางเสียง/โมเดล → อะแดปเตอร์ผู้ให้บริการ → ผู้ให้บริการ TTS**

อะแดปเตอร์ของผู้ให้บริการแต่ละรายสามารถเปิดเผยอินเทอร์เฟซภายในแบบเดียวกัน พร้อมแปลงคำขอเป็นรูปแบบที่ผู้ให้บริการรายนั้นคาดหวัง

### **หลีกเลี่ยงการกระจายตรรกะเฉพาะผู้ให้บริการไปทุกที่**

หากไม่มีชั้นนามธรรม โค้ดอาจเต็มไปด้วยเงื่อนไข เช่น:

**ถ้าผู้ให้บริการเป็น A ให้ทำแบบนี้ ถ้าผู้ให้บริการเป็น B ให้ทำอีกแบบ**

เมื่อเพิ่มผู้ให้บริการ ก็จะดูแลรักษาได้ยากขึ้น อินเทอร์เฟซผู้ให้บริการร่วมกันช่วยให้ส่วนอื่นของระบบทำงานกับแนวคิดต่าง ๆ เช่น:

1. สร้างเสียงพูด
2. เรียกดูเสียงที่รองรับ
3. ตรวจสอบคำขอ
4. ส่งคืนเสียง

อะแดปเตอร์ของผู้ให้บริการแต่ละรายจัดการรายละเอียดการทำงาน

## **การสลับไปใช้ผู้ให้บริการสำรอง: มีประโยชน์ แต่ไม่ง่ายเสมอไป**

คุณอาจอยากส่งทุกคำขอที่ล้มเหลวไปยังผู้ให้บริการรายอื่นโดยอัตโนมัติ บางครั้งวิธีนี้ใช้ได้ดี แต่บางครั้งก็ไม่ ผู้ให้บริการสองรายอาจไม่มีเสียงที่เทียบเท่ากัน และเสียงสำรองอาจฟังแตกต่างจากเสียงเดิมอย่างสิ้นเชิง ซึ่งอาจยอมรับไม่ได้สำหรับหนังสือเสียงยาวหรือวิดีโอหลายฉาก

การตัดสินใจสลับผู้ให้บริการควรพิจารณา:

1. มีเสียงที่เทียบเท่ากันหรือไม่
2. ความสม่ำเสมอสำคัญหรือไม่
3. ความล้มเหลวเป็นแบบชั่วคราวหรือไม่
4. ความแตกต่างด้านต้นทุน
5. ภาษาเป้าหมาย
6. ความต้องการของผู้ใช้

การสลับผู้ให้บริการเป็นเครื่องมือด้านสถาปัตยกรรม ไม่ใช่หลักประกันว่าควรกำหนดเส้นทางใหม่ให้ทุกคำขอที่ล้มเหลวทันที

## **ขั้นตอนที่ 9: จัดการขีดจำกัดอัตราอย่างถูกต้อง**

HTTP 429 เป็นหนึ่งในปัญหาที่พบบ่อยที่สุดในระบบที่ใช้ API มาก HTTP 429 อาจบ่งชี้ถึงขีดจำกัดของผู้ให้บริการ รวมถึงอัตราคำขอหรือจำนวนคำขอพร้อมกัน ตรวจรายละเอียดข้อผิดพลาดและคำแนะนำการลองใหม่ของผู้ให้บริการ รวมถึง Retry-After หากมี ก่อนตัดสินใจว่าจะลองใหม่อย่างไรและเมื่อใด

การตอบสนองที่ไม่ถูกต้องคือ:

**ลองใหม่ทันทีให้เร็วที่สุด**

โดยทั่วไป วิธีนี้จะสร้างคำขอเพิ่มและทำให้ปัญหาแย่ลง แนวทางที่ดีกว่าใช้:

1. ขีดจำกัดการทำงานพร้อมกัน
2. การหน่วงเวลาแบบเอ็กซ์โพเนนเชียล
3. Jitter
4. นโยบายจำกัดอัตราเฉพาะผู้ให้บริการ
5. การหน่วงในคิว

ในเชิงแนวคิด:

**429 → รอ → ลองใหม่ภายหลัง**

ไม่ใช่:

**429 → ลองใหม่ทันที → 429 → ลองใหม่ทันที → 429**

## **ขั้นตอนที่ 10: ลองใหม่เฉพาะข้อผิดพลาดที่กู้คืนได้**

การลองใหม่เป็นสิ่งจำเป็น แต่ไม่ควรลองใหม่กับทุกความล้มเหลว การจัดประเภทที่มีประโยชน์คือ:

| ประเภทข้อผิดพลาด            | การดำเนินการทั่วไป                   |
|-----------------------------|-------------------------------------|
| 429 Too Many Requests       | รอแล้วลองใหม่โดยเว้นระยะ             |
| 500 Internal Server Error   | ตรวจสอบผลการดำเนินการเดิม แล้วลองใหม่เมื่อปลอดภัยเท่านั้น                |
| 502 / 503 Temporary Failure | ตรวจสอบผลการดำเนินการเดิมก่อนลองใหม่หรือสลับผู้ให้บริการสำรอง |
| หมดเวลารอเครือข่าย          | ตรวจสอบผลการดำเนินการเดิมก่อนลองใหม่                 |
| 400 Invalid Request         | อย่าลองใหม่โดยไม่ตรวจสอบ              |
| เสียงที่ไม่รองรับ            | แก้ไขคำขอหรือการกำหนดเส้นทาง          |
| เครดิตผู้ใช้ไม่เพียงพอ       | ปฏิเสธก่อนประมวลผลกับผู้ให้บริการ       |

การหมดเวลารอ ข้อผิดพลาด 5xx หรือความล้มเหลวของเวิร์กเกอร์อาจทำให้ไม่ทราบผลที่ผู้ให้บริการ ก่อนลองใหม่หรือสลับผู้ให้บริการ ให้ตรวจสอบ ID การดำเนินการเดิม สถานะ และการใช้งานเมื่อรองรับ ใช้ผลที่ดำเนินการสำเร็จแล้วซ้ำ และใช้ idempotency ที่ผู้ให้บริการรองรับ เก็บสถานะไม่ทราบผลไว้แทนการทำซ้ำคำขอที่อาจเสร็จแล้วโดยไม่ตรวจสอบ

นโยบายการลองใหม่ควรกำหนดจำนวนครั้งสูงสุดด้วย มิฉะนั้น งานที่มีปัญหาหนึ่งงานอาจค้างอยู่ในระบบตลอดไป

## **ใช้ Idempotency เพื่อป้องกันงานซ้ำ**

คำขอซ้ำเกิดขึ้นบ่อยในแอปพลิเคชันจริง ผู้ใช้อาจคลิกปุ่มสองครั้ง frontend อาจลองใหม่หลังหมดเวลารอเครือข่าย ข้อความในคิวอาจถูกส่งซ้ำ หรือเวิร์กเกอร์อาจทำงานสำเร็จแต่แครชก่อนยืนยันรับข้อความ

หากระบบถือว่าทุกข้อความไม่ซ้ำกัน ก็อาจสร้างและเรียกเก็บเงินสำหรับเสียงเดิมหลายครั้ง Idempotency หมายถึงการประมวลผลคำขอเชิงตรรกะเดียวกันหลายครั้งไม่ควรสร้างผลลัพธ์ที่ไม่ตั้งใจหลายรายการ

เทคนิคที่ใช้ได้ ได้แก่:

1. คีย์ idempotency
2. ตัวระบุงานที่ไม่ซ้ำกัน
3. แฮชแคช
4. ข้อจำกัดความไม่ซ้ำกันในฐานข้อมูล
5. ตรวจสอบสถานะบล็อกก่อนประมวลผล

เรื่องนี้สำคัญเป็นพิเศษเมื่อเกี่ยวข้องกับการชำระเงิน เครดิต หรือต้นทุนผู้ให้บริการ

## **Idempotency ระดับงานเทียบกับระดับบล็อก**

สำหรับคำขอ TTS สั้น ๆ idempotency ระดับงานอาจเพียงพอ สำหรับงานขนาดใหญ่ที่มีหลายบล็อก idempotency ระดับบล็อกมักมีประโยชน์กว่า

ลองนึกถึงงานหนังสือเสียง 500 บล็อกที่บล็อก 487 ล้มเหลว คุณไม่ต้องการสร้างบล็อก 1 ถึง 486 ใหม่

**บล็อกที่เสร็จแล้ว → เก็บไว้**

**บล็อกที่ล้มเหลว → ตรวจสอบสถานะผู้ให้บริการ → ลองใหม่เมื่อปลอดภัยเท่านั้น**

วิธีนี้ช่วยลดต้นทุนและเวลาในการกู้คืนได้อย่างมาก

## **ขั้นตอนที่ 11: ตรวจสอบเสียงที่สร้างขึ้น**

การตอบกลับจากผู้ให้บริการที่สำเร็จไม่ได้รับประกันว่าจะได้เอาต์พุตที่ใช้งานได้เสมอไป ก่อนทำเครื่องหมายว่างานเสร็จสมบูรณ์ คุณอาจต้องตรวจสอบว่า:

1. มีการส่งคืนไฟล์เสียงหรือไม่?
2. ขนาดไฟล์มากกว่าศูนย์หรือไม่?
3. ถอดรหัสเสียงได้หรือไม่?
4. ระยะเวลาฟังดูสมเหตุสมผลหรือไม่?
5. รูปแบบที่ร้องขอถูกต้องหรือไม่?

สำหรับเวิร์กโฟลว์ขั้นสูง การตรวจสอบระยะเวลายังช่วยตรวจจับเอาต์พุตที่น่าสงสัย เช่น คำพูดที่สั้นหรือยาวผิดคาด

## **ขั้นตอนที่ 12: จัดเก็บเสียงไว้นอกเซิร์ฟเวอร์แอปพลิเคชัน**

โดยทั่วไป เสียงที่สร้างขึ้นไม่ควรพึ่งพาดิสก์ในเครื่องของ API หรือเวิร์กเกอร์อินสแตนซ์เดียว หากสร้างคอนเทนเนอร์ขึ้นใหม่ ไฟล์อาจหายไป

สถาปัตยกรรมที่ดีกว่าคือ:

**เวิร์กเกอร์ → Object Storage → CDN → ผู้ใช้**

Object Storage แยกสินทรัพย์ที่สร้างขึ้นออกจากโครงสร้างพื้นฐานสำหรับประมวลผล จากนั้น CDN สามารถส่งเสียงให้ผู้ใช้ในตำแหน่งต่าง ๆ ได้อย่างมีประสิทธิภาพ

ตรวจสอบสิทธิ์เข้าถึงงาน สถานะ และผลลัพธ์เสียงแต่ละรายการ เก็บเสียงที่บันทึกไว้เป็นส่วนตัว และใช้ลิงก์จำกัดขอบเขตและมีวันหมดอายุเมื่อจำเป็น แทนการถือว่า URL เป็นหลักฐานสิทธิ์เข้าถึง

### ควรจัดเก็บอะไรไว้ในฐานข้อมูล?

โดยปกติฐานข้อมูลไม่จำเป็นต้องเก็บไบต์เสียงดิบ แต่ให้จัดเก็บข้อมูลเมตา เช่น:

1. คีย์พื้นที่จัดเก็บ
2. URL เสียง
3. ระยะเวลา
4. ขนาดไฟล์
5. รูปแบบ
6. ผู้ให้บริการ
7. เสียง
8. เวลาที่สร้าง

ไฟล์เสียงจริงสามารถอยู่ใน Object Storage ต่อไปได้

## **คำนึงถึงวันหมดอายุของไฟล์**

ไฟล์ TTS ที่สร้างขึ้นไม่จำเป็นต้องอยู่ตลอดไปทุกไฟล์ พื้นที่จัดเก็บอาจมีค่าใช้จ่ายสูงขึ้นอย่างเงียบ ๆ เมื่อไฟล์เสียงชั่วคราวนับล้านสะสมกัน

พิจารณานโยบายการเก็บรักษาสำหรับ:

1. ไฟล์ที่ผู้ใช้แบบ guest สร้างขึ้น
2. ไฟล์ประมวลผลชั่วคราว
3. บล็อกระหว่างการประมวลผล
4. โปรเจ็กต์ของผู้ใช้ที่เสร็จสมบูรณ์
5. เสียงแคชที่นำกลับมาใช้ซ้ำได้

โดยมากไฟล์ระหว่างการประมวลผลสามารถเก็บไว้ในช่วงเวลาที่สั้นกว่าเอาต์พุตสุดท้ายของผู้ใช้มาก

## **ขั้นตอนที่ 13: ส่งคืนผลลัพธ์ด้วย Polling หรือ Callback**

เมื่อคำขอ TTS ทำงานแบบอะซิงโครนัส ไคลเอนต์ต้องมีวิธีทราบว่าการประมวลผลเสร็จเมื่อใด มีรูปแบบที่ใช้กันทั่วไปสองแบบ

### **Polling**

ไคลเอนต์ถามเป็นระยะ:

**GET /jobs/{jobId}**

เซิร์ฟเวอร์ตอบกลับในลักษณะคล้าย:

**status = processing**

และภายหลัง:

**status = completed, audioUrl = ...**

Polling ทำได้ง่ายและใช้ได้ดีกับเว็บแอปพลิเคชันจำนวนมาก

### **Webhook หรือ Callback**

ลูกค้า API อาจส่ง URL สำหรับ callback มาให้ เมื่อการประมวลผลเสร็จ เซิร์ฟเวอร์ของคุณจะส่งการแจ้งเตือนโดยอัตโนมัติ

เวิร์กโฟลว์จะเป็น:

**สร้างงาน → ส่งคืนรหัสงาน → ประมวลผล → Callback ไปยังไคลเอนต์**

วิธีนี้มีประโยชน์เมื่อระบบภายนอกประมวลผลงานขนาดใหญ่และไม่ต้องการ polling อยู่ตลอดเวลา

### การรองรับทั้งสองแบบอาจมีประโยชน์

API สำหรับระบบโปรดักชันอาจเปิดให้ polling สถานะงานเป็นกลไกพื้นฐานสำหรับทุกกรณี พร้อมเสนอ webhook เป็นทางเลือกเพื่อความสะดวก

## **ติดตามความคืบหน้าของงานขนาดใหญ่**

สำหรับคำขอ TTS 5 วินาที ความคืบหน้าอาจไม่สำคัญ แต่สำหรับโปรเจ็กต์เสียงยาวหนึ่งชั่วโมง ความคืบหน้าสำคัญมาก หากงานมี 1,000 บล็อก ก็ประเมินความคืบหน้าจากงานที่เสร็จแล้วได้ดังนี้:

**ความคืบหน้า = บล็อกที่เสร็จแล้ว / จำนวนบล็อกทั้งหมด**

วิธีนี้ช่วยให้ frontend แสดงสถานะ:

1. อยู่ในคิว
2. กำลังประมวลผล 27%
3. กำลังประมวลผล 83%
4. กำลังจัดเตรียมเสียงขั้นสุดท้าย
5. เสร็จสมบูรณ์

ตัวบ่งชี้ความคืบหน้าที่ยังมองเห็นได้ยังช่วยลดโอกาสที่ผู้ใช้จะคิดว่าแอปพลิเคชันค้างและส่งงานเดิมซ้ำ

## **ขั้นตอนที่ 14: ปกป้องระบบด้วยการจำกัดอัตรา**

ผู้ให้บริการของคุณมีขีดจำกัดอัตรา API ของคุณเองก็ควรมีเช่นกัน การจำกัดอัตราทำได้ตาม:

1. ผู้ใช้
2. API key
3. ที่อยู่ IP
4. แผนการสมัครสมาชิก
5. Endpoint
6. ผู้ให้บริการ

การจำกัดอัตราช่วยปกป้องโครงสร้างพื้นฐานและโควตาผู้ให้บริการ อีกทั้งยังป้องกันไม่ให้ผู้ใช้ที่ใช้งานหนักรายเดียวใช้ช่องเวิร์กเกอร์ที่มีอยู่ทั้งหมด

## **การจัดลำดับความสำคัญอาจมีประโยชน์กว่าคิวรวมคิวเดียว**

เมื่อผลิตภัณฑ์เติบโตขึ้น งานแต่ละรายการอาจไม่ควรมีความสำคัญเท่ากันทั้งหมด ตัวอย่างเช่น:

1. คำขอ TTS แบบโต้ตอบที่สั้นอาจต้องตอบสนองรวดเร็ว
2. งานเอกสารขนาดใหญ่รอได้นานขึ้นเล็กน้อย
3. ผู้ใช้แบบชำระเงินอาจได้รับลำดับความสำคัญในการประมวลผลสูงกว่า
4. งาน API จำนวนมากที่ทำเบื้องหลังอาจใช้ความจุเวิร์กเกอร์แยกต่างหาก

สถาปัตยกรรมที่เป็นไปได้คือ:

**คิวความสำคัญสูง → เวิร์กเกอร์เร็ว**

**คิวปกติ → เวิร์กเกอร์ทั่วไป**

**คิวจำนวนมาก → เวิร์กเกอร์ประมวลผลชุดงาน**

การออกแบบที่แน่นอนขึ้นอยู่กับรูปแบบการใช้งาน แต่การแยกภาระงานช่วยป้องกันไม่ให้งานใหญ่เพียงไม่กี่งานทำให้คำขอสั้นทุกคำขอล่าช้า

## **ขั้นตอนที่ 15: ติดตามการใช้งานและต้นทุน**

ผู้ให้บริการ TTS ต่างรายอาจคิดค่าบริการต่างกัน บางรายคิดตามจำนวนอักขระ บางรายคิดตามโทเค็น บางรายคิดตามระยะเวลาเสียงที่สร้าง และบางรายใช้รูปแบบราคาที่ซับซ้อนกว่า

ระบบโปรดักชันควรทราบคร่าว ๆ ว่าแต่ละงานใช้ทรัพยากรเท่าใด เมตริกที่มีประโยชน์ได้แก่:

1. อักขระขาเข้า
2. โทเค็นขาเข้า
3. ระยะเวลาที่สร้างขึ้น
4. ผู้ให้บริการ
5. โมเดล
6. ประเภทเสียง
7. จำนวนครั้งที่ลองใหม่
8. ต้นทุนผู้ให้บริการโดยประมาณ
9. เครดิตผู้ใช้ที่ใช้ไป

หากไม่มีการติดตามการใช้งาน ก็ยากที่จะทราบว่าฟีเจอร์ทำกำไรหรือไม่ หรือผู้ให้บริการรายใดมีค่าใช้จ่ายสูงขึ้นอย่างไม่คาดคิด

## **เรียกเก็บเงินเพียงครั้งเดียว**

การเรียกเก็บเงินและการลองใหม่ต้องประสานกันอย่างระมัดระวัง หากผู้ให้บริการล้มเหลวสามครั้งก่อนสำเร็จ โดยทั่วไปไม่ควรเรียกเก็บเงินจากผู้ใช้แยกกันสามครั้งสำหรับคำขอสร้างเดียวกันในเชิงตรรกะ

หากงานทั้งหมดล้มเหลวถาวร ระบบของคุณต้องมีนโยบายชัดเจนว่าจะคืนหรือปล่อยเครดิตที่สำรองไว้หรือไม่ Idempotency สำคัญอย่างยิ่งในเรื่องนี้ การเรียกเก็บเงินควรยึดวงจรชีวิตของงานเชิงตรรกะ ไม่ใช่จำนวนครั้งที่ลองใหม่ภายในระบบ

## **ขั้นตอนที่ 16: เพิ่มความสามารถในการสังเกตการณ์ระบบก่อนที่จะจำเป็น**

เมื่อผู้ใช้รายงานว่า TTS ช้า ข้อมูลนั้นเพียงอย่างเดียวไม่ได้บอกว่าปัญหาอยู่ตรงไหน งานอาจใช้เวลา:

1. 20 วินาทีรออยู่ในคิว
2. 2 วินาทีภายในเวิร์กเกอร์
3. 30 วินาทีรอผู้ให้บริการ
4. 10 วินาทีประมวลผลเสียง
5. 5 วินาทีอัปโหลดเอาต์พุต

หากไม่มีการวัด ทุกขั้นตอนจะดูเหมือนเป็นคำขอเดียวที่ช้า

### **เมตริก TTS ที่มีประโยชน์**

ติดตามเมตริก เช่น:

1. เวลาแฝงของคำขอ API
2. ความลึกของคิว
3. เวลารอในคิว
4. จำนวนเวิร์กเกอร์ที่ทำงานอยู่
5. เวลาตอบกลับของผู้ให้บริการ
6. อัตราความสำเร็จในการสร้าง
7. อัตราข้อผิดพลาดแยกตามผู้ให้บริการ
8. อัตรา 429
9. อัตราการลองใหม่
10. ระยะเวลาประมวลผลเสียง
11. ระยะเวลาอัปโหลด
12. ระยะเวลารวมของงาน
13. ต้นทุนต่องาน

### **วัดผู้ให้บริการแยกกัน**

หากรองรับผู้ให้บริการหลายราย เมตริกรวมอาจซ่อนข้อมูลสำคัญ ตัวอย่างเช่น อัตราความสำเร็จโดยรวมอาจอยู่ที่ 98% ขณะที่ผู้ให้บริการรายหนึ่งลดลงเหลือ 85%

ดังนั้น เมตริกควรกรองตามมิติต่าง ๆ ได้ เช่น:

1. ผู้ให้บริการ
2. โมเดล
3. เสียง
4. ภาษา
5. เวิร์กเกอร์
6. ภูมิภาค

## **บันทึกควรมี ID งาน**

ระบบแบบกระจายตรวจแก้ปัญหาได้ง่ายขึ้นเมื่อทุกบรรทัดบันทึกที่เกี่ยวข้องกับคำขอมีตัวระบุงานเดียวกัน ID เดียวกันอาจปรากฏใน:

1. บันทึก API
2. ข้อความในคิว
3. บันทึกเวิร์กเกอร์
4. การเรียกผู้ให้บริการ
5. การดำเนินการด้านพื้นที่จัดเก็บ

เมื่อเกิดข้อผิดพลาด คุณสามารถค้นหา ID งานหนึ่งรายการและสร้างเส้นทางการทำงานทั้งหมดขึ้นมาใหม่ได้

## **จะเกิดอะไรขึ้นเมื่อผู้ให้บริการ TTS ล่ม?**

ผู้ให้บริการภายนอกย่อมขัดข้องในที่สุด ดังนั้นสถาปัตยกรรมที่ทนทานจึงควรถือว่าเรื่องนี้เกิดขึ้นได้ เมื่ออัตราความล้มเหลวเพิ่มขึ้น ระบบของคุณสามารถ:

1. ลดความถี่ของการลองใหม่
2. ลดจำนวนการเรียกผู้ให้บริการพร้อมกันชั่วคราว
3. หยุดคิวที่ได้รับผลกระทบชั่วคราว
4. กำหนดเส้นทางคำขอที่เข้าเกณฑ์ไปยังผู้ให้บริการรายอื่น
5. แจ้งผู้ใช้ว่าการประมวลผลล่าช้า

โดยทั่วไป กลยุทธ์ที่แย่ที่สุดคือส่งคำขอลองใหม่เพิ่มขึ้นเรื่อย ๆ ไปยังผู้ให้บริการที่กำลังขัดข้องอยู่แล้ว

## **พิจารณาใช้ Circuit Breaker**

Circuit breaker สามารถหยุดคำขอที่ส่งไปยังผู้ให้บริการชั่วคราวหลังเกิดความล้มเหลวซ้ำ ๆ แนวคิดโดยสรุป:

**ผู้ให้บริการปกติ → อนุญาตคำขอ**

**ล้มเหลวซ้ำ → วงจรเปิด → บล็อกคำขอชั่วคราว**

**ทดสอบการกู้คืนสำเร็จ → เปิดใช้งานผู้ให้บริการอีกครั้ง**

วิธีนี้ช่วยป้องกันไม่ให้การพึ่งพาระบบที่ล้มเหลวรายเดียวใช้ความจุเวิร์กเกอร์จำนวนมาก

## **แล้ว TTS แบบสตรีมมิงล่ะ?**

ภาระงาน TTS ไม่จำเป็นต้องทำงานแบบอะซิงโครนัสทั้งหมด ผู้ช่วยเสียงและระบบสนทนาแบบเรียลไทม์อาจต้องเริ่มเล่นเสียงพูดก่อนที่เสียงทั้งหมดจะถูกสร้างเสร็จ

ระบบเหล่านี้อาจใช้:

**สตรีมข้อความ → สตรีม TTS → ชิ้นส่วนเสียง → เล่นบนไคลเอนต์**

สิ่งที่ให้ความสำคัญจะแตกต่างออกไป:

1. เวลาจนได้ยินเสียงแรก
2. เวลาแฝงของสตรีมมิง
3. การขัดจังหวะ
4. ความเสถียรของการเชื่อมต่อ

ดังนั้น แพลตฟอร์มโปรดักชันอาจรองรับสองเส้นทางแยกกัน:

**TTS เรียลไทม์ → เส้นทางสตรีมมิง**

**TTS แบบยาว → คิวและเส้นทางงานเบื้องหลัง**

การบังคับให้ภาระงานทั้งสองประเภทผ่านสถาปัตยกรรมเดียวกันทุกประการ อาจทำให้ปรับแต่งระบบได้ยากโดยไม่จำเป็น

## **สถาปัตยกรรม TTS API เทียบกับสถาปัตยกรรม SRT-to-Speech**

โดยทั่วไป TTS API ปกติเริ่มจากข้อความ ส่วนระบบ SRT-to-Speech เริ่มจากบล็อกคำบรรยายที่มีไทม์ไลน์กำกับอยู่แล้ว

ไปป์ไลน์ TTS พื้นฐานอาจเป็น:

**ข้อความ → คิว → TTS → เสียง**

เวิร์กโฟลว์ SRT อาจเป็น:

**SRT → แยกวิเคราะห์บล็อก → TTS → วัดระยะเวลา → ปรับเวลา → รวมเสียง**

รูปแบบ SRT เพิ่มปัญหาหลายอย่าง:

1. การรักษาการประทับเวลา
2. ระยะเวลาเป้าหมาย
3. การจับคู่ผู้พูด
4. ความยาวของคำแปล
5. การซิงโครไนซ์เสียง
6. การลองใหม่ระดับบล็อก

## **ข้อผิดพลาดทั่วไปในการออกแบบสถาปัตยกรรม TTS**

### **1. เรียกผู้ให้บริการโดยตรงจากคำขอ HTTP ทุกครั้ง**

วิธีนี้ง่ายในช่วงแรก แต่เปราะบางเมื่อใช้กับภาระงานที่ใช้เวลานาน

### **2. ใช้การทำงานพร้อมกันแบบไม่จำกัด**

การมีเวิร์กเกอร์มากขึ้นไม่ได้ช่วย หากผู้ให้บริการ CPU หรือเครือข่ายกลายเป็นคอขวด

### **3. ลองใหม่ทุกข้อผิดพลาด**

ข้อผิดพลาดการตรวจสอบที่ถาวรไม่ควรเข้าสู่วงจรการลองใหม่ไม่รู้จบ

### **4. สร้างบล็อกที่สำเร็จแล้วขึ้นมาใหม่**

งานขนาดใหญ่ควรเก็บงานที่เสร็จแล้วไว้ และลองใหม่เฉพาะส่วนที่ล้มเหลว

### **5. จัดเก็บเสียงสำคัญไว้บนดิสก์ภายในเครื่องเท่านั้น**

คอนเทนเนอร์เวิร์กเกอร์และเซิร์ฟเวอร์ชั่วคราวไม่ควรกลายเป็นที่จัดเก็บสินทรัพย์ถาวร

### **6. มองข้ามขีดจำกัดเฉพาะของผู้ให้บริการ**

ผู้ให้บริการแต่ละรายอาจต้องใช้กลยุทธ์การทำงานพร้อมกันและการจำกัดอัตราที่ต่างกัน

### **7. เพิ่มการมอนิเตอร์หลังเกิดปัญหาเท่านั้น**

หากไม่มีเมตริก ปัญหาด้านประสิทธิภาพก็จะกลายเป็นการคาดเดา

### **8. รวมภาระงานทุกประเภทไว้ในคิวเดียว**

เอกสารขนาดใหญ่มากหนึ่งรายการอาจทำให้คำขอแบบโต้ตอบขนาดเล็กหลายสิบรายการล่าช้า หากไม่จัดลำดับความสำคัญของภาระงานอย่างเหมาะสม

## **สถาปัตยกรรมที่ดีเริ่มต้นอย่างเรียบง่ายได้**

คุณไม่จำเป็นต้องสร้างทุกองค์ประกอบตั้งแต่วันแรก แอปพลิเคชัน TTS ระยะแรกอาจเริ่มต้นด้วย:

**API → ผู้ให้บริการ → พื้นที่จัดเก็บ**

จากนั้น เมื่อการใช้งานเติบโตขึ้น:

**API → คิว → เวิร์กเกอร์ → ผู้ให้บริการ → พื้นที่จัดเก็บ**

และต่อมา:

**API → แคช → คิวตามลำดับความสำคัญ → กลุ่มเวิร์กเกอร์ → ตัวกำหนดเส้นทางผู้ให้บริการ → ผู้ให้บริการหลายราย → พื้นที่จัดเก็บ/CDN → Webhooks + การมอนิเตอร์**

สถาปัตยกรรมควรเติบโตตามคอขวดที่เกิดขึ้นจริง แทนที่จะซับซ้อนตามทฤษฎี สิ่งสำคัญคือเลือกขอบเขตที่ช่วยให้ปรับปรุงในอนาคตได้

## **ควรเพิ่มคิวเมื่อใด?**

คิวจะมีประโยชน์มากขึ้นเมื่อ:

1. การสร้างเสียงอาจใช้เวลานานกว่าสองสามวินาที
2. ผู้ใช้ส่งข้อความยาว
3. งานมีหลายบล็อก
4. คุณชนขีดจำกัดของผู้ให้บริการเป็นประจำ
5. ปริมาณการใช้งานมาเป็นระลอก
6. คุณต้องการการลองใหม่ที่เชื่อถือได้
7. คุณต้องการปรับขนาดเวิร์กเกอร์แยกจาก API

หากทุกคำขอมีขนาดเล็กและเสร็จเกือบจะทันที ในช่วงแรกอาจยังไม่จำเป็นต้องมีคิว

## **ควรเพิ่มผู้ให้บริการหลายรายเมื่อใด?**

การรองรับผู้ให้บริการหลายรายเหมาะสมเมื่อมีเหตุผลที่ชัดเจน เช่น:

1. ต้องใช้เสียงที่แตกต่างกัน
2. ผู้ให้บริการรายหนึ่งไม่มีภาษาที่ต้องการ
3. คุณต้องการความจุรวมที่สูงขึ้น
4. คุณต้องการระดับราคาที่แตกต่างกัน
5. คุณต้องการผู้ให้บริการสำรองสำหรับภาระงานสำคัญ

การเพิ่มผู้ให้บริการเพื่อความสวยงามทางสถาปัตยกรรมเพียงอย่างเดียวอาจเพิ่มภาระการดูแลรักษาโดยไม่ได้สร้างคุณค่ามากนัก

## **ควรแคชเอาต์พุต TTS เมื่อใด?**

การแคชมีประโยชน์อย่างยิ่งเมื่อ:

1. มีการสร้างเนื้อหาเดิมบ่อยครั้ง
2. การเรียกผู้ให้บริการ TTS มีค่าใช้จ่ายสูง
3. เอาต์พุตบางประเภทมีความคงที่เพียงพอที่จะนำกลับมาใช้ซ้ำ
4. ผู้ใช้ลองใหม่หรือเปิดโปรเจ็กต์เดิมซ้ำบ่อยครั้ง
5. มีการแก้ไขเพียงไม่กี่บล็อกในโปรเจ็กต์ขนาดใหญ่แต่ละครั้ง

แม้จะใช้เสียงทั้งชุดซ้ำไม่ได้เสมอไป การแคชระดับบล็อกก็ยังช่วยประหยัดได้มาก

## **TTS โปรดักชันเป็นปัญหาด้านการประสานงานระบบ**

โมเดล TTS จริงเป็นเพียงองค์ประกอบหนึ่ง ระบบโปรดักชันต้องประสานงานระหว่าง:

**ผู้ใช้ + งาน + คิว + เวิร์กเกอร์ + ผู้ให้บริการ + เสียง + พื้นที่จัดเก็บ + การเรียกเก็บเงิน + การมอนิเตอร์**

นี่อธิบายได้ว่าทำไมการสาธิต TTS ในเครื่องจึงสร้างได้รวดเร็ว ขณะที่แพลตฟอร์ม TTS สาธารณะที่เชื่อถือได้ต้องใช้ความพยายามด้านวิศวกรรมมากกว่ามาก ความซับซ้อนมาจากทุกสิ่งรอบตัวโมเดล

## **ข้อคิดส่งท้าย**

ควรออกแบบ Text-to-Speech API สำหรับระบบโปรดักชันโดยคำนึงถึงความล้มเหลว การทำงานพร้อมกัน และการประมวลผลที่ใช้เวลานานตั้งแต่เริ่มต้น

สถาปัตยกรรมหลักนั้นตรงไปตรงมา:

**รับคำขอ → ตรวจสอบ → ใช้เอาต์พุตเดิมซ้ำเมื่อทำได้ → สร้างงาน → ใส่งานเข้าคิว → สร้างเสียงพูด → ลองใหม่เมื่อเกิดความล้มเหลวที่กู้คืนได้ → จัดเก็บเสียง → ส่งคืนผลลัพธ์**

เมื่อปริมาณการใช้งานเพิ่มขึ้น ชั้นเพิ่มเติมอย่างการกำหนดเส้นทางผู้ให้บริการ คิวตามลำดับความสำคัญ การประมวลผลระดับบล็อก การควบคุมขีดจำกัดอัตรา การติดตามต้นทุน callbacks และการสังเกตการณ์ระบบก็มีความสำคัญมากขึ้นเรื่อย ๆ

บทเรียนที่สำคัญที่สุดคือ โดยทั่วไปการสร้างเสียงพูดเป็นส่วนที่ง่าย ความท้าทายที่แท้จริงในระบบโปรดักชันคือการสร้างระบบที่สร้างเสียงพูดได้อย่างน่าเชื่อถือสำหรับผู้ใช้จำนวนมาก ผ่านผู้ให้บริการหลายราย พร้อมควบคุมต้นทุนและความล้มเหลว
