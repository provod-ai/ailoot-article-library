# Gemini: เลือกระหว่างแอปกับ API

> คู่มือปฏิบัติในการเลือกระหว่างแอป Gemini กับ API ประเมินโมเดล และประมาณค่าใช้จ่ายในการใช้งาน



Gemini ใช้ได้ผ่านแอปสำหรับผู้ใช้ทั่วไปของ Google หรือผสานเข้ากับซอฟต์แวร์ผ่าน API จุดเริ่มต้นที่เหมาะสมขึ้นอยู่กับว่าคุณต้องการทำงานด้วยตนเองหรือสร้างขั้นตอนงานที่ทำซ้ำได้สำหรับผู้อื่น

## เริ่มจากงานที่ต้องทำ

สำหรับงานครั้งเดียว เช่น ร่างข้อความหรือสำรวจแนวคิด แอปแบบโต้ตอบเป็นพื้นที่ให้ถามคำถามและปรับคำตอบ ตรวจสอบผลก่อนนำไปใช้ เพราะคำตอบที่อ่านคล่องอาจยังมีข้อผิดพลาด ขาดบริบท หรืออ้างแหล่งที่มาไม่ถูกต้อง

API มีประโยชน์เมื่อแอปพลิเคชันต้องส่งข้อมูลเข้าและประมวลผลข้อมูลออกเป็นส่วนหนึ่งของขั้นตอนงาน เช่น แอปสนับสนุนอาจสรุปคำร้องให้ผู้ตรวจที่เป็นมนุษย์ นักพัฒนาต้องจัดการคำสั่ง การเข้าถึงข้อมูล ข้อผิดพลาด และวิธีแสดงหรือจัดเก็บผลลัพธ์

แอปและ API เป็นผลิตภัณฑ์คนละตัว อย่าสมมติว่าฟีเจอร์ ขีดจำกัด การสมัครสมาชิก หรือการตั้งค่าข้อมูลของตัวหนึ่งจะใช้ได้กับอีกตัวโดยอัตโนมัติ ตรวจเอกสารและการตั้งค่าของผลิตภัณฑ์และบัญชีที่คุณใช้จริง

## เลือกโมเดลให้เหมาะกับงาน

เริ่มจากตัวอย่างที่เป็นตัวแทนสักสองสามรายการ แทนการเลือกโมเดลจากชื่อเพียงอย่างเดียว สำหรับงานสรุป ให้รวมข้อความสั้น ข้อความยาว และกรณีที่ข้อมูลขาดหาย กำหนดว่าคำตอบที่ดีต้องรักษาอะไรไว้ ห้ามแต่งเติมอะไร และควรยาวเพียงใด

หากงานเกี่ยวข้องกับภาพ เสียง หรือข้อมูลเข้าประเภทอื่น ให้ตรวจว่าโมเดลและ endpoint ที่เลือกสนับสนุนรูปแบบที่ต้องการ ประเภทข้อมูลที่รองรับ ขีดจำกัดบริบท และความพร้อมใช้งานอาจแตกต่างกันตามโมเดลและเปลี่ยนแปลงได้ ตรวจตัวเลือกและรูปแบบคำขอล่าสุดได้จาก[เอกสาร Gemini API](https://ai.google.dev/gemini-api/docs) ของ Google

## ประมาณค่าใช้จ่ายด้วยตัวอย่างที่สมจริง

สำหรับขั้นตอนงาน API ให้บันทึกปริมาณข้อมูลเข้าและข้อมูลออกที่ใช้ในชุดคำขอตัวแทนขนาดเล็ก คูณปริมาณที่วัดได้ด้วยราคาที่เผยแพร่ที่เกี่ยวข้อง โดยคำนึงถึงข้อมูลเข้าและข้อมูลออกทุกประเภทที่ใช้ จากนั้นประมาณความถี่ที่จะรันขั้นตอนงานและเผื่อการลองซ้ำกับความยาวคำตอบที่เปลี่ยนแปลง

ถือว่าผลเป็นประมาณการ ไม่ใช่ยอดเรียกเก็บที่รับประกัน ตรวจ[ราคา Gemini API](https://ai.google.dev/gemini-api/docs/pricing) โควตา และการตั้งค่าการเรียกเก็บเงินปัจจุบันของบัญชี การสมัครใช้แอปและการใช้งาน API อาจมีเงื่อนไขต่างกัน

## ประเมินก่อนขยายการใช้งาน

เปรียบเทียบผลกับตัวอย่างที่มนุษย์ตรวจแล้ว ตรวจข้อเท็จจริงของแต่ละคำตอบเทียบกับข้อมูลเข้า รูปแบบที่ขอ และกฎเฉพาะของงาน รวมกรณีที่ยากและกรณีที่โมเดลควรปฏิเสธหรือส่งต่อให้คนตรวจ คำตอบที่ดูถูกแบบไม่ได้ถูกต้องเสมอไป

ติดตามข้อผิดพลาดและปรับขั้นตอนงานทีละส่วน ได้แก่ คำสั่ง การเตรียมข้อมูลเข้า โมเดล หรือการตรวจสอบผลลัพธ์ รันทดสอบชุดเดิมซ้ำหลังเปลี่ยนแปลง หากโมเดลหรือประเภทข้อมูลขาเข้าเปลี่ยน ให้ประเมินผลใหม่แทนการสมมติว่าผลประเมินเดิมยังใช้ได้

## จัดการข้อมูลและข้อผิดพลาดอย่างรอบคอบ

ส่งเฉพาะข้อมูลที่จำเป็นต่องานและตรวจการตั้งค่าการจัดการข้อมูลของผลิตภัณฑ์ที่เกี่ยวข้องก่อนใช้ข้อมูลอ่อนไหว ตรวจสอบผลลัพธ์ก่อนให้แอปพลิเคชันดำเนินการตาม วางแผนรับมือขีดจำกัดอัตรา การหมดเวลา และผลลัพธ์ที่ไม่ครบ แสดงข้อผิดพลาดที่ดำเนินการต่อได้หรือส่งกรณีไปตรวจทาน แทนการถือว่าข้อผิดพลาดเป็นงานที่เสร็จแล้วโดยไม่แจ้ง

สำหรับคำขอที่อาจกระตุ้นการดำเนินการภายนอก ให้บันทึกการดำเนินการและตรวจสถานะก่อนลองซ้ำ การตอบกลับที่สูญหายระหว่างทางไม่ได้พิสูจน์ว่าการดำเนินการล้มเหลว
