# การเพิ่มประสิทธิภาพต้นทุนการอนุมาน LLM: กลยุทธ์เพื่อลดค่าใช้จ่ายด้านโครงสร้างพื้นฐาน AI

> คู่มือเชิงปฏิบัติเกี่ยวกับต้นทุนการอนุมาน LLM และวิธีลดต้นทุน ตั้งแต่การประมวลผลแบบแบตช์และการควอนไทซ์ ไปจนถึงการเปรียบเทียบ API กับการโฮสต์เอง



## บทนำ

ต้นทุนการอนุมานเป็นค่าใช้จ่ายในการดำเนินงานที่เกิดขึ้นซ้ำสำหรับผลิตภัณฑ์ที่ขับเคลื่อนด้วย AI และเพิ่มขึ้นตามการใช้งาน ต้นทุนขึ้นอยู่กับโมเดล เวิร์กโหลด ฮาร์ดแวร์ และการตั้งค่าระบบให้บริการ เทคนิคการเพิ่มประสิทธิภาพประกอบด้วยการควอนไทซ์ การประมวลผลแบบแบตช์ การแคช และการเลือกโมเดล ผลกระทบต่อค่าใช้จ่ายและคุณภาพของผลลัพธ์ขึ้นอยู่กับเวิร์กโหลดแต่ละแบบและควรวัดผล

## องค์ประกอบของต้นทุนการอนุมาน

ต้นทุนการอนุมานได้รับอิทธิพลจากการประมวลผล หน่วยความจำ และการเคลื่อนย้ายข้อมูล

### การประมวลผล

ในการถอดรหัสแบบถดถอยอัตโนมัติมาตรฐาน แต่ละขั้นจะทำนายโทเค็นใหม่หนึ่งโทเค็นต่อหนึ่งลำดับ ความต้องการด้านการประมวลผลขึ้นอยู่กับขนาดโมเดล สถาปัตยกรรม ความแม่นยำ และวิธีการให้บริการ

### หน่วยความจำ

น้ำหนักของโมเดลใช้หน่วยความจำ GPU ส่วนแคชคีย์-แวลู (KV) จัดเก็บข้อมูล attention ระหว่างกลางสำหรับลำดับที่กำลังทำงาน ความต้องการแคชเพิ่มขึ้นตามความยาวของบริบทและจำนวนคำขอที่ทำงานพร้อมกัน จึงอาจเป็นข้อจำกัดสำคัญของการให้บริการ

### แบนด์วิดท์

การสร้างแบบ autoregressive เคลื่อนย้ายน้ำหนักโมเดลและข้อมูลแคชผ่านหน่วยความจำซ้ำหลายครั้ง แบนด์วิดท์หน่วยความจำอาจจำกัด throughput และการลดจำนวนไบต์ที่ใช้แทนน้ำหนักอาจช่วยลดการเคลื่อนย้ายข้อมูล

## ข้อแลกเปลี่ยนระหว่างการอนุมานแบบแบตช์กับแบบเรียลไทม์

การประมวลผลแบบแบตช์จะรวมคำขอเข้าด้วยกันเพื่อเพิ่มประสิทธิภาพการใช้ฮาร์ดแวร์ ส่วนการประมวลผลแบบเรียลไทม์ให้ความสำคัญกับเวลาแฝงของการตอบสนอง แบตช์ขนาดใหญ่อาจเพิ่ม throughput ขณะที่การรอคิวอาจเพิ่มเวลาแฝง แนวทางที่เหมาะสมขึ้นอยู่กับรูปแบบการเข้ามาของคำขอและข้อกำหนดด้านเวลาแฝง

สำหรับแอปพลิเคชันอย่างแชต เสียง และการค้นหา การให้บริการที่มีเวลาแฝงต่ำหรือแบตช์ไดนามิกขนาดเล็กอาจเหมาะสม งานออฟไลน์ เช่น การเพิ่มคุณค่าให้ข้อมูล การสร้างเนื้อหา และการวิเคราะห์ข้อมูลปริมาณมาก มักรองรับแบตช์ขนาดใหญ่กว่าได้

## การควอนไทซ์โมเดล: INT8 เทียบกับ INT4 เทียบกับ FP8

การควอนไทซ์ลดจำนวนบิตที่ใช้แทนน้ำหนักโมเดล ซึ่งช่วยลดการใช้หน่วยความจำและความต้องการแบนด์วิดท์ได้ ผลกระทบต่อ throughput ต้นทุน และคุณภาพของโมเดลแตกต่างกันไปตามฮาร์ดแวร์ โมเดล และวิธีการควอนไทซ์ ควรประเมินโมเดลที่ผ่านการควอนไทซ์กับเวิร์กโหลดเป้าหมายก่อนนำไปใช้งาน

### FP8

FP8 ใช้การแทนค่าเลขทศนิยมแบบ 8 บิต การรองรับและผลกระทบต่อคุณภาพขึ้นอยู่กับฮาร์ดแวร์และโมเดล วิธีนี้อาจเป็นจุดเริ่มต้นสำหรับทีมที่กำลังประเมินการอนุมานด้วยความแม่นยำต่ำลง

### INT8

INT8 แทนน้ำหนักด้วยจำนวนเต็ม 8 บิต วิธีอย่าง SmoothQuant และ LLM.int8() ใช้สำหรับควอนไทซ์โมเดล ให้วัดคุณภาพและประสิทธิภาพสำหรับโมเดลและการนำไปใช้งานที่เลือก

### INT4

INT4 ใช้การแทนค่าแบบ 4 บิตและช่วยลดความต้องการหน่วยความจำได้มากขึ้น วิธีอย่าง GPTQ และ AWQ ใช้สำหรับควอนไทซ์น้ำหนัก ผลกระทบต่อคุณภาพอาจแตกต่างกัน จึงควรประเมินผลกับงานที่เกี่ยวข้อง

## การถอดรหัสแบบคาดการณ์ล่วงหน้า

การถอดรหัสแบบคาดการณ์ล่วงหน้าวิธีหนึ่งที่ใช้กันทั่วไปให้โมเดลร่างขนาดเล็กกว่าเสนอแนะโทเค็น แล้วให้โมเดลเป้าหมายตรวจสอบ ประสิทธิภาพขึ้นอยู่กับความถี่ที่โมเดลเป้าหมายยอมรับโทเค็นจากโมเดลร่างและการนำไปใช้งาน วิธีนี้ประเมินได้สำหรับเวิร์กโหลดที่ไวต่อเวลาแฝงและมีข้อจำกัดในการประมวลผลแบบแบตช์

มีการนำการถอดรหัสแบบคาดการณ์ล่วงหน้าไปใช้ในเฟรมเวิร์กการให้บริการ เช่น vLLM และ TensorRT-LLM ให้ทดสอบ throughput เวลาแฝง และพฤติกรรมของผลลัพธ์ในการนำไปใช้งานเป้าหมาย

## การเพิ่มประสิทธิภาพแคช KV

แคช KV จัดเก็บค่า attention ระหว่างกลางสำหรับลำดับที่กำลังทำงาน ความต้องการหน่วยความจำขึ้นอยู่กับสถาปัตยกรรมของโมเดล ความยาวบริบท และจำนวนงานที่ทำงานพร้อมกัน การจัดการแคชอาจส่งผลต่อจำนวนคำขอที่ให้บริการได้ต่อ GPU

### การควอนไทซ์แคช KV

การลดความแม่นยำของรายการในแคช KV ช่วยลดการใช้หน่วยความจำได้ ผลกระทบต่อคุณภาพขึ้นอยู่กับโมเดลและเวิร์กโหลด การรองรับและตัวเลือกการกำหนดค่าในเฟรมเวิร์กการให้บริการแตกต่างกันไป

### การแคชคำนำหน้า

เมื่อคำขอใช้คำนำหน้าร่วมกัน ระบบให้บริการอาจนำการคำนวณที่แคชไว้กลับมาใช้ซ้ำได้ วิธีนี้ช่วยลดงานที่ต้องทำซ้ำสำหรับ system prompt หรือเอกสารบริบทที่ใช้ร่วมกัน ทั้งนี้ขึ้นอยู่กับการนำไปใช้และรูปแบบคำขอ

### PagedAttention

PagedAttention จัดการหน่วยความจำแคช KV เป็นบล็อก โดย vLLM ใช้เพื่อจัดการการจัดสรรและการใช้แคชร่วมกัน ผลในทางปฏิบัติขึ้นอยู่กับเวิร์กโหลดและการกำหนดค่าการให้บริการ

## กลยุทธ์การประมวลผลแบบแบตช์

กลยุทธ์การประมวลผลแบบแบตช์ส่งผลต่อ throughput และเวลาแฝง การประมวลผลแบบแบตช์ไดนามิกและแบบต่อเนื่องเป็นสองวิธีที่ใช้กันทั่วไปในการจัดกำหนดการคำขอ ส่วนการแยกขั้นประมวลผลอินพุตออกจากการถอดรหัสเป็นทางเลือกในการติดตั้งที่ใช้ร่วมกับการประมวลผลแบบแบตช์ได้

### การประมวลผลแบบแบตช์ไดนามิก

การประมวลผลแบบแบตช์ไดนามิกจะรวบรวมคำขอในช่วงเวลาหนึ่งหรือจนกว่าจะถึงเกณฑ์ขนาดแบตช์ จากนั้นจึงประมวลผลพร้อมกัน วิธีนี้ช่วยเพิ่มประสิทธิภาพการใช้ทรัพยากรได้ แต่ช่วงเวลารออาจเพิ่มเวลาแฝง

### การประมวลผลแบบแบตช์ต่อเนื่อง (การประมวลผลแบบแบตช์ระหว่างทำงาน)

การประมวลผลแบบแบตช์ต่อเนื่องสามารถนำลำดับที่เสร็จแล้วออกและเพิ่มลำดับใหม่ ขณะที่ลำดับอื่นยังทำงานต่อไป วิธีนี้ช่วยลดงานที่ไม่มีการใช้งานเมื่อความยาวของผลลัพธ์แตกต่างกัน vLLM, TensorRT-LLM และ TGI มีการนำการประมวลผลแบบแบตช์ต่อเนื่องไปใช้

### การให้บริการแบบแยกส่วน

การให้บริการแบบแยกส่วนจัดวาง prefill ซึ่งประมวลผลบริบทอินพุต และ decode ซึ่งสร้างโทเค็น ไว้บนทรัพยากร GPU แยกกัน ผลต่อประสิทธิภาพขึ้นอยู่กับเวิร์กโหลดและการจัดสรรทรัพยากร

## การกลั่นโมเดลเพื่อลดต้นทุน

การกลั่นความรู้ฝึกโมเดลนักเรียนขนาดเล็กให้สร้างพฤติกรรมที่เลือกไว้ของโมเดลครูขนาดใหญ่ขึ้น โมเดลขนาดเล็กอาจใช้ทรัพยากรน้อยลงสำหรับงานที่กำหนด แต่ผลลัพธ์ขึ้นอยู่กับข้อมูลฝึก วัตถุประสงค์ และการประเมินผล

การกลั่นขึ้นอยู่กับงาน: โมเดลที่ฝึกมาสำหรับการสรุปอาจทำงานสร้างโค้ดได้ไม่ดี ทีมต้องใช้ข้อมูลฝึกและการประเมินผลเฉพาะงานเพื่อพิจารณาว่าโมเดลขนาดเล็กตอบโจทย์ความต้องการหรือไม่ เปรียบเทียบต้นทุนการฝึกและการนำไปใช้งานกับการประหยัดค่าให้บริการที่คาดไว้ ณ ปริมาณเป้าหมาย

## วิธีเปรียบเทียบต้นทุนการอนุมาน

สำหรับ API ข้อความ ให้นำปริมาณโทเค็นอินพุตและเอาต์พุตที่เรียกเก็บเงินมาคูณด้วยอัตราของแต่ละประเภทตามหน่วยคิดเงินของผู้ให้บริการ ใช้อัตราแคชหรือการประมวลผลแบบแบตช์เมื่อเข้าเงื่อนไข หากโฮสต์เอง ให้นำต้นทุนความจุ GPU รวมช่วงที่ไม่ได้ใช้งาน มาบวกกับต้นทุนโครงสร้างพื้นฐานอื่น ๆ และการดำเนินงาน หารยอดรวมแต่ละแบบด้วยจำนวนคำตอบที่นำไปใช้ได้ในช่วงเวลาเดียวกัน แล้วเปรียบเทียบภายใต้เป้าหมายด้านคุณภาพและเวลาแฝงที่เทียบเท่ากัน

## การติดตามต้นทุนต่อคำค้น

ติดตามต้นทุนต่อคำค้นควบคู่กับเวลาแฝงและคุณภาพ ตัวชี้วัดที่เป็นประโยชน์ ได้แก่:

- **ต้นทุนต่อการสร้าง** — ต้นทุนการประมวลผลหารด้วยจำนวนครั้งที่สร้าง โดยติดตามแยกตามโมเดล กรณีใช้งาน และเทมเพลตพรอมป์ต์
- **ต้นทุนต่อโทเค็น** — ต้นทุนการประมวลผลหารด้วยจำนวนโทเค็นเอาต์พุตที่สร้างขึ้น
- **การใช้ GPU** — กิจกรรมของ GPU ระหว่างการสร้างผลลัพธ์ โดยตีความตามบริบทของเวิร์กโหลด
- **อัตราแคชฮิตของ KV** — สัดส่วนของงานที่แคชได้และให้บริการจากแคชคำนำหน้าแทนการคำนวณใหม่

การติดตามอาจเผยให้เห็นพรอมป์ต์ที่ใหญ่เกินไป โมเดลที่มีต้นทุนสูงเกินสัดส่วนเมื่อเทียบกับงาน และการกำหนดค่าการประมวลผลแบบแบตช์ที่ทำให้ GPU ถูกใช้งานไม่เต็มที่ เครื่องมือวัดผลช่วยระบุโอกาสในการเพิ่มประสิทธิภาพ

## ขั้นตอนการเพิ่มประสิทธิภาพ: นำทุกอย่างมารวมกัน

สามารถใช้หลายเทคนิคร่วมกันได้ แต่ผลลัพธ์ขึ้นอยู่กับเวิร์กโหลดและไม่ควรคาดว่าจะทวีคูณ ให้วัดผลของการเปลี่ยนแปลงแต่ละอย่างบนเวิร์กโหลดเป้าหมาย

ลำดับการประเมินที่นำไปใช้ได้จริงมีดังนี้:

1. ประเมินน้ำหนักที่ใช้ความแม่นยำต่ำลง เช่น FP8
2. ประเมินการประมวลผลแบบแบตช์ต่อเนื่องในเฟรมเวิร์กการให้บริการ
3. วัดประโยชน์ของการแคชคำนำหน้าสำหรับคำนำหน้าที่ใช้ซ้ำ
4. ประเมินตัวเลือกความแม่นยำของแคช KV
5. ทดสอบการถอดรหัสแบบคาดการณ์ล่วงหน้าเมื่อการประมวลผลแบบแบตช์มีข้อจำกัด
6. ประเมินน้ำหนัก INT4 สำหรับเส้นทางปริมาณสูงที่เหมาะสม
7. เปรียบเทียบการกลั่นเฉพาะงานกับโมเดลที่มีอยู่

ขั้นตอนแรก ๆ ใช้ฟีเจอร์ของเฟรมเวิร์กการให้บริการและการตั้งค่าแอปพลิเคชันได้ การกลั่นต้องลงทุนด้านการฝึกและการประเมินผลเฉพาะงาน

## สรุป

การเพิ่มประสิทธิภาพต้นทุนการอนุมานเป็นกระบวนการต่อเนื่อง การควอนไทซ์ การถอดรหัสแบบคาดการณ์ล่วงหน้า การจัดการแคช KV การประมวลผลแบบแบตช์ และการกลั่น เป็นทางเลือกที่ควรประเมินกับเวิร์กโหลดเฉพาะ วัดต้นทุน เวลาแฝง และคุณภาพของผลลัพธ์เมื่อมีการเปลี่ยนแปลง

ฮาร์ดแวร์และเฟรมเวิร์กการให้บริการยังคงพัฒนาอย่างต่อเนื่อง ทีมที่วัดประสิทธิภาพและต้นทุนการอนุมานจะตัดสินใจได้อย่างมีข้อมูลเมื่อโมเดลและรูปแบบการใช้งานเปลี่ยนไป
