# ต้นทุนการอนุมาน LLM: อะไรเป็นตัวกำหนดและลดได้อย่างไร

> ทำความเข้าใจปัจจัยหลักที่ส่งผลต่อต้นทุนการอนุมาน LLM และวิธีจัดการการใช้โทเค็น การเลือกโมเดล บริบท และโครงสร้างพื้นฐานในทางปฏิบัติ



การอนุมาน LLM คือการที่โมเดลที่ผ่านการฝึกแล้วทำงานในขณะรันไทม์ โดยแปลงพรอมป์ต์ของคุณเป็นคำตอบทีละโทเค็นบนฮาร์ดแวร์เร่งความเร็วประสิทธิภาพสูงราคาแพง การฝึกสร้างโมเดลขึ้นมาครั้งเดียว ส่วนการอนุมานรันโมเดลนั้นไปเรื่อย ๆ ทุกคำขอ สำหรับผู้ใช้ทุกคน

คำว่า “ไปเรื่อย ๆ” คือประเด็นสำคัญเมื่อพูดถึงงบประมาณ การฝึกเป็นค่าใช้จ่ายลงทุนที่เกิดขึ้นครั้งเดียว ซึ่งคุณอาจอ่านพบในพาดหัวข่าว ส่วนต้นทุนการอนุมานเป็นค่าใช้จ่ายดำเนินงานที่เพิ่มขึ้นตามความสำเร็จ ได้แก่ ผู้ใช้มากขึ้น ฟีเจอร์มากขึ้น เอเจนต์มากขึ้น และค่าใช้จ่ายมากขึ้น ผลรวมค่าใช้จ่ายการอนุมานของผลิตภัณฑ์ที่ประสบความสำเร็จจะแซงหน้าค่าใช้จ่ายการฝึก และไม่หันกลับมามองอีก

หน่วยที่ใช้คิดค่าใช้จ่ายคือโทเค็น ซึ่งมีขนาดประมาณสามในสี่ของคำภาษาอังกฤษ ราคาการอนุมานทั้งหมดคิดเป็นอัตราต่อโทเค็นหนึ่งล้านหน่วย โดยแยกราคาสำหรับอินพุต (พรอมป์ต์และบริบทของคุณ) กับเอาต์พุต (สิ่งที่โมเดลสร้างขึ้น) ต้นทุนต่อโทเค็นนั้นน้อยมาก แต่ปริมาณไม่เคยน้อย ทุกดอลลาร์ที่คุณจะใช้จ่ายกับการอนุมานล้วนคำนวณจากหน่วยนี้

## ต้นทุนการอนุมาน LLM ต่อโทเค็นหมายถึงอะไรกันแน่?

ต้นทุนการอนุมาน LLM ต่อโทเค็นไม่ได้มีเพียงตัวเลขเดียว สำหรับแต่ละโมเดลมีตัวเลขอย่างน้อยสี่ค่า และส่วนต่างระหว่างตัวเลขเหล่านี้เป็นตัวกำหนดค่าใช้จ่ายในระบบใช้งานจริง:

### อัตราค่าอินพุตมาตรฐานเทียบกับเอาต์พุต

ตามที่กล่าวไปข้างต้น เอาต์พุตมีราคาประมาณ 5x ของอินพุต กำหนดจำนวนโทเค็นสูงสุดให้เหมาะกับแต่ละกรณีใช้งาน และสั่งให้โมเดลตอบอย่างกระชับ สัดส่วนที่ลดลงเพียงเล็กน้อย แต่เกิดขึ้นทุกครั้งที่เรียกใช้และต่อเนื่องไปเรื่อย ๆ

### โทเค็นการใช้เหตุผล

โมเดลที่คิดก่อนตอบจะคิดค่าใช้จ่ายของการคิดนั้นเป็นเอาต์พุต ซึ่งเป็นประเภทที่แพง และผู้ใช้จะไม่เห็นเนื้อหาส่วนนั้น หากค่าใช้จ่ายของคุณพุ่งขึ้นทั้งที่ปริมาณการใช้งานไม่ได้เพิ่ม ให้ตรวจดูว่าค่าเริ่มต้นถูกเปลี่ยนเป็นโหมดใช้เหตุผลโดยไม่รู้ตัวหรือไม่ บางครั้งการใช้เหตุผลที่ลึกขึ้นก็คุ้มกับค่าใช้จ่าย แต่บ่อยครั้งไม่มีใครตรวจสอบ

## อะไรทำให้ต้นทุนการอนุมาน LLM สูงขึ้น?

ปัจจัยห้าข้อ เรียงตามความถี่ที่ใช้อธิบายใบเรียกเก็บเงินที่น่าตกใจ:

4.  **เอาต์พุตที่ไม่มีขีดจำกัด** ค่าเริ่มต้นที่ตอบยืดยาว ไม่ได้กำหนดจำนวนโทเค็นสูงสุด และเปิดโหมดใช้เหตุผลทิ้งไว้แม้กับงานง่าย ๆ ล้วนทำให้ค่าใช้จ่ายส่วนที่แพงพุ่งสูง ไม่มีใครอนุมัติค่าใช้จ่ายนี้ เพราะมันมาในรูปคำตอบยืดยาวทีละคำตอบ ซึ่งเป็นเหตุผลว่าทำไมค่าใช้จ่ายจึงสะสมโดยไม่มีใครติดตาม

## จะลดต้นทุนการอนุมาน LLM ได้อย่างไร?

การเพิ่มประสิทธิภาพต้นทุน LLM ใช้คันโยกแปดข้อ เรียงตามความพยายามเมื่อเทียบกับเงินที่ประหยัดได้:

2.  **กำหนดเส้นทางโดยพิจารณาต้นทุน เวลาแฝง และคุณภาพร่วมกัน** ระบบกำหนดเส้นทางที่ดีจะให้คะแนนทั้งสามด้าน การกำหนดเส้นทางโดยดูเฉพาะคุณภาพเป็นวิธีทำให้งบประมาณหมด แม้แต่ระบบสองระดับที่เริ่มจากโมเดลราคาถูก แล้วเลื่อนไปใช้โมเดลอื่นเมื่อความเชื่อมั่นต่ำ ก็ให้ประโยชน์ได้เกือบทั้งหมดและใช้เวลาพัฒนาราวหนึ่งสุดสัปดาห์

4.  **ควบคุมเอาต์พุต** กำหนดจำนวนโทเค็นสูงสุดตามกรณีใช้งาน สั่งให้ตอบอย่างกระชับ และอย่าจ่ายอัตราเอาต์พุตไปกับคำพูดสุภาพที่ไม่จำเป็น

8.  **วัดค่าใช้จ่ายแยกตามฟีเจอร์ก่อนปรับแต่งสิ่งใด** ข้อนี้อาจฟังไม่สบายใจ แต่จะกำหนดเป้าหมายให้คันโยกทั้งเจ็ดข้อข้างต้นไม่ได้ หากไม่รู้ว่าผลิตภัณฑ์ ฟีเจอร์ หรือลูกค้ารายใดเป็นต้นเหตุของค่าใช้จ่าย การปรับแต่งต้นทุนการอนุมาน LLM โดยไม่จัดสรรค่าใช้จ่ายก็เหมือนการเดาอย่างมั่นใจ และมักลงเอยด้วยการปรับแชตบอตที่มองเห็นได้ ขณะที่ไปป์ไลน์เบื้องหลังใช้ 80% ของงบประมาณ

## ควรโฮสต์เองเพื่อลดต้นทุนการอนุมานหรือไม่?

**ทำก็ต่อเมื่อคุณสามารถใช้ฮาร์ดแวร์ให้คุ้มค่าได้** การโฮสต์เองเปลี่ยนจากการคิดค่าบริการตามโทเค็นเป็นรายชั่วโมง และความคุ้มค่าทางธุรกิจทั้งหมดขึ้นอยู่กับอัตราการใช้งาน ทราฟฟิกปริมาณสูงที่ต่อเนื่องและคาดการณ์ได้บนคลัสเตอร์ที่ใช้งานเต็มที่มีต้นทุนต่ำกว่าอัตรา API อย่างชัดเจน ส่วนทราฟฟิกที่ขึ้นลงเป็นช่วง ๆ หรือมีปริมาณปานกลางบน GPU ที่ไม่ได้ใช้งาน ย่อมแพงกว่า API ทุกครั้ง และคุณยังต้องรับภาระดูแลทีมปฏิบัติการเป็นการชดเชย

**จากนั้นจึงทดสอบประสิทธิภาพอย่างตรงไปตรงมา:** ข้อมูลเกณฑ์มาตรฐานการอนุมาน LLM ที่เผยแพร่วัดจำนวนโทเค็นต่อวินาทีต่อ GPU โดยใช้ขนาดแบตช์และความยาวบริบทที่คุณใช้งานจริง ซึ่งเป็นสิ่งที่แยกแผนงานออกจากความหวัง เศรษฐศาสตร์ของการอนุมาน AI ในกรณีนี้สนับสนุนคำตอบที่เรียบง่าย หากปริมาณการใช้งานยังไม่แน่นอนหรือทีมไม่พร้อมทุ่มเทงานวิศวกรรม ให้ใช้ API ต่อไปและนำแรงไปลงกับคันโยกทั้งแปดข้อข้างต้น

## จะติดตามต้นทุนการอนุมาน LLM ในระดับผลิตภัณฑ์ได้อย่างไร?

เริ่มจากคำถามที่แดชบอร์ดของผู้ให้บริการตอบไม่ได้: ฟีเจอร์ ทีม หรือลูกค้ารายใดก่อให้เกิดค่าใช้จ่ายนี้ และคุ้มค่าหรือไม่? คอนโซล API แสดงยอดรวมแยกตามคีย์ แต่ยอดรวมเหล่านั้นตอบไม่ได้เมื่อ CFO ต้องการทราบผลกระทบของฟีเจอร์ AI ใหม่ต่ออัตรากำไรเป็นตัวเลขภายในวันพฤหัสบดี

**การหาคำตอบต้องมีสามชั้น** ติดแท็กการใช้งานตามฟีเจอร์และสภาพแวดล้อม เพื่อให้รู้ว่าใครรับผิดชอบการใช้งานนั้น รวมข้อมูลจากผู้ให้บริการต่าง ๆ ไว้ในมุมมองเดียว เพราะสแต็กที่ใช้หลายโมเดลเป็นเรื่องปกติ และผู้ขายแต่ละรายรายงานข้อมูลต่างกัน จากนั้นจัดสรรค่าใช้จ่ายตามเศรษฐศาสตร์ต่อหน่วย ได้แก่ ค่าใช้จ่ายการอนุมานต่อฟีเจอร์ ต่อลูกค้า และต่อธุรกรรม ซึ่งเป็นตัวหารที่ธุรกิจใช้จริง
