# 7 เกณฑ์ในการเลือกเครื่องมือกำหนดเส้นทาง LLM

> ประเมินเครื่องมือกำหนดเส้นทาง LLM สำหรับระบบใช้งานจริงจากคุณภาพการกำหนดเส้นทาง การบังคับใช้นโยบาย การควบคุมข้อมูล เพดานค่าใช้จ่าย การตรวจสอบย้อนกลับ และความพยายามในการนำไปใช้งาน



ระบบ LLM สำหรับใช้งานจริงแทบไม่ล้มเหลวเพราะทีมเลือกโมเดลเรือธงผิด แต่ล้มเหลวเพราะแต่ละแอปพลิเคชันเลือกผู้ให้บริการแยกกัน การควบคุมค่าใช้จ่ายอยู่ในสเปรดชีต ข้อมูลอ่อนไหวไปถึงปลายทางโดยไม่มีการตรวจสอบ และไม่มีใครสามารถตรวจสอบย้อนกลับได้ว่าทำไมจึงสร้างคำตอบหนึ่งขึ้นมา เครื่องมือกำหนดเส้นทาง LLM ที่ดีที่สุดช่วยแก้ช่องว่างในการดำเนินงานนี้ โดยทำหน้าที่เป็นจุดควบคุมระหว่างแอปพลิเคชันกับผู้ให้บริการโมเดล

สำหรับผู้นำด้านวิศวกรรม การตัดสินใจไม่ได้มีเพียงว่าจะเลือกเราเตอร์ตัวใดที่เลือกโมเดลราคาถูกที่สุดได้ คำถามที่เป็นประโยชน์คือ แพลตฟอร์มสามารถบังคับใช้การเลือกโมเดล นโยบายความปลอดภัย การจัดการข้อมูล และการควบคุมค่าใช้จ่ายกับทุกคำขอได้หรือไม่ โดยไม่บังคับให้ทีมผลิตภัณฑ์แต่ละทีมสร้างและดูแลมิดเดิลแวร์ของตนเอง

## เครื่องมือกำหนดเส้นทาง LLM ควรทำอะไรได้บ้างในระบบใช้งานจริง

ในความหมายที่แคบที่สุด การกำหนดเส้นทางคือการเลือกโมเดลสำหรับคำขอที่เข้ามา เราเตอร์อาจเลือกตามราคา ความพร้อมใช้งาน เวลาแฝง ความสามารถของโมเดล เส้นทางที่ตั้งชื่อไว้ หรือกฎที่ทีมแพลตฟอร์มกำหนด นอกจากนี้ เราเตอร์ควรเปลี่ยนไปใช้ผู้ให้บริการสำรองได้เมื่อผู้ให้บริการที่ต้องการไม่สามารถรองรับทราฟฟิกได้

สิ่งเหล่านี้จำเป็น แต่ยังไม่เพียงพอ คำขอในระบบใช้งานจริงมีวงจรชีวิต และการเลือกโมเดลเป็นเพียงขั้นตอนหนึ่งเท่านั้น ก่อนที่คำขอใดจะออกจากสภาพแวดล้อมของคุณ แพลตฟอร์มควรตรวจคัดกรองการโจมตีแบบ prompt injection และความพยายาม jailbreak ใช้มาตรการป้องกันข้อมูลสูญหาย แล้วจึงกำหนดเส้นทางไปยังผู้ให้บริการและโมเดลที่ได้รับอนุมัติ ก่อนส่งคำตอบกลับไปยังแอปพลิเคชัน ระบบควรตรวจสอบผลลัพธ์ตามนโยบายที่คุณกำหนดไว้

ลำดับนี้สำคัญ การกำหนดเส้นทางคำขอก่อนใช้มาตรการควบคุมพรอมป์ต์และข้อมูลทำให้การตัดสินใจด้านธรรมาภิบาลที่สำคัญที่สุดตกอยู่กับแต่ละแอปพลิเคชัน แต่ระนาบควบคุมที่ออกแบบมาอย่างเหมาะสมจะสร้างประตูทางเข้าที่มีการกำกับดูแลเพียงจุดเดียว ซึ่งใช้มาตรการควบคุมอย่างสม่ำเสมอไม่ว่าท้ายที่สุดแล้วผู้ให้บริการรายใดจะเป็นผู้จัดการคำขอนั้น

## 7 ข้อที่ควรตรวจสอบเมื่อประเมินเครื่องมือกำหนดเส้นทาง LLM ที่ดีที่สุด

### 1. การกำหนดเส้นทางหลายผู้ให้บริการต้องคำนึงถึงนโยบาย

เราเตอร์ที่มีประโยชน์รองรับผู้ให้บริการที่ทีมของคุณต้องใช้งานจริง แทนที่จะตั้งสมมติฐานว่าผู้ขายรายเดียวจะเหมาะที่สุดกับทุกภาระงาน ข้อกำหนดด้านความสามารถ เวลาแฝง ราคา และภูมิภาคย่อมแตกต่างกัน งานที่ต้องใช้การให้เหตุผลสูง คำขอจัดประเภทภายในแบบสั้น และผู้ช่วยที่ให้บริการลูกค้า ไม่ควรใช้โมเดลเดียวกันโดยอัตโนมัติ

มองหาเส้นทางที่ตั้งชื่อไว้ กฎการกำหนดเส้นทาง และลำดับความสำคัญที่ช่วยให้ทีมส่วนกลางระบุความแตกต่างเหล่านี้ได้ ความแตกต่างที่สำคัญคือระหว่างระบบที่เพียงเปิดให้ใช้โมเดลจำนวนมาก กับระบบที่นำการตัดสินใจภายใต้การกำกับดูแลมาใช้กับแต่ละคำขอได้ คุณควรตรวจสอบการทำงานของการสลับไปใช้ผู้ให้บริการสำรองโดยอัตโนมัติ และทำความเข้าใจว่าผู้ให้บริการรายใดบ้างที่อนุญาตให้ใช้แทนกันในเส้นทางหนึ่ง

การมีตัวเลือกมากขึ้นย่อมมีต้นทุน เพราะอาจเพิ่มความซับซ้อนในการดำเนินงานเป็นทวีคูณ เครื่องมือที่ดีที่สุดทำให้จัดการความยืดหยุ่นในการเลือกผู้ให้บริการได้ ไม่ใช่แค่มีตัวเลือกให้ใช้

### 2. มาตรการควบคุมความปลอดภัยต้องทำงานก่อนกำหนดเส้นทาง

Prompt injection ไม่ใช่ปัญหาการเลือกผู้ให้บริการ แต่เป็นปัญหาความปลอดภัยของอินพุต หากแอปพลิเคชันของคุณเชื่อมต่อกับโมเดลโดยตรง ทีมต่าง ๆ อาจใช้มาตรการป้องกันไม่สอดคล้องกัน หรือข้ามมาตรการเหล่านั้นเมื่อใกล้ถึงกำหนดส่งงาน

ประเมินว่าชั้นกำหนดเส้นทางใช้ระบบป้องกัน prompt injection และ jailbreak ก่อนเลือกโมเดลหรือไม่ การตรวจสอบเดียวกันนี้ใช้กับการป้องกันข้อมูลสูญหายด้วย เครื่องมือควรรองรับการดำเนินการที่ชัดเจนเมื่อพบข้อมูลอ่อนไหว ได้แก่ บันทึก แจ้งเตือน ปกปิด หรือบล็อก การปกปิดข้อมูลต้องชัดเจนและคาดการณ์ได้ เช่น แทนค่าที่ตรวจพบด้วย `[REDACTED]` เพื่อให้ทีมแอปพลิเคชันเข้าใจว่าโมเดลในขั้นตอนถัดไปจะได้รับข้อมูลใด

การดำเนินการที่เหมาะสมขึ้นอยู่กับเวิร์กโฟลว์ เครื่องมือร่างเอกสารภายในที่มีความเสี่ยงต่ำอาจใช้การแจ้งเตือนและบันทึกการตรวจสอบ ส่วนเวิร์กโฟลว์สำหรับลูกค้าที่อยู่ภายใต้การกำกับดูแลอาจต้องบล็อก สิ่งสำคัญคือนโยบายต้องกำหนดจากส่วนกลาง บังคับใช้อย่างสม่ำเสมอ และไม่ปล่อยให้ขึ้นอยู่กับแนวปฏิบัติที่ไม่เป็นทางการของแต่ละแอปพลิเคชัน

### 3. มองการตรวจสอบผลลัพธ์เป็นมาตรการควบคุมแยกต่างหาก

การป้องกันอินพุตไม่ได้ทำให้ไม่จำเป็นต้องตรวจสอบผลลัพธ์ โมเดลอาจสร้างคำตอบที่ไม่ปลอดภัย ไม่เหมาะสม หรือละเมิดนโยบายได้ แม้พรอมป์ต์จะไม่มีเจตนาร้ายก็ตาม ดังนั้นการตรวจสอบผลลัพธ์ควรเป็นส่วนหนึ่งของเส้นทางคำขอ หลังจากกำหนดเส้นทางและสร้างคำตอบแล้ว

ระหว่างการประเมิน ให้ถามว่าผลการพิจารณาตามนโยบายปรากฏใน trace อย่างไร และผลลัพธ์ที่ถูกบล็อกหรือผ่านการตรวจสอบถูกส่งกลับไปยังแอปพลิเคชันที่เรียกใช้อย่างไร ทีมความปลอดภัยและทีมผลิตภัณฑ์ต้องมีข้อมูลเพียงพอสำหรับวินิจฉัยพฤติกรรม พร้อมหลีกเลี่ยงการเก็บพรอมป์ต์และคำตอบอ่อนไหวไว้นานเกินจำเป็น

เราเตอร์ที่มีการเลือกโมเดลแต่ไม่มีมาตรการควบคุมอินพุตและเอาต์พุตอาจเหมาะกับการทดลอง แต่เมื่อนำไปใช้จริง ยังต้องทำงานผสานระบบอีกมาก

### 4. ต้องบังคับใช้ขีดจำกัดค่าใช้จ่ายได้ ไม่ใช่แค่แนะนำ

การกำกับดูแลค่าใช้จ่าย LLM ทำได้ยากเมื่อผลิตภัณฑ์ ทีม และสภาพแวดล้อมแต่ละแห่งมีข้อมูลรับรองผู้ให้บริการแยกกัน ฝ่ายการเงินดูใบแจ้งหนี้ย้อนหลังได้ แต่ไม่สามารถป้องกันอย่างน่าเชื่อถือไม่ให้เอเจนต์ที่ทำงานเกินควบคุม รูปแบบทราฟฟิกที่ไม่คาดคิด หรือการออกแบบพรอมป์ต์ที่มีข้อบกพร่องสร้างความเสี่ยงเพิ่มเติม

เลือกขอบเขตที่ต้องการใช้เพดานค่าใช้จ่าย เช่น องค์กร ทีม โครงการ หรือเส้นทาง การแจ้งเตือนงบประมาณจะแจ้งเจ้าของงบเมื่อค่าใช้จ่ายถึงเกณฑ์ที่กำหนด หากต้องการทดสอบเพดานแบบตายตัว ให้ตรวจสอบว่าเราเตอร์ปฏิเสธคำขอใหม่ที่มีค่าใช้จ่ายในขอบเขตนั้นทันทีที่บันทึกว่าแตะเพดานแล้ว ตรวจสอบว่าแอปพลิเคชันได้รับข้อผิดพลาดอะไร และเราเตอร์นำคำขอที่อยู่ระหว่างประมวลผลมาพิจารณาในการคิดค่าใช้จ่ายอย่างไร

อย่าสับสนระหว่างการกำหนดเส้นทางตามต้นทุนกับการบังคับใช้งบประมาณ การส่งทราฟฟิกไปยังโมเดลที่มีต้นทุนต่ำกว่าสามารถลดค่าใช้จ่ายเฉลี่ยได้ แต่ไม่อาจรับประกันว่าค่าใช้จ่ายจะอยู่ภายในเพดานที่กำหนด คุณต้องมีทั้งสองความสามารถ พร้อมแบ่งหน้าที่รับผิดชอบระหว่างทีมแพลตฟอร์ม การเงิน และผลิตภัณฑ์อย่างชัดเจน

### 5. ติดตามทุกคำขอโดยไม่เก็บทุกเพย์โหลด

เมื่อมีลูกค้ารายงานคำตอบที่ไม่ดี หรือวิศวกรตรวจสอบสาเหตุที่ค่าใช้จ่ายเพิ่มขึ้น การวิเคราะห์ข้อมูลแบบรวมยังไม่เพียงพอ ทีมต้องมี trace รายคำขอที่แสดงการตัดสินใจเลือกเส้นทาง การเลือกผู้ให้บริการและโมเดล เวลาแฝง ปริมาณการใช้งาน และผลการตรวจสอบตามนโยบาย

อย่างไรก็ตาม การบันทึกพรอมป์ต์และคำตอบแบบเต็มจะสร้างภาระด้านความปลอดภัยและความเป็นส่วนตัวขึ้นเอง การออกแบบที่ดีกว่าคือบันทึกเฉพาะเมทาดาทาเป็นค่าเริ่มต้น และเปิดให้เก็บเพย์โหลดได้เมื่อมีการเลือกเข้าร่วมอย่างชัดเจนเท่านั้น แนวทางนี้มอบหลักฐานด้านการดำเนินงานให้ทีมแพลตฟอร์ม พร้อมทำให้การจัดการข้อมูลได้สัดส่วนกับกรณีใช้งาน

### 6. ความพยายามในการติดตั้งใช้งานเป็นส่วนหนึ่งของการประเมินทางเทคนิค

โครงการกำหนดเส้นทางจะหมดแรงส่งเมื่อจำเป็นต้องเขียนแอปพลิเคชันใหม่ ใช้ไลบรารีไคลเอนต์ใหม่ และเปลี่ยนตรรกะทางธุรกิจในทุกบริการ เครื่องมือที่ใช้งานได้จริงที่สุดใช้เกตเวย์ API ที่เข้ากันได้กับ OpenAI ทำให้การเชื่อมต่อที่มีอยู่คงรูปแบบคำขอเดิมไว้ได้ โดยเปลี่ยนเพียงข้อมูลรับรองและ URL ฐาน

นี่เป็นมากกว่าเรื่องความสะดวก รูปแบบการติดตั้งใช้งานที่มีแรงเสียดทานต่ำทำให้ทีมแพลตฟอร์มเริ่มนำธรรมาภิบาลมาใช้ทีละขั้น วัดพฤติกรรม และนำบริการเพิ่มเติมมาอยู่ภายใต้การควบคุมได้ โดยไม่ต้องรอแผนงานของแต่ละแอปพลิเคชัน ตรรกะของแอปพลิเคชันยังคงเหมือนเดิมทุกไบต์ ขณะที่การตัดสินใจกำหนดเส้นทางและนโยบายย้ายไปอยู่ในชั้นส่วนกลาง

ตรวจสอบว่าแพลตฟอร์มจัดการคีย์ API แบบกำหนดขอบเขต เส้นทาง และการแยกสภาพแวดล้อมอย่างไร การใช้ข้อมูลรับรองสำหรับระบบจริงร่วมกันชุดเดียวอาจเริ่มต้นได้เร็ว แต่ทำให้ความรับผิดชอบลดลงและแยกเหตุการณ์ที่เกิดขึ้นได้ยากขึ้น

### 7. รูปแบบการดำเนินงานต้องเหมาะกับองค์กรของคุณ

ไม่มีเครื่องมือกำหนดเส้นทาง LLM ใดดีที่สุดสำหรับทุกองค์กร สตาร์ตอัปที่มีแอปพลิเคชันเดียวอาจให้ความสำคัญกับการสลับผู้ให้บริการสำรองอย่างรวดเร็วและการมองเห็นค่าใช้จ่าย องค์กรขนาดใหญ่ที่มีหลายทีมอาจต้องการเวิร์กโฟลว์อนุมัติ การเข้าถึงแบบกำหนดขอบเขต บันทึกการตรวจสอบโดยละเอียด การจัดเก็บข้อมูลในสหภาพยุโรป และคำมั่นสัญญาเรื่องเวลาให้บริการตามสัญญา

ประเมินเครื่องมือตามงานที่คุณยังต้องทำเพิ่มเติมรอบ ๆ เครื่องมือนั้น ทีมความปลอดภัยกำหนดนโยบายได้โดยไม่ต้องปรับใช้โค้ดหรือไม่ FinOps ตรวจสอบค่าใช้จ่ายตามหน่วยงานที่รับผิดชอบได้หรือไม่ ทีมวิศวกรรมระบุกฎที่แน่ชัดและการตัดสินใจเลือกโมเดลที่นำไปสู่เหตุการณ์ได้หรือไม่ ทีมกำกับการปฏิบัติตามข้อกำหนดขอหลักฐานได้โดยไม่ต้องให้ผู้พัฒนาไปค้นบันทึกที่กระจัดกระจายหรือไม่

การประเมินที่ดีใช้ทราฟฟิกที่เป็นตัวแทนการใช้งานจริง ไม่ใช่มีเพียงพรอมป์ต์สังเคราะห์ ควรมีคำขอทั่วไปที่ใกล้เคียงกับการใช้งานจริง รูปแบบข้อมูลลับ ความพยายามโจมตีแบบ injection สถานการณ์ผู้ให้บริการหยุดทำงาน และการทดสอบขีดจำกัดงบประมาณ ผลลัพธ์ควรวัดได้ ได้แก่ ใช้การตัดสินใจตามนโยบายได้ถูกต้อง เข้าใจพฤติกรรมการสลับผู้ให้บริการ มีข้อมูล trace พร้อมใช้งาน และไม่มีการเปลี่ยนแปลงแอปพลิเคชันที่ไม่คาดคิด

## แนวทางปฏิบัติสำหรับจัดทำรายชื่อผู้เข้ารอบ

เริ่มจากแยกผลิตภัณฑ์ที่ทำเฉพาะการกำหนดเส้นทางออกจากเกตเวย์ AI ที่มีการกำกับดูแล เครื่องมือที่ทำเฉพาะการกำหนดเส้นทางอาจเหมาะเมื่อองค์กรของคุณมีชั้นความปลอดภัย DLP การสังเกตการณ์ระบบ และการควบคุมค่าใช้จ่ายที่พัฒนามาอย่างดีแล้ว ครอบคลุมทุกการเรียกใช้ LLM ทีมส่วนใหญ่ไม่ได้มีความพร้อมเช่นนั้น โดยเฉพาะเมื่อมีผลิตภัณฑ์และผู้ให้บริการหลายรายเกี่ยวข้อง

จากนั้นทดสอบตัวเลือกที่เหลือด้วยโฟลว์คำขอเดียว ตรวจสอบว่าระบบป้องกันพรอมป์ต์ทำงานก่อน ตามด้วย DLP จากนั้นจึงกำหนดเส้นทาง และปิดท้ายด้วยการตรวจสอบผลลัพธ์ ทดสอบการตั้งค่าการบันทึกข้อมูลเริ่มต้น ไม่ใช่เฉพาะการกำหนดค่าที่มีฟีเจอร์มากที่สุดซึ่งนำมาแสดงในการสาธิต

ตัวเลือกที่ดีที่สุดไม่ใช่แพลตฟอร์มที่มีแคตตาล็อกโมเดลยาวที่สุด แต่เป็นแพลตฟอร์มที่มอบวิธีควบคุมให้ทีมของคุณนำโมเดลใหม่มาใช้ จำกัดค่าใช้จ่าย ปกป้องข้อมูล และอธิบายการตัดสินใจสำคัญของทุกคำขอได้เมื่อปริมาณการใช้งานเพิ่มขึ้น
