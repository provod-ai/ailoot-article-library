# AI Inference คืออะไร? คู่มือฉบับสมบูรณ์

> การอนุมาน AI คือระยะรันไทม์ที่โมเดลซึ่งผ่านการฝึกแล้วสร้างผลลัพธ์จากอินพุตใหม่ เป็นเลเยอร์ที่กำหนดต้นทุน เวลาแฝง และความน่าเชื่อถือของผลิตภัณฑ์ที่ขับเคลื่อนด้วย AI ในสภาพแวดล้อมใช้งานจริง



การอนุมาน AI คือกระบวนการที่โมเดลแมชชีนเลิร์นนิงซึ่งผ่านการฝึกแล้วสร้างผลลัพธ์เพื่อตอบสนองต่ออินพุตใหม่ เมื่อแชตบอตตอบคำถาม ระบบค้นหาส่งคืนผลลัพธ์ที่จัดอันดับไว้ หรือโมเดลสร้างภาพสร้างรูปภาพ การอนุมานคือขั้นตอนที่เปลี่ยนชุดน้ำหนักของโมเดลที่บันทึกไว้ให้เป็นคำตอบที่ผู้ใช้เห็น การฝึกสร้างโมเดล ส่วนการอนุมานจะเรียกใช้โมเดลทุกครั้งที่มีคนใช้งาน

ทุกคำตอบจากแชตบอต การเติมโค้ดด้วย AI และสรุปผลการค้นหาที่สร้างด้วย AI ล้วนต้องอาศัยการอนุมาน การฝึกโมเดลเกิดขึ้นครั้งเดียว ขณะที่การอนุมานทำงานกับคำขอของผู้ใช้แต่ละรายการ ดังนั้นต้นทุน เวลาแฝง และความน่าเชื่อถือของเลเยอร์การให้บริการจึงมีผลต่อเศรษฐศาสตร์ของผลิตภัณฑ์ที่ขับเคลื่อนด้วย AI

## ความหมายที่แท้จริงของการอนุมาน

การอนุมานคือการประมวลผลโมเดลที่ผ่านการฝึกแล้วในรันไทม์ด้วยน้ำหนักที่คงที่ ระหว่างการฝึก น้ำหนักของโมเดลจะเปลี่ยนแปลงเมื่อเรียนรู้จากตัวอย่าง หลังการฝึก น้ำหนักเหล่านั้นจะถูกบันทึกไว้ การอนุมานนำค่าน้ำหนักที่คงที่เหล่านี้มารวมกับอินพุตใหม่ แล้วคำนวณผลลัพธ์ ตัวโมเดลเองไม่เปลี่ยนแปลงระหว่างการอนุมาน แต่ทำการคำนวณ forward แบบอ่านอย่างเดียว

สำหรับโมเดลภาษาขนาดใหญ่ คำขออนุมานหนึ่งรายการมีสี่ขั้นตอน ซึ่งแต่ละขั้นมีรูปแบบต้นทุนและเวลาแฝงของตนเอง:

![ไปป์ไลน์การอนุมาน LLM: พรอมป์ต์ถูกแปลงเป็นโทเค็น ประมวลผลในขั้น prefill แบบขนาน จากนั้นสร้างโทเค็นทีละตัวในขั้นถอดรหัสแบบ autoregressive ก่อนแปลงกลับเป็นข้อความ]()

1. **การแปลงเป็นโทเค็น** ข้อความอินพุตถูกแบ่งเป็นโทเค็น ซึ่งเป็นหน่วยที่มีขนาดโดยประมาณเท่าพยางค์หรือคำสั้น ๆ และคำศัพท์ของโมเดลแทนค่าเป็นตัวเลข เอกสาร 500 คำอาจกลายเป็น 600 ถึง 800 โทเค็น ทั้งนี้ขึ้นอยู่กับ tokenizer การแปลงเป็นโทเค็นมีผลต่อจำนวนโทเค็นที่ประมวลผลในแต่ละคำขอ
2. **Prefill** โทเค็นจะผ่านเลเยอร์ต่าง ๆ ของโมเดลในการประมวลผล forward เพียงรอบเดียว เพื่อสร้างตัวแทนของอินพุตและโทเค็นเอาต์พุตตัวแรก ขั้นตอนนี้จำกัดด้วยกำลังประมวลผลและรองรับการทำงานแบบขนานได้ดี
3. **การถอดรหัสแบบ autoregressive** โมเดลสร้างโทเค็นเอาต์พุตถัดไปทีละตัว โดยโทเค็นใหม่แต่ละตัวขึ้นอยู่กับโทเค็นก่อนหน้า ขั้นตอนนี้จำกัดด้วยแบนด์วิดท์หน่วยความจำมากกว่ากำลังประมวลผล ซึ่งช่วยอธิบายบทบาทของขั้นตอนนี้ต่อเวลาแฝงของคำตอบที่ยาว
4. **การแปลงกลับจากโทเค็น** โทเค็นเอาต์พุตถูกแปลงกลับเป็นข้อความที่ผู้ใช้มองเห็นและได้รับ

Prefill รวดเร็วและทำงานแบบขนาน ส่วนการถอดรหัสช้ากว่าและทำงานตามลำดับ ความแตกต่างนี้เป็นเหตุผลหนึ่งที่ทำให้การอนุมาน LLM พัฒนาโครงสร้างพื้นฐานเฉพาะทางซึ่งแตกต่างจากการให้บริการโมเดลแมชชีนเลิร์นนิงแบบดั้งเดิม และยังช่วยอธิบายประสิทธิภาพการอนุมานด้วย: เวลาจนถึงโทเค็นแรกได้รับผลจาก prefill ส่วนจำนวนโทเค็นต่อวินาทีได้รับผลจากการถอดรหัส ทั้งสองส่วนตอบสนองต่อการปรับแต่งที่แตกต่างกัน

## การอนุมานกับการฝึก: สรุปสั้น ๆ

การฝึกและการอนุมานแตกต่างกันในหลายมิติด้านการดำเนินงาน การฝึกใช้ชุดข้อมูลขนาดใหญ่และสร้างชุดน้ำหนักขึ้นมา ส่วนการอนุมานใช้ข้อมูลอินพุตซ้ำ ๆ เพื่อสร้างผลลัพธ์

| มิติ | การฝึก | การอนุมาน |
|----|----|----|
| ความถี่ | หนึ่งครั้งต่อโมเดลแต่ละเวอร์ชัน | หนึ่งครั้งต่อคำขอของผู้ใช้ |
| ระยะเวลา | หลายวันถึงหลายเดือน | หลายมิลลิวินาทีถึงหลายวินาที |
| ฮาร์ดแวร์ | คลัสเตอร์ GPU ที่เชื่อมต่อกันอย่างใกล้ชิด พร้อมแบนด์วิดท์ระหว่างโหนดสูง | GPU รายตัวหรือกลุ่มขนาดเล็ก |
| ลักษณะต้นทุน | คล้ายเงินลงทุน จ่ายล่วงหน้า | คล้ายค่าใช้จ่ายดำเนินงาน แปรผันตามการใช้งาน |
| ผู้รับภาระต้นทุน | ผู้สร้างโมเดล | ทีมแอปพลิเคชัน |
| ลำดับความสำคัญในการปรับแต่ง | คุณภาพโมเดล | ต้นทุน เวลาแฝง ความน่าเชื่อถือ |

สำหรับทีมที่สร้างผลิตภัณฑ์บนโมเดลพื้นฐาน ผู้ให้บริการโมเดลมักจัดการเศรษฐศาสตร์ด้านการฝึก ส่วนทีมแอปพลิเคชันจัดการเศรษฐศาสตร์ด้านการอนุมาน การตัดสินใจเรื่องผู้ให้บริการ ตำแหน่งการติดตั้ง การประมวลผลแบบแบตช์ แคช และระบบสำรอง ล้วนส่งผลต่อการอนุมาน

## ประเภทของเวิร์กโหลดการอนุมาน

คำจำกัดความนี้ครอบคลุมทุกกรณีที่โมเดลซึ่งผ่านการฝึกแล้วสร้างผลลัพธ์ แต่ลักษณะของเวิร์กโหลดแตกต่างกันมากพอที่จะเรียกหมวดหมู่หลักแยกจากกัน

![แผนภาพประเภทเวิร์กโหลดการอนุมาน LLM ทั้งห้าประเภทตามเวลาแฝงของการตอบสนองและต้นทุนต่อคำขอ: embeddings มีต้นทุนต่ำและเร็วที่สุด chat อยู่ตรงกลาง ส่วน vision และ reasoning ช้าลงและมีต้นทุนสูงขึ้นตามลำดับ และ batch เป็นตัวเลือกลดราคาที่รองรับเวลาแฝงได้]()

**การสร้างข้อความ (chat)** เวิร์กโหลดการอนุมานที่พบได้ทั่วไป มีพรอมป์ต์เข้ามา โทเค็นถูกสร้างทีละตัว และอาจสตรีมคำตอบไปยังผู้ใช้

**Reasoning และ chain-of-thought** รูปแบบหนึ่งของการสร้างข้อความที่โมเดลสร้างช่วงการให้เหตุผลภายในก่อนส่งคำตอบที่มองเห็นได้ ตัวอย่างได้แก่ o-series ของ OpenAI, โหมด extended thinking ของ Anthropic และ DeepSeek-R1

**Embeddings** อินพุตข้อความสร้างเวกเตอร์ความยาวคงที่แทนข้อความที่สร้างขึ้น Embeddings ใช้สำหรับการค้นหา การสร้างแบบเพิ่มประสิทธิภาพด้วยการดึงข้อมูล (RAG) การจัดกลุ่ม และการกำจัดรายการซ้ำ การอนุมาน embeddings รองรับระบบค้นหาและระบบความจำสมัยใหม่จำนวนมาก

**Vision และมัลติโมดัล** ภาพ เฟรมวิดีโอ หรือคลิปเสียงที่รวมกับข้อความจะสร้างผลลัพธ์เป็นข้อความหรือข้อมูลแบบมีโครงสร้าง เวลาแฝงอาจเพิ่มตามความละเอียดของอินพุต และต้นทุนขึ้นอยู่กับจำนวนโทเค็นที่อินพุตถูกถอดรหัสออกมา โครงสร้างพื้นฐานการให้บริการเดียวกันรองรับเวิร์กโหลดเหล่านี้ได้ แต่การแปลงเป็นโทเค็นอาจมีต้นทุนสูงกว่าข้อความธรรมดา

**การอนุมานแบบ batch** สำหรับไปป์ไลน์ที่ไม่ต้องการคำตอบแบบเรียลไทม์ เช่น การเพิ่มข้อมูลในช่วงกลางคืน การประเมินผลแบบออฟไลน์ หรือการเตรียมข้อมูลตามกำหนดเวลา การอนุมานแบบ batch สามารถลดต้นทุนได้

## การอนุมานทำงานที่ใด

การเรียกใช้การอนุมานในระดับคุณภาพที่พร้อมใช้งานจริงขึ้นอยู่กับโครงสร้างพื้นฐานสามเลเยอร์ ซึ่งมองไม่เห็นจากหน้าตาของ API แต่ส่งผลต่อต้นทุน

**ระดับ GPU** LLM สมัยใหม่ต้องใช้ GPU ที่มีความจุหน่วยความจำและแบนด์วิดท์สูง การ์ด NVIDIA H100 และ H200 ใช้กับโมเดลขนาดใหญ่ โมเดลขนาดเล็กกว่ารันบนการ์ด A100 หรือ L40S ได้ ส่วนโมเดลขนาดเล็กมากรันบนการ์ดสำหรับผู้ใช้ทั่วไปได้ การเลือกการ์ดส่งผลต่ออัตราการประมวลผลและขนาดโมเดลขั้นต่ำที่ให้บริการได้โดยไม่ต้องแบ่งโมเดลข้ามการ์ดหลายใบ การกำหนดขนาดหน่วยความจำ GPU เป็นส่วนสำคัญของการวางแผนการอนุมาน LLM

**Serving engine** การเข้าถึง GPU โดยตรงยังไม่เพียงพอ การให้บริการโมเดลอย่างมีประสิทธิภาพจำเป็นต้องใช้ engine ซึ่งเรียกอีกอย่างว่า inference engine หรือ inference server เพื่อจัดการ KV cache ประมวลผลคำขอพร้อมกันแบบแบตช์ และปรับเลย์เอาต์หน่วยความจำให้เหมาะสม engine ที่นิยมใช้ ได้แก่ vLLM (โอเพนซอร์ส ใช้งานทั่วไป), TensorRT-LLM (เฉพาะ NVIDIA ประสิทธิภาพสูง) และ SGLang (โอเพนซอร์ส ปรับแต่งสำหรับการสร้างแบบมีโครงสร้าง) Serving engine อาจส่งผลต่ออัตราการประมวลผลอย่างมาก แม้ใช้ฮาร์ดแวร์ชุดเดียวกัน

**การติดตั้งใช้งานระดับภูมิภาค** เวลาในการคำนวณเป็นปัจจัยสำคัญของเวลาแฝงในการอนุมาน และการเดินทางไปกลับของเครือข่ายเพิ่มความล่าช้าอีก สำหรับเวิร์กโหลดที่ผู้ใช้เป็นผู้เรียกใช้ การให้บริการจากภูมิภาคที่อยู่ใกล้ผู้ใช้อาจส่งผลต่อความรวดเร็วที่ผู้ใช้รับรู้

การดำเนินงานสแตกนี้อาจเหมาะกับทีมที่มีปริมาณงานสูงและวิศวกรโครงสร้างพื้นฐานโดยเฉพาะ ส่วนทีมอื่นอาจซื้อโครงสร้างพื้นฐาน ทำให้การเลือกรูปแบบการซื้อเป็นเรื่องสำคัญ

## วิธีที่ทีมเข้าถึงการอนุมานในทางปฏิบัติ

รูปแบบสามแบบครอบคลุมการตั้งค่าการอนุมานในระบบใช้งานจริงได้หลายลักษณะ

![การเปรียบเทียบสถาปัตยกรรมของรูปแบบการเข้าถึงการอนุมานสามแบบ: สแตกที่โฮสต์เองพร้อม serving engine และ GPU แบบเช่า, API โดยตรงจากผู้ให้บริการรายเดียว และแพลตฟอร์มแบบรวมที่กำหนดเส้นทาง API เดียวผ่านผู้ให้บริการหลายราย]()

**โฮสต์เองบน GPU แบบเช่า** ทีมเช่าความจุ GPU ติดตั้งโมเดลแบบ open-weight บน serving engine และดำเนินงานสแตกทั้งหมด วิธีนี้ทำให้ทีมควบคุมระบบได้ และอาจประหยัดต้นทุนเมื่อมีปริมาณงานสูงมาก แต่ต้องมีความเชี่ยวชาญด้านโครงสร้างพื้นฐาน เช่น การปรับแต่ง KV cache, autoscaling, failover และ observability

**API โดยตรงจากผู้ให้บริการ** ทีมเรียกใช้ API ของผู้ให้บริการรายเดียว ผู้ให้บริการจัดการโครงสร้างพื้นฐานให้ นี่เป็นเส้นทางที่รวดเร็วในการทำให้ผลิตภัณฑ์ใช้งานได้จริง และเป็นวิธีเริ่มต้นที่พบได้ทั่วไป ข้อแลกเปลี่ยนคือความเสี่ยงจากการพึ่งพาผู้ให้บริการรายเดียวและโครงสร้างราคาของรายนั้น ต้นทุน เวลาแฝง และความน่าเชื่อถือของแต่ละคำขอขึ้นอยู่กับบริการของผู้ให้บริการรายนั้น

**แพลตฟอร์มการอนุมานแบบรวม** ทีมเรียกใช้ API เดียวที่กำหนดเส้นทางคำขอไปยังผู้ให้บริการเบื้องหลังหลายราย และอาจมีระบบสำรอง observability และการควบคุมต้นทุน วิธีนี้รักษาข้อได้เปรียบด้านความรวดเร็วในการเปิดตัวผลิตภัณฑ์ของ API โดยตรงจากผู้ให้บริการไว้ได้ ขณะเดียวกันก็ลดความเสี่ยงจากการกระจุกตัวที่ผู้ให้บริการรายเดียวและเปิดให้กำหนดเส้นทางตามเวิร์กโหลดได้ เช่น ใช้โมเดลต้นทุนต่ำกว่าสำหรับคำถามง่าย ๆ และโมเดลที่มีความสามารถสูงกว่าสำหรับคำถามซับซ้อน

## เหตุใดการอนุมานจึงเป็นศูนย์กลางต้นทุนต่อเนื่อง

การอนุมานส่งผลต่อเศรษฐศาสตร์ของผลิตภัณฑ์ที่ขับเคลื่อนด้วย AI เพราะต้นทุนเพิ่มขึ้นตามการใช้งาน ต้นทุนการฝึกโมเดลเป็นต้นทุนคงที่และผู้ให้บริการหรือทีมที่ฝึกโมเดลจ่ายเพียงครั้งเดียว คำขออนุมานแต่ละรายการใช้กำลังประมวลผลเพิ่มเติม ผู้ใช้สิบคนสร้างการอนุมานสิบครั้ง ผู้ใช้หนึ่งล้านคนสร้างการอนุมานหนึ่งล้านครั้ง ในทางปฏิบัติ เศรษฐศาสตร์ต่อหน่วยของผลิตภัณฑ์ AI ขึ้นอยู่กับเศรษฐศาสตร์ต่อหน่วยของการอนุมาน

![กราฟต้นทุนสะสมตลอดอายุการใช้งานของโมเดล: ต้นทุนการฝึกเพิ่มขึ้นครั้งเดียวแล้วคงที่ ส่วนต้นทุนการอนุมานเริ่มจากศูนย์และเพิ่มขึ้นตามทุกคำขอที่ให้บริการ จนในที่สุดสูงกว่าต้นทุนการฝึกทั้งหมด]()

โครงสร้างนี้มีผลสองประการ ประการแรก ต้นทุนของฟีเจอร์ AI เพิ่มขึ้นตามการใช้งาน: ฟีเจอร์ที่มีการใช้งานน้อยมีค่าใช้จ่ายการอนุมานต่ำ ส่วนฟีเจอร์ที่มีการใช้งานมากมีค่าใช้จ่ายสูงกว่า ประการที่สอง ตัวเลือกด้านสถาปัตยกรรมที่เปลี่ยนต้นทุนการอนุมานจะสะสมผลเมื่อการใช้งานเพิ่มขึ้น ตัวเลือกเหล่านี้ได้แก่ การเลือกโมเดล การออกแบบพรอมป์ต์ กลยุทธ์แคช การเลือกผู้ให้บริการ และนโยบายการลองซ้ำ การลดต้นทุนต่อคำขอลง 20% จะลดต้นทุนส่วนเพิ่มในสัดส่วนเดียวกันเมื่อการใช้งานเพิ่มขึ้น

ตัวเลขต้นทุนต่อหนึ่งล้านโทเค็นที่พาดหัวไว้สื่อถึงสถานการณ์คำขอแบบหนึ่งโดยเฉพาะ เวิร์กโหลดในระบบใช้งานจริงอาจแตกต่างจากสถานการณ์นั้น

## สิ่งที่คู่มือการอนุมานส่วนใหญ่มักไม่กล่าวถึง

กลไกข้างต้นมีการบันทึกไว้อย่างดี แต่ข้อพิจารณาด้านการดำเนินงานบางประการจะเห็นชัดขึ้นเมื่อเรียกใช้การอนุมานผ่านผู้ให้บริการหลายรายในระบบใช้งานจริง:

- **โมเดลที่ถูกที่สุดแทบไม่ใช่ระบบที่ถูกที่สุด** โมเดลที่มีราคาต่อโทเค็นต่ำกว่าแต่อาจล้มเหลวบ่อยกว่า ต้องใช้พรอมป์ต์ยาวขึ้นเพื่อให้ได้คุณภาพเท่าเดิม หรือทำให้ต้องลองซ้ำมากขึ้น อาจมีต้นทุนต่อภารกิจที่เสร็จสมบูรณ์สูงกว่าโมเดลที่ดูเหมือนมีราคาแพงกว่า ต้นทุนที่แท้จริงขึ้นอยู่กับเส้นทางคำขอทั้งหมด ดังนั้นการปรับต้นทุนให้เหมาะสมจึงเกี่ยวข้องทั้งกับสถาปัตยกรรมและรายการราคา
- **ความยาวเอาต์พุตเป็นปัจจัยที่ปรับได้อย่างมีประสิทธิภาพ** เนื่องจากการถอดรหัสส่งผลทั้งต่อเวลาแฝงในการอนุมานและต้นทุนเอาต์พุต การปรับพรอมป์ต์ให้คำตอบสั้นลงจึงช่วยปรับปรุงทั้งสองด้านได้
- **นโยบาย fallback ส่งผลต่อราคา** ผู้ให้บริการอาจขัดข้องหรือจำกัดอัตราการเรียกใช้ การตัดสินใจว่าระบบจะล้มเหลว เข้าคิว หรือเปลี่ยนเส้นทางในช่วงดังกล่าวเป็นการตัดสินใจทางเศรษฐกิจ ลำดับ fallback ส่งผลต่อความพร้อมใช้งานและต้นทุน
- **สภาพแวดล้อมอาจเปลี่ยนไปโดยไม่แจ้งให้ทราบ** ผู้ให้บริการอาจเปลี่ยนราคา ทำ quantization ให้กับการติดตั้งใช้งาน หรือสลับเวอร์ชันโมเดลภายใต้ชื่อเดิม การตั้งค่าการอนุมานที่ปรับแต่งครั้งเดียวแล้วไม่ตรวจสอบอีกอาจเสื่อมประสิทธิภาพลงเมื่อเวลาผ่านไป
- **อันดับจากเกณฑ์มาตรฐานไม่ได้ตัดสินว่าโมเดลใดจะให้บริการคำขอ** ตารางคะแนนจัดอันดับช่วยระบุโมเดลที่มีความสามารถได้ แต่การเลือกโมเดลสำหรับคำขอหนึ่ง ๆ ยังต้องพิจารณาข้อจำกัดด้านต้นทุน เวลาแฝง และความพร้อมใช้งานด้วย

ข้อพิจารณาเหล่านี้ไม่ใช่ส่วนหนึ่งของคำจำกัดความของการอนุมาน แต่ส่งผลต่อต้นทุนในระบบใช้งานจริงได้อย่างมาก

## คำถามที่ตามมาจากการอนุมาน

การเข้าใจการอนุมานเป็นจุดเริ่มต้น การตัดสินใจสำหรับระบบใช้งานจริงรวมถึงโมเดลที่จะจัดการคำขอแต่ละรายการ ผู้ให้บริการที่ใช้ ราคาเท่าใด และมี fallback แบบใด การเลือกโมเดลตายตัวหนึ่งโมเดลหมายถึงการตัดสินใจเหล่านี้ครั้งเดียวสำหรับทราฟฟิกทั้งหมดในอนาคต อีกแนวทางคือถือว่าการเลือกโมเดลเป็นการตัดสินใจรายคำขอตามความต้องการของคำขอนั้น

สำหรับทีมที่จับคู่เวิร์กโหลดกับโมเดล การเลือกโมเดลเกี่ยวข้องกับการชั่งน้ำหนักข้อกำหนดของเวิร์กโหลดเทียบกับความสามารถและต้นทุนของโมเดล
