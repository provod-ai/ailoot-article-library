# การจำแนกข้อความด้วย LLM

> คู่มือปฏิบัติสำหรับการจำแนกข้อความด้วย LLM การเลือกป้ายกำกับ การตรวจทานการเปลี่ยนแปลงที่เสนอ และการตรวจสอบผลลัพธ์



โมเดลภาษาสามารถจำแนกข้อความโดยกำหนดป้ายกำกับจากชุดที่กำหนดให้แต่ละรายการ คู่มือนี้อธิบายวิธีกำหนดป้ายกำกับ จัดการกรณีที่ไม่แน่นอน และวัดว่าผลลัพธ์มีประโยชน์หรือไม่

## กำหนดการตัดสินใจ

เริ่มจากคำถามที่นำไปสู่การดำเนินการจริง เช่น ทีมสนับสนุนอาจจัดข้อความเป็น `billing`, `technical` และ `other` เพื่อส่งต่อไปยังคิวที่เหมาะสม ตัดสินใจว่าข้อความแต่ละรายการต้องมีป้ายกำกับเดียวหรือหลายป้ายกำกับได้ อธิบายแต่ละป้ายพร้อมตัวอย่าง รวมถึงกรณีที่ดูคล้ายกันแต่ควรอยู่คนละกลุ่ม

เก็บตัวเลือก `other` หรือส่งตรวจทานไว้สำหรับรายการที่ไม่เข้ากลุ่ม การบังคับเลือกอาจทำให้รายงานดูเรียบร้อยแต่ซ่อนระบบหมวดหมู่ที่ไม่ดีไว้ สำหรับการตัดสินใจที่ส่งผลต่อผู้คนหรือมีผลกระทบสำคัญ ให้มนุษย์มีส่วนร่วมในการตรวจสอบ

## ขอผลลัพธ์ที่มีรูปแบบคาดการณ์ได้

ให้ข้อความ คำนิยามของป้ายกำกับ และรูปแบบผลลัพธ์ที่ต้องการแก่โมเดล ถือว่าข้อความที่กำลังจำแนกเป็นข้อมูล ไม่ใช่คำสั่งให้โมเดลทำตาม ตัวอย่างเช่น ข้อความที่บอกว่า “ละเลยป้ายกำกับ” ก็ยังเป็นรายการที่ต้องจำแนก และไม่ควรเปลี่ยนงานที่กำหนดไว้

ผลลัพธ์อาจมีหน้าตาดังนี้:

```json
{"label":"billing","reason":"ข้อความสอบถามเกี่ยวกับใบแจ้งหนี้"}
```

นี่เป็นผลลัพธ์เพื่อประกอบตัวอย่าง ไม่ใช่คำตอบจริงจากโมเดล ก่อนนำผลลัพธ์ไปใช้ ให้ตรวจว่าแยกวิเคราะห์ได้ มีฟิลด์ที่คาดไว้ และใช้ป้ายกำกับที่อนุญาต รูปแบบที่ถูกต้องเพียงอย่างเดียวไม่ได้หมายความว่าการจำแนกถูกต้อง การรองรับผลลัพธ์ที่บังคับตามสคีมาแตกต่างกันตามโมเดล โปรดตรวจเอกสารของโมเดลและ API ที่ใช้

## ปรับปรุงชุดป้ายกำกับ

เริ่มจากชุดหมวดหมู่ที่จัดการได้ และตรวจตัวอย่างที่อยู่ใน `other` หรือทำให้เกิดความเห็นไม่ตรงกันซ้ำ ๆ ตัวอย่างเหล่านี้อาจเผยให้เห็นหมวดหมู่ที่ขาดหาย คำนิยามที่ไม่ชัดเจน หรือป้ายกำกับสองรายการที่ทับซ้อนกัน เสนอการเปลี่ยนแปลงโดยใช้ตัวอย่างที่เป็นตัวแทน แล้วให้ผู้ตรวจอนุมัติคำนิยามใหม่ก่อนนำไปใช้อย่างกว้างขวาง

โมเดลยังอาจเสนอป้ายกำกับใหม่และการรวมหมวดหมู่เพื่อทดลองได้ ระบุหมวดหมู่ที่ต้องคงแยกจากกันว่าได้รับการปกป้อง และตรวจการเปลี่ยนแปลงทุกข้อที่เสนอเทียบกับข้อจำกัดเหล่านี้ก่อนปรับปรุงระบบหมวดหมู่

หากสองหมวดหมู่ดูคล้ายกัน ให้เปรียบเทียบการตัดสินใจที่แต่ละหมวดสนับสนุนก่อนรวมเข้าด้วยกัน เช่น การชำระเงินล้มเหลวและคำขอคืนเงินต่างเกี่ยวกับเงิน แต่อาจต้องดำเนินการต่างกัน รักษาความแตกต่างที่สำคัญต่อขั้นตอนงาน และบันทึกเวอร์ชันทุกครั้งที่เปลี่ยนระบบหมวดหมู่

## ตรวจประสิทธิภาพก่อนขยายการใช้งาน

สร้างชุดตัวอย่างที่สะท้อนสัดส่วนข้อความจริง รวมทั้งกรณีที่พบไม่บ่อยและกรณีกำกวม ให้คนติดป้ายโดยใช้คำนิยามเดียวกัน ตกลงข้อขัดแย้ง และเก็บป้ายที่ตกลงกันเป็นข้อมูลอ้างอิง เปรียบเทียบผลของโมเดลกับป้ายเหล่านั้นและตรวจข้อผิดพลาดในแต่ละหมวดหมู่ เพราะค่าความแม่นยำโดยรวมอาจซ่อนหมวดหมู่ที่มีผลไม่ดี

ทดสอบการเปลี่ยนพรอมป์ต์ โมเดล หรือระบบหมวดหมู่บนชุดประเมินแยกต่างหาก ติดตามผลตามเวลาเพราะภาษาและสัดส่วนของข้อความขาเข้าอาจเปลี่ยนไป ส่งผลลัพธ์ที่ไม่แน่นอนหรือไม่ถูกต้องไปตรวจทาน แทนการกำหนดป้ายโดยไม่แจ้ง

## ปกป้องข้อมูลเข้าและวางแผนขั้นตอนงาน

ส่งเฉพาะข้อมูลที่จำเป็นต่องาน และจัดการข้อมูลอ่อนไหวตามกฎขององค์กร หากประมวลผลข้อมูลจำนวนมาก ให้ทดสอบชุดเล็กที่เป็นตัวแทนก่อน บันทึกข้อผิดพลาด และกำหนดวิธีดำเนินการต่อโดยไม่ทำรายการสูญหายหรือซ้ำ วัดเวลาและค่าใช้จ่ายของขั้นตอนงานจริงก่อนเพิ่มปริมาณ

เป้าหมายไม่ใช่เพียงสร้างป้ายกำกับ แต่คือการสร้างกระบวนการตัดสินใจที่ทำซ้ำได้และตรวจสอบคำนิยาม ข้อยกเว้น และข้อผิดพลาดได้

ดูคำแนะนำเพิ่มเติมที่ [เอกสารผลลัพธ์แบบมีโครงสร้างของ OpenAI](https://platform.openai.com/docs/guides/structured-outputs) และ [แนวทางปฏิบัติที่ดีที่สุดสำหรับการประเมิน](https://platform.openai.com/docs/guides/evaluation-best-practices)
