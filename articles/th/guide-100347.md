# แพลตฟอร์มการอนุมานประกอบกันอย่างไร

08 มี.ค. 2026 | วิศวกรรม | อ่าน 4 นาที

เกตเวย์ การกำหนดเส้นทาง การแคช และการให้บริการโมเดลทำงานร่วมกันอย่างไร รวมถึงบริบทของคำขอสามารถส่งต่อผ่านชั้นต่าง ๆ เหล่านั้นได้อย่างไร

บริบทของคำขอสามารถเดินทางผ่านเกตเวย์และเราเตอร์ไปยังการให้บริการโมเดลได้ บริบทนั้นเชื่อมโยงการเลือกโมเดล การใช้แคชซ้ำ และการดำเนินการเข้ากับตัวตนของผู้เรียกและต้นทุนของการลองแต่ละครั้ง เราเตอร์ที่ไม่สนใจสถานะแคชอาจใช้เงินส่วนที่ประหยัดได้จากชั้นข้างเคียงไปจนหมด

การแชร์บริบทต้องอาศัยงานผสานระบบ และเราเตอร์ที่อ่านสถานะแคชจะเปลี่ยนแทนได้ยากกว่า การส่งบริบทไปพร้อมกับคำขอโดยแยกผลิตภัณฑ์ออกจากกัน ช่วยให้ทีมใช้เกตเวย์และเราเตอร์กับรันไทม์ของผู้ให้บริการรายอื่นได้ จากนั้นเราเตอร์จะตัดสินใจโดยใช้ข้อมูลที่ผู้ให้บริการรายนั้นเปิดเผย

## เส้นทางที่ถูกกว่าอาจมีต้นทุนสูงกว่า

ลองพิจารณาบริการสกัดข้อมูลจากเอกสารตัวอย่างที่มีคำสั่งคงที่ยาว ๆ และเอกสารสั้นหนึ่งฉบับในแต่ละคำขอ ทั้งการแคชคำนำหน้าและการกำหนดเส้นทางต่างก็ดูน่าสนใจ และแต่ละอย่างอาจหักล้างข้อดีของอีกอย่างได้ คำนำหน้าที่แคชไว้คือสถานะคีย์-แวลูที่คำนวณโดยโมเดลหนึ่ง ดังนั้นคำขอที่กำหนดเส้นทางไปยังอีกโมเดลจะต้องอ่านคำสั่งใหม่ตั้งแต่ต้น

ราคาการแคชห้านาทีที่ Anthropic เผยแพร่คือ 1.25 เท่าของราคาขาเข้าพื้นฐานสำหรับการเขียน และ 0.1 เท่าสำหรับการอ่าน โดยมีข้อยกเว้นแยกตามโมเดล ([ประกาศ](https://www.anthropic.com/news/prompt-caching), [เอกสารประกอบ](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)) เมื่อเทียบกับแคชอุ่นนี้ ทางเลือกที่ไม่แคชต้องคิดราคาต่ำกว่าหนึ่งในสิบของราคาขาเข้าของโมเดลเดิม จึงจะคุ้มกว่าสำหรับคำนำหน้าที่ใช้ร่วมกัน การเขียนหนึ่งครั้งและการอ่านแคชที่พบหนึ่งครั้งมีต้นทุนเท่ากับการประมวลผลขาเข้า 1.35 รอบในส่วนที่แคชไว้ เทียบกับสองรอบหากไม่แคช การเขียนที่ไม่มีคำขอในภายหลังมาอ่านมีต้นทุน 1.25

เราเตอร์ที่เปรียบเทียบราคาตามรายการอาจเห็นโมเดลที่มีราคาขาเข้าเพียงครึ่งหนึ่งแล้วเปลี่ยนไปใช้โมเดลนั้น ทำให้ต้องจ่ายค่าคำนำหน้าอย่างน้อยห้าเท่า การกำหนดเส้นทางที่ประกาศไว้จะระบุว่าโมเดลใดใช้แทนกันได้ ส่วนบริบทที่ใช้ร่วมกันจะแสดงให้เห็นว่าการแทนแต่ละครั้งมีต้นทุนเท่าใด

แคชคำตอบส่งคืนเอาต์พุตที่จัดเก็บไว้ ส่วนแคชเชิงความหมายยังตัดสินด้วยว่าคำขอสองรายการที่ต่างกันควรได้รับคำตอบเดียวกันเมื่อใด [GPTCache](https://github.com/zilliztech/GPTCache) ตัดสินว่าพบแคชหรือไม่โดยดูจากความคล้ายคลึงของเวกเตอร์ฝังตัว และ README เตือนถึง “ผลบวกลวงขณะพบแคช”

ในการสกัดข้อมูล ผลบวกลวงอาจทำให้ได้หมายเลขบัญชีที่ผิด: ใบแจ้งหนี้สองฉบับจากเทมเพลตผู้ขายเดียวกันอาจอยู่ใกล้กันในพื้นที่เวกเตอร์ฝังตัว และแคชอาจส่งหมายเลขบัญชีของใบแจ้งหนี้ฉบับแรกให้กับฉบับที่สอง แคชเชิงความหมายที่ไม่มีตัวตนของแอปพลิเคชันกำกับอาจทำให้เกิดบั๊กด้านความถูกต้อง ขณะที่แดชบอร์ดอัตราการพบแคชนับคำตอบที่ผิดทุกครั้งเป็นการประหยัด

Anthropic แยกแคชพรอมป์ต์ระหว่างองค์กร และบน API ของตนเองก็แยกตามเวิร์กสเปซด้วย แม้ว่าแคชคำนำหน้าจะไม่ส่งคืนคำตอบที่จัดเก็บไว้ แคชคำตอบต้องมีขอบเขตอย่างน้อยเท่านี้ แอปพลิเคชันสามารถประกาศได้ว่างานยอมรับการใช้ซ้ำกับอินพุตที่คล้ายกันหรือไม่ และคีย์สำหรับการใช้ซ้ำอาจอิงตามผู้เรียก ข้อมูลที่ผู้เรียกนั้นอ่านได้ และเวอร์ชันของงาน

การสกัดข้อมูลอาจใช้การจับคู่ที่ตรงกันทุกประการเพื่อนำกลับมาใช้ซ้ำ หรือไม่ใช้การนำกลับมาใช้ซ้ำเลย โดยคีย์ที่ไม่รู้จักจะทำให้คำนวณใหม่ กฎนี้ทำให้อัตราการพบแคชลดลงและต้องจ่ายสำหรับงานที่แคชแบบผ่อนปรนกว่าจะข้ามไปได้ ค่าเริ่มต้นอาจเข้มงวดเกินไป: สำหรับคำถามที่พบบ่อยสาธารณะขนาดใหญ่ การคำนวณใหม่เมื่อพบคีย์ที่ไม่รู้จักอาจมีต้นทุนสูงกว่าคำตอบผิดที่เกิดขึ้นไม่บ่อยซึ่งกฎนี้ป้องกันไว้

## ติดตามความล้มเหลวก่อนเลือกวิธีแก้

สมมติว่าโมเดลที่ถูกกว่าส่งคืนฟิลด์ที่ไม่ถูกต้อง แล้วโมเดลที่ใหญ่กว่ามาแก้ ทำให้ค่าบริการและเวลาหน่วงของเอกสารนั้นเพิ่มขึ้น สามารถนับต้นทุนต่อการสกัดข้อมูลที่ถูกต้องภายในเวลาแฝงตามที่กำหนด โดยราคาของโทเค็นในการเรียกครั้งแรกเป็นหนึ่งในปัจจัยนำเข้า

บทวิเคราะห์ระบบ AI แบบประกอบของ Berkeley เสนอให้ปรับองค์ประกอบที่มีปฏิสัมพันธ์กันให้เหมาะสมร่วมกัน เทรซต้องแยกความล้มเหลวของโมเดลออกจากการใช้ข้อมูลเก่าซ้ำ เครื่องมือที่ช้า หรือเส้นทางที่ไม่ดี เพราะแต่ละกรณีชี้ไปยังวิธีแก้ในคนละชั้น การควบคุมการดำเนินการอาจช่วยระบุได้ว่าต้นทุนเกิดจากจุดใด ขณะที่รันไทม์ที่เร็วกว่าอาจย้ายความสูญเปล่าไปอยู่ในการตัดสินใจรอบ ๆ การทำงานนั้น การเชื่อมเทรซเข้ากับการประเมินบนทราฟฟิกจริงในระบบผลิตสามารถทดสอบได้ว่าการเปลี่ยนแปลงช่วยให้งานดีขึ้นหรือไม่ รวมถึงเส้นทางกู้คืนด้วย

ผู้ปฏิบัติการใช้เทรซนั้นเพื่อเปลี่ยนชั้นที่เกิดความล้มเหลวได้ การเก็บประวัติคำขอ กรณีประเมิน และตัวเลือกการดีพลอยไว้ภายในแอปพลิเคชันของลูกค้า ช่วยให้การปรับปรุงต่อยอดจากประสบการณ์ของแอปพลิเคชันนั้นเอง
