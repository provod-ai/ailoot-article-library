# การออกแบบเครื่องมือสำหรับ AI Agent: บทเรียนสำหรับขั้นตอนงาน Claude Code

> คู่มือปฏิบัติในการกำหนดและทดสอบเครื่องมือสำหรับ AI Agent พร้อมตัวอย่างสำหรับขั้นตอนงานเขียนโค้ด



AI Agent ต้องการมากกว่าโมเดลที่ดี: มันต้องมีเครื่องมือที่เลือก เข้าใจ และใช้ภายในขอบเขตของงานได้ คู่มือนี้แสดงวิธีออกแบบส่วนติดต่อเหล่านั้น โดยใช้ขั้นตอนงานเขียนโค้ดเป็นตัวอย่างเชิงปฏิบัติ

## เริ่มจากงานที่สังเกตผลได้

อธิบายสิ่งที่เอเจนต์ต้องทำให้สำเร็จก่อนตัดสินใจว่าจะเปิดเครื่องมือใดให้ใช้ สำหรับคำถามเกี่ยวกับ repository งานอาจเป็นการหาว่ามีการอ่านค่าตั้งค่าที่ใดและอ้างอิงไฟล์ที่เกี่ยวข้อง ชุดเครื่องมือที่เหมาะสมอาจให้เอเจนต์แสดงรายการไฟล์ ค้นหาข้อความ และอ่านไฟล์ที่เลือก โดยไม่จำเป็นต้องมีสิทธิ์ deploy เพื่อตอบคำถามนั้น

จดผลลัพธ์ที่คาดหวังและการกระทำที่อยู่นอกขอบเขต เครื่องมือมีประโยชน์เมื่อข้อมูลเข้าและผลลัพธ์ช่วยให้เอเจนต์ตัดสินใจขั้นต่อไป และเมื่อแอปพลิเคชันตรวจสอบได้ว่าการกระทำนั้นได้รับอนุญาต

## กำหนดข้อตกลงของแต่ละเครื่องมือให้ชัดเจน

คำอธิบายเครื่องมือควรระบุว่าทำอะไร ต้องการข้อมูลเข้าใด และผลลัพธ์มีรูปแบบอย่างไร ใช้ชื่อและคำอธิบายพารามิเตอร์ที่แตกต่างกันเมื่อเครื่องมือมีวัตถุประสงค์คล้ายกัน หากการดำเนินการมีขีดจำกัดที่สำคัญให้ระบุไว้ เช่น เครื่องมือค้นหาอาจส่งคืนรายการพาธที่ตรงกันซึ่งจำกัดจำนวน แทนเนื้อหาของทุกไฟล์

ตัวอย่างคำขอสำหรับเครื่องมือค้นหาข้อความอาจมีคำค้นและไดเรกทอรี ผลลัพธ์อาจมีพาธและหมายเลขบรรทัดที่ตรงกัน แอปพลิเคชันควรตรวจสอบไดเรกทอรีและจัดการพาธที่ไม่มีอยู่หรือการค้นหาที่ล้มเหลวอย่างชัดเจน คำขอที่มีรูปแบบถูกต้องไม่ใช่หลักฐานว่าคำตอบที่พบถูกต้อง

## สร้างสมดุลระหว่างความยืดหยุ่นกับการควบคุม

เชลล์ทั่วไปช่วยงานได้หลายแบบ แต่ก็เปิดให้ดำเนินการได้กว้าง เครื่องมือที่เฉพาะเจาะจงกว่าอาจทำให้การดำเนินการที่ใช้บ่อยเข้าใจง่ายและจำกัดสิ่งที่ทำได้ ทางเลือกที่เหมาะสมขึ้นอยู่กับงาน สภาพแวดล้อม และสิทธิ์ที่มี เครื่องมือที่มากขึ้นไม่ได้ทำให้ผลลัพธ์ดีขึ้นโดยอัตโนมัติ

รักษาชุดเริ่มต้นให้เล็กพอที่จะเลือกใช้ได้สะดวก เพิ่มเครื่องมือเฉพาะเมื่อความล้มเหลวที่พบหรืองานซ้ำเป็นเหตุผลรองรับ หากเครื่องมือเปลี่ยนข้อมูลหรือติดต่อบริการภายนอกได้ ให้ระบุผลนั้นในคำอธิบายอย่างชัดเจนและบังคับใช้สิทธิ์ที่เกี่ยวข้องในแอปพลิเคชัน

## ถามข้อมูลที่ขาดในเวลาที่เหมาะสม

เอเจนต์ไม่ควรสมมติการตัดสินใจที่ขาดไป หากงานขึ้นอยู่กับข้อมูลที่หาไม่ได้จริง ๆ คำถามแบบมีโครงสร้างสามารถแสดงตัวเลือกที่เกี่ยวข้องและอธิบายผลของแต่ละตัวเลือกได้ หากมีงานอิสระที่พร้อมทำ ขั้นตอนงานสามารถทำส่วนนั้นต่อระหว่างรอคำตอบ

ถามให้เฉพาะเจาะจง เช่น หากรายงานต้องใช้ช่วงวันที่ที่ไม่ได้ระบุ ให้ถามช่วงวันที่แทนการขอให้ผู้ใช้เล่าโจทย์ทั้งหมดใหม่ อย่าใช้คำถามแทนการตรวจสอบบริบทที่มีอยู่

## ทดสอบเครื่องมือและเอเจนต์ร่วมกัน

สร้างชุดงานตัวแทนขนาดเล็ก ได้แก่ คำขอทั่วไป ข้อมูลเข้าที่กำกวม ไฟล์ที่ไม่พร้อมใช้งาน และความพยายามใช้เครื่องมือนอกขอบเขตที่กำหนด ตรวจว่าเลือกเครื่องมือใด ส่งอาร์กิวเมนต์อะไร ได้ผลลัพธ์อะไร และคำตอบสุดท้ายเป็นอย่างไร การเรียก API สำเร็จอาจยังส่งคืนข้อมูลไม่ครบ จึงต้องตรวจคำตอบเทียบกับหลักฐานต้นทาง

เมื่อวินิจฉัยความล้มเหลวที่เกิดซ้ำ ให้เปลี่ยนส่วนติดต่อทีละส่วน บันทึกเวอร์ชันคำอธิบายเครื่องมือและทดสอบส่วนที่เกี่ยวข้องซ้ำ สำหรับการกระทำที่มีผลข้างเคียง ให้ตรวจสอบผลที่ไม่แน่นอนก่อนลองใหม่ เพราะการลองซ้ำอาจทำให้การกระทำที่สำเร็จแล้วเกิดขึ้นอีก

## นำแนวคิดไปใช้กับขั้นตอนงานเขียนโค้ด

Claude Code รองรับขั้นตอนงานที่รวมเครื่องมือและคำสั่งที่ใช้ซ้ำได้ ดู[เอกสารการใช้เครื่องมือของ Claude](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)ฉบับปัจจุบันสำหรับข้อตกลง API และ[เอกสาร skills ของ Claude Code](https://code.claude.com/docs/en/skills)สำหรับการจัดระเบียบคำสั่งที่ใช้ซ้ำได้ ความพร้อมใช้งานและส่วนติดต่อที่แน่นอนอาจเปลี่ยน จึงควรตรวจเอกสารของเวอร์ชันที่ใช้

คำถามในการออกแบบเดียวกันใช้ได้กับเฟรมเวิร์กเอเจนต์ต่าง ๆ: งานต้องการอะไร เอเจนต์สังเกตอะไรได้ เครื่องมือแต่ละตัวเปลี่ยนอะไรได้ และจะตรวจสอบผลอย่างไร
