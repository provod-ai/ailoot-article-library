# LLM ในฐานะผู้ตัดสิน: คู่มือฉบับสมบูรณ์

> LLM-as-a-judge คือการใช้โมเดลภาษาโมเดลหนึ่งประเมินผลลัพธ์ของอีกโมเดลหนึ่งตามเกณฑ์ที่กำหนด ทำให้การประเมิน AI ในวงกว้างทำได้จริงสำหรับแชตบอต ระบบ RAG และเอเจนต์ บทความนี้อธิบายโหมดการตัดสินหลักทั้งสามแบบ จุดที่ผู้ตัดสิน LLM ทำงานได้ดีและจุดที่ทำงานพลาด วิธีเขียนเกณฑ์ที่เชื่อถือได้ และเหตุใดจึงต้องปรับเทียบกับชุดข้อมูลทองคำที่ติดป้ายกำกับก่อนนำไปใช้จริง




LLM-as-a-judge คือการใช้โมเดลภาษาโมเดลหนึ่งประเมินผลลัพธ์ของอีกโมเดลหนึ่งตามเกณฑ์ที่กำหนด ทำให้การประเมิน AI ในวงกว้างทำได้จริงสำหรับแชตบอต ระบบ RAG และเอเจนต์ บทความนี้อธิบายโหมดการตัดสินหลักทั้งสามแบบ จุดที่ผู้ตัดสิน LLM ทำงานได้ดีและจุดที่ทำงานพลาด วิธีเขียนเกณฑ์ที่เชื่อถือได้ และเหตุใดจึงต้องปรับเทียบกับชุดข้อมูลทองคำที่ติดป้ายกำกับก่อนนำไปใช้จริง

> **สรุปสั้น ๆ —** LLM ในฐานะผู้ตัดสินคือการใช้โมเดลภาษาให้คะแนนผลลัพธ์ของโมเดลอื่นตามเกณฑ์ที่เขียนไว้ แทนที่ผู้ประเมินที่เป็นมนุษย์หรือใช้ควบคู่กัน ใช้การให้คะแนนคำตอบเดียวพร้อมเกณฑ์ที่ชัดเจนสำหรับการประเมินในระบบจริง ใช้การเปรียบเทียบเป็นคู่เพื่อจัดอันดับเวอร์ชันของโมเดล และอย่าเชื่อถือผู้ตัดสินที่ยังไม่ได้วัดผลเทียบกับชุดข้อมูลทองคำที่ติดป้ายกำกับ

บทความนี้เหมาะสำหรับวิศวกรที่สร้างการประเมินอยู่แล้วและต้องการคำตอบที่มีหลักฐานรองรับสำหรับคำถามว่า “เราควรใช้ผู้ตัดสิน LLM ที่นี่หรือไม่ และถ้าควร จะใช้อย่างไร” หากคุณไม่เคยเขียนการประเมินมาก่อน ให้เริ่มจากตัวอย่างติดป้ายกำกับจำนวนเล็กน้อย

## “LLM ในฐานะผู้ตัดสิน” หมายถึงอะไรกันแน่

ผู้ตัดสิน LLM คือโมเดลที่เรียกใช้ด้วย prompt ซึ่งขอให้ประเมินบางสิ่ง โดยทั่วไปคือคำตอบของโมเดลอื่น โดยจะส่งกลับคะแนน ป้ายกำกับ หรือความชอบ นั่นคือสถาปัตยกรรมทั้งหมด สิ่งที่น่าสนใจอยู่ที่ prompt เกณฑ์ และวิธีวัดว่าคำตัดสินของผู้ตัดสินตรงกับความเป็นจริงหรือไม่

เหตุผลที่วิธีนี้ได้รับความนิยมเป็นเรื่องการปฏิบัติงาน ไม่ใช่ปรัชญา กระบวนการประเมินที่ใช้มนุษย์ทั้งหมดขยายขนาดได้ยาก สิ่งที่ต้องแลกคือผู้ตัดสินมีอคติของตัวเอง และอคติเหล่านั้นเป็นระบบ ซึ่งต่างจากอคติของผู้ประเมินที่เป็นมนุษย์

## ผู้ตัดสิน LLM ให้คะแนนผลลัพธ์อย่างไร

มีวิธีให้คะแนนสามแบบ และการเลือกใช้แต่ละแบบจะเปลี่ยนสิ่งที่การประเมินของคุณบอกได้และบอกไม่ได้

- ‍**การเปรียบเทียบเป็นคู่** ขอให้ผู้ตัดสินเลือกว่าคำตอบใดจากสองคำตอบดีกว่า ใช้การเปรียบเทียบเป็นคู่เมื่อทดสอบ A/B ระหว่างโมเดลสองเวอร์ชันหรือ prompt สองแบบ อย่าใช้เมื่อจำเป็นต้องมีเกณฑ์คุณภาพแบบสัมบูรณ์ เพราะคะแนนจากการเปรียบเทียบเป็นคู่ไม่มีค่าขั้นต่ำ: คำตอบ B อาจชนะทุกการเปรียบเทียบแต่ยังใช้งานไม่ได้**‍**
- **การให้คะแนนคำตอบเดียวตามเกณฑ์** ขอให้ผู้ตัดสินให้คะแนนคำตอบหนึ่งรายการตามมาตรฐานที่ชัดเจน นี่คือวิธีที่ควรใช้ในระบบจริง เพราะทุกคำตอบจะได้คะแนนบนแกนเดียวกัน และคุณกำหนดเงื่อนไขการนำไปใช้ได้ (“เผยแพร่หากเกณฑ์ด้านความเที่ยงตรงผ่านในการทดสอบ canary”) เลือกสเกลที่มีความละเอียดต่ำที่สุดแต่ยังแยกความแตกต่างที่คุณสนใจได้: ผ่าน/ไม่ผ่านแบบสองค่าเมื่อคำถามคือ “โมเดลละเมิดเกณฑ์หรือไม่ ใช่หรือไม่” สเกลสามระดับ (ไม่ผ่าน / ผ่านบางส่วน / ผ่าน) เมื่อระดับความล้มเหลวมีความสำคัญต่อการคัดกรอง และใช้สเกล 1 ถึง 5 หรือ 1 ถึง 10 เฉพาะเมื่อจำเป็นต้องใช้ความละเอียดดังกล่าวจริง ๆ และมีข้อมูลชุดทองคำเพื่อยืนยันว่าผู้ตัดสินใช้สเกลนั้นได้ สเกลที่ละเอียดเกินไปเปิดช่องให้ผู้ตัดสินสร้างความแตกต่างที่ตนเองอธิบายรองรับไม่ได้ และสัญญาณรบกวนที่เกิดขึ้นจะกลบสัญญาณที่คุณต้องการวัด คุณภาพของเกณฑ์สำคัญกว่าการเลือกสเกล เกณฑ์ที่คลุมเครือ (“ให้คะแนนความเป็นประโยชน์จาก 1 ถึง 5”) ให้ตัวเลขที่ไม่มีสารสนเทศ ส่วนเกณฑ์ระดับข้อกล่าวอ้าง (“ให้คะแนน 0 หากมีข้อกล่าวอ้างเชิงข้อเท็จจริงข้อใดไม่ได้รับการรองรับโดยตรงจากข้อความที่ดึงมา”) ให้ตัวเลขที่นำไปใช้ตัดสินใจได้ ควรทบทวนเกณฑ์เมื่อข้อกำหนดการประเมินเปลี่ยนแปลง**‍**
- **การให้คะแนนโดยอ้างอิงคำตอบต้นแบบ** ให้คำตอบที่ทราบว่าถูกต้องแก่ผู้ตัดสิน แล้วถามว่าคำตอบของผู้สมัครใกล้เคียงเพียงใด วิธีนี้คล้ายกับเมตริก NLP แบบดั้งเดิมอย่าง BLEU และ ROUGE มากที่สุด แต่ใช้ความหมายแทนการทับซ้อนของ n-gram วิธีนี้ทำงานได้ดีกับงานที่มีผลลัพธ์จำกัดขอบเขต (การแปล การสรุปโดยเทียบกับบทสรุปทองคำ และการดึงข้อมูลแบบมีโครงสร้าง) แต่ใช้ไม่ได้ผลกับงานปลายเปิด เพราะมักมีคำตอบที่ยอมรับได้หลายแบบ และผู้ตัดสินจะลงโทษคำตอบที่ดีแต่แตกต่างออกไป

ในทางปฏิบัติ การตั้งค่าระบบจริงส่วนใหญ่ใช้การให้คะแนนคำตอบเดียวแยกตามแต่ละเกณฑ์ (ความเที่ยงตรง ความเกี่ยวข้อง และการทำตามรูปแบบ) และใช้การเปรียบเทียบเป็นคู่เฉพาะระหว่างการพัฒนาเพื่อเลือก prompt ที่เหมาะสมจากตัวเลือกที่มี

## เมื่อใดผู้ตัดสิน LLM จึงเป็นเครื่องมือที่เหมาะสม

ผู้ตัดสิน LLM ทำงานได้ดีกับงานที่การตัดสินโดยพื้นฐานแล้วเป็นปัญหาการอ่านจับใจความตามเกณฑ์ที่ระบุชัดเจน “คำตอบนี้มีข้อกล่าวอ้างเชิงข้อเท็จจริงที่ไม่ได้รับการรองรับจากบริบทที่ดึงมาหรือไม่” เป็นคำถามด้านการอ่านจับใจความ เช่นเดียวกับ “คำตอบนี้ปฏิเสธที่จะตอบในกรณีที่ข้อกำหนดระบุว่าต้องปฏิเสธหรือไม่” โมเดลผู้ตัดสินต้องดึงข้อกล่าวอ้างออกมา ค้นหาข้อความที่รองรับ (หรือระบุว่าไม่มี) แล้วส่งคำตัดสิน โมเดลระดับแนวหน้าทำสิ่งนี้ได้ดี

วิธีนี้ทำงานได้ไม่ดีนักกับงานที่ผู้ตัดสินต้องรู้อะไรบางอย่างซึ่งไม่สามารถระบุไว้ใน prompt ได้ “คำตอบนี้ตลกไหม” เป็นคำถามที่ทุกโมเดลจะตอบ แต่คำตอบจะสะท้อนอคติเดิมของผู้ตัดสิน ไม่ใช่ของผู้อ่านคุณ “โค้ดนี้เป็น Rust ที่เขียนตามสำนวนมาตรฐานหรือไม่” ต้องอาศัยผู้ตัดสินที่ซึมซับธรรมเนียมแบบเดียวกับทีมของคุณ ซึ่งอาจไม่ได้เป็นเช่นนั้น สำหรับงานเหล่านี้ ให้ถือว่าผู้ตัดสินเป็นสัญญาณหนึ่งในหลายสัญญาณ ไม่ใช่ความจริงสูงสุด

การใช้วิธีนี้ส่งผลเสียโดยตรงกับงานที่ต้นทุนจากความล้มเหลวที่ตรวจไม่พบสูง และรูปแบบความล้มเหลวเกิดขึ้นไม่บ่อย ผู้ตัดสินอาจพลาดความล้มเหลว ซึ่งเป็นเรื่องสำคัญเมื่อผลกระทบจากปัญหาที่พลาดไปมีความรุนแรง ในกรณีเหล่านั้น ผู้ตัดสินเป็นตัวกรองเพื่อคัดกรองเบื้องต้น (ช่วยลดจำนวนกรณีที่ผู้ตรวจสอบซึ่งเป็นมนุษย์ต้องดู) ไม่ใช่ผู้ตัดสินขั้นสุดท้าย

## ตัวอย่างที่ทำตามได้: ผู้ตัดสินความเที่ยงตรงใน 40 บรรทัด

ผู้ตัดสินที่มีประโยชน์และเรียบง่ายที่สุดคือเกณฑ์ความเที่ยงตรงสำหรับคำตอบเดียวของคำตอบ RAG ตัวอย่างนี้ใช้ OpenAI Python SDK:

```

from openai import OpenAI
from pydantic import BaseModel

client = OpenAI()

JUDGE_PROMPT = """You are evaluating whether an assistant's response is faithful
to a retrieved context passage. Faithful means every factual claim in the response
is directly and explicitly supported by the context. A claim is unfaithful if it
is added, modified, or drawn from outside the context.

Steps:
1. Enumerate every factual claim in the response (numbers, rules, entity names,
   negations, comparisons).
2. For each claim, locate the specific sentence in the context that supports it.
3. If any claim has no direct support, the response is unfaithful.
4. Truncated or cut-off context counts as zero support for whatever follows.

Return JSON: {{"verdict": "faithful" | "unfaithful", "reason": ""}}.

CONTEXT:
{context}

RESPONSE:
{response}
"""

class Verdict(BaseModel):
    verdict: str
    reason: str

def judge(context: str, response: str) -> Verdict:
    completion = client.beta.chat.completions.parse(
        model="gpt-4o-2024-11-20",
        messages=[{"role": "user",
                   "content": JUDGE_PROMPT.format(context=context, response=response)}],
        response_format=Verdict,
        temperature=0.0,
    )
    return completion.choices[0].message.parsed
  
```

prompt ขอให้ผู้ตัดสินแจกแจงข้อกล่าวอ้างก่อนประเมิน จึงเกิดการตรวจสอบในระดับข้อกล่าวอ้าง มีการระบุวิธีจัดการบริบทที่ถูกตัดทอนไว้อย่างชัดเจน เพราะกระบวนการดึงข้อมูลจะตัดข้อความตรงขอบเขตของชังก์ และหากไม่ระบุไว้ ผู้ตัดสินอาจถือว่าประโยคที่ไม่สมบูรณ์เป็นหลักฐานรองรับทั้งหมด ตั้งค่าอุณหภูมิเป็นศูนย์ เพราะอุณหภูมิที่ไม่เป็นศูนย์ในงานจำแนกแบบสองค่าทำให้เกิดความแปรปรวนที่ตีความไม่ได้

เท่านี้ก็เพียงพอสำหรับการรัน แต่ยังไม่เพียงพอสำหรับนำไปใช้จริง สองหัวข้อถัดไปครอบคลุมสิ่งที่เปลี่ยนตัวอย่างที่ทำงานได้ให้กลายเป็นผู้ตัดสินที่พร้อมใช้งานจริง ได้แก่ การปรับ prompt ให้เหมาะสม และการวัดว่าผู้ตัดสินเห็นพ้องกับมนุษย์จริงหรือไม่

## การเขียน prompt และเกณฑ์สำหรับผู้ตัดสิน

prompt ของผู้ตัดสินเป็นจุดที่สร้างความก้าวหน้าส่วนใหญ่ในระบบ LLM-as-a-judge โมเดลถูกกำหนดโดยผู้ให้บริการของคุณ สเกลการให้คะแนนถูกกำหนดโดยการออกแบบเกณฑ์ และชุดข้อมูลทองคำถูกกำหนดโดยโดเมนของคุณ prompt เป็นองค์ประกอบหนึ่งที่คุณปรับปรุงซ้ำได้ในระหว่างเปรียบเทียบผู้ตัดสินกับตัวอย่างติดป้ายกำกับ

prompt สำหรับผู้ตัดสินที่ใช้งานได้มีองค์ประกอบสี่ประการ ได้แก่ คำจำกัดความของเกณฑ์ด้วยคำที่ใช้ในโดเมนของคุณ ไม่ใช่ศัพท์ ML ทั่วไป (“เที่ยงตรงต่อบริบทที่ดึงมา” เป็นคำจำกัดความเฉพาะโดเมน ส่วน “คุณภาพสูง” ไม่ใช่) โครงสร้างการให้เหตุผลที่ชัดเจน ซึ่งสั่งให้ผู้ตัดสินแจกแจงข้อกล่าวอ้าง เงื่อนไข หรือการเรียกใช้เครื่องมือแต่ละรายการก่อนให้คะแนน (วิธีนี้ให้ลำดับการตรวจสอบที่ชัดเจนแก่ผู้ตัดสิน) กฎการให้คะแนนที่แปลงผลการให้เหตุผลเป็นสเกล เช่น “หากข้อกล่าวอ้างข้อใดที่แจกแจงไว้ไม่ได้รับการรองรับโดยตรงจากบริบทที่ดึงมา ให้คะแนน 0” ไม่ใช่ “ใช้วิจารณญาณของคุณ” และข้อกำหนดในการจัดการกรณีขอบที่พบในระบบจริง ได้แก่ บริบทที่ถูกตัดทอน ผลการดึงข้อมูลที่ว่างเปล่า คำตอบบางส่วน และการปฏิเสธ

สิ่งที่ไม่ควรใส่ไว้ใน prompt คือรายการยาว ๆ เช่น “ตรวจสอบให้แน่ใจว่าคำตอบของคุณเป็นประโยชน์ ซื่อสัตย์ และไม่ก่ออันตราย” คำสั่งทั่วไปมักถูกละเลย แต่กฎเฉพาะในระดับข้อกล่าวอ้างจะได้รับการปฏิบัติตาม อีกสิ่งที่ควรหลีกเลี่ยงคือการระบุรูปแบบคำตัดสินละเอียดเกินไป หากโมเดลต้องสร้างเหตุผลแบบมีโครงสร้างยาวเหยียดก่อนให้คะแนน คุณกำลังจ่ายค่า tokens ที่จะไม่ได้อ่าน

## อคติที่ทำให้ผู้ตัดสินแบบง่าย ๆ ไม่น่าเชื่อถือ

อคติหลายอย่างอาจส่งผลต่อผู้ตัดสิน LLM ควรคำนึงถึงอคติเหล่านี้เมื่อออกแบบการประเมิน

- ‍**อคติด้านตำแหน่ง** คือแนวโน้มที่จะชอบคำตอบที่ปรากฏก่อน (หรือบางครั้งปรากฏทีหลัง) ในการเปรียบเทียบเป็นคู่ วิธีแก้คือประเมินการเปรียบเทียบแต่ละครั้งทั้งสองลำดับ และนับเฉพาะกรณีที่คำตัดสินสอดคล้องกัน ซึ่งต้องให้คะแนนการเปรียบเทียบทั้งสองลำดับ**‍**
- **อคติด้านความยาว** คือแนวโน้มที่จะชอบคำตอบที่ยาวกว่า คำตอบที่ยาวกว่าอาจได้รับความชอบ แม้ความยาวจะไม่ใช่เกณฑ์ในการประเมินก็ตาม หากเกณฑ์ของคุณไม่ได้ระบุว่า “คำตอบที่กระชับจะได้คะแนนเท่ากันหรือดีกว่าคำตอบที่ยืดยาวเมื่อความถูกต้องเท่ากัน” ผู้ตัดสินก็จะปรับผลลัพธ์ให้เอื้อต่อความยาวโดยปริยาย วิธีบรรเทาคือระบุความเป็นกลางต่อความยาวในเกณฑ์อย่างชัดเจน**‍**
- **อคติชอบผลงานตนเอง** คือแนวโน้มที่ผู้ตัดสินจะชอบผลลัพธ์จากตระกูลโมเดลเดียวกับตนเอง หลีกเลี่ยงการใช้โมเดลตัดสินการเปรียบเทียบที่มีผลลัพธ์จากตระกูลโมเดลเดียวกัน ใช้โมเดลตัวที่สามเป็นผู้ตัดสิน หรือใช้ผู้ประเมินที่เป็นมนุษย์สำหรับการเปรียบเทียบครั้งนั้นโดยเฉพาะ

ปัญหาอื่นที่อาจเกิดขึ้น ได้แก่ อคติด้านความรู้สึกและการประจบเอาใจ ให้ใส่รูปแบบความล้มเหลวที่เกี่ยวข้องไว้ในชุดข้อมูลทองคำที่ติดป้ายกำกับซึ่งใช้ปรับเทียบ

## การปรับเทียบผู้ตัดสินกับชุดข้อมูลทองคำที่ติดป้ายกำกับ

ควรตรวจสอบ prompt ของผู้ตัดสินเทียบกับชุดข้อมูลทองคำที่ติดป้ายกำกับก่อนนำไปใช้จริง วิธีตรวจสอบก่อนนำไปใช้คือการปรับเทียบ: รันผู้ตัดสินเทียบกับชุดข้อมูลทองคำที่ติดป้ายกำกับ วัดช่องว่างระหว่างคำตัดสินกับป้ายกำกับจากมนุษย์ และปรับ prompt ซ้ำจนช่องว่างลดลง

วงจรการปรับเทียบมีข้อมูลนำเข้าสามอย่าง ได้แก่ ชุดข้อมูลทองคำที่ติดป้ายกำกับซึ่งมาจากการกระจายของงานประเมิน การรันค่าพื้นฐานที่บันทึกเมตริกความเห็นตรงกันและเมตริกข้อผิดพลาดที่เกี่ยวข้อง และขั้นตอนการปรับปรุงที่แก้ไข prompt โดยอิงจากตัวอย่างที่ผู้ตัดสินไม่เห็นด้วยกับป้ายกำกับ ให้ปรับเทียบซ้ำเมื่อ prompt หรือการกระจายของงานประเมินเปลี่ยนแปลง

ความแม่นยำโดยรวมซ่อนค่า recall รายคลาส ค่า Kappa ที่ต่ำแม้ความแม่นยำสูงอาจบ่งชี้ว่าความเห็นตรงกันใกล้เคียงกับการเดาสุ่ม ค่า Kappa ที่สูงขึ้นบ่งชี้ว่าความเห็นตรงกันเหนือกว่าระดับที่เกิดจากความบังเอิญ รายงานมากกว่าความแม่นยำเพียงอย่างเดียวเมื่อประเมินผู้ตัดสิน

## การสร้างชุดข้อมูลทองคำ

การปรับเทียบขึ้นอยู่กับชุดข้อมูลทองคำ และชุดข้อมูลทองคำไม่ได้มีมาให้โดยอัตโนมัติ การสร้างชุดข้อมูลดังกล่าวเป็นขั้นตอนเบื้องต้นที่กำหนดว่าสิ่งที่ทำต่อจากนั้นจะวัดสิ่งที่เกิดขึ้นจริงหรือวัดเพียงสัญญาณรบกวน

ชุดข้อมูลทองคำคือกลุ่มคู่ข้อมูลนำเข้าและผลลัพธ์ที่ผู้เชี่ยวชาญในโดเมนติดป้ายกำกับด้วยคำตัดสินที่คุณต้องการให้ผู้ตัดสินสร้าง คุณสมบัติสามประการทำให้ชุดข้อมูลทองคำเป็นรากฐานสำคัญสำหรับการประเมิน ชุดข้อมูลต้องมาจากการกระจายของงานประเมินจริง ได้แก่ คำค้นหาจริง บริบทที่ดึงมาจริง และคำตอบจากเอเจนต์จริง ไม่ใช่ตัวอย่างสังเคราะห์ที่ดูสมเหตุสมผลสำหรับคนที่เขียนชุดข้อมูล ต้องมีตัวแทนของประเภทความล้มเหลว หากชุดข้อมูลทองคำมีตัวอย่าง 100 รายการที่เที่ยงตรงทั้งหมด ก็ไม่ได้บอกอะไรเลยว่าผู้ตัดสินตรวจจับความไม่เที่ยงตรงได้หรือไม่ ทั้งที่นี่คือความล้มเหลวเดียวที่สำคัญ และต้องวัดความเห็นตรงกันระหว่างผู้ประเมินในชุดข้อมูลทองคำก่อนนำไปใช้ หากผู้เชี่ยวชาญในโดเมนมักไม่เห็นตรงกันในเรื่องป้ายกำกับ ให้ชี้แจงเกณฑ์ก่อนปรับเทียบ เพื่อหลีกเลี่ยงการปรับผลลัพธ์ให้เข้ากับสัญญาณรบกวนแทนรูปแบบความล้มเหลว

การสร้างคำค้นหาและคำตอบสังเคราะห์ที่สมจริงสำหรับชุดข้อมูลทองคำเป็นปัญหาทางวิศวกรรมในตัวเอง ปัจจุบันมีเฟรมเวิร์กหลายตัวที่สร้างข้อมูลเหล่านี้จากเอกสารต้นทางของคุณ และความแตกต่างระหว่างเฟรมเวิร์กเหล่านี้ส่งผลต่อประเภทความล้มเหลวที่ชุดข้อมูลทองคำซึ่งได้มาจะเปิดเผย 

## ความเห็นตรงกันระหว่างผู้ตัดสินกับมนุษย์ขึ้นอยู่กับงาน

ความเห็นตรงกันระหว่างผู้ตัดสิน LLM กับผู้ประเมินที่เป็นมนุษย์อาจแตกต่างกันไปตามงาน และมีข้อแตกต่างหลายประการที่สำคัญ

ความเห็นตรงกันมักตีความได้ง่ายกว่าในงานแบบปิดที่มีผลลัพธ์ตรวจสอบได้ เมื่อเทียบกับงานปลายเปิดที่ผู้ประเมินอาจมีความเห็นต่างกัน ไม่สามารถประเมินผู้ตัดสินแยกจากความเห็นตรงกันระหว่างผู้ประเมินที่เป็นมนุษย์ในงานนั้นได้

ข้อที่สองคือความเห็นตรงกันไม่เหมือนกับการสอดคล้องกัน ผู้ตัดสินอาจดูแม่นยำโดยรวม แต่พลาดประเภทความล้มเหลวที่สำคัญ (เช่น ให้ผ่านคำตอบที่ไม่มีหลักฐานรองรับว่าเที่ยงตรง) ตัวเลขรวมทำให้ผู้ตัดสินดูดีกว่าความเป็นจริง ส่วนค่า recall รายคลาสจะบอกว่าควรนำไปใช้จริงหรือไม่ หัวข้อการปรับเทียบข้างต้นช่วยแก้ปัญหานี้: วัดทั้งสองอย่าง แก้ prompt ตามความล้มเหลว แล้วทำซ้ำ

ข้อที่สามคือเมตริกความเห็นตรงกันขึ้นอยู่กับเมตริกที่ใช้ การรายงานความแม่นยำดิบในชุดข้อมูลทองคำที่ไม่สมดุล (ส่วนใหญ่เป็นตัวอย่างที่ผ่านและมีความล้มเหลวเพียงเล็กน้อย) ทำให้ผู้ตัดสินดูดีกว่าความเป็นจริง การรายงาน Cohen’s Kappa ซึ่งปรับค่าตามความเห็นตรงกันที่เกิดจากความบังเอิญนั้นบิดเบือนได้ยากกว่า ค่า Kappa ต่ำแม้ความแม่นยำจะดูสูงอาจบ่งชี้ว่าความเห็นตรงกันใกล้เคียงกับการเดาสุ่ม Pearson correlation มีประโยชน์กับคะแนนต่อเนื่อง ส่วน Spearman ใช้ได้ดีกว่าหากคุณเชื่อถือเฉพาะการจัดอันดับ ไม่ใช่ค่าตัวเลขสัมบูรณ์

สำหรับกระบวนการในระบบจริง ให้วัดผลกับชุดข้อมูลทองคำที่ติดป้ายกำกับและรายงานเมตริกความเห็นตรงกันหรือเมตริกข้อผิดพลาดที่เหมาะสมมากกว่าหนึ่งรายการ

การตัดสินใจว่าจะใช้ผู้ตัดสิน LLM เพียงอย่างเดียว ใช้เป็นตัวกรองคัดกรองเบื้องต้นโดยให้มนุษย์ตรวจสอบกลุ่มย่อยที่ถูกทำเครื่องหมายไว้ หรือข้ามผู้ตัดสินและใช้มนุษย์เท่านั้น ขึ้นอยู่กับตัวแปรสามอย่าง ได้แก่ ต้นทุนของความล้มเหลวที่ตรวจไม่พบ ปริมาณการประเมิน และอัตราการเปลี่ยนแปลงของการกระจายงานประเมิน

## จากตัวอย่างสู่ระบบจริง: การเชื่อมต่อผู้ตัดสิน

ตัวอย่าง 40 บรรทัดก่อนหน้าในบทความนี้เพียงพอสำหรับให้คะแนนคำตอบหนึ่งรายการใน Python REPL การวางผู้ตัดสินไว้หน้าคำตอบทุกรายการในระบบจริง (หรือรันกับทุก pull request ใน CI) เป็นปัญหาทางวิศวกรรมอีกแบบหนึ่ง

สิ่งที่ต้องทำเมื่อขยายขนาดไม่ใช่เรื่องน่าตื่นเต้น การจัดกลุ่มคำขอเพื่อไม่ให้การอนุมานของผู้ตัดสินครอบงำเวลาแฝงตั้งแต่ต้นจนจบ การจัดการการลองซ้ำในกรณีที่ผู้ตัดสินส่งคืน JSON ที่ผิดรูปแบบ เกินขีดจำกัดอัตราการเรียกใช้ หรือหมดเวลา การบันทึกคำตัดสินและร่องรอยการให้เหตุผลแบบมีโครงสร้าง เพื่อให้วินิจฉัยได้ภายหลังว่าเหตุใดกรณีใดกรณีหนึ่งจึงถูกทำเครื่องหมายไว้ การตรวจจับการถดถอยที่ทำงานเมื่อความสอดคล้องกับชุดข้อมูลทองคำ canary ลดลงระหว่างการเผยแพร่ การจัดการเวอร์ชันของ prompts สำหรับผู้ตัดสินเช่นเดียวกับการจัดการเวอร์ชันของโค้ดแอปพลิเคชัน เพื่อระบุการเปลี่ยนแปลงของความสอดคล้องกับการแก้ไข prompt ที่เฉพาะเจาะจง และการผสานเข้ากับระบบ CI ของคุณ เพื่อให้การรันผู้ตัดสินเป็นส่วนหนึ่งของเงื่อนไขก่อนเผยแพร่ แทนการตรวจสอบด้วยตนเองที่ใครบางคนอาจลืมทำเมื่อมีเวลาจำกัด

ไม่มีเรื่องใดในนี้ยากในเชิงความคิด แต่ทุกอย่างต้องใช้แรงงาน และลำดับที่คุณนำไปใช้ส่งผลต่อว่าคุณจะพบความล้มเหลวแบบใดในระบบจริงก่อน หากไม่มีการจัดการเวอร์ชันของ prompt ก็จะระบุสาเหตุของการถดถอยได้ยากขึ้นเมื่อความสอดคล้องเปลี่ยนแปลง

## เมื่อใดที่ไม่ควรใช้ผู้ตัดสิน LLM

มีสามสถานการณ์ที่ไม่ควรเลือกใช้ผู้ตัดสิน แต่ทีมต่าง ๆ ก็ยังทำเช่นนั้นเป็นประจำ

เมื่องานมีการตรวจสอบความถูกต้องแบบกำหนดผลลัพธ์แน่นอน อย่าใช้ผู้ตัดสิน การตรวจสอบความเทียบเท่าของคิวรี SQL การตรวจสอบความถูกต้องของ JSON schema การจับคู่ regex การเปรียบเทียบสตริงแบบตรงตัว และการจับคู่อาร์กิวเมนต์ของการเรียกใช้เครื่องมือล้วนเป็นปัญหาที่แก้ได้แล้ว การนำผู้ตัดสิน LLM มาครอบงานเหล่านี้เพิ่มเวลาแฝง เพิ่มต้นทุน และเพิ่มโอกาสที่ไม่เป็นศูนย์ในการตัดสินผิดเกี่ยวกับสิ่งที่มีคำตอบแน่นอน ใช้การตรวจสอบแบบกำหนดผลลัพธ์แน่นอน ให้ไม่ผ่านทันทีเมื่อไม่ตรงกัน และเรียกใช้ผู้ตัดสินเฉพาะส่วนที่ต้องใช้การให้เหตุผลด้วยภาษาธรรมชาติจริง ๆ

หากคุณยังไม่ได้สร้างชุดข้อมูลทองคำที่ติดป้ายกำกับ อย่าใช้ผู้ตัดสินในระบบจริง ผู้ตัดสินให้ตัวเลขแก่คุณ หากไม่มีค่าความจริงอ้างอิง คุณจะบอกไม่ได้ว่าตัวเลขนั้นมีความหมายหรือไม่ ชุดข้อมูลทองคำควรแสดงถึงงานประเมินจริงและมีกรณีความล้มเหลวที่สำคัญรวมอยู่ด้วย

เมื่อต้นทุนของความล้มเหลวที่ตรวจไม่พบสูงกว่าต้นทุนการตรวจสอบโดยมนุษย์ อย่าใช้ผู้ตัดสินเป็นด่านตัดสินขั้นสุดท้าย ให้ใช้เป็นตัวกรองคัดกรองเบื้องต้นที่ลดจำนวนกรณีที่มนุษย์ต้องตรวจสอบ การนำผู้ตัดสินไปใช้ในโดเมนที่มีการกำกับดูแลโดยไม่มีมนุษย์ร่วมตรวจสอบเป็นการตัดสินใจอีกแบบหนึ่ง และควรตัดสินใจอย่างชัดเจนโดยมีฝ่ายกฎหมายและฝ่ายกำกับดูแลการปฏิบัติตามกฎระเบียบร่วมด้วย ไม่ใช่ตัดสินใจโดยปริยายเพียงเพราะผู้ตัดสินได้คะแนนสูงในชุดข้อมูลสำหรับการพัฒนา

ผู้ตัดสินเป็นเครื่องมือ ไม่ใช่คำตัดสินขั้นสุดท้าย ผู้ตัดสินสมควรได้ใช้งานเมื่อช่วยจับความล้มเหลวที่ไม่เช่นนั้นจะหลุดไปสู่ระบบจริง และหมดความเหมาะสมทันทีเมื่อคุณหยุดวัดว่ายังทำเช่นนั้นได้อยู่หรือไม่
