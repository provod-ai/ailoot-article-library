# ต้นทุนที่แท้จริงของการอนุมาน LLM คือ GPU ที่คุณไม่ได้ใช้งาน

> ราคาอ้างอิงโทเคนอินพุตของ API สองค่าในอดีตต่างกัน 600 เท่า อัตราการใช้งาน GPU ชั่วโมงเช่าที่เครื่องว่าง และอัตราช่วงพีกมีผลต่อต้นทุนการอนุมาน LLM



งานศึกษาปี 2026 (arXiv:2603.28576, §4) เปรียบเทียบราคา API ที่ใช้เป็นเกณฑ์อ้างอิงสองรายการ งานศึกษานี้ใช้ราคาอ้างอิงต่อโทเคนอินพุตหนึ่งล้านโทเคนที่ 60 ดอลลาร์สหรัฐสำหรับ GPT-3 ในปี 2020 และ 0.10 ดอลลาร์สหรัฐสำหรับ Gemini 2.0 Flash กลุ่มประหยัดในเดือนกุมภาพันธ์ 2025 ซึ่งต่างกัน 600 เท่า งานศึกษาประเมินว่าราคาในกลุ่มประหยัดที่ศึกษาลดลงครึ่งหนึ่งในเวลา 1.1 ปี

สิ่งที่พาดหัวข่าวเรื่องภาวะเงินฝืดไม่ได้บอกคือปัจจัยที่กำหนดค่าใช้จ่ายของคุณจริง ๆ นั่นคือ GPU ของคุณทำงานที่เป็นประโยชน์อยู่กี่ชั่วโมง การอนุมานคิดค่าบริการตามจำนวนโทเคน แต่ให้บริการตามชั่วโมง

แถวภายในศูนย์ข้อมูลที่มีเซิร์ฟเวอร์ GPU โดยส่วนใหญ่ส่องสว่างขณะทำงาน ส่วนหนึ่งเครื่องมืดและไม่ได้ใช้งาน

## ตัวเลขที่ทีมมักมองข้าม

การทดสอบประสิทธิภาพ vLLM ในเดือนมิถุนายน 2026 (arXiv:2606.11690, §§4–5) รัน Mixtral 8x7B Instruct ที่ความแม่นยำระดับ FP16 บน GPU H100 NVL สองตัว โดยใช้การประมวลผลเทนเซอร์แบบขนาน (TP=2) ค่าเช่า GPU รวมอยู่ที่ 13.96 ดอลลาร์สหรัฐต่อชั่วโมง การทดสอบใช้คำขอจำลองที่มีโทเคนอินพุต 512 โทเคนและเอาต์พุต 256 โทเคนต่อคำขอ โดยปิดการแคชคำนำหน้า ต้นทุนในตารางคำนวณจากค่าเช่า GPU หารด้วยจำนวนโทเคนเอาต์พุตที่วัดได้ในช่วงเวลาเดียวกัน อัตราคำขอนับจากจำนวนคำขอที่ส่งไปยังเซิร์ฟเวอร์

| Mixtral 8x7B บน GPU H100 NVL สองตัว | ต้นทุนที่แท้จริงต่อโทเคนเอาต์พุต 1M โทเคน |
|--------------------------------------------|---------------------------------------------|
| 1 คำขอต่อวินาที (เกือบไม่ได้ใช้งาน)        | ประมาณ 15.25 ดอลลาร์                        |
| ส่ง 100 คำขอต่อวินาที (ใกล้ถึงจุดอิ่มตัว)                           | ประมาณ 0.87 ดอลลาร์                         |

ต้นทุนที่วัดได้ทั้งสองค่าต่างกัน 17.5 เท่า เมื่อส่ง 25 คำขอต่อวินาที ต้นทุนอยู่ที่ประมาณ 0.95 ดอลลาร์สหรัฐต่อโทเคนเอาต์พุตหนึ่งล้านโทเคน เมื่อส่ง 100 คำขอต่อวินาที เซิร์ฟเวอร์ประมวลผลจนเสร็จประมาณ 17.4 คำขอต่อวินาที งานศึกษาพบว่าต้นทุนอยู่ระหว่าง 0.21 ถึง 15.25 ดอลลาร์สหรัฐต่อโทเคนเอาต์พุตหนึ่งล้านโทเคน เมื่อทดสอบการตั้งค่า H100 หกรูปแบบและภาระงานในระดับที่ศึกษา ตัวเลขเหล่านี้เป็นค่าที่วัดจากภาระงานทดสอบนี้ ในระบบที่ใช้งานจริง ให้วัดอัตราการประมวลผลที่ระดับภาระงานซึ่งยังเป็นไปตามเป้าหมายเวลาแฝงของคุณ

หากค่าเช่าต่อชั่วโมงเท่าเดิม การสร้างโทเคนเอาต์พุตได้เพียง 40% ของอัตราสูงสุดจะทำให้ต้นทุนต่อโทเคนเอาต์พุตเพิ่มเป็น 2.5 เท่า ในตัวอย่างต่อไปนี้ อัตราการใช้งานคือสัดส่วนระหว่างอัตราการสร้างโทเคนเอาต์พุตที่บริการทำได้จริงกับอัตราสูงสุด ตัวชี้วัดการทำงานของ GPU อาจสูงแม้จะได้โทเคนเอาต์พุตน้อย

นี่จึงเป็นเหตุผลที่สองทีมซึ่งรันโมเดลเดียวกันอาจรายงานต้นทุนต่อหน่วยต่างกันมาก ทีมหนึ่งรันแชตบอตที่มีทราฟฟิกพุ่งเป็นช่วง ๆ ด้วยอัตราการใช้งาน 40 เปอร์เซ็นต์ ส่วนอีกทีมรันไปป์ไลน์ประมวลผลแบบแบตช์ที่ทำงานเต็มกำลัง 90 เปอร์เซ็นต์ โมเดล ฮาร์ดแวร์ และราคาที่ติดไว้เหมือนกัน แต่ต้นทุนต่อหน่วยไม่เหมือนกัน เมื่อผู้ให้บริการเสนอราคาต่อโทเคน ให้ถามว่าราคานั้นตั้งอยู่บนสมมติฐานเรื่องอัตราการใช้งานเท่าใด

## โมเดลแบบเปิดน้ำหนักทำให้เรื่องนี้แย่ลง

โมเดล Mixture-of-Experts (MoE) ใช้น้ำหนักเพียงบางส่วนในการประมวลผลแต่ละโทเคน Mixtral 8x7B เปิดใช้พารามิเตอร์ประมาณ 12.9 พันล้านตัวต่อโทเคน จากทั้งหมด 46.7 พันล้านตัว หากรันโมเดลทั้งหมดบน GPU ให้เผื่อหน่วยความจำสำหรับน้ำหนักทั้งหมดตามความแม่นยำที่ใช้จัดเก็บ รวมถึงแคช KV และหน่วยความจำส่วนเพิ่มขณะรันโมเดล จำนวนพารามิเตอร์ที่เปิดใช้ช่วยประมาณปริมาณการคำนวณต่อโทเคน แบนด์วิดท์หน่วยความจำ วิธีที่โมเดลเลือกใช้เอ็กซ์เพิร์ต และขนาดแบตช์ก็ส่งผลต่ออัตราการประมวลผลด้วย

ประเมินจุดคุ้มทุนสำหรับภาระงานของคุณ รวมค่าเช่า GPU สำหรับทุกชั่วโมงที่ต้องเช่า แม้ในช่วงที่ไม่ได้ใช้งาน แล้วบวกต้นทุนการเดินระบบ นำยอดที่ได้ไปเทียบกับค่าใช้ API สำหรับโทเคนอินพุตและเอาต์พุตในปริมาณและสัดส่วนเดียวกัน วัดอัตราการสร้างโทเคนเอาต์พุตตามรูปแบบทราฟฟิกของคุณในสภาวะที่เป็นไปตามเป้าหมายเวลาแฝง ราคา API การตั้งค่าโมเดล และอัตราการใช้งานล้วนส่งผลต่อผลลัพธ์

## ปัจจัยที่เปลี่ยนตัวเลขจริง ๆ

หากคุณกำลังประเมินงบประมาณสำหรับการอนุมาน ให้ไล่ดูรายการนี้ก่อนเปรียบเทียบราคาโมเดล:

1.  ดูอัตราการใช้งานก่อนฮาร์ดแวร์ H200 ที่มีอัตราการใช้งาน 40 เปอร์เซ็นต์อาจมีต้นทุนต่อโทเคนสูงกว่า H100 ที่ทำงานเต็มกำลัง
2.  ตรวจสอบว่าผู้ให้บริการของคุณคิดราคาต่ำลงเมื่ออินพุตตรงกับข้อมูลในแคชหรือไม่ การนำพรอมป์ต์ระบบที่ยาวหรือคำนำหน้าร่วมกลับมาใช้ซ้ำอาจช่วยลดค่าอินพุต หากอินพุตนั้นเข้าเงื่อนไขอัตราสำหรับแคชที่ตรงกัน
3.  ถ่วงน้ำหนักอัตราช่วงพีกและนอกพีกตามสัดส่วนทราฟฟิกของคุณ เมื่อใช้ API ของ DeepSeek โดยตรงและมีปริมาณโทเคนกับเงื่อนไขแคชเท่ากัน ค่าใช้จ่ายช่วงพีกจะเป็นสองเท่าของช่วงนอกพีก
4.  รวมงานเบื้องหลังที่รอได้ เช่น การทำดัชนี RAG และการดึงข้อมูลจำนวนมาก ไว้ประมวลผลเป็นแบตช์ วัดอัตราการสร้างโทเคนเอาต์พุตและเวลาแฝงด้วยการตั้งค่าแบตช์ที่คุณจะใช้
5.  สำหรับโมเดล MoE ให้ใช้จำนวนพารามิเตอร์ที่เปิดใช้เพื่อประมาณปริมาณการคำนวณ และเผื่อหน่วยความจำสำหรับน้ำหนักทั้งหมด แคช KV รวมทั้งหน่วยความจำส่วนเพิ่มขณะรันโมเดล
