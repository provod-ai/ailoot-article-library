# LLM routeri nima?

> Model routing qanday ishlashi, router tarkibiy qismlari, o‘zingiz yaratish yoki tayyor yechimni tanlash o‘rtasidagi murosalar va router qachon kerak bo‘lmasligi mumkinligini bilib oling.



## LLM routeri nima — va u sizga rostdan ham kerakmi?

LLM router ilova va modellarning API nuqtalari o‘rtasida ishlaydi. U har bir inferens so‘rovi uchun modelni, shu modelni taqdim etuvchi provayderni yoki ikkalasini tanlashi mumkin. Qoidalar xatodan keyin qachon boshqa API nuqtasini sinashni belgilaydi.

Bu atama hozir urfda, demak, uni tegishli bo‘lmagan narsalarga nisbatan ham ishlata boshlashdi. Istalgan routerni baholash yoki o‘zingiz yaratishdan oldin uning tarkibida aslida nimalar borligini aniq bilib olish kerak.

## Bir xil nom bilan ataladigan ikki xil narsa

**Modellarni marshrutlash** so‘rovni bajaradigan modelni tanlaydi. Oddiy tasniflash uchun kichikroq model yetishi mumkin, murakkab sintez uchun esa kuchlirog‘i kerak bo‘lishi mumkin. **Provayderlar orasida marshrutlash** birinchi provayder vaqtincha ortiqcha yuklansa, tanlangan modelni saqlagan holda boshqa mos API nuqtasiga o‘tish imkonini beradi.

**Vosita chaqiruvlarini marshrutlash** agent vositani tanlaganidan keyin chaqiruvni bajaradigan xizmatni tanlaydi. Veb-qidiruvni mahalliy indeksdan boshlab, kengroq qamrov zarur bo‘lsa, boshqa qidiruv API’sini sinash mumkin. Zanjirdagi xizmatlar bir xil amalni bajaradi.

Har ikki holatda qoidalar so‘rov talablariga javob beradigan variantlarni tartiblaydi. Model javobining sifatini oldindan baholash qiyin bo‘lishi mumkin. Ayrim vosita natijalari osonroq tekshiriladi, masalan, ajratib olishda maqola matni qaytdimi. Qidiruv natija qaytarganida ham foydalanuvchi savoli javobsiz qolishi mumkin.

Bu maqolada ikkalasi ham ko‘rib chiqiladi, chunki ularning tuzilishi umumiy.

## LLM routeri ichida aslida nimalar bor

Marketing gaplarini olib tashlasak, router to‘rtta tarkibiy qismdan iborat. Mahsulot sizga shu to‘rttasini ham ko‘rsata olmasa, u o‘z qarashlariga ega proksidir.

**Siyosat.** Avval so‘rovga kerakli imkoniyatlar bo‘yicha saralang. Mos variantlarni kutilayotgan sifat, narx yoki kechikish bo‘yicha tartiblang. Qat’iy ustuvorlik ro‘yxati yetarli bo‘lishi mumkin. Model darajasini tasniflagich tanlasa, u qanday yaxshilanish berishini o‘lchang.

**Holat ko‘rsatkichlari.** Har bir API nuqtasi uchun xatolar ulushi, vaqt chegarasidan oshgan urinishlar va kechikish persentillarini kuzating. API javob bermasa chaqiruv davom etishi uchun har urinishga vaqt chegarasi qo‘ying. Bir nechta so‘rovdagi o‘zgarishlarga qarab, yomonlashgan API nuqtasini qachon vaqtincha chetlab o‘tishni belgilang.

**Zaxiraga o‘tish qoidalari.** Qaysi xatolar navbatdagi urinishga ruxsat berishini belgilang. Masalan, so‘rovni xavfsiz takrorlash mumkin bo‘lsa, vaqtincha ortiqcha yuklanish yoki vaqt chegarasidan oshish. Natijasiz HTTP 200 javobi uchun alohida qoida belgilang. Urinishlar soni va jami vaqtni cheklang. Mijoz kutish vaqti tugaganida natija va ehtimoliy to‘lov hali noma’lum.

**Xarajat hisobi.** Javob bergan model va xizmatni, kechikishni hamda mavjud foydalanish va to‘lov ma’lumotlarini yozib boring. Barcha urinishlarni, muvaffaqiyatsizlarini ham, bitta so‘rovga bog‘lang. Butun zanjirning xarajatini taqqoslash uchun taxminiy qiymatlarni tasdiqlangan to‘lovlardan ajrating.

## O‘zingiz yaratasizmi yoki tayyor yechimni tanlaysizmi?

Oddiy router mos API nuqtalari ro‘yxati, har bir urinish uchun va umumiy vaqt chegarasi, zaxiraga o‘tish qoidalari va urinishlar jurnalidan boshlanishi mumkin. Bu qoidalar ehtiyojni qoplaguncha ilovada qolishi mumkin.

Yaratish va qo‘llab-quvvatlash zerikarli bo‘lgan qismlar kerak bo‘lsa, tayyor yechimni tanlang: API o‘zgarishlarini kuzatib boradigan provayder integratsiyalari, oqilona standart sozlamalar bilan holatni kuzatish, yangilanib turadigan xarajat jadvallari va transport infratuzilmasi. MCP serveri vositani bitta interfeysdan taqdim etib, chaqiruvni bajaradigan provayderni tanlashi mumkin.

Provayderlarga kirish ma’lumotlarini boshqarish, foydalanish yozuvlarini eksport qilish va chaqiruvlarni qayta yozmasdan API nuqtalarini almashtirish mumkinligini tekshiring. O‘zingiz ishlatadigan va xostingdagi router xarajatlarini, jumladan router to‘lovlarini, taqqoslang.

## Router ortiqcha bo‘ladigan holatlar

Bu bo‘lim ochiqchasiga yozilgan, chunki sarlavhadagi savolga ba’zan javob «yo‘q» bo‘ladi.

Bitta provayderning bitta modeliga kam murojaat qiladigan, kritik bo‘lmagan vazifada router ko‘pincha kerak emas. Masalan, oylik hisob 40 dollar bo‘lsa, mumkin bo‘lgan tejashni ishlab chiqish va texnik xizmat xarajatlari bilan solishtiring.

Kichik integratsiyaga bitta zaxira provayder yetishi mumkin. Muayyan vaqtinchalik xatoni qayta ishlang va so‘rovni xavfsiz takrorlash mumkin bo‘lsa, belgilangan muddat ichida mos zaxirani sinang.

Bir vazifani bir necha provayder bajarsa, uzilishlar foydalanuvchilarga ta’sir qilgan bo‘lsa, o‘lchangan xarajatlar ishni oqlasa yoki qoidalar ilova bo‘ylab tarqalgan bo‘lsa, ularni bir joyga jamlang. Umumiy siyosat qarorlarni bitta joyda saqlash va sinash imkonini beradi.

Mos API nuqtalari, ularni sinash tartibi va navbatdagi urinish mumkin bo‘ladigan shartlar ro‘yxatidan boshlang. Avvaliga qat’iy ro‘yxat yetishi mumkin. Vazifaga kerak bo‘lganda zaxira qo‘shing.
