# LLM 라우터란?

> 모델 라우팅과 라우터 구성 요소, 직접 구축할지 도입할지에 따른 장단점, 라우터가 필요하지 않을 수 있는 경우를 알아보세요.



## LLM 라우터란 무엇이며, 정말 필요한가요?

LLM 라우터는 애플리케이션과 모델 엔드포인트 사이에서 동작합니다. 추론 요청마다 모델, 해당 모델을 제공하는 공급자 또는 두 가지 모두를 선택할 수 있습니다. 실패 후 다른 엔드포인트를 시도할 시점은 라우팅 정책이 정합니다.

요즘 이 용어가 주목받으면서 본래 포함되어서는 안 되는 것까지 가리키도록 의미가 확장되고 있습니다. 라우터를 평가하거나 직접 만들기 전에 실제로 무엇이 들어 있는지 정확히 짚어볼 필요가 있습니다.

## 같은 이름으로 불리는 서로 다른 두 가지

**모델 라우팅**은 요청을 처리할 모델을 고릅니다. 일상적인 분류는 작은 모델로 충분할 수 있고, 복잡한 정보 종합에는 더 강력한 모델이 필요할 수 있습니다. **공급자 라우팅**은 선택한 모델을 유지하면서 첫 공급자가 일시적으로 과부하 상태일 때 호환되는 다른 엔드포인트로 전환할 수 있습니다.

**도구 호출 라우팅**은 에이전트가 도구를 고른 뒤 실제 호출을 실행할 서비스를 정합니다. 웹 검색은 로컬 색인에서 시작하고 검색 범위를 넓힐 필요가 있으면 다른 검색 API를 시도할 수 있습니다. 체인에 있는 서비스는 같은 도구 작업을 수행합니다.

두 경우 모두 요청 요건을 만족하는 대상을 정책에 따라 정렬합니다. 모델 응답의 품질을 미리 평가하기는 어려울 수 있습니다. 도구 출력은 문서 본문이 추출됐는지처럼 더 쉽게 확인할 수 있는 경우가 있습니다. 검색 결과가 있어도 사용자가 찾는 답과 관련이 없을 수 있습니다.

이 글은 두 가지를 모두 다룹니다. 구조가 같기 때문입니다.

## LLM 라우터의 실제 구성 요소

마케팅을 걷어내면 라우터는 네 가지 구성 요소로 이루어져 있습니다. 제품이 이 네 가지를 모두 보여주지 못한다면, 나름의 의견을 가진 프록시에 불과합니다.

**정책.** 요청에 필요한 기능을 지원하는 대상부터 추립니다. 그다음 예상 품질, 가격 또는 응답 시간으로 우선순위를 정합니다. 고정 목록만으로 충분할 때도 있습니다. 분류기가 모델 등급을 정한다면 실제로 무엇이 개선되는지 측정합니다.

**상태 지표.** 엔드포인트별 오류율, 시간 초과 횟수, 지연 시간 백분위수를 추적합니다. 응답이 없는 엔드포인트에서 처리를 이어갈 수 있게 시도마다 시간 제한을 둡니다. 여러 요청에서 관찰한 추세를 토대로 상태가 나쁜 대상을 일시적으로 건너뛸지 정합니다.

**대체 경로 규칙.** 일시적 과부하나, 요청을 안전하게 반복할 수 있는 경우의 시간 초과처럼 어떤 실패가 다음 시도를 허용하는지 정합니다. 검색 결과가 없으면서 HTTP 200을 반환한 경우에는 별도의 규칙을 둡니다. 시도 횟수와 전체 시간을 제한합니다. 클라이언트 시간 제한이 끝나도 결과와 과금 여부는 확정되지 않습니다.

**비용 기록.** 응답한 모델과 서비스, 지연 시간, 확인 가능한 사용량 및 과금 정보를 기록합니다. 실패한 시도를 포함해 모든 시도를 동일한 원래 요청에 연결합니다. 예상 비용과 확인된 청구액을 구분하면 전체 체인의 비용을 비교할 수 있습니다.

## 직접 만들까, 도입할까?

간단한 라우터는 호환 대상 목록, 시도별 시간 제한, 전체 마감 시간, 대체 규칙과 시도 기록으로 시작할 수 있습니다. 필요한 작업을 처리할 수 있는 동안에는 규칙을 애플리케이션에 둘 수 있습니다.

구축과 유지 관리가 번거로운 부분이 필요하다면 기존 솔루션을 도입하세요. API 변경을 따라가는 제공업체 통합, 합리적인 기본값을 갖춘 상태 추적, 최신 상태로 유지되는 비용표, 전송 계층 설정 등이 여기에 해당합니다. MCP 서버는 단일 인터페이스로 도구를 제공하고 호출을 실행할 공급자를 내부에서 선택할 수 있습니다.

공급자 자격 증명을 제어하고, 사용 기록을 내보내고, 호출 코드를 다시 작성하지 않고도 엔드포인트를 변경할 수 있는지 확인합니다. 자체 운영과 호스팅 방식의 비용을 비교할 때는 라우터 자체의 비용도 포함합니다.

## 라우터가 과한 경우

제목의 질문에 대한 답이 때로는 ‘아니요’이기 때문에, 솔직하게 짚고 넘어가겠습니다.

중요도가 낮고 호출도 적은 작업에서 한 공급자의 모델 하나만 사용한다면 라우터가 필요 없는 경우가 많습니다. 예를 들어 월 청구액이 40달러라면 기대할 수 있는 절약액과 개발 및 유지 관리 비용을 비교합니다.

작은 연동에는 예비 공급자 하나면 충분할 수 있습니다. 특정 일시 오류를 처리하고 요청을 안전하게 반복할 수 있을 때에만 기한 내에 호환되는 예비 공급자를 시도합니다.

여러 공급자가 같은 작업을 처리하거나, 장애가 사용자에게 영향을 줬거나, 측정한 비용을 볼 때 개발이 타당하거나, 라우팅 로직이 애플리케이션에 흩어져 있다면 규칙을 한곳에 모읍니다. 공통 정책이 있으면 한곳에서 판단 규칙을 관리하고 테스트할 수 있습니다.

호환되는 엔드포인트, 시도 순서, 다음 시도를 허용하는 조건을 먼저 적습니다. 처음에는 고정 목록이면 충분할 수 있습니다. 작업에 필요해지면 대체 경로를 추가합니다.
