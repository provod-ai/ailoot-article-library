# 소형 언어 모델이란? 10B 미만 모델이 강점을 발휘하는 영역과 한계를 드러내는 영역

> 소형 언어 모델이 무엇인지, 10억~100억 매개변수 범위의 오픈 웨이트 모델이 프로덕션에서 사용되는 이유, 그리고 프런티어 모델 대신 소형 언어 모델을 선택해야 하는 경우를 설명합니다.



이 가이드에서는 파라미터가 약 10억~100억 개인 모델을 소형 언어 모델(SLM)의 기준으로 삼습니다. 일부 모델은 가중치를 공개합니다. 효율과 비용이 중요할 때 특정 작업의 대량 추론이나 기기 내 추론에 활용할 수 있습니다.

학습 방법, 추론 경제성, 성숙해지는 오픈 웨이트 생태계 덕분에 소형 모델 체크포인트는 다양한 작업에서 경쟁력을 갖추게 되었습니다. 이 가이드에서는 모델 크기가 프로덕션 AI 워크로드에 어떤 영향을 미치는지 살펴봅니다.

## SLM이란 정확히 무엇인가

소형 언어 모델은 일반적으로 매개변수가 10억 개에서 100억 개 사이인 트랜스포머 기반 언어 모델을 뜻합니다. 10억 개 미만의 모델은 흔히 초소형 언어 모델 또는 온디바이스 언어 모델이라고 부릅니다. 이러한 모델은 휴대전화, 노트북 CPU, 임베디드 하드웨어에 적합하며, 양자화와 아키텍처 선택이 배포 방식에 영향을 줍니다. 100억 개를 넘으면 비용과 지연 시간이 달라집니다. 소비자용 단일 GPU에서 배포하기가 더 어려워지고, 파인튜닝 비용이 증가하며, 고려해야 할 상충 관계도 달라집니다.

양자화는 더 적은 비트로 가중치를 저장합니다. 파라미터가 700억 개인 Llama는 4비트로 양자화해도 파라미터 수가 같습니다. 메모리 사용량과 출력 품질은 달라질 수 있습니다.

## 지금 이 범주가 존재하는 이유

세 가지 학습 기술의 발전이 격차를 줄이는 데 기여했습니다. 첫째, 합성 데이터와 선별된 데이터 구성이 소형 모델에 더 높은 품질의 학습 토큰을 제공했습니다.

둘째, 지시 튜닝과 선호도 최적화를 통해 프런티어 모델의 일부 역량을 더 작은 모델로 이전했습니다. 지시 튜닝이 잘된 소형 기본 모델은 해당 튜닝의 대상 작업에서 훨씬 큰 원시 모델에 가까운 사용성을 보일 수 있습니다. 셋째, 증류는 다양한 프롬프트에 걸쳐 소형 모델이 대형 모델을 모방하도록 학습시킵니다. 이를 통해 순수 사전 학습만으로 같은 수준에 도달하려면 필요했을 더 큰 토큰 예산 없이도 앞서 나갈 수 있습니다.

이 기술들이 결합되어 매개변수당 역량 비율이 2022년의 스케일링 법칙에 대한 예상으로는 믿기 어려울 만큼 높은 오픈 웨이트 소형 모델이 탄생했습니다. 오늘날의 SLM 범주는 이러한 발전의 결과입니다.

## 모델 현황

아래는 2026년 5월까지 공개된 사례입니다. 같은 제품군에도 더 큰 모델이 있으므로 구체적인 버전을 확인하세요.

Microsoft의 Phi 계열은 더 작은 규모에 속하며, Phi-3 mini와 Phi-3.5 mini 변형 모델은 비용 한도가 있는 추론 워크로드에 사용됩니다. Google의 [Gemma 2](https://blog.google/technology/developers/google-gemma-2/)는 2B, 9B, 27B 변형 모델로 제공됩니다. Meta의 Llama 3.1 8B와 Llama 3.2(1B 및 3B)는 다양한 오픈 웨이트 SLM 배포 사례를 지원합니다.

Mistral 7B와 Ministral 3 (3B, 8B) 계열도 이 부문의 선택지입니다. Alibaba의 [Qwen 2.5](https://qwenlm.github.io/blog/qwen2.5/)는 0.5B, 3B, 7B, 14B 변형 모델로 제공됩니다. 더 작은 [DeepSeek](https://www.deepseek.com/) 변형 모델도 시장의 일부를 차지합니다.

주요 프런티어 모델 학습 업체들도 자사 아키텍처의 소형 변형 모델을 출시합니다. 여러 규모에 걸쳐 아키텍처, 데이터 파이프라인, 인프라를 재사용하면 더 적은 연산량으로도 소형 모델이 대형 형제 모델의 강점과 약점을 물려받을 수 있습니다. 이는 모델 계열마다 추론, 지시 수행, 코딩, 배포 범위 등이 다른 이유를 설명하는 데 도움이 될 수 있습니다.

## SLM이 프런티어에 가까운 수준으로 수행할 수 있는 작업

SLM과 프런티어 모델 사이의 역량 격차는 작업에 따라 다릅니다. 일반적인 프로덕션 작업에서는 격차가 비용을 주요 요인으로 만들 만큼 작을 수 있습니다. SLM은 분류(감성, 의도, 주제, 콘텐츠 조정, 언어 감지), 구조화된 추출(개체명, 키-값 쌍, 스키마에 맞춘 JSON 출력), 짧거나 중간 길이 문서의 요약, 익숙한 주제에 대한 단일 턴 질의응답, 재작성·번역·확장·축약·형식 변경 같은 일상적인 생성 작업을 처리할 수 있습니다.

도구 설명이 명확하면 소형 모델로도 도구를 호출할 수 있습니다. 실제 요청에서 도구 선택과 스키마 유효성을 검증하세요. 도구 수나 작업 복잡도가 달라지면 다시 테스트하세요.

코드 생성도 SLM이 유용할 수 있는 분야입니다. Python, JavaScript, SQL, Java처럼 익숙한 언어와 CRUD, 접착 코드, 스크립팅, 리팩터링, 간단한 알고리즘 같은 표준 작업에서는 코딩에 맞춰 파인튜닝된 변형 모델이 쓸 만한 결과를 낼 수 있습니다. 새로운 아키텍처, 여러 파일에 걸친 변경, 덜 익숙한 엣지 케이스에서는 프런티어 코딩 모델과의 격차가 더 뚜렷해집니다.

이러한 작업 전반에서 프롬프트가 모델의 학습 및 지시 튜닝 분포에 들어맞을수록 성능이 좋은 경향이 있습니다. 프로덕션에서 핵심 질문은 프롬프트가 그 분포를 벗어날 때도 모델의 견고성이 유지되는지 여부입니다.

## SLM이 잘하지 못하는 작업

역량의 한계는 분명하며, 특정 작업에서는 프런티어 모델과의 격차가 가장 큽니다. 학습 중 함께 등장하지 않았던 사실들을 조합해야 하는 답변에서는 새로운 다단계 추론이 어려울 수 있습니다. 장기 계획도 쉽지 않습니다. 중간 작업을 수행하는 동안 계획을 작업 메모리에 유지해야 하는 과제는 흐트러지거나 일관성을 잃을 수 있습니다. 서로 비슷하지만 미묘하게 다른 도구가 많은 레지스트리에서 복잡하게 도구를 선택할 때도 격차가 드러날 수 있습니다. 학습 중 함께 등장하는 경우가 드물었던 주제를 결합하는 교차 영역 프롬프트에서도 마찬가지입니다.

긴 컨텍스트에서의 성능도 약점입니다. SLM이 128K 이상의 컨텍스트 창을 지원한다고 내세우더라도, 그 창 전체에서 정보를 검색하는 정확도는 같은 길이의 프런티어 모델보다 더 빠르게 저하될 수 있으며 전체 컨텍스트를 대상으로 하는 추론도 약할 수 있습니다. 표시된 컨텍스트 길이와 실제로 효과적인 컨텍스트 길이는 다를 수 있고, 모델 규모가 작을수록 그 차이가 커지는 경향이 있습니다. 긴 문서 작업에서는 더 작은 창을 사용하는 프런티어 모델이나 검색 증강 아키텍처가 총비용을 낮추면서 더 나은 성능을 낼 수 있습니다.

학습 분포에서 참고할 만한 기반이 거의 없는 경우 역량 격차가 특히 두드러집니다. 예를 들어 개방형 창작 글쓰기, 공개 학습 데이터가 부족한 분야의 전문가 질의응답, 흔치 않은 사실 여러 개를 결합하는 다단계 추론이 이에 해당합니다. 프로덕션 AI 사용의 상당 부분을 차지하는 대량의 일상 작업에서는 격차가 덜 두드러집니다.

## 파인튜닝의 이점

가중치에 접근할 수 있으면 LoRA와 QLoRA로 미세 조정에 필요한 메모리를 줄일 수 있습니다. 비용은 모델, 데이터, 하드웨어에 따라 다릅니다. 실제 작업에서 미세 조정의 효과를 검증하세요.

따라서 SLM 계층은 경제적인 동시에 전략적으로도 유용합니다. 프런티어 모델 학습 업체는 주력 모델의 소형 변형을 출시하고 프로덕션 팀이 이를 특화할 수 있도록 합니다. SLM은 오픈 웨이트 생태계에 도메인별 가치를 더할 수 있는 계층이 됩니다. 파인튜닝에 성공하면 다른 공급업체의 호스팅 API에는 쉽게 이전되지 않을 수 있는 사내 기술도 축적됩니다.

실질적인 선택은 대개 기본 상태의 SLM이 프런티어 모델과 대등한지 여부가 아닙니다. 더 유용한 질문은 파인튜닝된 SLM이 팀의 데이터와 작업에서 프런티어 모델과 대등한지 여부입니다. 기본 상태의 모델을 비교했을 때 예상되는 것보다 그럴 가능성이 더 높을 수 있습니다.

## 배포 경제성

같은 품질 기준을 통과한 결과당 비용을 비교하세요. 호스팅 API는 입력과 출력 요금, 재시도를 계산하세요. 자체 호스팅은 하드웨어, 전력, 사용률을 포함하세요. 입력 길이와 동시 요청 수를 맞춘 상태에서 첫 토큰까지 걸리는 시간과 전체 지연 시간을 측정하세요.

SLM은 소비자용 GPU, 단일 호스트 서버, 엣지 기기, 사용자 하드웨어에서 실행할 수 있습니다. 이를 통해 온디바이스 추론, 오프라인 제품, 그리고 프런티어 모델을 실제로 호스팅할 수 없는 엄격한 지연 시간 예산의 시스템을 구현할 수 있습니다. 하드웨어 선택과 관련한 절충 사항은 LLM 추론용 GPU 용량 산정 가이드에서 다룹니다.

## SLM을 사용해야 하는 경우

핵심 질문은 SLM의 비용 대비 역량이 특정 워크로드에 적합한지 여부입니다. 다음과 같은 유형에서는 일반적으로 SLM이 유리합니다.

- **대량의 한정된 작업.** 프로덕션 규모의 분류, 추출, 라우팅, 간단한 질의응답, 요약 작업은 파인튜닝 비용을 분산시키고 낮은 추론 비용을 운영비 절감으로 연결할 수 있습니다.
- **지연 시간에 민감한 루프 내 작업.** 음성 에이전트, IDE 보조 도구, 실시간 분류, 사용자가 모델의 응답을 기다리는 기능은 더 낮은 지연 시간과 더 높은 처리량의 이점을 얻을 수 있습니다.
- **온디바이스 또는 오프라인 배포.** 데이터를 외부로 보낼 수 없거나 네트워크 접속이 불안정한 모바일 앱, 데스크톱 소프트웨어, 엣지 기기에는 SLM이 필요할 수 있습니다.
- **보유 데이터 기반의 특화.** 라벨이 지정된 데이터나 도메인별 데이터가 있는 팀은 해당 특성을 반영하도록 SLM을 파인튜닝할 수 있습니다.
- **비용 한도가 있는 프로덕션 루프.** 멀티턴 에이전트 루프, 대규모 배치 추론 등 호출당 비용이 누적되는 유형에서는 SLM이 유리할 수 있습니다.

다음과 같은 유형에서는 일반적으로 SLM이 불리합니다.

- **정말로 새로운 추론.** 어려운 수학, 복잡한 코드, 익숙하지 않은 영역의 다단계 계획에는 학습 범위가 더 넓은 프런티어 모델이 유리합니다.
- **컨텍스트가 중요한 장문 컨텍스트 작업.** SLM의 장문 컨텍스트 검색은 신뢰하기 어려울 수 있습니다. 50K가 넘는 토큰 창 전체에서 정확하게 정보를 기억해야 답할 수 있다면 프런티어 모델이나 검색 아키텍처의 성능이 더 나을 수 있습니다.
- **품질을 유지해야 하는 영역 간 전이.** 개방형 글쓰기, 여러 분야에 걸친 전문가 질의응답, 정교한 창작 작업은 광범위한 학습 범위에 의존하며, 이를 프런티어 규모 미만의 모델로 재현하기는 더 어려울 수 있습니다.
- **프롬프트를 미리 알 수 없는 워크로드.** 작업 범위를 사전에 파악할 수 없다면 SLM의 더 좁은 견고성 여유가 위험 요소가 될 수 있습니다.

## 요약 표

| 기준 | 소형 언어 모델 (1-10B) | 프런티어 LLM |
|----|----|----|
| 합격한 결과당 비용 | 범위가 좁은 작업에서 더 낮은 경우가 많음 | 모델, 요금, 재시도에 따라 다름 |
| 하드웨어 요구 사항 | GPU 한 개나 로컬 기기로 충분할 수 있음 | 자체 호스팅에 여러 GPU가 필요할 수 있음 |

## 실제로 의미하는 바

프로덕션 AI에서는 어려운 문제에 프런티어 모델을, 일상적인 요청에 SLM을 사용하는 경우가 많습니다. 일부 워크로드는 SLM만 사용하고, 다른 워크로드는 라우팅 계층을 사용해 쉬운 요청을 SLM으로, 어려운 요청을 프런티어 모델로 보냅니다. 소형 모델이 개선되고 프로덕션 팀이 파인튜닝 경험을 쌓으면 SLM의 비중이 늘어날 수 있습니다.

엔지니어링 팀에서 모델을 선택할 때 역량은 더 이상 유일한 의미 있는 기준이 아닙니다. 프로토타입 제작에서는 비용보다 역량이 중요할 수 있으므로 프런티어 모델이 유용한 기본 선택지가 될 수 있습니다. 파인튜닝된 SLM이나 SLM과 프런티어 모델을 신중하게 조합한 라우팅 방식은 워크로드별 비용 대비 역량이 중요한 프로덕션에 더 적합할 수 있습니다. 워크로드별로 모델 적합성을 측정하지 않는 팀은 SLM으로 처리할 수 있는 작업에 프런티어 요금을 지불할 수 있습니다.

멀티모델 배포에서는 라우팅 계층이 필요한 역량에 따라 들어오는 트래픽을 분류하고, 적합한 모델 중 가장 작은 모델로 요청을 보낼 수 있습니다. 소형 모델이 요청을 거부하거나 검증에 실패하면 더 큰 모델로 전환하고, 클래스별 성공률을 추적해 임계값을 조정할 수도 있습니다. 요청마다 적절한 크기의 모델을 선택하는 것이 모델 라우팅의 핵심입니다. 팀은 이를 자체적으로 구축하거나 모델 라우팅을 서비스로 제공하는 플랫폼을 사용할 수 있습니다.

단일 API를 통해 여러 SLM 및 프런티어 모델 계열을 평가하는 팀은 공급업체의 통합 추론 서비스들을 비교하고, 어떤 모델이 일관된 도구 호출 및 구조화된 출력 동작을 지원하는지 확인할 수 있습니다. 자체 호스팅 여부는 목표 처리량을 달성하는 데 필요한 GPU 용량에도 좌우됩니다.
