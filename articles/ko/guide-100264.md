# AI 추론이란 무엇인가? 완벽 가이드

> AI 추론은 학습된 모델이 새로운 입력으로부터 출력을 생성하는 런타임 단계입니다. 이는 프로덕션 환경에서 AI 기반 제품의 비용, 지연 시간, 안정성을 좌우하는 계층입니다.



AI 추론은 학습된 머신러닝 모델이 새로운 입력에 응답해 출력을 생성하는 과정입니다. 챗봇이 질문에 답하거나, 검색 시스템이 순위가 매겨진 결과를 반환하거나, 이미지 모델이 그림을 생성할 때 추론은 저장된 모델 가중치를 사용자가 보는 응답으로 바꾸는 단계입니다. 학습은 모델을 만들고, 추론은 누군가 모델을 사용할 때마다 모델을 실행합니다.

챗봇의 모든 답변, AI 코드 자동 완성, AI 생성 검색 요약에는 추론이 필요합니다. 모델 학습은 한 번 이루어지지만 추론은 사용자 요청마다 실행됩니다. 따라서 서빙 계층의 비용, 지연 시간, 안정성은 AI 기반 제품의 경제성에 영향을 미칩니다.

## 추론의 실제 의미

추론은 고정된 가중치를 사용하는 학습된 모델의 런타임 실행입니다. 학습 중에는 모델이 예시를 통해 배우면서 가중치가 바뀝니다. 학습이 끝나면 해당 가중치가 저장됩니다. 추론은 고정된 가중치에 새로운 입력을 결합해 출력을 계산합니다. 추론 중에 모델 자체는 바뀌지 않습니다. 읽기 전용 순방향 계산을 수행합니다.

대규모 언어 모델의 단일 추론 요청은 네 단계로 이루어지며, 각 단계마다 비용과 지연 시간 특성이 다릅니다.

![LLM 추론 파이프라인: 프롬프트를 토큰화하고 병렬 프리필 단계에서 처리한 다음, 자기회귀 디코드 단계에서 토큰을 하나씩 생성하고 다시 텍스트로 변환합니다]()

1. **토큰화.** 입력 텍스트를 토큰으로 나눕니다. 토큰은 대략 음절이나 짧은 단어 크기의 단위이며, 모델의 어휘집에서 숫자로 표현됩니다. 500단어 문서는 토크나이저에 따라 600~800개의 토큰이 될 수 있습니다. 토큰화는 요청당 처리하는 토큰 수에 영향을 줍니다.
2. **프리필.** 토큰이 한 번의 순방향 계산으로 모델 계층을 통과해 입력 표현과 첫 번째 출력 토큰을 만듭니다. 이 단계는 연산량에 좌우되며 병렬화하기 쉽습니다.
3. **자기회귀 디코드.** 모델은 다음 출력 토큰을 하나씩 생성하며, 각각의 새 토큰은 이전 토큰을 조건으로 합니다. 이 단계는 연산량보다 메모리 대역폭에 좌우되며, 이는 긴 응답의 지연 시간에서 이 단계가 어떤 역할을 하는지 설명하는 데 도움이 됩니다.
4. **디토큰화.** 출력 토큰을 사용자가 받는 읽을 수 있는 텍스트로 변환합니다.

프리필은 빠르고 병렬로 처리되며, 디코드는 더 느리고 순차적으로 진행됩니다. 이러한 차이는 LLM 추론에 기존 머신러닝 모델 서빙과는 다른 인프라 전문 분야가 생긴 이유 중 하나입니다. 추론 성능을 설명하는 데도 도움이 됩니다. 첫 토큰까지 걸리는 시간은 프리필의 영향을 받고, 초당 토큰 수는 디코드의 영향을 받습니다. 두 지표에는 서로 다른 최적화가 적용됩니다.

## 추론과 학습: 간단히 비교

학습과 추론은 여러 운영 측면에서 다릅니다. 학습은 대규모 데이터 세트를 소비해 가중치 집합을 만들고, 추론은 입력을 반복해서 받아 출력을 생성합니다.

| 항목 | 학습 | 추론 |
|----|----|----|
| 빈도 | 모델 버전당 한 번 | 사용자 요청당 한 번 |
| 기간 | 며칠에서 몇 달 | 밀리초에서 몇 초 |
| 하드웨어 | 노드 간 대역폭이 높은 긴밀하게 연결된 GPU 클러스터 | 개별 GPU 또는 소규모 그룹 |
| 비용 구조 | 자본 비용과 유사하며 선불로 지불 | 운영 비용과 유사하며 사용량에 비례 |
| 비용 부담 주체 | 모델 제작자 | 애플리케이션 팀 |
| 최적화 우선순위 | 모델 품질 | 비용, 지연 시간, 안정성 |

기반 모델을 활용해 제품을 만드는 팀에서는 학습 경제성을 모델 제공업체가 담당하는 경우가 많고, 애플리케이션 팀은 추론 경제성을 관리합니다. 제공업체, 배포 위치, 배치 처리, 캐싱, 대체 경로에 관한 결정은 모두 추론에 영향을 줍니다.

## 추론 워크로드 유형

추론의 정의에는 학습된 모델이 출력을 생성하는 모든 경우가 포함되지만, 워크로드 특성은 크게 다르므로 주요 범주를 구분해 부르는 것이 유용합니다.

![응답 지연 시간과 요청당 비용에 따라 다섯 가지 LLM 추론 워크로드 유형을 배치한 지도: 임베딩이 가장 저렴하고 빠르며, 채팅은 중간에 위치하고, 비전과 추론은 점차 느리고 비용이 많이 들며, 배치는 지연을 허용하는 할인 옵션입니다]()

**텍스트 생성(채팅).** 흔한 추론 워크로드입니다. 프롬프트가 입력되고 토큰이 하나씩 생성되며, 응답을 사용자에게 스트리밍할 수 있습니다.

**추론 및 chain-of-thought.** 모델이 사용자에게 표시되는 응답에 앞서 내부 추론 블록을 생성하는 텍스트 생성의 변형입니다. 예를 들어 OpenAI의 o 시리즈, Anthropic의 extended thinking 모드, DeepSeek-R1이 있습니다.

**임베딩.** 텍스트 입력으로 생성된 텍스트 대신 고정 길이 벡터가 출력됩니다. 임베딩은 검색, 검색 증강 생성(RAG), 클러스터링, 중복 제거에 사용됩니다. 임베딩 추론은 여러 최신 검색 및 메모리 시스템을 지원합니다.

**비전 및 멀티모달.** 이미지, 비디오 프레임 또는 오디오 클립을 텍스트와 결합해 텍스트나 구조화된 출력을 만듭니다. 입력 해상도가 높아지면 지연 시간이 늘어날 수 있으며, 비용은 입력이 디코딩되어 몇 개의 토큰이 되는지에 따라 달라집니다. 동일한 서빙 인프라로 이러한 워크로드를 처리할 수 있지만, 토큰화 비용은 일반 텍스트보다 높을 수 있습니다.

**배치 추론.** 실시간 응답이 필요하지 않은 파이프라인, 예를 들어 야간 데이터 보강, 오프라인 평가, 예약된 데이터 준비 작업에서는 배치 추론으로 비용을 줄일 수 있습니다.

## 추론은 어디에서 실행되는가

프로덕션 수준의 품질로 추론을 실행하려면 API 표면에서는 보이지 않지만 비용에 영향을 주는 세 가지 인프라 계층에 의존해야 합니다.

**GPU 계층.** 최신 LLM은 메모리 용량과 대역폭이 큰 GPU를 필요로 합니다. 대형 모델에는 NVIDIA H100 및 H200 카드가 사용됩니다. 더 작은 모델은 A100 또는 L40S 카드에서 실행할 수 있고, 매우 작은 모델은 소비자용 카드에서 실행할 수 있습니다. 카드 선택은 처리량과 여러 카드에 분할하지 않고 서빙할 수 있는 최소 모델 크기에 영향을 줍니다. GPU 메모리 용량 산정은 LLM 추론 계획의 핵심입니다.

**Serving engine.** GPU에 직접 접근하는 것만으로는 충분하지 않습니다. 효율적인 모델 서빙에는 KV 캐시를 관리하고, 동시 요청을 배치 처리하며, 메모리 레이아웃을 최적화하는 엔진이 필요합니다. 이를 inference engine 또는 inference server라고도 합니다. 널리 쓰이는 엔진에는 vLLM(오픈 소스, 범용), TensorRT-LLM(NVIDIA 전용, 고성능), SGLang(오픈 소스, 구조화된 생성에 최적화)이 있습니다. 동일한 하드웨어에서도 serving engine에 따라 처리량이 크게 달라질 수 있습니다.

**지역별 배포.** 연산 시간은 추론 지연 시간의 주요 원인이며, 네트워크 왕복은 지연을 더합니다. 사용자 대상 워크로드에서는 사용자와 가까운 지역에서 서빙하면 체감 응답성에 영향을 줄 수 있습니다.

이 스택의 운영은 상당한 규모와 전담 인프라 엔지니어링 역량을 갖춘 팀에 적합할 수 있습니다. 다른 팀은 인프라를 구매할 수 있으며, 이때 구매 모델을 선택하는 일이 중요합니다.

## 팀이 실제로 추론에 접근하는 방법

프로덕션 추론 환경에는 다음 세 가지 방식이 널리 사용됩니다.

![세 가지 추론 접근 방식의 아키텍처 비교: serving engine과 임대 GPU를 사용하는 자체 호스팅 스택, 단일 제공업체의 직접 API, 하나의 API 요청을 여러 제공업체로 라우팅하는 통합 플랫폼]()

**임대 GPU에서 자체 호스팅.** 팀이 GPU 용량을 임대하고, 오픈 웨이트 모델을 serving engine에 배포한 뒤 전체 스택을 운영합니다. 팀이 직접 제어할 수 있고 트래픽이 매우 많을 때 경제적일 수 있지만, KV 캐시 튜닝, 오토스케일링, 장애 조치, 관측 가능성 같은 영역의 인프라 전문 지식이 필요합니다.

**제공업체 직접 API.** 팀이 단일 제공업체의 API를 호출하고, 제공업체가 인프라를 관리합니다. 작동하는 제품을 빠르게 만들 수 있어 흔히 사용되는 시작 방법입니다. 단점은 집중 위험과 단일 가격 체계에 대한 의존성입니다. 각 요청의 비용, 지연 시간, 안정성은 해당 제공업체의 서비스에 달려 있습니다.

**통합 추론 플랫폼.** 팀이 여러 기반 제공업체로 요청을 라우팅하는 단일 API를 호출하며, 여기에 대체 경로, 관측 가능성, 비용 제어 기능이 포함될 수 있습니다. 이를 통해 제공업체 직접 API의 빠른 출시 이점을 유지하면서 단일 제공업체 집중 위험을 줄이고, 간단한 질의에는 저렴한 모델을, 복잡한 질의에는 더 뛰어난 모델을 사용하는 등 워크로드를 고려한 라우팅을 할 수 있습니다.

| 접근 방식 | 출시 속도 | 운영 부담 | 경제적인 사용량 | 집중 위험 |
|----|----|----|----|----|
| 임대 GPU에서 자체 호스팅 | 느림 | 높음(전체 인프라 스택) | 매우 높은 사용량 | 없음 |
| 제공업체 직접 API | 빠름 | 낮음 | 낮음에서 중간 수준의 사용량 | 높음(단일 제공업체) |
| 통합 추론 플랫폼 | 빠름 | 낮음 | 모든 사용량, 혼합 워크로드 | 낮음(여러 제공업체) |

이 방식들 가운데 선택하는 기준은 규모, 엔지니어링 역량, 제공업체별 비용과 안정성의 차이를 팀이 직접 얼마나 관리할 의향이 있는지에 따라 달라집니다.

## 추론이 지속적인 비용 발생 지점인 이유

추론 비용은 사용량에 따라 늘어나므로 AI 기반 제품의 경제성에 영향을 줍니다. 모델 학습 비용은 고정되어 있으며 제공업체나 모델을 학습한 팀이 한 번 지불합니다. 추론 요청이 발생할 때마다 추가 연산 자원이 소비됩니다. 사용자 10명은 추론 10회를 만들고, 사용자 100만 명은 추론 100만 회를 만듭니다. 실제로 AI 제품의 단위 경제성은 추론의 단위 경제성에 달려 있습니다.

![모델 수명 전체의 누적 비용 그래프: 학습 비용은 한 번 증가한 뒤 일정하게 유지되지만, 추론 비용은 0에서 시작해 처리하는 요청마다 증가하여 결국 전체 학습 비용을 넘어섭니다]()

이 구조에는 두 가지 결과가 따릅니다. 첫째, AI 기능의 비용은 사용량에 따라 증가합니다. 도입률이 낮은 기능은 추론 비용이 적고, 도입률이 높은 기능은 더 큰 추론 비용을 발생시킵니다. 둘째, 추론 비용을 바꾸는 아키텍처 선택의 효과는 사용량이 증가하면서 누적됩니다. 여기에는 모델 선택, 프롬프트 설계, 캐싱 전략, 제공업체 선택, 재시도 정책이 포함됩니다. 요청당 비용을 20% 줄이면 사용량 증가에 따른 한계 비용도 같은 비율로 줄어듭니다.

헤드라인에 표시된 토큰 100만 개당 비용은 특정 요청 시나리오를 설명하는 수치이며, 프로덕션 워크로드는 그 시나리오와 다를 수 있습니다.

## 대부분의 추론 가이드에서 빠뜨리는 내용

앞서 설명한 작동 원리는 잘 문서화되어 있습니다. 프로덕션에서 여러 제공업체를 통해 추론을 실행하다 보면 몇 가지 운영상 고려 사항이 분명해집니다.

- **가장 저렴한 모델이 가장 저렴한 시스템인 경우는 드뭅니다.** 토큰당 가격은 낮지만 더 자주 실패하거나, 같은 품질을 내려면 더 긴 프롬프트가 필요하거나, 재시도를 더 많이 유발하는 모델은 명목 가격이 더 비싼 모델보다 완료된 작업당 비용이 더 클 수 있습니다. 실제 비용은 전체 요청 경로에 따라 달라지므로, 비용 최적화에는 가격표뿐 아니라 아키텍처도 고려해야 합니다.
- **출력 길이는 강력한 조정 수단입니다.** 디코드는 추론 지연 시간과 출력 비용 모두에 영향을 주므로, 응답을 짧게 만드는 프롬프트 변경은 두 가지를 모두 개선할 수 있습니다.
- **대체 경로 정책은 가격에 영향을 줍니다.** 제공업체는 서비스 중단이나 요청 제한을 겪을 수 있습니다. 그런 상황에서 시스템이 실패할지, 요청을 대기열에 넣을지, 다른 곳으로 라우팅할지는 경제적인 결정입니다. 대체 경로 체계는 가용성과 비용에 영향을 줍니다.
- **기반 환경은 조용히 바뀔 수 있습니다.** 제공업체는 가격을 변경하고, 배포 모델을 양자화하거나, 안정된 이름 뒤에서 모델 버전을 바꿀 수 있습니다. 한 번 조정한 뒤 다시 확인하지 않은 추론 설정은 시간이 지나면서 성능이 저하될 수 있습니다.
- **벤치마크 순위가 어떤 모델이 요청을 처리할지 결정하지는 않습니다.** 순위표는 성능이 뛰어난 모델을 찾는 데 도움이 되지만, 특정 요청에 사용할 모델을 선택할 때는 비용, 지연 시간, 가용성 제약도 고려해야 합니다.

이러한 고려 사항은 추론의 정의에 포함되지는 않지만 프로덕션 비용에 큰 영향을 줄 수 있습니다.

## 추론이 이끄는 질문

추론을 이해하는 것은 출발점입니다. 프로덕션에서 내려야 할 결정에는 각 요청을 어떤 모델이 처리할지, 어느 제공업체에서 처리할지, 비용은 얼마인지, 어떤 대체 경로를 둘지가 포함됩니다. 하나의 고정 모델을 선택하면 앞으로 발생할 모든 트래픽에 대해 이 결정을 한 번에 내리게 됩니다. 또 다른 방식은 요청별 필요에 따라 모델을 선택하는 것입니다.

워크로드를 모델에 매핑하는 팀은 워크로드의 요구사항을 모델의 기능 및 비용과 비교해 모델을 선택해야 합니다.
