# LLM 추론의 삼중 딜레마: 처리량, 지연 시간, 비용

> 하드웨어, 모델, 스케줄링 선택에 따른 배포상의 절충을 포함해 LLM 추론에서 처리량, 지연 시간, 비용의 균형을 맞추는 실용 가이드입니다.



기존 웹 서비스를 확장할 때는 무상태 마이크로서비스 앞에 로드 밸런서를 배치하고 트래픽이 늘어남에 따라 CPU 인스턴스를 추가하는 경우가 많습니다. 대규모 언어 모델은 추론이 상태를 유지하고 메모리 대역폭에 의해 병목이 생길 수 있으며 물리적 하드웨어 인터커넥트에 의존하기 때문에 이러한 접근 방식을 바꿉니다. LLM 추론 확장은 다차원 최적화 문제입니다.

## 고전적인 삼중 딜레마

처리량을 늘리면 지연 시간이 증가할 수 있습니다. 지연 시간을 줄이면 GPU 비용이 증가할 수 있습니다. 비용을 최적화하려면 나머지 두 차원 중 하나에서 절충해야 할 수 있습니다.

처리량, 지연 시간, 비용 사이의 이러한 긴장은 전용 LLM 호스팅의 핵심 엔지니어링 과제입니다. 이를 이해하면 팀이 경제성과 인프라 예산을 고려하면서 확장할 수 있습니다.

이 가이드에서는 절충 관계, 추론 비용의 여러 차원, 비용에 영향을 미치는 선택, 하드웨어 선정과 벤치마킹을 통해 비용 지형을 파악하는 방법을 설명합니다. 처리량이나 지연 시간 중 무엇을 최적화해야 하는지와 그에 따른 절충점도 다룹니다.

## LLM 추론에서 ‘비용’은 실제로 무엇을 의미할까요?

일반적인 웹 호스팅에서는 트래픽이 늘어 서버를 추가하면서 비용이 증가하는 경우가 많습니다. LLM 호스팅에서 비용은 다차원 지표입니다. 추론 비용은 흔히 **토큰 100만 개당 달러**로 표시하지만, 전용 인프라에서 LLM을 서비스하는 비용에는 적어도 네 가지 차원이 있습니다.

### 자본 비용(CapEx): 노드 전체에 대한 비용

하드웨어 비용입니다. GPU는 NVLink 같은 고속 인터커넥트로 연결되므로 노드 단위로 용량을 구매해야 할 수 있습니다. 예를 들어 70B 모델에 GPU 네 개만 필요하더라도 8-GPU H100 노드를 한 번에 구매해야 할 수 있습니다. 모델은 클러스터 용량의 일부만 사용할 수 있지만 전체 용량에 대한 비용은 계속 발생합니다.

### 운영 비용(OpEx): 전기와 클라우드 비용

하드웨어를 소유하면 전력과 냉각 비용이 지속적으로 발생하고, 대여하면 이러한 비용이 시간당 요금으로 전환됩니다. 클라우드 대여는 OpEx 대안이며, 유휴 용량 비용은 OpEx 효율성의 과제로 남습니다.

### 기회비용: 활용률 격차

트래픽이 적은 시간에 GPU가 유휴 상태인 매분은 비용을 지불했지만 사용하지 않은 용량입니다. 성능 저하 없이 전용 하드웨어를 여러 모델이 공유하기 어려울 수 있으므로, 트래픽이 불규칙하면 지불한 용량과 실제 사용량 사이에 격차가 생길 수 있습니다.

오케스트레이션이나 전용 인프라 기반 서버리스 구성이 없으면 전용 노드의 제한적인 멀티테넌시가 투자 수익률을 낮출 수 있습니다.

따라서 자동 확장은 비용 최적화 도구이자 안정성 메커니즘으로 기능할 수 있습니다. 예를 들어 북미 개발자를 지원하는 코딩 어시스턴트는 태평양 시간 기준 오전 2시부터 6시 사이에 단일 복제본으로 축소해 GPU 유휴 시간을 줄일 수 있습니다.

### 엔지니어링 비용: 전문 인력

엔지니어링 비용은 흔히 과소평가됩니다. 하드웨어 외에도 배포를 튜닝할 전문 인력이 필요합니다. vLLM 또는 TensorRT-LLM에 적합한 구성을 찾으려면 상당한 시스템 엔지니어링 시간이 들 수 있습니다.

소프트웨어 스택에는 Nsight를 이용한 프로파일링과 CUDA 버전 관리 등의 작업이 포함됩니다. 월별 GPU 비용을 낮추는 것이 목표일 때도 벤치마킹에는 상당한 엔지니어링 시간이 필요할 수 있습니다.

## 비용을 좌우하는 요소

모델 아키텍처, 양자화, 병렬 처리, 배칭은 배포 간 비용 차이의 상당 부분을 설명합니다. 이러한 선택은 엔지니어링 의사결정과 경제성을 연결합니다.

### 모델 아키텍처: Dense와 MoE

Llama 3 70B 같은 Dense 모델에서는 메모리와 VRAM 요구량에 따라 비용이 증가합니다. DeepSeek-V3 같은 전문가 혼합(MoE) 모델에서는 통신이 주요 요인일 수 있습니다. Dense 70B 모델은 토큰마다 700억 개의 파라미터를 모두 활성화합니다. DeepSeek-V3는 총 671B개의 파라미터를 갖지만 토큰당 약 37B개를 활성화하므로 비용 계산 방식이 달라집니다.

BF16 파라미터 하나당 2바이트를 쓰면 70B 모델은 가중치에 약 140 GB가 필요합니다. 80 GB H100 두 개는 총 160 GB이고 MI300X 하나에는 192 GB가 있습니다. 구성을 선택하기 전에 KV 캐시와 런타임 버퍼에 쓸 수 있는 메모리가 얼마나 남는지 확인하세요. Llama 4 Maverick은 총 400B 파라미터 중 토큰마다 17B가 활성화됩니다. BF16으로 가중치만 저장해도 약 800 GB로, 80 GB GPU 여덟 개의 640 GB를 넘습니다. 카드별 사용 가능 메모리와 측정한 런타임 요구량으로 배포 규모를 산정하세요.

Dense 모델의 비용 과제는 메모리입니다. 모든 파라미터가 토큰마다 활성화되므로 비용은 GPU가 HBM에서 연산 코어로 가중치를 얼마나 빠르게 옮길 수 있는지에 따라 달라집니다. 메모리 대역폭이 낮으면 지연 시간이 늘어날 수 있습니다.

MoE 모델에서는 과제가 순수 연산에서 통신으로 옮겨갑니다. 토큰마다 일부 전문가만 활성화되므로 총 연산량은 많지 않을 수 있습니다. 그러나 전문가가 여러 GPU에 분산되어 있어 인터커넥트에 부담을 줄 수 있는 ‘all-to-all’ 라우팅 패턴이 필요합니다.

### 양자화: 정밀도와 효율성의 교환

FP8은 BF16보다 가중치 원본을 저장하는 공간을 대략 절반으로 줄일 수 있습니다. 총 VRAM에는 KV 캐시, 런타임 버퍼, 양자화 메타데이터도 영향을 줍니다.

FP8(E4M3/E5M2)은 프로덕션에서 사용됩니다. DeepSeek-V3는 FP8로 네이티브 학습되었으며 Qwen3 같은 모델에는 공식 FP8 체크포인트가 있습니다. Qwen3-235B-A22B-FP8 모델 카드는 참고 자료에 기재되어 있습니다.

지원되는 가속기(H100, H200, B300, MI300X)에서 FP8은 모델과 워크로드에 따라 품질을 허용 가능한 수준으로 유지하면서 디코드 처리량을 높일 수 있습니다.

INT4(GPTQ, AWQ)는 가중치를 4분의 1 크기로 압축하지만 반올림 오차가 누적되는 다단계 추론 작업에서는 품질을 낮출 수 있습니다. MXFP4/NVFP4는 블록 단위 스케일링 마이크로스케일링을 사용하며 네이티브 지원에는 Blackwell 또는 MI350X GPU가 필요합니다.

### 병렬 처리 전략: 텐서, 전문가, 데이터 병렬 처리

모델을 GPU에 분산하는 방식은 하드웨어 비용과 지연 시간 모두에 영향을 줍니다.

- <strong>텐서 병렬 처리(TP)</strong>는 각 레이어 안에서 가중치 행렬을 GPU 여러 대에 분할합니다. 모든 GPU가 모든 토큰을 처리하므로 토큰당 지연 시간은 줄지만 AllReduce 동기화와 고대역폭 인터커넥트가 필요합니다. GPU 8대를 넘으면 확장성이 떨어집니다.
- <strong>전문가 병렬 처리(EP)</strong>는 서로 다른 MoE 전문가를 서로 다른 GPU에 배치합니다. 활성화된 전문가만 통신하므로 TP보다 대역폭을 효율적으로 사용할 수 있지만 일부 전문가에 작업이 몰리면 부하 불균형이 생길 수 있습니다.
- <strong>데이터 병렬 처리(DP)</strong>는 서로 다른 요청을 별개의 모델 복제본으로 처리합니다. 요청이 균등하게 분배되고 공유 자원에 여유가 있으면 처리량을 늘릴 수 있습니다. 부하 상태에서 지연 시간을 측정하세요.

비용 효율적인 병렬 처리 전략을 선택하려면 모델 아키텍처를 배포 목표에 맞춰야 합니다. 지연 시간이 중요한 Dense 70B 모델의 경우 단일 8-GPU 노드에서 텐서 병렬 처리(TP=8)를 사용하는 방법이 있습니다. 처리량 중심 MoE 배포에서는 EP로 모델 가중치를 수용하고 DP로 요청 처리를 확장할 수 있습니다.

### 배칭과 스케줄링

디코딩이 메모리 대역폭에 묶이는 구간에서는 배치 내 여러 시퀀스가 가중치를 읽는 작업을 공유할 수 있습니다. 다른 자원이 병목이 되기 전에는 배치 크기를 키워 처리량이 증가할 수 있습니다.

포화 지점 B_sat에 가까워지면 시퀀스를 추가해도 처리량 증가폭은 작아지고 지연 시간은 길어질 수 있습니다. 연속 배치와 청크 프리필은 이런 한계가 나타나는 지점을 바꿀 수 있습니다.

같은 워크로드에서 여러 배치 크기를 시험하세요. 크기별 처리량과 꼬리 지연 시간을 비교해 처리량 증가폭이 작아지거나 지연 시간이 목표를 넘는 지점을 찾으세요.

## 처리량과 지연 시간 중 무엇을 최적화할까요?

보편적인 정답은 없습니다. 올바른 선택은 워크로드, 사용자, 비즈니스 모델에 따라 달라집니다.

LLM 성능을 설명하는 데 도움이 되는 원칙은 두 가지입니다.

1. **리틀의 법칙: QPS, 지연 시간, 동시성 연결하기**

```
Average in-flight requests = QPS * mean end-to-end time in seconds
```

안정적으로 초당 10개 요청이 들어오고 평균 종단 간 시간이 2초라면 대기열에 있는 요청까지 포함해 시스템 안에 평균 약 20개 요청이 있습니다. 활성 시퀀스와 컨텍스트 길이로 KV 캐시 요구량을 추정하세요.

벤치마크에서 복제본 하나가 목표 지연 시간 안에서 16 QPS를 유지한다면 100 QPS를 내려면 여유 용량을 더하기 전에 최소 일곱 개가 필요합니다. 실제와 비슷한 트래픽으로 전체 배포를 시험하세요.

2. **Roofline 모델**

Roofline 모델은 성능이 처리 능력(연산 병목) 또는 데이터 이동 속도(메모리 병목) 중 무엇에 의해 제한되는지 파악합니다. 이 구분은 하드웨어 결정을 안내하는 데 도움이 됩니다.

이 모델은 LLM 추론의 두 단계에 다음과 같이 대응합니다.

| **단계** | **병목** | **효율성 목표** |
|----|----|----|
| 프리필(입력) | 연산 | 프롬프트 청크를 병렬 처리 |
| 디코드(출력) | 메모리 | 배치 안의 여러 시퀀스에서 가중치 읽기 공유 |

### 지연 시간에 민감한 워크로드

대화형 채팅, 코드 완성, 실시간 에이전트, 검색 증강 및 기타 사용자 대상 애플리케이션에서는 지연 시간이 중요합니다.

주요 SLO 지표에는 TTFT(첫 토큰까지 걸리는 시간)와 ITL(토큰 간 지연 시간)이 포함됩니다. 사용자는 TTFT를 응답성으로, ITL을 스트리밍 속도로 인식합니다.

#### 튜닝 방법

큐잉이 TTFT를 늦출 수 있으므로 배치 크기를 적당하게 유지합니다.

- 배치 크기를 제한해 B_Sat ‘무릎점’보다 충분히 낮게 유지합니다.
- 지연 시간에 민감한 애플리케이션에서는 평균 처리량이 아니라 **P99 꼬리 지연 시간**을 최적화합니다.
- 배치에 요청이 하나 추가될 때마다 프리필 급증으로 다른 사용자의 토큰이 지연될 가능성이 커집니다.

모든 GPU가 모든 토큰을 처리하도록 TP를 사용해 토큰당 지연 시간을 최소화합니다.

- 단일 NVLink 연결 노드 안에서 텐서 병렬 처리(TP)를 확장합니다.
- Ethernet 또는 InfiniBand로 노드 간 통신을 시작하면 GPU 통신 오버헤드가 ITL을 **늘릴** 수 있습니다.
- 지연 시간에 민감한 작업에서는 필요한 메모리 대역폭을 제공하는 최소한의 GPU 수로 모델을 유지합니다.

긴 프롬프트가 디코드 단계를 막지 않도록 청크 단위 프리필을 활성화합니다.

- 청크 분할이 없으면 큰 프롬프트(예: 20k 토큰 문서)가 프리필이 끝날 때까지 GPU를 점유해 다른 사용자가 기다릴 수 있습니다.
- 프롬프트를 더 작은 청크(예: 512 토큰)로 나누면 엔진이 프리필 작업과 다른 활성 요청의 디코드 단계를 번갈아 수행할 수 있습니다.
- 이렇게 하면 토큰 간 지연 시간(ITL)을 일정하게 유지하고 스케줄러가 사용되지 않을 GPU 연산 주기를 채우도록 도울 수 있습니다. 또한 프리필의 높은 연산 집약도와 메모리 병목인 디코드의 특성 사이에 균형을 맞출 수 있습니다.

유효 ITL을 줄이기 위해 추측 디코딩을 고려합니다.

- 추측 디코딩은 초안 모델로 토큰을 미리 예측해 연산 효율을 낮추는 대신 ITL을 줄입니다.
- 이는 연산 효율(OpEx 비용)을 낮은 ITL(지연 시간)과 맞바꾸는 방식입니다.

트래픽 급증을 큐잉 없이 처리할 여분의 용량을 마련합니다.

- 사용률이 낮아져 토큰당 비용이 증가할 수 있지만 사용자 경험 요구사항을 충족하는 데 필요할 수 있습니다.

### 처리량에 민감한 워크로드

배치 요약, 오프라인 데이터 추출, 합성 데이터 생성, 평가 파이프라인, 개별 요청의 지연 시간보다 전체 작업 완료 시간이 중요한 워크로드에서는 처리량을 우선할 수 있습니다.

초당 토큰 수(또는 달러당 토큰 수)가 주요 지표입니다. 전체 배치가 요구된 시간 내에 완료된다면 개별 요청 지연 시간은 부차적입니다.

#### 튜닝 방법

측정한 처리량과 워크로드의 지연 시간 또는 작업 완료 시간 한도를 기준으로 배치 크기를 정하세요.

- 메모리 대역폭이 병목일 때는 배치 안의 여러 시퀀스가 가중치 읽기를 공유할 수 있습니다.
- 배치 크기를 늘리면 로드한 가중치 데이터 1바이트당 더 많은 산술 연산을 수행합니다.
- 실제 워크로드를 대표하는 요청 조합으로 측정된 포화 지점 B_sat 주변을 시험하세요.
- 작업 마감 시간과 요청별 지연 시간 한도를 지키면서 전체 실측 처리량이 가장 높은 설정을 사용하세요.

데이터 병렬 복제본을 추가해 전체 처리량을 높이세요.

- 데이터 병렬 처리는 서로 다른 요청을 별개의 복제본으로 처리합니다. 복제본 하나를 여러 GPU에 걸쳐 구성할 수 있습니다. DP를 TP와 결합하거나 지원되는 경우 EP와 조합할 수 있습니다.
- 독립적인 복제본 4개가 각각 초당 1,000개 토큰을 처리하면 이상적인 합계는 초당 4,000개 토큰입니다. 공유 인프라와 실제 트래픽에서 처리량을 측정하세요.
- 규모를 늘린 상태에서 처리량을 측정할 때는 TP나 EP의 통신과 공유 자원을 함께 고려하세요.

큰 프롬프트 청크를 더 효율적으로 처리하고 GPU 사용률을 극대화할 수 있도록 프리필 중 동시 토큰 처리 한도를 높입니다.

- 프리필은 프로세스에서 연산 집약도가 가장 높은 부분입니다. 처리량을 극대화하려면 GPU의 Tensor Cores를 계속 사용하도록 합니다.
- 큰 토큰 청크를 동시에 처리하면 GPU를 바쁘게 유지하고 초당 사용 FLOPS를 극대화할 수 있습니다.

품질 요구사항이 허용한다면 공격적인 양자화(INT4/GPTQ)를 사용합니다. 메모리에 더 많이 담아 얻는 처리량 증가가 정확도 비용보다 클 수 있습니다.

- 처리량은 VRAM에 들어가는 시퀀스 수에 부분적으로 좌우됩니다.
- 추론 엔진과 하드웨어가 지원하는 범위에서 모델 가중치 양자화와 KV 캐시 정밀도를 별도로 설정하세요.
- 실제 컨텍스트 길이에서 동시에 처리하는 요청 수, 처리량, 지연 시간을 측정해 양자화가 토큰당 비용을 줄이는지 확인하세요.
- 양자화 후 모델을 평가해 정확도에 미치는 영향이 허용 가능한지 확인합니다.

큐잉이 허용되는 경우 과잉 용량을 최소화하고 GPU를 높은 사용률로 운영합니다.

- 배치 워크로드에서는 큐잉이 유용할 수 있습니다.
- 큐가 있으면 요청 하나가 끝났을 때 다음 요청이 바로 처리될 수 있습니다.
- 응답을 기다리는 사람이 없다면 높은 사용률에서 발생하는 지연 시간 급증이 허용될 수 있습니다.
- 성공 여부는 **전체 작업을 완료하는 데 걸리는 총시간**으로 측정하며, GPU가 유휴 상태에 있지 않을 때 이 시간이 최소화됩니다.

### 하이브리드 현실

대부분의 프로덕션 시스템은 지연 시간에 민감한 워크로드와 처리량에 민감한 워크로드를 결합합니다. 배포 환경은 업무 시간에 대화형 채팅을 제공하고 야간에는 배치 평가 작업을 실행할 수 있습니다.

비용 효율적인 접근 방식은 워크로드 인식 스케줄링을 활용할 수 있습니다.

- **동적 자동 확장**: 대화형 트래픽이 몰리는 시간에는 GPU 복제본을 늘리고 한산한 시간에는 줄입니다. 자동 확장기는 큐 깊이(반응형)와 트래픽 예측(예측형)에 모두 대응할 수 있습니다.
- **우선순위 큐잉**: 대화형 요청은 낮은 지연 시간으로 처리하고 여유 용량이 있을 때 배치 요청은 백그라운드에서 처리합니다.
- **워크로드별 구성**: 튜닝 매개변수가 다른 vLLM 인스턴스를 별도로 실행합니다. 하나는 저지연 대화형 트래픽용이고 다른 하나는 고처리량 배치 처리용입니다.

## 의사결정 프레임워크

이러한 절충점 속에서 어떻게 결정을 내릴 수 있을까요? 다음 프레임워크가 도움이 될 수 있습니다.

**1단계: 워크로드 특성 파악**

ISL/OSL 분포, QPS 요구사항(평균 및 피크), 지연 시간 SLO(p50, p95, p99 기준 TTFT 및 ITL)를 고려합니다.

**2단계: 모델과 양자화 선택**

품질 요구사항을 충족하는 가장 작은 모델부터 시작합니다. FP8은 작은 정확도 절충으로 효율성 이점을 제공할 수 있으므로 먼저 벤치마킹합니다. 테스트에서 FP8의 품질 저하가 확인되면 BF16을 사용합니다.

**3단계: 후보 하드웨어에서 벤치마크 실행**

최소 두 가지 하드웨어 옵션에서 다양한 QPS로 ISL/OSL 스윕을 실행합니다. 워크로드에서 측정한 처리량을 바탕으로 결정합니다.

**4단계: 무릎점 찾기**

각 하드웨어 옵션에서 지연 시간 SLO를 충족하는 최대 QPS를 찾습니다. 이것이 인스턴스당 지속 가능한 용량입니다.

**5단계: 배포 규모 산정**

피크 트래픽과 목표 지연 시간 안에서 측정한 복제본당 QPS로 복제본 수를 추정하세요. 복제본별 지연 시간을 목표 안에 유지하면서 급증을 감당할 수 있도록 여유 용량을 확보하세요.

**6단계: 총비용 계산**

```
TCO_per_token = (capital allocated to period + operating costs + engineering costs) / tokens served in the same period
```

하드웨어 옵션별 수치를 비교합니다. 가장 저렴한 GPU가 가장 저렴한 배포를 만드는 것은 아닙니다.

**7단계: 자동 확장 계획**

트래픽 변동이 있다면 한산한 시간대의 비용 절감과 콜드 스타트 지연 시간을 맞바꾸는 자동 확장 정책을 설계합니다. 남는 용량은 배치 워크로드에 사용합니다.

## 벤치마크가 아니라 실제 워크로드에 맞춰 구축하세요

처리량, 지연 시간, 비용의 삼중 딜레마는 관리해야 하는 긴장 관계입니다. 모든 구성 선택은 세 차원 사이의 균형을 바꾸며, 어디서나 완벽한 구성은 없습니다.

팀은 사양표만 의존하는 대신 구체적인 프롬프트, 모델, 하드웨어를 사용해 워크로드를 벤치마킹하고 특성화함으로써 더 나은 배포 결정을 내릴 수 있습니다.

서빙 프레임워크와 하드웨어는 계속 발전하지만 LLM 추론의 기본 물리 법칙은 변하지 않습니다. 비즈니스에 중요한 지표를 기준으로 벤치마킹하고 튜닝하면 팀이 절충점을 다루는 데 도움이 될 수 있습니다.
