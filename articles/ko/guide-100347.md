# 추론 플랫폼의 구성 방식

> 게이트웨이, 라우팅, 캐싱, 모델 서빙이 어떻게 상호작용하는지, 그리고 요청 컨텍스트가 이러한 계층을 어떻게 거쳐 전달될 수 있는지 설명합니다.




MAR 08, 2026 | 엔지니어링 | 읽는 데 4분

게이트웨이, 라우팅, 캐싱, 모델 서빙이 어떻게 상호작용하는지, 그리고 요청 컨텍스트가 이러한 계층을 어떻게 거쳐 전달될 수 있는지 설명합니다.

요청 컨텍스트는 게이트웨이와 라우터를 거쳐 모델 서빙으로 전달될 수 있습니다. 이 컨텍스트는 모델 선택, 캐시 재사용, 실행을 호출자의 신원 및 각 시도의 비용과 연결합니다. 캐시 상태를 무시하는 라우터는 인접 계층이 절감한 비용을 다시 지출하게 만들 수 있습니다.

컨텍스트 공유에는 통합 작업이 필요하며, 캐시 상태를 읽는 라우터는 교체하기가 더 어렵습니다. 제품은 분리한 채 요청과 함께 컨텍스트를 보내면 팀은 다른 공급자의 런타임에서도 게이트웨이와 라우터를 사용할 수 있습니다. 그러면 라우터는 해당 공급자가 제공하는 정보를 바탕으로 결정을 내립니다.

## 더 저렴한 경로가 비용을 더 키울 수 있습니다

요청마다 고정된 긴 지침과 짧은 문서 하나를 처리하는, 설명을 위한 문서 추출 서비스를 생각해 봅시다. 프리픽스 캐싱과 라우팅은 모두 매력적으로 보이지만, 어느 한쪽이 다른 쪽의 이점을 상쇄할 수 있습니다. 캐시된 프리픽스는 한 모델이 계산한 키-값 상태이므로, 다른 모델로 라우팅된 요청은 지침을 처음부터 다시 읽습니다.

Anthropic이 공개한 5분 캐시 가격은 쓰기의 경우 기본 입력 가격의 1.25배, 읽기의 경우 0.1배이며 모델별 예외가 있습니다([발표](https://www.anthropic.com/news/prompt-caching), [문서](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). 캐시가 워밍된 상태를 기준으로 보면, 캐시를 사용하지 않는 대안이 공유 프리픽스 비용에서 이기려면 기존 모델 입력 가격의 10분의 1보다 낮은 가격을 제시해야 합니다. 캐시된 부분에 쓰기 한 번과 적중 한 번이 발생하면 입력 처리량은 1.35회분이며, 캐싱이 없으면 2회분입니다. 이후 요청에서 읽히지 않는 쓰기는 1.25회분의 비용이 듭니다.

목록 가격을 비교하는 라우터는 입력 가격이 절반인 모델을 발견해 전환할 수 있지만, 프리픽스 비용은 최소 5배로 늘어납니다. 명시적인 라우팅 설정은 어떤 모델이 다른 모델을 대체할 수 있는지 밝히고, 공유 컨텍스트는 각 대체에 얼마의 비용이 들었는지 보여줍니다.

## 응답을 재사용하려면 호출자의 신원이 필요합니다

<figure>
<ol>
<li><strong>정확한 응답</strong> — 일치하는 요청에 응답 재사용</li>
<li><strong>프리픽스</strong> — 입력 계산을 재사용하고 새 응답 생성</li>
<li><strong>시맨틱</strong> — 서로 다른 요청을 언제 동등한 것으로 볼지 결정</li>
</ol>
재사용 시 모델, 프롬프트, 스키마, 최신성 요구사항을 고려해야 합니다.
<figcaption>서로 다른 세 가지 재사용 방식 · 응답 캐시는 프리픽스 캐시가 아닙니다.</figcaption>
</figure>

응답 캐시는 저장된 출력을 반환합니다. 시맨틱 캐시는 서로 다른 두 요청에 같은 응답을 제공해도 되는지도 판단합니다. [GPTCache](https://github.com/zilliztech/GPTCache)는 임베딩 유사도를 기준으로 캐시 적중 여부를 결정하며, README에서는 “캐시 적중 시 오탐”을 경고합니다.

정보 추출에서 오탐은 잘못된 계좌 번호를 반환할 수 있습니다. 같은 공급업체 템플릿으로 작성된 두 청구서는 임베딩 공간에서 서로 가까울 수 있고, 캐시가 두 번째 청구서에 첫 번째 청구서의 계좌 번호를 반환할 수 있습니다. 애플리케이션 신원이 없는 시맨틱 캐시는 정확성 버그를 일으킬 수 있지만, 캐시 적중률 대시보드는 잘못된 응답도 모두 절감으로 집계합니다.

Anthropic은 조직 간에 프롬프트 캐시를 격리하고, 자체 API에서는 워크스페이스별로도 격리합니다. 프리픽스 캐시는 저장된 응답을 반환하지 않지만, 응답 캐시에는 최소한 이와 같은 경계가 필요합니다. 애플리케이션은 유사한 입력 간 재사용을 작업에서 허용할지 선언할 수 있습니다. 재사용 키에는 호출자, 호출자가 읽을 수 있는 데이터, 작업 버전을 포함할 수 있습니다.

정보 추출에서는 정확히 일치하는 경우에만 재사용하거나 재사용을 전혀 하지 않을 수 있습니다. 알 수 없는 키가 들어오면 다시 계산합니다. 이 규칙은 적중률을 낮추고, 더 느슨한 캐시라면 건너뛸 작업에도 비용을 지불하게 합니다. 기본 설정은 지나치게 엄격할 수 있습니다. 규모가 큰 공개 FAQ에서는 알 수 없는 키를 다시 계산하는 비용이 이를 통해 막을 수 있는 드문 오답의 비용보다 클 수 있습니다.

## 해결책을 고르기 전에 실패를 추적하세요

더 저렴한 모델이 유효하지 않은 필드를 반환하고 더 큰 모델이 이를 수정한다고 가정해 봅시다. 그러면 해당 문서의 비용과 지연이 늘어납니다. 비용은 요구되는 지연 시간 안에 정확한 추출을 완료한 건당 계산할 수 있으며, 첫 번째 호출의 토큰 가격은 여러 입력값 중 하나입니다.

Berkeley의 복합 AI 시스템 분석은 상호작용하는 구성 요소를 함께 최적화해야 한다고 주장합니다. 추적 기록은 모델 실패와 오래된 데이터 재사용, 느린 도구, 잘못된 경로를 구분해야 합니다. 원인마다 서로 다른 계층의 해결책이 필요하기 때문입니다. 실행을 제어하면 비용이 발생하는 지점을 파악하는 데 도움이 될 수 있지만, 더 빠른 런타임은 주변 의사결정 과정으로 낭비를 옮길 수도 있습니다. 추적 기록을 프로덕션 트래픽 평가와 연결하면 복구 경로를 포함해 변경 사항이 작업을 개선하는지 확인할 수 있습니다.

운영자는 추적 기록을 바탕으로 실패가 발생한 계층을 변경할 수 있습니다. 요청 기록, 평가 사례, 배포 선택을 고객의 애플리케이션 안에 유지하면 해당 애플리케이션의 경험을 토대로 개선을 이어갈 수 있습니다.

## Ailoot · 회사와 그 프로젝트 포트폴리오

Ailoot는 축적된 운영 경험, 폭넓은 고객 기반, 안정적인 서비스, 지속적인 KPI 관리를 바탕으로 합니다.

회사와 그 프로젝트 포트폴리오: 수백만 고객, 매월 수십억 규모의 매출.

Ailoot는 이러한 운영 경험을 고객의 제품, 에이전트, 애플리케이션, 자동화에서 AI 기능을 이용할 수 있는 API 접근에 활용합니다.

[추론 플랫폼의 구성 방식](<https://ailoot.ai/blog/ko/how-an-inference-platform-fits-together/>)

[Ailoot의 LLM API](<https://ailoot.ai/>)에 연결하면 Ailoot가 발급한 API 키 하나로 15개 카테고리의 모델과 변형 모델, 총 1,284종을 호출할 수 있습니다. Ailoot는 모델 수 기준으로 세계 최대 규모의 AI 라우터 중 하나입니다. 코드 작성에는 Claude나 Qwen, 이미지 생성에는 FLUX, 동영상 생성에는 Kling을 활용하세요. Scribe로 음성을 텍스트로 옮기고, Lyria로 음악을 만들고, Tripo3D로 3D 에셋을 제작할 수 있습니다. BGE 임베딩은 시맨틱 검색에 활용할 수 있습니다.

제품에 주요 텍스트, 코드, 미디어 모델을 연결할 때 [Ailoot API](<https://ailoot.ai/>)를 이용하세요. Claude의 추론, FLUX의 이미지 생성, Kling의 동영상 생성을 하나의 워크플로에 담을 수 있습니다.

Ailoot의 상용 라이선스는 자체 유료 소프트웨어에도 적용됩니다. 프로젝트마다 별도의 키를 발급하고, Ailoot 워크스페이스에서 회사의 모델 사용량을 관리할 수 있습니다.

구독 하나로 Ailoot 카탈로그의 모든 모델을 이용할 수 있습니다. 새 플래그십 모델도 출시 당일부터 쓰던 키로 바로 호출할 수 있습니다. [https://ailoot.ai/](<https://ailoot.ai/>)에서 구독과 프로모션 코드를 확인하세요. 모델 제공사의 공식 API 요금 대비 최대 50%를 절약할 수 있습니다.
