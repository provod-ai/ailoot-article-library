# LLM 심사자: 완벽 가이드

> LLM-as-a-judge는 한 언어 모델을 사용해 루브릭에 따라 다른 모델의 출력을 평가하는 방식으로, 챗봇, RAG 시스템, 에이전트의 AI 평가를 확장 가능하게 해줍니다. 이 글에서는 세 가지 핵심 평가 방식, LLM 심사자가 잘 작동하는 경우와 실패하는 경우, 신뢰할 수 있는 루브릭을 작성하는 방법, 그리고 프로덕션에서 사용하기 전에 라벨이 지정된 골드 세트로 반드시 보정해야 하는 이유를 설명합니다.




LLM-as-a-judge는 한 언어 모델을 사용해 루브릭에 따라 다른 모델의 출력을 평가하는 방식으로, 챗봇, RAG 시스템, 에이전트의 AI 평가를 확장 가능하게 해줍니다. 이 글에서는 세 가지 핵심 평가 방식, LLM 심사자가 잘 작동하는 경우와 실패하는 경우, 신뢰할 수 있는 루브릭을 작성하는 방법, 그리고 프로덕션에서 사용하기 전에 라벨이 지정된 골드 세트로 반드시 보정해야 하는 이유를 설명합니다.

> **요약 —** LLM 심사자 방식은 사람이 평가하는 대신(또는 사람 평가자와 함께) 언어 모델을 사용해 작성된 루브릭에 따라 다른 모델의 출력에 점수를 매기는 방법입니다. 프로덕션 평가에는 명시적인 루브릭을 사용한 단일 응답 채점을, 모델 버전 순위 비교에는 쌍별 비교를 사용하고, 라벨이 지정된 골드 세트와 대조해 측정하지 않은 심사자를 절대 신뢰하지 마세요.

이 글은 이미 평가 시스템을 만들고 있으며 “여기에 LLM 심사자를 써야 할까? 쓴다면 어떻게 해야 할까?”라는 질문에 근거 있는 답을 원하는 엔지니어를 위한 글입니다. 평가를 작성해 본 적이 없다면 소규모의 라벨링된 예시 세트부터 시작하세요.

## “LLM 심사자”가 실제로 의미하는 것

LLM 심사자는 모델에 프롬프트를 보내 무언가를 평가하도록 요청하는 방식이며, 보통 다른 모델의 응답을 평가합니다. 심사자는 점수, 라벨 또는 선호도를 반환합니다. 이것이 전체 아키텍처입니다. 중요한 것은 모두 프롬프트, 루브릭, 그리고 심사자의 판정이 현실과 일치하는지 측정하는 방법에 있습니다.

이 방식이 널리 쓰이게 된 이유는 철학적인 것이 아니라 운영상의 이유입니다. 사람만으로 구성된 평가 파이프라인은 확장성이 떨어집니다. 대신 심사자 자체의 편향이 개입하며, 사람 평가자의 편향과 달리 그 편향은 체계적입니다.

## LLM 심사자가 출력을 채점하는 방법

채점 방식은 세 가지이며, 그중 무엇을 선택하느냐에 따라 평가를 통해 알 수 있는 것과 알 수 없는 것이 달라집니다.

- ‍**쌍별 비교**는 두 응답 중 어느 쪽이 더 나은지 심사자에게 선택하도록 요청합니다. 두 모델 버전 또는 두 프롬프트를 A/B 테스트할 때 사용하세요. 절대적인 품질 기준이 필요할 때는 사용하지 마세요. 쌍별 점수에는 최저 기준이 없으므로 응답 B가 모든 비교에서 이기더라도 실제로는 사용할 수 없을 수 있습니다.**‍**
- **루브릭을 이용한 단일 응답 채점**은 명시적인 기준에 따라 응답 하나를 채점하도록 심사자에게 요청합니다. 모든 응답이 같은 기준으로 점수를 받으므로 프로덕션에서 사용하기 적합한 방식이며, 이를 바탕으로 배포 기준을 설정할 수 있습니다(“카나리 세트에서 충실성 기준을 통과하면 배포”). 중요하게 여기는 차이를 구분할 수 있는 가장 낮은 정밀도의 척도를 선택하세요. “모델이 루브릭을 위반했는가, 예 또는 아니오인가?”가 질문이라면 통과/실패 이진 척도를, 실패 정도가 분류를 위해 중요하다면 3점 척도(실패 / 부분 통과 / 통과)를 사용하세요. 1\~5 또는 1\~10 척도는 정말로 그 정도의 해상도가 필요하고, 골드 세트 데이터로 심사자가 그 척도를 사용할 수 있음을 검증한 경우에만 선택하세요. 세분화된 척도는 심사자가 근거를 댈 수 없는 차이를 지어내게 만들며, 그 결과 생기는 잡음은 측정하려던 신호를 약화합니다. 척도의 선택보다 루브릭의 품질이 더 중요합니다. 모호한 루브릭(“유용성을 1\~5점으로 평가하세요”)은 정보가 없는 숫자를 만들어냅니다. 주장 단위의 루브릭(“사실 주장 중 하나라도 검색된 문단에서 직접 뒷받침되지 않으면 0점을 매기세요”)은 실제 조치를 취할 수 있는 숫자를 만들어냅니다. 평가 요구사항이 바뀌면 루브릭을 검토해야 합니다.**‍**
- **참조 기반 채점**은 정답으로 알려진 답변을 심사자에게 제공하고 후보 응답이 그 답변과 얼마나 가까운지 평가하도록 합니다. n-그램 중복이 아니라 의미를 기준으로 한다는 점을 제외하면 BLEU와 ROUGE 같은 기존 NLP 지표에 가장 가까운 방식입니다. 출력이 제한된 작업(번역, 골드 요약과 대조하는 요약, 구조화된 데이터 추출)에는 잘 맞습니다. 그러나 열린 작업에서는 허용 가능한 답변이 대개 여러 가지이고, 심사자가 좋지만 다른 답변을 불이익 처리하므로 효과가 떨어집니다.

실제로 대부분의 프로덕션 구성에서는 기준별(충실성, 관련성, 형식 준수)로 단일 응답 채점을 사용하며, 후보 프롬프트 중 하나를 고르는 개발 단계에서만 쌍별 비교를 사용합니다.

## LLM 심사자가 적합한 경우

LLM 심사자는 명확히 제시된 루브릭을 기준으로 읽고 이해하는 것이 핵심인 작업에서 잘 작동합니다. “이 응답에 검색된 컨텍스트가 뒷받침하지 않는 사실 주장이 포함되어 있는가?”는 독해 문제입니다. “명세에서 답변을 거부하도록 요구하는 경우에 이 응답은 답변을 거부하는가?”도 마찬가지입니다. 심사 모델은 주장을 추출하고, 이를 뒷받침하는 문장을 찾거나 문장이 없음을 확인한 뒤 판정을 내려야 합니다. 최첨단 모델은 이 작업을 잘 수행합니다.

프롬프트에 담을 수 없는 지식이 필요한 작업에서는 효과가 떨어집니다. “이 응답은 웃긴가?”라는 질문에는 어떤 모델이든 답하겠지만, 그 답은 독자의 기준이 아니라 심사자의 사전 관점을 반영합니다. “이 코드는 관용적인 Rust 코드인가?”를 판단하려면 심사자가 팀과 같은 관례를 익혀야 하는데, 그렇지 않을 가능성이 큽니다. 이런 작업에서는 심사자를 정답으로 취급하지 말고 여러 신호 중 하나로 다루세요.

실패를 놓쳤을 때의 비용이 크고 그 실패 유형이 드문 작업에서는 오히려 적극적으로 해가 됩니다. 심사자는 실패를 놓칠 수 있으며, 문제를 놓친 결과가 심각한 경우 이는 중요한 한계입니다. 이런 경우 심사자는 분류 도구입니다(사람 검토자가 확인해야 할 사례의 양을 줄입니다). 최종 판단자가 아닙니다.

## 40줄로 구현하는 예시: 충실성 심사자

가장 간단하면서도 유용한 심사자는 RAG 응답에 단일 응답 충실성 루브릭을 적용합니다. 다음은 OpenAI Python SDK를 사용하는 예시입니다.

```

from openai import OpenAI
from pydantic import BaseModel

client = OpenAI()

JUDGE_PROMPT = """You are evaluating whether an assistant's response is faithful
to a retrieved context passage. Faithful means every factual claim in the response
is directly and explicitly supported by the context. A claim is unfaithful if it
is added, modified, or drawn from outside the context.

Steps:
1. Enumerate every factual claim in the response (numbers, rules, entity names,
   negations, comparisons).
2. For each claim, locate the specific sentence in the context that supports it.
3. If any claim has no direct support, the response is unfaithful.
4. Truncated or cut-off context counts as zero support for whatever follows.

Return JSON: {{"verdict": "faithful" | "unfaithful", "reason": ""}}.

CONTEXT:
{context}

RESPONSE:
{response}
"""

class Verdict(BaseModel):
    verdict: str
    reason: str

def judge(context: str, response: str) -> Verdict:
    completion = client.beta.chat.completions.parse(
        model="gpt-4o-2024-11-20",
        messages=[{"role": "user",
                   "content": JUDGE_PROMPT.format(context=context, response=response)}],
        response_format=Verdict,
        temperature=0.0,
    )
    return completion.choices[0].message.parsed
  
```

이 프롬프트는 심사자에게 평가에 앞서 주장을 나열하도록 요청하므로 주장 단위 검사를 구성합니다. 검색 파이프라인은 청크 경계에서 텍스트를 자르며, 이를 명시적으로 처리하지 않으면 심사자가 불완전한 문장을 완전한 근거로 취급할 수 있으므로 잘린 컨텍스트도 명시적으로 다룹니다. 이진 분류 작업에서 온도를 0이 아닌 값으로 설정하면 해석할 수 없는 변동이 생기므로 온도는 0입니다.

이 정도면 실행할 수 있지만 배포하기에는 충분하지 않습니다. 다음 두 절에서는 작동하는 예시를 배포 가능한 심사자로 발전시키는 방법, 즉 프롬프트를 제대로 작성하는 방법과 실제로 인간과 일치하는지 측정하는 방법을 다룹니다.

## 심사자 프롬프트와 루브릭 작성하기

LLM 심사자 구성에서 성능 향상의 대부분은 심사자 프롬프트에서 나옵니다. 모델은 공급자가 정하고, 채점 척도는 루브릭 설계가 정하며, 골드 세트는 도메인이 정합니다. 프롬프트는 라벨이 지정된 예시와 심사자를 비교하면서 반복 개선할 수 있는 부분입니다.

제대로 작동하는 심사자 프롬프트에는 네 가지 요소가 있습니다. 일반적인 ML 용어가 아니라 해당 도메인에서 사용하는 표현으로 쓴 기준의 정의(“검색된 컨텍스트에 충실하다”는 도메인 정의지만 “품질이 높다”는 그렇지 않습니다). 점수를 매기기 전에 심사자가 구체적인 주장, 조건 또는 도구 호출을 열거하도록 지시하는 명시적인 추론 구조(심사자가 명확한 검사 순서를 따르게 합니다). 추론 결과를 척도에 대응시키는 채점 규칙(예: “열거한 주장 중 하나라도 검색된 컨텍스트에서 직접 뒷받침되지 않으면 0점을 매기세요”)으로, “판단에 맡기세요”와 같은 지침이 아닙니다. 그리고 프로덕션에서 나타나는 경계 사례, 즉 잘린 컨텍스트, 검색 결과가 없는 경우, 부분 답변, 거부 응답을 처리하는 조항입니다.

프롬프트에 “답변이 유용하고 정직하며 해롭지 않도록 하세요” 같은 긴 목록을 넣어서는 안 됩니다. 일반적인 지침은 무시됩니다. 구체적인 주장 단위 규칙은 따릅니다. 피해야 할 또 한 가지는 판정 형식을 지나치게 세세하게 지정하는 것입니다. 점수를 내기 전에 모델이 긴 구조화된 근거를 작성해야 한다면 읽지 않을 토큰에 비용을 지불하게 됩니다.

## 단순한 심사자를 신뢰할 수 없게 만드는 편향

LLM 심사자에게는 여러 편향이 영향을 미칠 수 있으므로 평가를 설계할 때 이를 고려하세요.

- ‍**위치 편향**은 쌍별 비교에서 먼저 제시된(때로는 마지막에 제시된) 응답을 더 선호하는 경향입니다. 비교를 양쪽 순서로 모두 평가하고 판정이 일치하는 사례만 집계하는 것이 해결책입니다. 두 순서 모두에서 비교 점수를 매겨야 합니다.**‍**
- **장황함 편향**은 더 긴 응답을 선호하는 경향입니다. 루브릭에서 길이를 기준으로 삼지 않더라도 긴 응답이 더 높은 선호를 받을 수 있습니다. 루브릭에 “정확성이 동일하다면 간결한 응답은 장황한 응답과 같거나 더 높은 점수를 받는다”라고 명시하지 않으면 심사자는 암묵적으로 길이를 최적화합니다. 루브릭에 길이에 대한 중립성을 명시하면 이 문제를 완화할 수 있습니다.**‍**
- **자기 선호 편향**은 심사자가 자신과 같은 모델 계열의 출력을 선호하는 경향입니다. 같은 모델 계열의 출력이 포함된 비교를 그 계열의 모델로 심사하지 마세요. 다른 모델을 심사자로 사용하거나 해당 비교에 한해서는 사람 평가자를 사용하세요.

감정 편향과 아첨 편향도 문제가 될 수 있습니다. 보정에 사용하는 라벨링된 골드 세트에 관련된 실패 유형을 포함하세요.

## 라벨이 지정된 골드 세트를 기준으로 심사자 보정하기

심사자 프롬프트는 배포 전에 라벨이 지정된 골드 세트와 대조해 점검해야 합니다. 배포 전에 이를 확인하는 방법이 보정입니다. 라벨이 지정된 골드 세트에 심사자를 실행하고, 심사자의 판정과 사람의 라벨 사이의 차이를 측정한 다음 그 차이가 줄어들 때까지 프롬프트를 반복 개선합니다.

보정 루프에는 세 가지 입력이 있습니다. 평가 분포에서 추출한 라벨이 지정된 골드 세트, 관련 일치도 및 오류 지표를 기록하는 기준 실행, 그리고 심사자가 라벨과 다른 판정을 내린 예시를 바탕으로 프롬프트를 수정하는 최적화 단계입니다. 프롬프트나 평가 분포가 바뀌면 보정을 반복하세요.

집계된 정확도는 클래스별 재현율을 가립니다. 정확도가 높아도 Kappa가 낮다면 일치도가 우연 수준에 가까울 수 있습니다. Kappa가 높을수록 우연을 넘어서는 일치도가 강하다는 뜻입니다. 심사자를 평가할 때는 정확도 외의 지표도 보고하세요.

## 골드 세트 만들기

보정에는 골드 세트가 필요하지만 골드 세트가 기본적으로 주어지는 것은 아닙니다. 골드 세트를 구축하는 것은 이후의 모든 단계가 실제 무언가를 측정할지 아니면 잡음을 측정할지를 결정하는 필수 단계입니다.

골드 세트는 도메인 전문가가 심사자가 내리기를 바라는 판정을 붙인 입력-출력 쌍의 모음입니다. 세 가지 특성이 있어야 골드 세트가 평가의 토대 역할을 할 수 있습니다. 실제 평가 분포에서 가져와야 합니다. 실제 쿼리, 실제 검색 컨텍스트, 실제 에이전트 응답이어야 하며, 데이터셋 작성자에게만 그럴듯해 보이는 합성 예시여서는 안 됩니다. 실패 유형이 대표되어야 합니다. 충실한 예시만 100개 모은 골드 세트로는 심사자가 불충실성을 잡아내는지 알 수 없습니다. 불충실성은 중요한 실패 유형입니다. 또한 사용하기 전에 골드 세트에 대한 평가자 간 일치도를 측정해야 합니다. 도메인 전문가들이 라벨에 자주 동의하지 않는다면 보정 전에 루브릭을 명확히 하세요. 실패 유형이 아니라 잡음을 대상으로 최적화하는 일을 피할 수 있습니다.

골드 세트용 쿼리와 합성한 현실적인 답변을 생성하는 일은 그 자체로 별도의 엔지니어링 문제입니다. 이제 소스 문서에서 이를 생성할 수 있는 프레임워크가 여럿 있으며, 프레임워크 간 차이는 결과물인 골드 세트가 어떤 종류의 실패를 드러내는지에 영향을 줍니다. 

## 심사자와 사람 간 일치도는 작업에 따라 다릅니다

LLM 심사자와 인간 평가자 간의 일치도는 작업마다 달라질 수 있으며, 몇 가지 구분이 중요합니다.

검증 가능한 결과가 있는 폐쇄형 작업의 일치도는 평가자들이 의견을 달리할 수 있는 개방형 작업보다 해석하기 쉬운 편입니다. 심사자는 해당 작업에서 인간 평가자들 간의 일치도와 분리해서 평가할 수 없습니다.

두 번째로, 일치도와 정렬은 같은 개념이 아닙니다. 심사자는 전체적으로 정확해 보이면서도 중요한 실패 유형을 놓칠 수 있습니다(예를 들어, 근거가 없는 응답을 충실하다고 통과시킵니다). 집계 수치는 심사자를 실제보다 좋아 보이게 합니다. 배포해도 되는지 알려주는 것은 클래스별 재현율입니다. 위의 보정 절차로 이를 해결할 수 있습니다. 두 가지를 모두 측정하고, 실패 사례를 바탕으로 프롬프트를 수정한 뒤 반복하세요.

세 번째로, 일치도 지표는 어떤 지표를 쓰느냐에 따라 달라집니다. 불균형한 골드 세트(통과 예시가 대부분이고 실패 사례는 적음)의 원시 정확도를 보고하면 심사자가 실제보다 좋아 보입니다. 우연에 의한 일치도를 보정하는 Cohen의 Kappa를 보고하면 이런 왜곡은 더 어렵습니다. 겉보기에는 정확도가 높아도 Kappa가 낮다면 일치도가 우연 수준에 가까울 수 있습니다. 연속 점수에는 Pearson 상관계수가 유용하며, 절댓값이 아니라 순위만 신뢰한다면 Spearman이 더 안정적입니다.

프로덕션 파이프라인에서는 라벨이 지정된 골드 세트로 측정하고, 적절한 일치도 또는 오류 지표를 하나 이상 보고하세요.

LLM 심사자만 단독으로 사용할지, 표시된 하위 집합을 사람이 검토하는 분류 필터로 사용할지, 아니면 심사자를 생략하고 사람만 사용할지는 세 가지 변수에 달려 있습니다. 놓친 실패의 비용, 평가량, 평가 분포가 변하는 속도입니다.

## 예시에서 프로덕션으로: 심사자 연결하기

앞서 소개한 40줄 예시는 Python REPL에서 응답 하나를 채점하기에는 충분합니다. 모든 프로덕션 응답 앞에 심사자를 두거나(또는 CI에서 모든 pull request에 실행하는 것)는 별개의 엔지니어링 문제입니다.

규모가 커지면 눈에 띄지 않는 실무 작업들이 생깁니다. 심사자 추론이 엔드투엔드 지연 시간을 지배하지 않도록 요청을 배치로 처리합니다. 심사자가 잘못된 JSON을 반환하거나, 속도 제한을 초과하거나, 타임아웃되는 경우의 재시도 처리를 구현합니다. 나중에 특정 사례가 표시된 이유를 진단할 수 있도록 판정과 추론 기록을 구조화해 로깅합니다. 배포 간 카나리 골드 세트의 정렬도가 떨어지면 작동하는 회귀 감지를 마련합니다. 특정 프롬프트 수정에 정렬도 변화의 원인을 연결할 수 있도록 애플리케이션 코드처럼 심사자 프롬프트도 버전 관리합니다. 그리고 CI 시스템에 통합해 심사자 실행이 배포 게이트의 일부가 되도록 합니다. 시간 압박 때문에 누군가 잊어버릴 수 있는 수동 점검에 맡겨서는 안 됩니다.

이 중 지적으로 어려운 일은 없습니다. 그러나 모두 작업이 필요하며, 구현 순서에 따라 어떤 프로덕션 실패를 먼저 만나게 될지가 달라집니다. 프롬프트 버전 관리가 없으면 정렬도가 바뀔 때 회귀의 원인을 찾기가 더 어려워집니다.

## LLM 심사자를 사용하지 말아야 할 때

심사자를 사용하면 안 되지만 팀들이 흔히 사용하는 세 가지 상황이 있습니다.

작업에 결정론적인 정확성 검사가 있다면 심사자를 사용하지 마세요. SQL 쿼리 동등성, JSON 스키마 검증, 정규식 매칭, 정확한 문자열 비교, 도구 호출 인수 매칭은 이미 해결된 문제입니다. 이들 검사에 LLM 심사자를 덧붙이면 지연 시간과 비용이 증가하고, 정답이 명확한 문제에서 틀릴 가능성도 생깁니다. 결정론적 검사를 실행하고 불일치가 있으면 빠르게 실패 처리한 다음, 자연어 추론이 실제로 필요한 부분에만 심사자를 호출하세요.

라벨이 지정된 골드 세트를 만들지 않았다면 프로덕션에서 심사자를 사용하지 마세요. 심사자는 숫자를 제공합니다. 기준이 되는 정답이 없다면 그 숫자가 의미하는 바를 알 수 없습니다. 골드 세트는 실제 평가 작업을 대표하고 중요한 실패 사례를 포함해야 합니다.

실패를 놓쳤을 때의 비용이 사람의 검토 비용보다 크다면 심사자를 최종 게이트로 사용하지 마세요. 사람의 검토 대상 사례 수를 줄이는 분류 필터로 사용하세요. 규제 대상 분야에서 사람이 개입하지 않는 심사자를 배포하는 것은 별개의 결정입니다. 개발 세트에서 심사자의 점수가 우연히 높았다는 이유로 암묵적으로 결정해서는 안 되며, 법무 및 컴플라이언스 부서와 함께 명시적으로 결정해야 합니다.

심사자는 도구이지 판결이 아닙니다. 심사자는 그렇지 않으면 배포했을 실패를 찾아낼 때 제 역할을 합니다. 계속 그러는지 측정하기를 멈추는 순간 그 역할을 잃습니다.
