# TTS API architektūra: nuo teksto iki gamybinio garso

> Sužinokite, kaip sukurti gamybinę TTS API su eilėmis, darbininkais, spartinimu, pakartotiniais bandymais, teikėjų maršrutizavimu, saugykla, užklausų dažnio ribojimu ir stebėsena.



Iškviesti teksto vertimo į kalbą (TTS) API paprasta. Patikimai ją eksploatuoti gamybinėje aplinkoje – ne.

Paprastą prototipą gali sudaryti tik trys žingsniai:

**Tekstas → TTS teikėjas → MP3**

Tai gali puikiai veikti bandant kelias užklausas vietoje. Atsiradus tikriems naudotojams, sistema turi apdoroti vienalaikes užduotis, teikėjo užklausų dažnio ribojimus, tinklo gedimus, ilgai trunkančias garso generavimo užduotis, pasikartojančias užklausas, saugojimą, pakartotinius bandymus, kvotas, kelis balso teikėjus ir atvejus, kai naudotojai atnaujina puslapį garsui vis dar apdorojant.

Architektūra greitai tampa sudėtingesnė už patį TTS API iškvietimą. Tikroviškesnė gamybinė darbo eiga atrodo taip:

**Klientas → API → Užduotis → Eilė → Darbininkas → TTS teikėjas → Saugykla / CDN → Rezultatas**

Šiame straipsnyje paaiškinama, kaip sukurti tokią architektūrą, kodėl reikalingas kiekvienas komponentas ir kokios problemos paprastai iškyla TTS programai išaugus iš paprastos demonstracijos.



## **Ką turi išspręsti gamybinė TTS API?**

Gamybinės TTS posistemės paskirtis – ne vien generuoti garsą. Ji turi tai daryti **patikimai, efektyviai ir nuspėjamai**.

Gera architektūra turėtų padėti atsakyti į tokius klausimus:

1. Kas nutinka, kai 100 naudotojų vienu metu generuoja kalbą?
2. Kas nutinka, kai TTS teikėjas grąžina HTTP 429?
3. Kas nutinka, kai TTS teikėjas tampa nepasiekiamas?
4. Kas nutinka, kai garso generavimo užduotis trunka kelias minutes?
5. Kas nutinka, kai naudotojas tą pačią užklausą pateikia du kartus?
6. Kaip neleisti vienam naudotojui sunaudoti visos teikėjo kvotos?
7. Kur turėtų būti saugomas sugeneruotas garsas?
8. Kaip klientas sužino, kad ilgai vykdoma užduotis baigta?
9. Kaip pakartoti nepavykusį darbą nebegeneruojant sėkmingai sukurto garso?
10. Kaip išmatuoti, kuris teikėjas lėtas arba nepatikimas?

Tai sistemos projektavimo, o ne kalbos sintezės problemos.

## **Pagrindinė TTS API užklausa**

Paprasčiausiu atveju TTS užklausą gali sudaryti:

1. Tekstas
2. Kalba
3. Balsas
4. Modelis
5. Kalbėjimo greitis
6. Garso formatas
7. Pasirenkamos balso instrukcijos

Pavyzdžiui, konceptualiai:

**POST /tts**

Serveris gauna užklausą, iškviečia TTS teikėją ir grąžina garso failą. Šį sinchroninį modelį lengva suprasti:

**HTTP užklausa → Teikėjas → Garsas → HTTP atsakymas**

Generuojant labai trumpą kalbą tai gali būti priimtina. Problemų kyla, kai generavimas sulėtėja, srautas išauga arba vienoje užklausoje pateikiama daug teksto.

## **Kodėl ilgos TTS užduotys neturėtų priklausyti nuo vienos HTTP užklausos**

Įsivaizduokite, kad naudotojas pateikia tiek teksto, jog sugeneruotų 30 minučių įgarsinimą. Jei jūsų API palieka pradinę HTTP užklausą atvirą, kol viskas baigiama, gali nutikti keli dalykai:

1. Naršyklėje gali baigtis laukimo laikas.
2. Atvirkštinis tarpinis serveris gali uždaryti užklausą.
3. Programos serveris gali būti paleistas iš naujo.
4. Teikėjas gali laikinai sutrikti.
5. Naudotojas gali uždaryti puslapį.
6. Gali nutrūkti mobilusis ryšys.

TTS darbas gali būti tinkamas vykdyti, bet jį pradėjęs ryšys jau nutrūko. Ilgai vykdomus TTS darbus paprastai geriau modeliuoti kaip **užduotis**.

Darbo eiga tampa tokia:

**Klientas → Sukurti užduotį → Grąžinti užduoties ID → Apdoroti fone**

Klientas gali vėliau patikrinti eigą.

## **1 žingsnis: priimkite ir patikrinkite užklausą**

Prieš perduodant darbą apdorojimo sistemai, API sluoksnis turėtų atlikti nesudėtingą patikrą. Įprasti klausimai:

1. Ar tekstas tuščias?
2. Ar tekstas ilgesnis už leidžiamą užklausos dydį?
3. Ar nurodytas balsas egzistuoja?
4. Ar pasirinktas modelis palaiko nurodytą kalbą?
5. Ar palaikomas nurodytas garso formatas?
6. Ar naudotojas autentifikuotas?
7. Ar naudotojas turi pakankamai kvotos arba kreditų?
8. Ar užklausą leidžia dažnio ribojimo taisyklės?

Netinkamos užklausos turėtų būti atmestos dar prieš joms pasiekiant darbininkus ar išorinius teikėjus. Taip taupomi infrastruktūros ištekliai ir teikėjo kvota.

Lygiagrečioms užduotims prieš jas priimdami atomiškai rezervuokite taikytiną kvotą ar kreditus ir pagal faktinį rezultatą bei atsiskaitymo taisykles vieną kartą už rezervaciją atsiskaitykite arba ją atlaisvinkite.

## **2 žingsnis: normalizuokite užklausą**

Prieš apdorojimą normalizuokite užklausą į nuspėjamą vidinį formatą. Pavyzdžiui:

1. Normalizuokite kalbos kodus.
2. Nustatykite tikrąjį balso ID.
3. Nustatykite pasirinkto balso teikėją.
4. Pritaikykite numatytąjį kalbėjimo greitį.
5. Normalizuokite tarpus.
6. Pasirinkite išvesties formatą.
7. Nustatykite modelio konfigūraciją.

Taip tolesniems darbininkams pateikiama nuosekli įvesties sutartis. Tai taip pat padeda spartinti darbą: logiškai tapačioms užklausoms idealiu atveju turėtų būti sukuriamas tas pats spartinančiosios atmintinės raktas.



## **3 žingsnis: patikrinkite, ar garsas jau yra**

Pakartotinai generuoti tą patį garsą – paprastas būdas švaistyti pinigus TTS sistemoje. Tarkime, naudotojas kelis kartus pateikia:

*„Sveiki atvykę į mūsų programą.“*

su tuo pačiu balsu, modeliu, greičiu ir nustatymais. Jei jūsų naudojimo atveju rezultatas pakankamai deterministinis, gali nebūti priežasties kaskart iškviesti teikėją.

Spartinančiosios atmintinės raktą galima sudaryti iš tokių reikšmių kaip:

1. Normalizuotas tekstas
2. Balso ID
3. Teikėjas
4. Modelis
5. Kalba
6. Greitis
7. Garso formatas
8. Stiliaus arba balso instrukcijos

Konceptualus raktas galėtų būti toks:

**HASH(text + voice + model + speed + format + settings)**

Visus generavimo laukus serializuokite vienareikšmiškai ir į spartinančiosios atmintinės tapatybę įtraukite tinkamą nuomininko arba prieigos sritį. Autorizuokite pakartotinį naudojimą ir prieigą prie rezultato; tarp nuomininkų dalykitės tik tada, kai tai aiškiai leidžiama.

Užklausos eiga tampa tokia:

**Užklausa → Spartinančiosios atmintinės patikra → Ar garsas jau yra?**

Jei taip:

**Grąžinti esamą rezultatą**

Jei ne:

**Sukurti generavimo užduotį**

### **Nespartinkite vien pagal tekstą**

Paprastai neteisinga kaip spartinančiosios atmintinės raktą naudoti tik tekstą. Ta pati frazė, sugeneruota dviem skirtingais balsais, neturėtų grąžinti to paties garso. Tas pats galioja modeliui, greičiui, kalbai, formatui ir stiliaus nustatymams.

Spartinančiosios atmintinės tapatybė turėtų apimti viską, kas gali iš esmės pakeisti išvestį.

## **4 žingsnis: sukurkite išliekamąją užduotį**

Prieš įtraukdami darbą į eilę, išsaugokite užduoties įrašą. TTS užduotyje gali būti:

1. Užduoties ID
2. Naudotojo ID
3. Būsena
4. Prašytas balsas
5. Teikėjas
6. Modelis
7. Simbolių skaičius
8. Sukūrimo laikas
9. Pradžios laikas
10. Pabaigos laikas
11. Pakartotinių bandymų skaičius
12. Eiga
13. Klaidos informacija
14. Išvesties URL

Paprasta būsenų seka galėtų būti tokia:

**Laukiama → Apdorojama → Baigta**

su nesėkmės būsena:

**Laukiama → Apdorojama → Nepavyko**

Taip pat gali reikėti pakartotinio bandymo, atšaukimo, dalinio užbaigimo arba pasibaigusio galiojimo būsenų.

Svarbu išsaugoti užduoties būseną, nes apdorojimo sistema neturėtų priklausyti nuo programos atminties. Jei API konteineris paleidžiamas iš naujo, naudotojai vis tiek turėtų galėti pasiekti savo užduotis.

## **5 žingsnis: nusiųskite užduotį į pranešimų eilę**

Pranešimų eilė atskiria užklausos priėmimą nuo garso apdorojimo. Vietoj:

**API → TTS teikėjas**

naudokite:

**API → Eilė → Darbininkas → TTS teikėjas**

API gali beveik iškart atsakyti užduoties identifikatoriumi, o darbininkai apdoroja užklausas fone.

Įrašytoms, bet į eilę neįtrauktoms užduotims naudokite transakcinę siuntimo lentelę arba patvarų atkūrimą, o eilės apdorojimą padarykite idempotentinį, kad gedimas ar pakartotinis pristatymas darbo neprarastų ir nedubliuotų.

### Kodėl eilės tokios naudingos TTS sistemoms

Eilės suteikia kelis svarbius privalumus:

1. Jos sugeria srauto šuolius.
2. Jos kontroliuoja, kiek darbo vykdoma vienu metu.
3. Jos apsaugo išorinių teikėjų kvotas.
4. Jos palengvina pakartotinius bandymus.
5. Jos leidžia užduotims tęstis pasibaigus pradinei HTTP užklausai.
6. Jos leidžia didėjant srautui pridėti darbininkų.

Tai ypač svarbu, kai TTS teikėjai riboja užklausų per minutę, simbolių, žetonų arba vienalaikių užklausų skaičių.



## **Eilė taip pat veikia kaip apkrovos ribojimo mechanizmas**

Tarkime, jūsų teikėjas gali saugiai apdoroti 20 užklausų vienu metu, tačiau API vienu metu gauna 200 užklausų. Neturėdami eilės, visas 200 užklausų galite nusiųsti tiesiai teikėjui. Tikėtini rezultatai:

1. Dažnio ribojimo klaidos
2. Laukimo pabaigos klaidos
3. Didelis procesoriaus naudojimas
4. Didelis atminties naudojimas
5. Teikėjo apkrovos ribojimas
6. Pakartotinių bandymų grandinė

Naudodama eilę, API gali priimti užduotis, o darbininkai jas apdoroja kontroliuojamu tempu. Sistema neprivalo visko apdoroti iškart vien todėl, kad užklausos atėjo iškart.

## **6 žingsnis: apdorokite užduotis TTS darbininkais**

Darbininkai vykdo generavimo eigą. Darbininkas gali:

1. Perskaityti užduotį iš eilės.
2. Įkelti užduoties konfigūraciją.
3. Prireikus suskaidyti ilgą tekstą.
4. Pasirinkti tinkamą teikėją.
5. Iškviesti TTS API.
6. Apdoroti laikinas klaidas.
7. Atsisiųsti arba gauti sugeneruotą garsą.
8. Patikrinti išvestį.
9. Įkelti rezultatą į saugyklą.
10. Atnaujinti užduoties būseną.

Darbininkai turėtų būti pakankamai nepriklausomi nuo būsenos, kad užduotį galėtų apdoroti kitas darbininkas, jei viena iš instancijų dingtų.

## **Kokį vienalaikiškumą turėtų naudoti darbininkas?**

Didesnis vienalaikiškumas savaime nereiškia didesnio našumo. Per agresyviai didinant darbininkų vienalaikiškumą gali kilti:

1. Teikėjo ribojimų pasiekimo rizika
2. Procesoriaus perkrova
3. Atminties trūkumas
4. Tinklo ribojimai
5. Disko įvesties ir išvesties ribojimai
6. FFmpeg kliūtys

TTS apkrovos gali naudoti kelių tipų išteklius. Nuotolinės kalbos API iškvietimas gali daugiausia apkrauti tinklą, o garso konvertavimas ar sujungimas gali apkrauti procesorių. Todėl gamybinei sistemai gali būti naudinga taikyti atskirus vienalaikiškumo apribojimus skirtingiems etapams.

Pavyzdžiui:

**Atsisiuntimų vienalaikiškumas: didelis**

**TTS teikėjo vienalaikiškumas: priklauso nuo teikėjo**

**Garso apdorojimo vienalaikiškumas: priklauso nuo procesoriaus**

Paprastai tai saugiau nei visur naudoti vieną didelę vienalaikiškumo reikšmę.

## **7 žingsnis: suskaidykite ilgą tekstą į mažesnius blokus**

Daugelis TTS teikėjų riboja užklausos dydį. Net jei teikėjas priima labai didelį tekstą, ilgus dokumentus vis tiek gali būti naudinga suskaidyti.

Ilga TTS užduotis gali tapti tokia:

**Dokumentas → 1 blokas + 2 blokas + 3 blokas + ... → TTS → Sujungimas**

Apdorojant blokus suteikiama kelių privalumų:

1. Patvirtinus, kad saugu, pakartotinai apdorojami tik nepavykę blokai.
2. Nepriklausomi blokai apdorojami vienu metu.
3. Stebima eiga.
4. Atsigaunama po dalinių klaidų.
5. Blokai spartinami atskirai.
6. Išvengiama teikėjo užklausos dydžio ribojimų.

### **Neskaidykite teksto aklai**

Kas tam tikrą simbolių skaičių suskaidžius tekstą, gali suprastėti kalbos kokybė, nes blokas gali baigtis sakinio viduryje. Geresnė skaidymo logika gali atsižvelgti į:

1. Pastraipų ribas
2. Sakinių ribas
3. Skyrybą
4. Teikėjo simbolių ribas
5. Konkrečios kalbos rašybos taisykles

Tikslas – sudaryti pakankamai mažus blokus patikimam apdorojimui ir kartu išsaugoti natūralų kalbos kontekstą.

## **8 žingsnis: nukreipkite užklausas tinkamam TTS teikėjui**

Gamybinė programa ilgainiui gali palaikyti kelis TTS teikėjus. Skirtingi teikėjai gali siūlyti skirtingus:

1. Kalbas
2. Balsų katalogus
3. Kainas
4. Kokybės lygius
5. Dažnio ribas
6. Delsą
7. Emocijų valdymo galimybes
8. Srautinio perdavimo galimybes

Užuot visoje programoje įterpę teikėjų logiką, naudokite maršrutizavimo arba abstrakcijos sluoksnį. Architektūra tampa tokia:

**Darbininkas → Balso / modelio maršrutizatorius → Teikėjo adapteris → TTS teikėjas**

Kiekvieno teikėjo adapteris gali pateikti bendrą vidinę sąsają ir paversti užklausas į konkrečiam teikėjui tinkamą formatą.

### **Nedubliuokite konkretaus teikėjo logikos visur**

Neturint abstrakcijos, kode gali prisikaupti tokių sąlygų:

**Jei teikėjas yra A, daryk taip. Jei teikėjas yra B, daryk kitaip.**

Pridėjus daugiau teikėjų, tokį kodą tampa sunku prižiūrėti. Bendra teikėjo sąsaja leidžia likusiai sistemos daliai dirbti su tokiomis sąvokomis kaip:

1. Generuoti kalbą
2. Gauti palaikomus balsus
3. Patikrinti užklausą
4. Grąžinti garsą

Kiekvienas teikėjo adapteris tvarko įgyvendinimo detales.

## **Teikėjo perjungimas: naudinga, bet ne visada paprasta**

Gali kilti pagunda automatiškai siųsti kiekvieną nepavykusią užklausą kitam teikėjui. Kartais tai veikia gerai, kartais – ne. Du teikėjai gali neturėti lygiaverčių balsų, o atsarginis balsas gali skambėti visiškai kitaip nei pradinis. Ilgai garsinei knygai ar kelių scenų vaizdo įrašui tai gali būti nepriimtina.

Sprendžiant, ar perjungti teikėją, reikėtų atsižvelgti į:

1. Ar yra lygiavertis balsas
2. Ar svarbus nuoseklumas
3. Ar gedimas laikinas
4. Kainų skirtumą
5. Tikslinę kalbą
6. Naudotojo nuostatas

Teikėjo perjungimas yra architektūros priemonė, o ne garantija, kad kiekviena nepavykusi užklausa turėtų būti iškart nukreipta kitur.

## **9 žingsnis: tinkamai apdorokite dažnio ribojimus**

HTTP 429 gali reikšti teikėjo apribojimą, įskaitant užklausų dažnio arba lygiagrečių užklausų ribą. Prieš nuspręsdami, ar ir kada kartoti, patikrinkite teikėjo klaidos informaciją ir kartojimo nurodymus, įskaitant Retry-After, jei jis pateiktas.

Netinkama reakcija:

**Iškart kartoti užklausą kuo greičiau.**

Paprastai taip sukuriama dar daugiau užklausų ir problema paaštrėja. Geresnis būdas apima:

1. Vienalaikiškumo ribas
2. Eksponentinį laukimo intervalo didinimą
3. Atsitiktinį intervalo svyravimą
4. Konkrečiam teikėjui skirtas dažnio ribojimo taisykles
5. Eilės delsas

Konceptualiai:

**429 → Palaukti → Bandyti vėliau**

ne:

**429 → Bandyti iškart → 429 → Bandyti iškart → 429**

## **10 žingsnis: kartokite tik tas užklausas, kurių klaidos gali išsispręsti**

Pakartotiniai bandymai būtini, tačiau ne kiekvieną klaidą reikia kartoti. Naudinga klasifikacija:

| Klaidos tipas               | Įprastas veiksmas                   |
|-----------------------------|-------------------------------------|
| 429 Too Many Requests       | Palaukti ir bandyti vėliau, didinant intervalą |
| 500 Internal Server Error   | Patikrinti pradinį rezultatą; kartoti tik jei saugu |
| 502 / 503 Temporary Failure | Prieš kartojant ar keičiant teikėją patikrinti pradinį rezultatą |
| Network Timeout             | Prieš kartojant patikrinti pradinį rezultatą          |
| 400 Invalid Request         | Nekartoti aklai                     |
| Unsupported Voice           | Pataisyti užklausą arba maršrutizavimą |
| Insufficient User Credits   | Nutraukti prieš apdorojimą teikėjui |

Pasibaigus laukimo laikui, įvykus 5xx ar darbininko gedimui teikėjo rezultatas gali būti nežinomas. Prieš kartodami ar keisdami teikėją, jei tai palaikoma, patikrinkite pradinės operacijos ID, būseną ir naudojimą, pakartotinai naudokite jau pritaikytą rezultatą ir naudokite teikėjo palaikomą idempotentiškumą. Išsaugokite nežinomo rezultato būseną, užuot aklai kartoję galbūt užbaigtą užklausą.

Pakartotinių bandymų taisyklėje taip pat turėtų būti nustatytas didžiausias bandymų skaičius. Priešingu atveju viena sugedusi užduotis gali amžinai likti sistemoje.

## **Naudokite idempotentiškumą, kad išvengtumėte pasikartojančio darbo**

Pasikartojančios užklausos tikrose programose dažnos. Naudotojas gali dukart spustelėti mygtuką, sąsaja gali pakartoti užklausą pasibaigus laukimo laikui, eilės pranešimas gali būti pristatytas dar kartą arba darbininkas gali sėkmingai baigti darbą, bet sugesti prieš patvirtindamas pranešimą.

Jei sistema daro prielaidą, kad kiekvienas pranešimas unikalus, ji gali sugeneruoti ir apmokestinti tą patį garsą kelis kartus. Idempotentiškumas reiškia, kad kelis kartus apdorojant tą pačią loginę užklausą neturėtų atsirasti kelių nenumatytų rezultatų.

Galimi būdai:

1. Idempotentiškumo raktai
2. Unikalūs užduočių identifikatoriai
3. Spartinančiosios atmintinės maišos
4. Duomenų bazės unikalumo apribojimai
5. Bloko būsenos patikra prieš apdorojimą

Tai ypač svarbu, kai naudojami mokėjimai, kreditai arba patiriamos teikėjo išlaidos.

## **Užduoties ir bloko lygmens idempotentiškumas**

Trumpoms TTS užklausoms gali pakakti užduoties lygmens idempotentiškumo. Didelėms, iš daugelio blokų sudarytoms užduotims dažnai naudingesnis bloko lygmens idempotentiškumas.

Įsivaizduokite garsinės knygos užduotį iš 500 blokų, kurioje nepavyko 487 blokas. Nenorite iš naujo generuoti 1–486 blokų.

**Baigti blokai → Palikti**

**Nepavykęs blokas → Patikrinti teikėjo būseną → Kartoti tik jei saugu**

Taip gerokai sumažinamos išlaidos ir atkūrimo laikas.

## **11 žingsnis: patikrinkite sugeneruotą garsą**

Sėkmingas teikėjo atsakymas ne visada garantuoja tinkamą naudoti išvestį. Prieš pažymėdami užduotį kaip baigtą, galite patikrinti:

1. Ar grąžintas garso failas?
2. Ar failo dydis didesnis už nulį?
3. Ar garsą galima dekoduoti?
4. Ar trukmė atrodo pagrįsta?
5. Ar atitinka prašytas formatas?

Pažangesnėse darbo eigose trukmės patikra taip pat gali aptikti įtartiną išvestį, pavyzdžiui, netikėtai trumpą arba ilgą kalbą.

## **12 žingsnis: saugokite garsą ne programos serveryje**

Sugeneruotas garsas paprastai neturėtų priklausyti nuo vienos API arba darbininko instancijos vietinio disko. Jei konteineris sukuriamas iš naujo, failas gali dingti.

Geresnė architektūra:

**Darbininkas → Objektų saugykla → CDN → Naudotojas**

Objektų saugykla atskiria sugeneruotus išteklius nuo skaičiavimo infrastruktūros. Tada CDN gali efektyviai pateikti garsą naudotojams įvairiose vietose.

Autorizuokite prieigą prie kiekvienos užduoties, būsenos ir garso rezultato. Laikomą garsą saugokite privačiai ir, kai reikia, naudokite ribotos apimties, ribotą laiką galiojančias nuorodas, o ne laikykite URL prieigos įrodymu.

### Ką reikėtų saugoti duomenų bazėje?

Duomenų bazėje paprastai nereikia laikyti neapdorotų garso baitų. Vietoj jų saugokite metaduomenis, pavyzdžiui:

1. Saugyklos raktą
2. Garso URL
3. Trukmę
4. Failo dydį
5. Formatą
6. Teikėją
7. Balsą
8. Generavimo laiką

Pats garsas gali likti objektų saugykloje.

## **Apgalvokite failų galiojimo pabaigą**

Ne kiekvienas sugeneruotas TTS failas turi būti saugomas amžinai. Saugykla gali nepastebimai brangti, kai susikaupia milijonai laikinų garso failų.

Apsvarstykite šių failų saugojimo taisykles:

1. Svečių sugeneruoti failai
2. Laikini apdorojimo failai
3. Tarpiniai blokai
4. Užbaigti naudotojų projektai
5. Pakartotinai naudojamas spartinamas garsas

Tarpinius failus dažnai galima saugoti gerokai trumpiau nei galutinius naudotojų rezultatus.

## **13 žingsnis: grąžinkite rezultatus naudodami apklausas arba atgalinius iškvietimus**

TTS užklausai tapus asinchroninei, klientui reikia būdo sužinoti, kada apdorojimas baigtas. Yra du įprasti šablonai.

### **Apklausa**

Klientas periodiškai klausia:

**GET /jobs/{jobId}**

Serveris grąžina maždaug tokį atsakymą:

**status = processing**

vėliau:

**status = completed, audioUrl = ...**

Apklausą lengva įgyvendinti, ji tinka daugeliui žiniatinklio programų.

### **Webhook arba atgalinis iškvietimas**

API klientas gali pateikti atgalinio iškvietimo URL. Baigus apdorojimą, jūsų serveris automatiškai išsiunčia pranešimą.

Darbo eiga tampa tokia:

**Sukurti užduotį → Grąžinti užduoties ID → Apdoroti → Pranešti klientui atgaliniu iškvietimu**

Tai naudinga, kai išorinės sistemos apdoroja dideles užduotis ir nenori nuolat apklausti serverio.

### Gali būti naudinga palaikyti abu būdus

Gamybinė API gali pasiūlyti užduočių apklausą kaip universalų mechanizmą, o webhookus – kaip pasirenkamą patogumą.

## **Stebėkite didelių užduočių eigą**

5 sekundžių TTS užklausai eigos rodymas gali būti nesvarbus. Vienos valandos garso projektui jis labai svarbus. Jei užduotį sudaro 1 000 blokų, eigą galima apytiksliai apskaičiuoti pagal atliktą darbą:

**Eiga = Baigti blokai / Visi blokai**

Taip sąsajoje galima rodyti:

1. Eilėje
2. Apdorojama 27 %
3. Apdorojama 83 %
4. Užbaigiamas garsas
5. Baigta

Matomas eigos indikatorius taip pat sumažina tikimybę, kad naudotojai pamanys, jog programa užstrigo, ir dar kartą pateiks tą pačią užduotį.

## **14 žingsnis: apsaugokite sistemą ribodami užklausų dažnį**

Teikėjas taiko dažnio ribojimus. Juos turėtų taikyti ir jūsų API. Užklausų dažnį galima riboti pagal:

## **Prioritetai gali būti naudingesni už vieną bendrą eilę**

Plečiantis produktui, ne visoms užduotims gali būti teikiamas vienodas prioritetas. Pavyzdžiui:

1. Interaktyvioms trumpoms TTS užklausoms gali reikėti greito atsakymo.
2. Didelės dokumentų užduotys gali palaukti ilgiau.
3. Mokamiems naudotojams galima suteikti aukštesnį apdorojimo prioritetą.
4. Fone vykdomoms masinėms API užduotims galima skirti atskirą darbininkų pajėgumą.

Galima architektūra:

**Aukšto prioriteto eilė → Greitieji darbininkai**

**Įprasta eilė → Bendrosios paskirties darbininkai**

**Masinių užduočių eilė → Paketinio apdorojimo darbininkai**

Tikslus sprendimas priklauso nuo srauto pobūdžio, tačiau atskyrus darbo krūvius galima neleisti kelioms milžiniškoms užduotims uždelsti visų trumpų užklausų.

## **15 žingsnis: stebėkite naudojimą ir išlaidas**

Skirtingi TTS teikėjai gali taikyti skirtingą kainodarą. Vieni skaičiuoja pagal simbolius, kiti – pagal žetonus, sugeneruoto garso trukmę, o kai kurie naudoja sudėtingesnius kainodaros modelius.

Gamybinė sistema turėtų apytiksliai žinoti, kokius išteklius sunaudoja kiekviena užduotis. Naudinga stebėti:

1. Įvesties simbolius
2. Įvesties žetonus
3. Sugeneruoto garso trukmę
4. Teikėją
5. Modelį
6. Balso tipą
7. Pakartotinių bandymų skaičių
8. Apskaičiuotas teikėjo išlaidas
9. Sunaudotus naudotojo kreditus

Nestebint naudojimo, sunku nustatyti, ar funkcija pelninga ir ar vienas teikėjas netikėtai daug nekainuoja.

## **Apmokestinkite tik vieną kartą**

Atsiskaitymus ir pakartotinius bandymus reikia kruopščiai suderinti. Jei teikėjas tris kartus sutrinka, o paskui užklausa pavyksta, paprastai naudotojas neturėtų būti apmokestintas tris kartus už tą pačią loginę generavimo užklausą.

Jei visa užduotis galiausiai nepavyksta, jūsų sistemai reikia aiškios taisyklės, nusakančios, ar rezervuoti kreditai grąžinami, ar atšaukiamas jų nurašymas. Čia ypač svarbus idempotentiškumas. Atsiskaitymai turėtų priklausyti nuo loginės užduoties gyvavimo ciklo, o ne nuo vidinių pakartotinių bandymų skaičiaus.

## **Kas nutinka sutrikus TTS teikėjo veikimui?**

Išoriniai teikėjai anksčiau ar vėliau sutriks, todėl patikima architektūra turi numatyti tokią galimybę. Padaugėjus klaidų, sistema gali:

2. Laikinai sumažinti teikėjo vienalaikiškumą.
3. Pristabdyti paveiktas eiles.
4. Tinkamas užklausas nukreipti kitam teikėjui.
5. Pranešti naudotojams, kad apdorojimas vėluoja.

Paprastai blogiausia strategija – siųsti vis daugiau pakartotinių užklausų teikėjui, kuris ir taip jau neveikia.

## **Apsvarstykite grandinės pertraukiklį**

Po daugkartinių klaidų grandinės pertraukiklis gali laikinai sustabdyti užklausas teikėjui. Konceptualiai:

**Teikėjas veikia → Užklausos leidžiamos**

**Pasikartojančios klaidos → Grandinė atveriama → Užklausos laikinai blokuojamos**

**Atkūrimo patikra pavyksta → Teikėjas vėl įjungiamas**

Taip galima neleisti vienai neveikiančiai priklausomybei sunaudoti didelės dalies darbininkų pajėgumo.

## **O kaip dėl srautinio TTS?**

Ne kiekvienas TTS darbo krūvis turi būti asinchroninis. Balso asistentams ir realaus laiko pokalbių sistemoms gali reikėti pradėti groti kalbą dar nebaigus generuoti viso garso.

Tokios sistemos gali naudoti:

**Teksto srautas → TTS srautas → Garso dalys → Atkūrimas kliente**

Prioritetai skiriasi:

1. Laikas iki pirmojo garso
2. Srautinio perdavimo delsa
3. Pertraukimai
4. Ryšio stabilumas

Todėl gamybinė platforma gali palaikyti du atskirus kelius:

**Realaus laiko TTS → Srautinis kelias**

**Ilgos formos TTS → Eilė ir foninių užduočių kelias**

Bandymas abiejų tipų darbo krūvius apdoroti visiškai vienoda architektūra gali be reikalo apsunkinti sistemos optimizavimą.

## **TTS API architektūra ir SRT įgarsinimo architektūra**

Įprasta TTS API pradeda nuo teksto. SRT įgarsinimo sistema pradeda nuo subtitrų blokų, jau susietų su laiko juosta.

Paprastas TTS srautas gali būti toks:

**Tekstas → Eilė → TTS → Garsas**

SRT darbo eiga gali būti tokia:

**SRT → Išanalizuoti blokus → TTS → Išmatuoti trukmę → Koreguoti laiką → Sujungti garsą**

SRT versija sukelia papildomų problemų:

1. Laiko žymų išsaugojimas
2. Tikslinė trukmė
3. Kalbėtojų susiejimas
4. Vertimo ilgis
5. Garso sinchronizavimas
6. Pakartotiniai bandymai bloko lygmeniu

## **Dažnos TTS architektūros klaidos**

### **1. Teikėjo iškvietimas tiesiai iš kiekvienos HTTP užklausos**

Iš pradžių tai paprasta, tačiau ilgai vykdomiems darbo krūviams tampa nepatikima.

### **2. Neribotas vienalaikiškumas**

Daugiau darbininkų nepadės, jei kliūtimi taps teikėjas, procesorius arba tinklas.

### **3. Kiekvienos klaidos pakartojimas**

Nuolatinės tikrinimo klaidos neturėtų patekti į nesibaigiančio pakartojimo ciklus.

### **4. Sėkmingai apdorotų blokų generavimas iš naujo**

Didelėse užduotyse reikėtų išsaugoti atliktą darbą ir kartoti tik tai, kas nepavyko.

### **5. Svarbaus garso saugojimas tik vietiniame diske**

Darbininkų konteineriai ir laikini serveriai neturėtų tapti nuolatine išteklių saugykla.

### **6. Konkrečių teikėjų ribojimų ignoravimas**

Kiekvienam teikėjui gali reikėti skirtingos vienalaikiškumo ir dažnio ribojimo strategijos.

### **7. Stebėsenos įdiegimas tik iškilus problemoms**

Neturint rodiklių, našumo problemos sprendžiamos spėliojant.

### **8. Visų darbo krūvių sujungimas į vieną eilę**

Jei darbo krūviai tinkamai neprioritetizuojami, vienas didžiulis dokumentas gali uždelsti dešimtis mažų interaktyvių užklausų.

## **Gera architektūra gali prasidėti paprastai**

Nebūtina nuo pirmos dienos kurti kiekvieno komponento. Pradžioje TTS programa gali naudoti:

**API → Teikėjas → Saugykla**

Vėliau, augant naudojimui:

**API → Eilė → Darbininkas → Teikėjas → Saugykla**

Dar vėliau:

**API → Spartinančioji atmintinė → Prioritetų eilės → Darbininkų grupės → Teikėjų maršrutizatorius → Keli teikėjai → Saugykla / CDN → Webhookai + Stebėsena**

Architektūra turėtų augti reaguojant į tikras kliūtis, o ne į teorinį sudėtingumą. Svarbiausia pasirinkti ribas, kurios leistų ateityje tobulinti sistemą.

## **Kada reikėtų pridėti eilę?**

Eilė tampa vis naudingesnė, kai:

1. Generavimas gali trukti ilgiau nei kelias sekundes.
2. Naudotojai pateikia daug teksto.
3. Užduotis sudaro keli blokai.
4. Dažnai pasiekiamos teikėjo ribos.
5. Srautas ateina bangomis.
6. Reikia patikimų pakartotinių bandymų.
7. Norite nepriklausomai nuo API didinti darbininkų skaičių.

Jei kiekviena užklausa labai maža ir įvykdoma beveik akimirksniu, iš pradžių eilės gali nereikėti.

## **Kada reikėtų pridėti kelis teikėjus?**

Kelių teikėjų palaikymas prasmingas, kai tam yra konkreti priežastis, pavyzdžiui:

1. Reikalingi skirtingi balsai.
2. Vienas teikėjas nepalaiko tam tikros kalbos.
3. Reikia didesnio bendro pajėgumo.
4. Reikia skirtingų kainų lygių.
5. Kritiniams darbo krūviams reikia atsarginio teikėjo.

Pridėjus teikėjų vien dėl architektūrinės elegancijos gali padaugėti priežiūros, bet vertės atsirasti nedaug.

## **Kada reikėtų spartinti TTS išvestį?**

Spartinimas ypač naudingas, kai:

1. Tas pats turinys generuojamas dažnai.
2. TTS teikėjo iškvietimai brangūs.
3. Kai kurios išvestys pakankamai deterministinės, kad jas būtų galima naudoti pakartotinai.
4. Naudotojai dažnai kartoja užklausas arba vėl atidaro esamus projektus.
5. Dideliuose projektuose vienu metu redaguojami tik keli blokai.

Net jei ne visada galima panaudoti visą garso įrašą pakartotinai, blokų lygmens spartinimas vis tiek gali gerokai sumažinti išlaidas.

## **Gamybinis TTS yra orkestravimo problema**

Pats TTS modelis tėra vienas komponentas. Gamybinė sistema turi koordinuoti:

**Naudotojus + Užduotis + Eiles + Darbininkus + Teikėjus + Garsą + Saugyklą + Atsiskaitymus + Stebėseną**

Todėl vietinę TTS demonstraciją galima sukurti greitai, o patikimai viešai TTS platformai reikia gerokai daugiau inžinerinio darbo. Sudėtingumą lemia viskas, kas supa modelį.

## **Baigiamosios mintys**

Gamybinę teksto vertimo į kalbą API nuo pat pradžių reikėtų projektuoti atsižvelgiant į gedimus, vienalaikiškumą ir ilgai vykdomą apdorojimą.

Pagrindinė architektūra paprasta:

**Priimti užklausą → Patikrinti ją → Kai įmanoma, pakartotinai panaudoti esamą išvestį → Sukurti užduotį → Įtraukti darbą į eilę → Generuoti kalbą → Kartoti išsprendžiamas klaidas → Išsaugoti garsą → Grąžinti rezultatą.**

Augant srautui, vis svarbesni tampa papildomi sluoksniai, tokie kaip teikėjų maršrutizavimas, prioritetų eilės, apdorojimas blokais, dažnio ribojimo valdymas, išlaidų stebėjimas, atgaliniai iškvietimai ir stebėsena.

Svarbiausia pamoka – kalbos generavimas paprastai yra lengvoji dalis. Tikras gamybinis iššūkis – sukurti sistemą, kuri patikimai generuotų kalbą daugeliui naudotojų ir per daug teikėjų, kartu valdydama išlaidas ir gedimus.
