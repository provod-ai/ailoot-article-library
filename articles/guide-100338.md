# Designing Tools for AI Agents: Lessons for Claude Code Workflows

> A practical guide to defining and testing tools for AI agents, with examples for coding workflows.



An AI agent needs more than a good model: it needs tools it can select, understand and use within the boundaries of a task. This guide shows how to design those interfaces, using coding workflows as a practical example.

## Start with an observable job

Describe what the agent should accomplish before deciding which tools to expose. For a repository question, the job might be to find where a setting is read and cite the relevant files. An appropriate tool set could let the agent list files, search text and read selected files; it does not need permission to deploy anything to answer that question.

Write down the expected result and the actions that are out of scope. A tool is useful when its input and output help the agent make the next decision, and when the application can check that the action is permitted.

## Give each tool a clear contract

A tool description should state what it does, the required inputs and the shape of its result. Use distinct names and parameter descriptions when tools have similar purposes. If an operation has a meaningful limit, describe it: for example, a search tool might return a bounded list of matching paths rather than every file's contents.

For a text-search tool, an illustrative request could contain a query and a directory. Its result could include paths and matching line numbers. The application should validate the directory and handle missing paths or failed searches explicitly. A well-formed request is not proof that the answer found is correct.

## Balance flexibility and control

A general-purpose shell can support many tasks, but it also exposes a broad set of actions. A narrower tool can make a common operation easier to understand and constrain the action it performs. The right choice depends on the task, the environment and the permissions available; more tools do not automatically produce better results.

Keep the initial set small enough to navigate. Add a specialised tool when observed failures or repeated work justify it. If a tool can change data or contact an external service, make that effect visible in its description and enforce the relevant permissions in the application.

## Ask for missing information at the right time

An agent should not invent a missing decision. If a task genuinely depends on information it cannot find, a structured question can present the relevant choices and explain their consequences. If independent work is ready, the workflow can continue that work while waiting for the answer.

Keep questions specific. For example, if a report requires a date range that was not supplied, ask for the range rather than asking the user to restate the whole assignment. Do not use a question as a substitute for checking available context.

## Test the tool and the agent together

Create a small set of representative tasks: ordinary requests, ambiguous inputs, unavailable files and attempts to use a tool outside its intended scope. Inspect which tool was chosen, the arguments passed, the returned result and the final answer. A successful API call can still return incomplete data, so check the answer against the underlying evidence.

Change one part of the interface at a time when diagnosing a recurring failure. Record the version of the tool description and repeat the relevant test. For actions with side effects, reconcile an uncertain result before retrying; a retry can repeat an action that already succeeded.

## Apply the ideas in a coding workflow

Claude Code supports workflows that combine tools and reusable instructions. Consult the current [Claude tool-use documentation](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) for the API contract and the [Claude Code skills documentation](https://code.claude.com/docs/en/skills) for how reusable instructions are organised. Availability and exact interfaces can change, so check the documentation for the version in use.

The same design questions apply across agent frameworks: what does the task require, what can the agent observe, what can each tool change, and how will you verify the result?
